# Specification: Continuous integration

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-09 -->

No workflow exists, so the first pull request on GitHub would merge on the author's word, and the invariants brief § 9 makes non-negotiable - no absolute path, `/` separators in every output - would be proven only on the one operating system a contributor happens to use. This Feature removes that failure state: every push to `main`, and every pull request that changes more than documentation, runs the build's gates on ubuntu and windows, each operating system reports as a check of its own under a name that does not change, and a specification violation in a file the pull request changes is annotated on its line in the diff.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 -->

Delivered so far by items 0064, 0102 and 0066.

- **The declaration** is [`.build/Build.GitHubActions.cs`](../../Build.GitHubActions.cs): Rocket.Surgery.Nuke's `[GitHubActionsSteps]` generator, which the owner chose (`487e5d8`), named `ci`, writing [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml) with `AutoGenerate` on, so any build run regenerates it and the regeneration is committed with the build change (C-1). Its `ContinuousIntegrationMiddleware` enhancement shapes what the generator emits; the rest is attribute settings. That the committed copy is current rests on C-1 alone: no run checks it (B-009 withdrawn, decision 0001).
- **Triggers.** `OnPullRequestBranches` and `OnPushBranches`, each `main` (B-001, B-002, A-2).
- **Whether a run builds** is decided inside each leg (C-5), never by a workflow path filter or a job condition. `GateOnChangedFiles` inserts a `changes` step after `git fetch --prune`, run under `shell: bash` - Git Bash on the windows image - so one script serves both legs. It writes `build=false` to its output only for a `pull_request` event whose `git diff --name-only --no-renames <base.sha>...<head.sha>` succeeds, lists at least one file, lists no file that does not end in `.md`, and lists none with a `.spec/` segment (B-012). Any other event, an empty list, or a failed diff writes `build=true` (B-002, B-014). The three-dot range diffs from the merge base, so the list is the pull request's own change, the one GitHub shows, and not whatever `main` gained since; `--no-renames` lists a renamed file under both names, so `a.cs` renamed to `a.md` still builds. The base commit is present because the checkout fetches full history (C-2). The script reads the event and both commits from step `env`, never from expressions inlined into it, and uses here-strings rather than pipes, because the runner's `bash -eo pipefail` would fail a pipe that `grep -q` closes early.
- **Every later step is gated** on `steps.changes.outputs.build == 'true'`: the .NET setup, each target step, the Codecov upload and its warning. A step's existing condition is kept and joined with `&&` in parentheses, so the upload stays `!cancelled()` on a run that builds. A skipped step does not fail its job, so on a run B-012 applies to both legs finish green under their usual names (B-013, B-007); a run that builds runs every gate as before (B-001, B-004). Like every other mechanism here, the decision has no test (§ 8): B-012 to B-014 are bound to no step definition, and the script was exercised by hand against real and synthetic commits when 0102 was delivered.
- **Violations annotated on the diff** (B-006, C-6) are written by the `SpecCheck` target in [`.build/Build.cs`](../../Build.cs), never by a problem matcher: NUKE relays each `specht` line through its logger with colour and a timestamp, which no matcher can read. `PassAnnotationContext` gives the `specCheck` step `EVENT_NAME`, `BASE_SHA`, `HEAD_SHA` and `MATRIX_OS` in its `env`, the same expressions the `changes` step reads; its `if:` gate and its place in the step order are unchanged. The target runs `specht` through NUKE's `DotNetTasks.DotNet` and passes the lines it returns to `AnnotateChangedFiles`. Its exit handler records whether `specht` exited 0, for the verdict the log line prints, and never throws, so exit 1 does not fail the target. It passes `ProcessTasks.DefaultLogger`, so the output prints exactly as before: `DotNetTasks`' own logger raises each `error SPEC###` line to an error, which NUKE repeats in its closing summary and, on GitHub Actions, writes as an unfiltered `::error::` from every leg, contrary to C-6. That returns at once unless NUKE's host is GitHub Actions, the event is `pull_request`, the leg is `ubuntu-latest` and both commits are set, so a local run, a push and the windows leg print what they always printed. Otherwise it lists the changed files through NUKE's `GitTasks.Git` with the `changes` step's `git diff --name-only --no-renames <base.sha>...<head.sha>`, its output unlogged and its exit handler never throwing, keeps each stdout line matching `path(line): error|warning SPEC###: message` (the line part absent when the line is 0) whose path is in that list, and writes it as `::error file=<path>,line=<line>,title=<rule>::<message>` (or `::warning`), its properties joined by a bare comma and `line` left out when absent. The message escapes `%`, `\r` and `\n`; each property escapes those and `:` and `,` as well: NUKE's two escape rules. The build writes this line itself rather than through NUKE's `GitHubActions.WriteCommand`: NUKE 10.1.0 joins properties with `", "`, and the runner splits them on `,` and `=` without trimming the names (`TryParseV2`), so `line` and `title` would be dropped (owner, 2026-10-09). A failed diff prints nothing on standard output, so it lists no file and annotates nothing. Nothing in the method throws or sets an exit code, so the annotations never change the target's outcome (C-4); GitHub's per-step cap drops what exceeds it, and the log keeps the full list (decision 0002).
- **A matrix of two images** - `ubuntu-latest` and `windows-latest` - in one `build` job. Each leg is its own check, `build (ubuntu-latest)` and `build (windows-latest)`, named by literals in the committed file and nothing computed from the commit (B-003, B-007, B-010). The middleware turns `fail-fast` off, so a failing leg never cancels the other and each operating system reports its own result (B-005).
- **One step per gate**, in dependency order: `Restore`, `Format`, `Compile`, `Test`, `SpecCheck`, `Pack`, each skipping what an earlier step already ran. The generator would run the first through a global `nuke` and the rest through the compiled build assembly; the middleware drops the global install (`0055-F1` C-3) and rewrites every step to `./build.cmd --target ...`, the entry script on every system (B-004). A failing target exits it non-zero and fails that step and that leg (B-005, `0055-F1` B-018). The middleware also keeps `Format` ahead of `Compile`, so a formatting failure is the first one reported.
- **The checkout** is the generator's `actions/checkout` step, which the owner's shared `Middleware` already gives `fetch-depth: 0` (C-2), followed by a `git fetch --prune` and `actions/setup-dotnet`. The CI middleware sets `ref: ${{ github.event.pull_request.head.sha }}`: a pull request builds its head commit rather than the merge GitHub synthesises (B-001), and a push, where the expression is empty, builds the pushed commit (B-002).
- **Nothing leaves a run** (B-008, C-3): no target in the list pushes, no step uploads an artifact, so `Pack`'s output is not kept (§ 5 #7), and the middleware replaces the generator's default token - which writes issues, pull requests and statuses - with `contents: read` and nothing else.
- **Not in this workflow:** the owner's Codecov upload, which is `0070`'s (it uploads `0069`'s reports), the `artifacts/logs/` upload, a path this build never writes, and `DeployMiddleware`'s registry and Azure logins, which belong to a release workflow, not to integration.
