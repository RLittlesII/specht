# Specification: Continuous integration

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-09 -->

No workflow exists, so the first pull request on GitHub would merge on the author's word, and the invariants brief § 9 makes non-negotiable - no absolute path, `/` separators in every output - would be proven only on the one operating system a contributor happens to use. This Feature removes that failure state: every pull request that changes more than documentation runs the build's gates on ubuntu, every push to `main` runs them on ubuntu and windows, each operating system reports on both events as a check of its own under a name that does not change, and a specification violation in a file the pull request changes is annotated on its line in the diff. A violation that exists only once a pull request is merged with `main` - an id both took, which git merges without a conflict - is reported by the pull request's run, not found on `main` afterwards.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 -->

Delivered so far by items 0064, 0102, 0066, 0114 and 0118.

- **The declaration** is [`.build/Build.GitHubActions.cs`](../../Build.GitHubActions.cs): Rocket.Surgery.Nuke's `[GitHubActionsSteps]` generator, which the owner chose (`487e5d8`), named `ci`, writing [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml) with `AutoGenerate` on, so any build run regenerates it and the regeneration is committed with the build change (C-1). Its `ContinuousIntegrationMiddleware` enhancement shapes what the generator emits; the rest is attribute settings. That the committed copy is current rests on C-1 alone: no run checks it (B-009 withdrawn, decision 0001).
- **Triggers.** `OnPullRequestBranches` and `OnPushBranches`, each `main` (B-001, B-002, A-2).
- **Whether a run builds** is decided inside each leg (C-5), never by a workflow path filter or a job condition. `GateOnChangedFiles` inserts a `changes` step after `git fetch --prune`, run under `shell: bash` - Git Bash on the windows image - so one script serves both legs. It writes `build=false` to its output in two cases. The first is a `pull_request` event on the windows leg, whatever the pull request changes and whether or not its changed files can be determined (B-015, and B-014 as amended): the script tests the runner's own `RUNNER_OS`, which is `Windows` on that image, before it runs any diff. `RUNNER_OS` was chosen over `matrix.os` because the runner sets it in every step, so the step needs no further `env` entry, and because it names the system the step is running on rather than the label the matrix asked for. The second, reached only when the first does not hold, is a `pull_request` event whose `git diff --name-only --no-renames <base.sha>...<head.sha>` succeeds, lists at least one file, lists no file that does not end in `.md`, and lists none with a `.spec/` segment (B-012). Any other event on either leg, and on the ubuntu leg an empty list or a failed diff, writes `build=true` (B-001, B-002, B-014), so a push to `main` builds on both legs whatever it changes (§ 5 #9). Each skip writes its own `::notice` onto the run: "Windows gates skipped" for the first case and "Build skipped" for the second; a documentation-only pull request's windows leg writes the first. The three-dot range diffs from the merge base, so the list is the pull request's own change, the one GitHub shows, and not whatever `main` gained since; `--no-renames` lists a renamed file under both names, so `a.cs` renamed to `a.md` still builds. The base commit is present because the checkout fetches full history (C-2). The script reads the event and both commits from step `env`, never from expressions inlined into it, and uses here-strings rather than pipes, because the runner's `bash -eo pipefail` would fail a pipe that `grep -q` closes early.
- **Every later step is gated** on `steps.changes.outputs.build == 'true'`: the .NET setup, each target step, the Codecov upload and its warning. A step's existing condition is kept and joined with `&&` in parentheses, so the upload stays `!cancelled()` on a run that builds. A skipped step does not fail its job, so on a run B-012 applies to both legs finish green under their usual names (B-013, B-007), and on every other pull request the windows leg does (B-016); a leg that builds runs every gate as before (B-001, B-004). The windows leg of a pull request still starts a runner and runs the checkout, the fetch and the decision step, which is what lets its required check report (C-5, decision 0003). Like every other mechanism here, the decision has no test (§ 8): B-012 to B-016 are bound to no step definition. The script was exercised by hand against real and synthetic commits when 0102 was delivered, and again for 0118 by running the script as generated into `ci.yml` under `bash -eo pipefail`, against `daa02e6~1...daa02e6` (code) and `58db716~1...58db716` (`README.md` alone). A pull request on `RUNNER_OS=Windows` wrote `build=false` for the code range, for the Markdown range, and for empty and unknown commits. A pull request on `RUNNER_OS=Linux` wrote `build=true` for the code range and for empty and unknown commits, and `build=false` for the Markdown range. A push wrote `build=true` on both. No runner was under test: the first live run is the one on the pull request that delivers 0118.
- **Violations annotated on the diff** (B-006, C-6) are written by the `SpecCheck` target in [`.build/Build.cs`](../../Build.cs), never by a problem matcher: NUKE relays each `specht` line through its logger with colour and a timestamp, which no matcher can read. `PassAnnotationContext` gives the `specCheck` step `EVENT_NAME`, `BASE_SHA`, `HEAD_SHA` and `MATRIX_OS` in its `env`, the same expressions the `changes` step reads; its `if:` gate and its place in the step order are unchanged. The target runs `specht` through NUKE's `DotNetTasks.DotNet` and passes the lines it returns to `AnnotateChangedFiles`. Its exit handler records whether `specht` exited 0, for the verdict the log line prints, and never throws, so exit 1 does not fail the target. It passes `ProcessTasks.DefaultLogger`, so the output prints exactly as before: `DotNetTasks`' own logger raises each `error SPEC###` line to an error, which NUKE repeats in its closing summary and, on GitHub Actions, writes as an unfiltered `::error::` from every leg, contrary to C-6. That returns at once unless NUKE's host is GitHub Actions, the event is `pull_request`, the leg is `ubuntu-latest` and both commits are set, so a local run and a push, on either leg, print what they always printed; on a pull request the windows leg does not run the step at all (B-015). Otherwise it lists the changed files through NUKE's `GitTasks.Git` with the `changes` step's `git diff --name-only --no-renames <base.sha>...<head.sha>`, its output unlogged and its exit handler never throwing, keeps each stdout line matching `path(line): error|warning SPEC###: message` (the line part absent when the line is 0) whose path is in that list, and writes it as `::error file=<path>,line=<line>,title=<rule>::<message>` (or `::warning`), its properties joined by a bare comma and `line` left out when absent. The message escapes `%`, `\r` and `\n`; each property escapes those and `:` and `,` as well: NUKE's two escape rules. The build writes this line itself rather than through NUKE's `GitHubActions.WriteCommand`: NUKE 10.1.0 joins properties with `", "`, and the runner splits them on `,` and `=` without trimming the names (`TryParseV2`), so `line` and `title` would be dropped (owner, 2026-10-09). A failed diff prints nothing on standard output, so it lists no file and annotates nothing. Nothing in the method throws or sets an exit code, so the annotations never change the target's outcome (C-4); GitHub's per-step cap drops what exceeds it, and the log keeps the full list (decision 0002).
- **A matrix of two images** - `ubuntu-latest` and `windows-latest` - in one `build` job. Each leg is its own check, `build (ubuntu-latest)` and `build (windows-latest)`, named by literals in the committed file and nothing computed from the commit or the event (B-003, B-007, B-010). Both legs are in every run, a pull request's included: B-015 is met by the `changes` step inside the windows leg, not by a matrix that leaves windows out (C-5). The middleware turns `fail-fast` off, so a failing leg never cancels the other and each operating system reports its own result (B-005).
- **One step per gate**: `Restore`, `Format`, `Compile`, `UnitTest`, `IntegrationTest`, `AcceptanceTest`, `SpecCheck`, each skipping what an earlier step already ran (B-004). `ContinuousIntegration` depends on those targets, not on `Test`. `Test` is in the attribute's `ExcludedTargets`, so no step runs it (§ 5 #17); it still needs excluding because `SpecCheck` depends on it, and the generator, which would otherwise skip it there as a target an earlier step ran, emits a bare `--target SpecCheck` once it is excluded. The middleware appends `--skip Test` to that step, so it neither reruns every test nor empties `.artifacts/coverage/`; NUKE skips `Compile` and `Restore` with it, as dependencies of a skipped target. It also adds `Test` to the `Continuous Integration` step's `--skip` list, so neither step relies on NUKE skipping `Test` only because a skipped `SpecCheck` depends on it. The generator orders steps by dependency-graph depth, which put `SpecCheck` ahead of the tiers and the tiers in reverse; the middleware moves the three tier steps, in tier order, to directly after `Compile`. The generator would run the first step through a global `nuke` and the rest through the compiled build assembly; the middleware drops the global install (`0055-F1` C-3) and rewrites every step to `./build.cmd --target ...`, the entry script on every system (B-004). A failing target exits it non-zero and fails that step and that leg (B-005, `0055-F1` B-018). The middleware also keeps `Format` ahead of `Compile`, so a formatting failure is the first one reported. The Codecov upload and its warning (`0055-F3` B-002) sit directly after `AcceptanceTest`, the last tier.
- **The checkout** is the generator's `actions/checkout` step, which the owner's shared `Middleware` already gives `fetch-depth: 0` (C-2), followed by a `git fetch --prune` and `actions/setup-dotnet`. The CI middleware sets `ref: ${{ github.event.pull_request.head.sha }}`: a pull request builds its head commit rather than the merge GitHub synthesises (B-001), and a push, where the expression is empty, builds the pushed commit (B-002).
- **Nothing leaves a run** (B-008, C-3): no target in the list packs or pushes (§ 5 #18), no step uploads an artifact, and the middleware replaces the generator's default token - which writes issues, pull requests and statuses - with `contents: read` and nothing else.
- **Not in this workflow's claims:** the Codecov upload, which is `0055-F3`'s (B-002) though it is a step here. **Not in this workflow:** the `artifacts/logs/` upload, a path this build never writes, and `DeployMiddleware`'s registry and Azure logins, which belong to a release workflow, not to integration.
