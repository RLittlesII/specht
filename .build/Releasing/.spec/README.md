# Specification: Release

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-11 (`0001-F7` decision 0007) -->

Nothing publishes `specht.tool`: `0001-F2` § 5 row 7 hands the release workflow to repository tooling that does not exist, so the first package would be pushed by hand from one machine, with no proof that what was pushed is what the gates checked - and a package once published stays, with the schema version it embeds never changed in place (`0001-F7` C-1). This Feature removes that failure state: pushing a `v*` tag runs the full build on the tagged commit, publishes the package to GitHub Packages on `rlittlesii/specht` only if every gate passed, and creates a GitHub Release for the tag; nothing else publishes.

## 2. User Needs

<!-- last written by: spec-author, 2026-10-08 -->

| #   | Persona                         | Need                                                               | Pain Point Today                            |
| --- | ------------------------------- | ------------------------------------------------------------------ | ------------------------------------------- |

| 2   | A consumer                      | A published package is exactly what passed the gates on its commit | A hand-pushed package carries no such proof |
| 3   | A consumer reading what changed | A GitHub Release per published version                             | Nothing marks a version                     |
| 4   | `0055-F7`                       | A package on the feed to install                                   | N/A (internal dependency)                   |

## 7. Technical Design

<!-- last written by: implementer, 2026-10-14 -->

On 2026-10-14, B-010 uses the native NuGet environment credential
`NuGetPackageSourceCredentials_specht`, supplied at the generated release build
job from `github.actor` and `secrets.GITHUB_TOKEN`. The workflow grants
`packages: read`; no stored read token or custom restore logic is used.
The existing Restore target restores the committed manifest unchanged.

**Built by item 0083 for B-001, B-002, B-005, B-008 and B-009, and by item 0084 for B-003, B-004, B-006, B-007, B-011 and B-012**, in the shape decisions 0001 and 0003 record: the generated file `release.yml`, the targets `Release` and `VerifyTag`, the job `build` on `ubuntu-latest` and the job `release`. No test proves it: for item 0083's five claims by decision 0002 and § 5 #9, and for item 0084's six by § 5 #9 alone, since decision 0002 names only the five. Decision 0003's 2026-10-14 addendum resolves OQ-16 for the first-publication reconciliation; § 8 records the evidence. The manual trigger carries no input, which is OQ-7's proposed default; OQ-7 and OQ-14 are open and block nothing here. B-010 is item 0085's; where this design leaves room for it, it says so and builds nothing.

Until 2026-10-11 the file was `publish.yml`, the second job `publish`, the enhancement `PublishMiddleware`, the aggregate target `Publish` and the source file `SpechtBuild.Publish.cs` (decision 0003). Where this section reports a probe of 2026-10-09 it keeps that day's names.

### What the generator can express

The generator is Rocket.Surgery.Nuke 2.9.12's `[GitHubActionsSteps]`, the one [`.build/SpechtBuild.GitHubActions.cs`](../../SpechtBuild.GitHubActions.cs) and [`.build/SpechtBuild.Renovate.cs`](../../SpechtBuild.Renovate.cs) already use (`0055-F2` C-1). Each line below was observed on 2026-10-09, in two probes, by declaring throwaway workflows in the build project, running `./build.sh Compile` and reading the files it wrote; the declarations and the files were then deleted, and nothing of either probe is committed. The lines the built workflow uses were observed again in the committed [`release.yml`](../../../.github/workflows/release.yml), regenerated on 2026-10-11.

- **A `v*` tag trigger: yes, by attribute.** `GithubActionsStepsAttributeBase.OnPushTags = ["v*"]` wrote `on: push: tags: - 'v*'`, with no `branches` key.
- **A manual trigger: yes, by attribute.** `On = [RocketSurgeonGitHubActionsTrigger.WorkflowDispatch]` beside `OnPushTags` wrote a bare `workflow_dispatch:` next to the `push` trigger. No enhancement is needed for it.
- **A manual trigger with an input: yes, by enhancement only.** Adding to `RocketSurgeonGitHubActionsConfiguration.DetailedTriggers` a `RocketSurgeonGitHubActionsWorkflowTrigger` of `Kind` `WorkflowDispatch` whose `Inputs` holds a `GitHubActionsInput(Name, Type, Default, Description, Required, Alias)` wrote `workflow_dispatch: inputs:` with the input's `type`, `description`, `required` and `default`. The built workflow has no input.
- **The workflow token's permissions: yes, by enhancement.** `configuration.Permissions = GitHubActionsPermissions.None with { Contents = Read, Packages = Write }` wrote all thirteen scopes, `contents: read`, `packages: write` and the rest `none`. With no enhancement the generator wrote its own default, which grants more than this run needs.
- **A full-depth checkout: yes, already.** `CheckoutStep.FetchDepth`, which the shared `Middleware` sets to 0, wrote `fetch-depth: '0'`. With `CheckoutStep.Ref` left unset the step has no `ref`, so the run checks out the commit the event names.
- **A condition, an environment and a shell on one step: yes.** `BaseGitHubActionsStep.If`, `BaseGitHubActionsStep.Environment` and `RunStep.Shell` wrote `if:`, `env:` and `shell:` on an inserted `RunStep`.
- **A tag check before the push: not as a setting.** The generator has no member that compares a tag with a version. It is a target, which the generator turns into a step like any other.
- **A publish step of its own: no.** `GithubActionsExtensions.AddNugetPublish` is marked obsolete with the message "Method no longer does anything, use PublishNugetJob attribute instead", so calling it fails this build, which treats warnings as errors. `PublishNugetPackagesJobAttribute` is the replacement it names; the next line is what that wrote.
- **`PublishNugetPackagesJobAttribute`: probed, and it does not fit.** `[PublishNugetPackagesJob("<secret name>", "<workflow name>", AutoGenerate = true)]` wrote a second file, `publish-nuget.yml`, named `Publish Nuget Packages`. Its trigger is `workflow_run` on the named workflow with `types: completed`. Its one job, `publish_nuget`, runs when `github.event.workflow_run.conclusion == 'success'`, prints the whole `github` context, downloads the artifact named `nuget` from the triggering run, and in a `pwsh` step runs `dotnet nuget push **/*.nupkg --skip-duplicate -s nuget.org --api-key $ENV:ApiKey` and the same for `**/*.snupkg`, the key being `${{ secrets.<secret name> }}`. The feed, both globs, the artifact name and the steps are literals inside the attribute; its constructor takes the secret's name, the triggering workflow, branches, a condition and images, and nothing else. It ignored `Enhancements`: an enhancement that renamed the workflow changed nothing. Its token carried the generator's default permissions, `packages: none` among them. So it names a feed C-3 rules out, pushes a glob where C-4 names one file, fetches from another run, which C-4 rules out, and needs a stored secret, which C-5 rules out.
- **A second job: yes, by enhancement.** Adding to `configuration.Jobs` a `RocketSurgeonsGithubActionsJob` with `Needs`, `If`, `Permissions`, a `Matrix` of one image name and its own `Steps` wrote a `publish:` job after `build:` with `needs: - build`, `if:`, a `permissions:` block, `runs-on: ubuntu-latest` and the steps given, in that order. `RunsOn` in place of `Matrix` writes the list form, `runs-on: [ubuntu-latest]`.
- **Workflow-level and job-level permissions are separate: yes.** `configuration.Permissions` wrote the block at the top of the file and the job's `Permissions` wrote the job's own. The probe had `packages: none` at the top and `packages: write` in `publish` alone; `build`, given no `Permissions`, wrote no block and so takes the top one.
- **Artifact steps: yes, as typed steps.** An `UploadArtifactStep` with `Name`, `Path`, `IfNoFilesFound` and `RetentionDays`, inserted after the step whose `Id` is `pack`, wrote `actions/upload-artifact@v4` with `name`, `path`, `if-no-files-found` and `retention-days`. A `DownloadArtifactStep` with `Name` and `Path` wrote `actions/download-artifact@v4`. The generator puts an emoji before both step names, as it does before `Restore`, `Compile`, `Test` and `Pack`. The action versions are the typed steps' own, as those of `actions/checkout` and `actions/setup-dotnet` are in `ci.yml`.
- **A `workflow_run` trigger: yes, by enhancement.** `RocketSurgeonGitHubActionsTrigger` has a `WorkflowRun` member, and a `RocketSurgeonGitHubActionsWorkflowTrigger` of that `Kind` with `Workflows` and `Types` wrote `on: workflow_run: workflows: - '<name>' types: - 'completed'`; it writes `Branches` too when given. `DownloadArtifactStep.RunId` and `GithubToken` wrote `run-id` and `github-token`, which is how a second workflow fetches from the run that started it.
- **The other workflows did not move.** With all of the above declared, the same regeneration left `ci.yml` and `renovate.yml` without a difference, and so did the regeneration that wrote the committed `publish.yml`. The regeneration of 2026-10-11 that wrote `release.yml` left `ci.yml`, `main.yml` and `renovate.yml` without a difference. It does not delete a file whose workflow is no longer declared: `publish.yml` was removed by hand.
- **The trigger order is the generator's.** It wrote `workflow_dispatch:` above `push:`.
- **The step order, when the targets are invoked one by one, needs no repair.** `InvokedTargets` naming the tag check, `Format`, `Compile`, `Test`, `Specht` and `Pack` wrote the steps in exactly that order after `Restore`, with `Specht` as `--skip Test` and `Pack` as `--skip Compile`. Invoking one aggregate target that depends on the six instead wrote `Format` after `Pack`, and after a push step inserted behind `Pack`, followed by a trailing step for the aggregate. That was the reason no aggregate was built on 2026-10-09. One exists now: commit `dc59b81` added it as `Publish`, and decision 0003 keeps it as `Release`. What the generator writes for it today is under "The file generated", and it is not what the probe wrote: `Release` depends on `VerifyTag` and `Pack` only, each gate depends on the one before it in [`SpechtBuild.cs`](../../SpechtBuild.cs), and the gates come out in the order they fail in. The trailing step is still written.
- **What the generator always writes and the enhancement must undo**, as `ContinuousIntegrationMiddleware` does for `ci.yml`: a `dotnet tool restore` step, a global `nuke` install, `nuke --target Restore` and `dotnet .build/bin/Debug/.build.dll --target ...` for every later target. `0055-F1` C-3 rules out the global install, and `0055-F2` B-004 runs every target through the entry script.
- **Adding or renaming a target changes [`.nuke/build.schema.json`](../../../.nuke/build.schema.json)**, which the same run regenerates.
- **A step's emoji is the generator's, by name.** It wrote `🚀 Publish` for the aggregate's step and writes a bare `Release` for the same step renamed. Nothing in the build project chooses either.

Nothing the claims need is beyond the generator: two attribute settings, one enhancement and two targets, one of them an aggregate.

**No line of `release.yml` is written by hand.** Every line comes from the attribute or from a typed step or job the enhancement adds. Two kinds of generated text are changed by the enhancement after the generator produced them, which is how `ci.yml` is already made by `ContinuousIntegrationMiddleware`: the `run:` line of each target step, rewritten from `dotnet .build/bin/Debug/.build.dll --target ...` and `nuke --target Restore` to `./build.cmd --target ...`; and the generator's `dotnet tool restore` and global `nuke` install steps, removed.

### What is declared

- **A partial of `SpechtBuild`**, [`.build/SpechtBuild.Release.cs`](../../SpechtBuild.Release.cs), beside `SpechtBuild.Renovate.cs`. It declares the attribute, the enhancement `ReleaseMiddleware` and the targets `Release` and `VerifyTag`.
- **The attribute**, `[GitHubActionsSteps("release", ...)]`, generating `.github/workflows/release.yml`. The name is decision 0003's, and `specht-conventions` § Layout carries it. One image: a release packs once and pushes one file, and the windows gates run on every push to `main` (`0055-F2` B-004).
- **The triggers** are two and no other: a pushed tag matching `v*`, and a run started by hand. No `branches`, no `pull_request`, no input.
- **The target `Release`**, the one target the attribute invokes. It depends on `VerifyTag` and `Pack` and executes nothing (decision 0003, § 5 #7). `./build.sh Release` on a developer's machine runs the gates and `Pack`, reports `VerifyTag` as `Skipped`, reads no token and pushes nothing.
- **The target `VerifyTag`**, depending on `Restore`, which is what restores `nbgv` (`0055-F5` § 7). It runs only when `GITHUB_REF_TYPE` is `tag`, through NUKE's `OnlyWhenDynamic`, and reports `Skipped` otherwise. It makes three checks, in this order, and fails on the first that does not hold. It is a gate, so it is a target (`0055-F1` C-1).
  - **The name.** It asks `dotnet nbgv get-version --variable NuGetPackageVersion` for the commit's version, the value `Pack` stamps (`0055-F5` B-005), and fails with the tag and the version in its message unless `GITHUB_REF_NAME` equals `v` followed by that version, the shape `version.json`'s `release.tagName` gives a tag made by `nbgv tag` (A-2). It reads the two variables the runner sets in every step, so the workflow passes it nothing and no tag name is ever written into a command line.
  - **The commit.** It fails, naming the tag, unless the checked-out commit is reachable from `origin/main` (B-011). "The tag's commit and `main`" below says how.
  - **The schema lock (B-013).** After the name and ancestry checks, it awaits `SchemaVersionLock.RequireAllLockedAsync` through the existing build-side file-system seam. The guard reuses the writer's canonical version discovery under `src/tool/schema/v*/` and reads `src/tool/schema/versions.lock.json`. Every shipped version must have a key; a missing lock means no versions are locked. Failure names the unlocked schema versions, ordered ordinally, and the relative lock path. It reads only: it never invokes `LockSchemaVersion`, writes a digest, or compares content digests (the latter belongs to `0001-F7` B-089). An older unlocked version fails even if the newest is locked. An unreadable or invalid lock fails closed. The existing generated `Verify Tag` step remains before `Pack`; no new workflow step is needed.
- **`RunThroughEntryScript`**, in [`.build/SpechtBuild.GitHubActions.cs`](../../SpechtBuild.GitHubActions.cs): the statements that remove the generator's tool-restore and global-install steps and rewrite every target step to `./build.cmd --target ...`. `ContinuousIntegrationMiddleware` held them; with a second caller they are one private method both enhancements call.
- **No target pushes, and none creates a Release.** `0055-F1` C-1 makes every gate a target; neither the push nor the Release creation is a gate, and C-1 here rules out a publish from a developer's machine, which a target that pushes would put one command away (§ 5 #7, decisions 0001 and 0003). Each is one `RunStep` the enhancement declares in the `release` job.
- **The feed and the token are the constraints', not this design's.** C-3 names GitHub Packages on `rlittlesii/specht` as the only feed, and C-5 the workflow's own token as the only credential. ### Where the push runs

In a second job, `release`, of the same generated file (decision 0001; named by decision 0003). The GitHub Release is created there too, in the step after the push. - **The second job is assembled entirely in the enhancement**: four steps, none of them a target, and the SDK version written a second time beside the one the shared `Middleware` holds.

- **The upload is told to include hidden files.** `Pack` writes under `.artifacts/`, a folder whose name starts with a dot. `actions/upload-artifact`'s README for the `v4` line says "With `v4.4` and later, hidden files are excluded by default" and defines them as "any file beginning with `.` or files within folders beginning with `.`"; its `action.yml` declares `include-hidden-files`, default `'false'`. Read that way the glob finds no file and `if-no-files-found: 'error'` fails the step, so the step carries `include-hidden-files: 'true'`. The glob still names only `*.nupkg` in that one folder, so no other hidden file is uploaded. This is the action's documentation, read on 2026-10-09, not something observed on a runner. The alternative, a staging path with no dot, would move where `Pack` writes and was not taken. `actions/download-artifact`'s README describes its `path` as "Destination path", by default the workspace, and says nothing about hidden files or folders, so the download into `.artifacts/nupkg` carries no such input.

### The tag's commit and `main`

`VerifyTag`'s second check (B-011, OQ-12, decision 0003).

- **The mechanism** is `git merge-base --is-ancestor HEAD origin/main`, started through the `Run(tool, arguments)` helper in [`SpechtBuild.cs`](../../SpechtBuild.cs) with NUKE's `GitTasks.GitPath`, the git on the path that `AnnotateChangedFiles` already uses. The command exits 0 when `HEAD` is `origin/main`'s tip or an ancestor of it, and the check passes only then.
- **It fails closed.** The command exits 1 when the commit is not reachable and 128 when `origin/main` does not resolve; the helper reports only whether the exit code was 0, so both fail the target with the one message, which names the tag and says its commit is not on `main`.
- **`HEAD` is the tagged commit.** The checkout names no `ref`, so on a tag's run it is the commit the tag points at.
- **`origin/main` comes from the shared `Middleware`**: the checkout has `fetch-depth: '0'`, which `actions/checkout` documents as all history for all branches and tags, and step 2 runs `git fetch --prune`. That the ref resolves on a tag's checkout on a runner is the action's documentation, not something observed here; it is first shown by item 0084's tag. If it does not resolve, the first tag's run fails at step 6 and nothing is packed.
- **It runs after the name check**, so a tag that is wrong on both counts reports its name. It runs under the same `OnlyWhenDynamic` condition and so never on a dry run from a branch.
- **It is step 6 of `build`**, before `Format` and before `Pack`, so nothing is packed, uploaded or pushed for such a tag. `Specht` and `Restore` run before it.
- **On a developer's machine `origin/main` is whatever was last fetched.** The hand runs in § 8 are against that.
- **The stated limit** (OQ-12): a tag's run takes its workflow file and its build project from the tagged commit. The check stops a correctly named tag cut on the wrong commit by mistake. A commit that removed the check, or the step, is not stopped by it.

### The Release step

The last step of `release` (B-004, B-006, B-007, B-012; decision 0003).

- **`gh`, not an action.** `0055-F4` C-6 has every action's version declared in the build project's source for Renovate to update. A release action would be one more pinned version; the step is a command line assembled in the enhancement, as the push is. `gh` is on GitHub's hosted runner images by GitHub's documentation; nothing installs it, and no version of it is pinned. That it is there, and new enough to know these flags, is first shown by the tag.
- **In the second job**, because that job is the only one that runs only for a pushed `v*` tag, already holds the downloaded file, and is the only one given a write token (C-7). A Release created in `build` would put `contents: write` beside the repository's own code and in every dry run.
- **After the push**, as a later step of the same job, so it runs only when the push step exited 0 (B-004).
- **`"$GITHUB_REF_NAME"`** is the tag, read from the runner's variable in the shell; no expression text and no tag name is written into the script.
- **`--verify-tag`** makes `gh` stop when the tag is not in the remote repository. Without it `gh release create` creates a missing tag from the default branch, which would be a tag this Feature made (§ 5 #1). On a tag's run the tag exists, so the flag changes nothing unless the tag was deleted meanwhile.
- **`--generate-notes`** has GitHub write the title and the notes through its release-notes API (B-006). The step passes no `--notes-start-tag`, so which earlier tag the notes start from is GitHub's choice, and with no earlier tag the notes are whatever GitHub writes for a first release (B-012). Neither is observed here. B-012 is first shown by item 0084's tag, and B-006's "since the previous `v*` tag" by the tag after it.
- **The file argument** attaches the package (B-007). It is the path the push step named, in the same job, so the attached file is the downloaded artifact that was pushed.
- **`--repo "$GITHUB_REPOSITORY"`**, because the job has no checkout and so no git remote for `gh` to read the repository from.
- **`GH_TOKEN`** is the variable `gh` reads its credential from. It is the workflow's own token, with the job's `contents: write` (C-5). No other secret is named.
- **Not a draft and not a prerelease.** The step passes neither flag, so the Release is published as it is created.

### A run that pushes and then fails

The push and the Release creation are two steps, so a run can publish the package and stop before the Release exists (decision 0003). Whether any of this is a claim is OQ-14, which is open; nothing here decides it.

- **`--skip-duplicate`** on the push line makes `dotnet nuget push` treat the feed's refusal of a version it already holds as a skip, and exit 0. It replaces nothing, so § 5 #4 holds.
- **A rerun of the `release` job alone** downloads the artifact of the same run, skips the push, and reaches the Release step, which attaches that same file. This is the rerun OQ-14's proposed default names.
- **The artifact is kept one day.** After that a rerun of `release` alone fails at the download, and only a rerun of the whole run is left.
- **A rerun of the whole run** has `Pack` write the file again. The push is skipped, so the feed keeps the first file, and the Release step would attach the second. Whether B-007 holds then is OQ-14's question.
- **A rerun after the Release exists** fails at the Release step: `gh release create` does not replace a Release.
- **What the flag costs.** A push of a version already on the feed no longer fails its step. The Release step is then the one that fails, when the Release exists too.
- **None of it is observed.** That GitHub's feed answers a duplicate in the way the flag expects is `dotnet nuget push`'s documentation, and no rerun has happened.

### The version and the file name

- **On a `v*` tag's run the version is public.** `nbgv` reads the runner's ref, and `version.json`'s `publicReleaseRefSpec` names `refs/tags/v` followed by digits and dots, so the tag `v0.1.14` on a commit of height 14 computes `0.1.14`, `Pack` writes `specht.tool.0.1.14.nupkg`, and the push line and the Release line, which strip the `v` from the tag, name that file. Both lines read `specht.tool.${GITHUB_REF_NAME#v}.nupkg` in the generated file, lines 145 and 151, which is the name § 10 found the workflow had lost and item `0171` restored.
- **Off `main` and off such a tag the version is a prerelease**, `0.1.<height>-g<commit>`, and `Pack` writes `specht.tool.0.1.<height>-g<commit>.nupkg`. A dry run started from `main` packs the public name; one started from another branch packs the prerelease name.
- **On a developer's machine `VerifyTag` compares with the prerelease**, no runner ref being set: by hand it passes only for `v0.1.<height>-g<commit>`, and only on a commit `origin/main` reaches. The comparison is the same; the version it is handed differs.

- **B-001.** A pushed `v*` tag starts the run. The push and the Release creation are both in `release`, so neither happens.
- **B-003.** On a pushed `v*` tag with `build` green, step 3 of `release` pushes the one downloaded file to GitHub's NuGet endpoint for `rlittlesii` with the workflow's token. The package names the repository itself (`0001-F2` B-018). First shown by item 0084's tag.
- **B-004.** Step 4 of `release` creates the Release for the tag. It follows the push in the same job, so it runs only when the push step succeeded. First shown by the tag.
- **B-005.** A branch push, a pull request, or a tag that does not match `v*` starts no run of this workflow: its triggers name none of them. `ci.yml`, `main.yml` and `renovate.yml` pack nothing, push nothing and create no Release, and their tokens have `packages: none`. The `release` job's own `if` repeats the rule, so it does not depend on the trigger list staying as it is. The glob `v*` is wider than a version: a tag such as `vnext` does start a run, and B-009 is what stops it.
- **B-006.** `--generate-notes` on the Release line. First shown by the tag after the first.
- **B-007.** The file argument on the Release line is the path the push line names. First shown by the tag.

- **C-1.** A manual run skips `release`, and no target pushes or creates a Release, so no command on a developer's machine does.
- **C-3.** One feed address, in one line.

- **C-5.** `secrets.GITHUB_TOKEN` is the only credential named, in the `env` of the push step and of the Release step, and only `release` can write a package or a Release with it.
- **C-6.** The `Specht` step is the target `0055-F1` built; nothing here changes when it gates.
- **C-7.** `contents: write` and `packages: write` each appear once in the file, lines 118 and 123, in the `release` job's block; the workflow's block has `contents: read` and `packages: none`, and `build` has no block of its own.

### Why a dry run cannot push

- **The event.** The only push command and the only Release command are the last two steps of `release`, and that job's `if` is false for every event but `push`. A manual run's event is `workflow_dispatch` whatever ref it is started from, a tag included.
- **The token.** No token that can write a package or a Release exists in a dry run: `build`'s is read-only in every run, a tag's included, and a skipped job is given none.
- **The file.** A manual run from a branch has `GITHUB_REF_NAME` equal to the branch's name, so the path the two steps name, `specht.tool.main.nupkg` from `main`, does not exist. This holds even if the `if` were lost. It does not hold for a manual run started from an existing `v*` tag; there the event and the token are the barriers.
- **The token's reach.** No target pushes, and neither `SpechtBuild.cs` nor `SpechtBuild.Release.cs` has code that reads the token. ### Schema-lock release guard (B-013)

[Decision 0005](decisions/0005-the-schema-lock-release-guard-has-automated-coverage.md)
adds automated coverage for B-013 alone. `SchemaReleaseGuardUnitTests` uses
`MockFileSystem` to prove missing and empty locks, an unlocked newest or older
version, deterministic diagnostic ordering, and success without digest
comparison or writes. `SchemaReleaseGuardIntegrationTests` starts the compiled
build in a synthetic local Git repository whose commit is reachable from its
own `origin/main`. It computes the matching tag locally, then runs `Release`
with restore and the ordinary build gates skipped. Each unlocked case fails
with the guard's diagnostic before `Pack` starts or creates its output folder.
With all shipped versions locked, `VerifyTag` passes. No remote, package push,
release creation or tool restore is used; child-process telemetry is disabled.
Missing locks, existing incomplete locks, and fully locked versions have
separate tests with one assertion path each; only process and repository
setup is shared.
The test project carries `NukeTelemetryVersion`, as the build project does,
so starting its copied build executable does not amend that project.

made all seven refusal cases fail (four unit and three integration); the two
passing controls stayed green. Restoring the body restored their passes.

confirmed invalid JSON and JSON `null` fail closed, a branch skips the target,
and every run preserves the lock's bytes or absence. The existing generated
workflow still places `Verify Tag` before `Format`, `Compile` and `Pack`.
