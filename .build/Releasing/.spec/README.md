# Specification: Release

## 1. Business Goal

<!-- last written by: spec-author, 2026-11-01 (decision 0007) -->

Nothing publishes `specht.tool`: `0001-F2` § 5 row 7 hands the release workflow to repository tooling that does not exist, so the first package would be pushed by hand from one machine, with no proof that what was pushed is what the gates checked - and a package once published stays, with the schema version it embeds never changed in place (`0001-F7` C-1). This Feature removes that failure state: pushing a `v*` tag runs the full build on the tagged commit, publishes the packages to nuget.org only if every gate passed, and creates a GitHub Release for the tag; nothing else publishes. Amended 2026-11-01 (decision 0007): was GitHub Packages on `rlittlesii/specht`.

### Item 0250 review amendment (2026-10-20)

The repository owner asked that the release job use NUKE targets instead of embedding package commands and filenames in generated workflow shell strings. The earlier exclusion of publish targets was the recorder's design inference, not an owner decision; decisions 0001 and 0003 now record that correction. The generated `release` job checks out the tagged commit, downloads the run's package artifact, sets up the pinned SDK, then invokes `PushReleasePackages` and `CreateGitHubRelease` through `build.cmd`. Superseded 2026-11-01 by decision 0009: the `release` job downloads no package; it checks out, sets up the SDK and invokes `CreateGitHubRelease` alone. Both targets require a pushed `v*` tag in GitHub Actions before reading a package or publishing. `PushReleasePackages` reads package IDs from the two packable projects and requires both versioned files before either push. Amended 2026-11-01 (decision 0009): was both targets reading the two files; `CreateGitHubRelease` reads none. `PushReleasePackages` uses NUKE's typed `DotNetNuGetPush` settings. `CreateGitHubRelease` invokes `gh` for the provider operation after the pushes. Only the second job receives contents write, and since item 0327 `id-token: write` in place of package write; the build job still runs the gates with read access. The generated workflow contains target invocations and no package-name shell strings. The earlier design detail below is retained as its historical record and is superseded for item 0250's release path.

### Item 0264 amendment (2026-10-23)

Both jobs, `build` and `release`, run on the owner's self-hosted pool, `runs-on: [self-hosted, macOS, ARM64]`, in place of `ubuntu-latest` (C-9; `0055-F2` C-12, decision 0005). In [`.build/SpechtBuild.Release.cs`](../../SpechtBuild.Release.cs) the `release` job's `Matrix` is the `RunnerPool` constant that [`.build/SpechtBuild.GitHubActions.cs`](../../SpechtBuild.GitHubActions.cs) declares, and its checkout sets `Clean = true`; the `build` job takes the same substitution and the same clean checkout from the shared `Middleware` (`0055-F2` § 7). Every checkout in [`release.yml`](../../../.github/workflows/release.yml) therefore writes `clean: 'true'` where the generator wrote `clean: 'false'`, so a pool runner's untracked and ignored files from an earlier job, an earlier `.artifacts/nupkg/` among them, are removed before the job reads its workspace (`0055-F2` C-11). The `release` job still takes its package only from this run's artifact (C-4). No step, target, permission or trigger changed. Where the design detail below names `ubuntu-latest` for either job, it describes the file before this amendment.

### Item 0214 amendment (2026-11-01)

`0109-F5` adds advisory comparison steps to the `release` job after "Create GitHub Release" (`0109-F5` decision 0005, ADR-0001), so a rerun of the whole run reaches them only if both publication steps pass. Two changes follow; no claim, constraint, grant or trigger changes.

- **The `release` job's checkout persists no credential** (`PersistCredentials = false`, `persist-credentials: 'false'`). The checkout this job has had since item 0250 no longer leaves the write token in the clone's git configuration; the token reaches only the steps that name it.
- **`CreateGitHubRelease` keeps a Release already published at this commit.** Before `gh release create` it asks `gh release view <tag> --json tagName,isDraft` and `gh api repos/<repository>/commits/tags/<tag> --jq .sha`. When the Release is under this tag, not a draft, and its tag resolves to `GITHUB_SHA`, the target logs that it keeps the Release and succeeds without changing it. Any other answer, a failed query or no Release included, runs `gh release create` exactly as before, so a first publication that fails still fails the job, and a Release left as a draft still fails at creation and needs a hand. B-004 holds: the Release kept is the one published under this tag at this commit, whether this Feature created it or a hand did. Amended 2026-11-01 (decision 0009; `0109-F5` A-6): was `--json tagName,isDraft,assets`, the Release kept only when both package file names were among its assets, a Release with one asset missing also failing at creation, and B-007 holding with both packages attached, the Release kept being described as the one this Feature created for that tag.

This supersedes "A rerun after the Release exists fails at the Release step" and the last sentence of "What the flag costs" below, for a Release complete at this commit. The rest of that list, OQ-14 included, is unchanged: a whole rerun still packs again, and the kept Release carries no package. Amended 2026-11-01 (decision 0009): was the kept Release carrying the first run's files. "`release` has no checkout" below describes the file before item 0250. ### The tag's commit and `main`

`VerifyTag`'s second check (B-011, OQ-12, decision 0003).

- **The mechanism** is `git merge-base --is-ancestor HEAD origin/main`, started through the `Run(tool, arguments)` helper in [`SpechtBuild.cs`](../../SpechtBuild.cs) with NUKE's `GitTasks.GitPath`, the git on the path that `AnnotateChangedFiles` already uses. The command exits 0 when `HEAD` is `origin/main`'s tip or an ancestor of it, and the check passes only then.
- **It fails closed.** The command exits 1 when the commit is not reachable and 128 when `origin/main` does not resolve; the helper reports only whether the exit code was 0, so both fail the target with the one message, which names the tag and says its commit is not on `main`.
- **`HEAD` is the tagged commit.** The checkout names no `ref`, so on a tag's run it is the commit the tag points at.
- **`origin/main` comes from the shared `Middleware`**: the checkout has `fetch-depth: '0'`, which `actions/checkout` documents as all history for all branches and tags, and step 2 runs `git fetch --prune`. That the ref resolves on a tag's checkout on a runner is the action's documentation, not something observed here; it is first shown by item 0084's tag. If it does not resolve, the first tag's run fails at step 6 and nothing is packed.
- **It runs after the name check**, so a tag that is wrong on both counts reports its name. It runs under the same `OnlyWhenDynamic` condition and so never on a dry run from a branch.
- **It is step 6 of `build`**, before `Format` and before `Pack`, so nothing is packed, uploaded or pushed for such a tag. `Specht` and `Restore` run before it.
- **On a developer's machine `origin/main` is whatever was last fetched.** The hand runs in § 8 are against that.
- **The stated limit** (OQ-12): a tag's run takes its workflow file and its build project from the tagged commit. The check stops a correctly named tag cut on the wrong commit by mistake. A commit that removed the check, or the step, is not stopped by it.

### The Release step

Amended 2026-11-01 (decision 0009): was also because the job held the downloaded file.

- **`"$GITHUB_REF_NAME"`** is the tag, read from the runner's variable in the shell; no expression text and no tag name is written into the script.
- **`--verify-tag`** makes `gh` stop when the tag is not in the remote repository. - **`GH_TOKEN`** is the variable `gh` reads its credential from. It is the workflow's own token, with the job's `contents: write` (C-5). No other secret is named.

### A run that pushes and then fails

The push and the Release creation are two steps, so a run can publish the package and stop before the Release exists (decision 0003). Whether any of this is a claim is OQ-14, which is open; nothing here decides it.

- **`--skip-duplicate`** on the push line makes `dotnet nuget push` treat the feed's refusal of a version it already holds as a skip, and exit 0. It replaces nothing, so § 5 #4 holds.
- **A rerun of the `release` job alone** reaches the Release step, which attaches no file; the push, in `publish`, does not run again. This is the rerun OQ-14's proposed default names. Amended 2026-11-01 (decision 0009): was a rerun that downloads the artifact of the same run and attaches that same file. Amended 2026-11-01 (item 0333): was a rerun that "skips the push", the push then being a step of `release`.
- **The artifact is kept one day.** After that a rerun of `publish` fails at the download; a rerun of `release` alone reads no artifact and is not affected. Amended 2026-11-01 (decision 0009): was a rerun of `release` alone failing at the download, leaving only a rerun of the whole run.
- **A rerun of the whole run** has `Pack` write the file again. The push is skipped, so the feed keeps the first file, and the Release step attaches neither. Amended 2026-11-01 (decision 0009): was the Release step attaching the second file, and whether B-007 then held was OQ-14's question, which no longer arises.
- **A rerun after the Release exists** fails at the Release step: `gh release create` does not replace a Release.
- **What the flag costs.** A push of a version already on the feed no longer fails its step. The Release step is then the one that fails, when the Release exists too.
- **None of it is observed.** That the feed answers a duplicate in the way the flag expects is `dotnet nuget push`'s documentation, for GitHub's feed until item 0327 and for nuget.org since, and no rerun has happened. On nuget.org the login step runs again on a rerun of `publish` and issues a fresh key, so a rerun does not reuse an expired one. Amended 2026-11-01 (item 0333): was "a rerun of `release` alone", the job that then held the login.

### The version and the file name

- **On a `v*` tag's run the version is public.** `nbgv` reads the runner's ref, and `version.json`'s `publicReleaseRefSpec` names `refs/tags/v` followed by digits and dots and, since item 0327, an optional `-preview` (`0055-F5` § 7). With `version` `0.3-preview` the tag `v0.3.14-preview` on a commit of height 14 computes `0.3.14-preview`, and `Pack` writes `specht.tool.0.3.14-preview.nupkg` and `Specht.CodeAnalysis.0.3.14-preview.nupkg`. `ReleasePackages` in [`.build/SpechtBuild.Release.cs`](../../SpechtBuild.Release.cs) strips the `v` from the tag and joins it to each project's `PackageId`, so `PushReleasePackages` names those two files. Amended 2026-11-01 (decision 0009): was both targets; `CreateGitHubRelease` names no file. The generated file names no package file since item 0250; the name item `0171` restored to it, as § 10 records, is now the target's.
- **Off `main` and off such a tag the version is a prerelease naming the commit**, `0.3.<height>-preview-g<commit>`, and `Pack` writes files of that version. A dry run started from `main` packs the public name, `0.3.<height>-preview`; one started from another branch packs the commit's. Both carry the label, so neither is a version `VerifyTag`'s first check refuses.
- **On a developer's machine `VerifyTag` compares with the version of the checked-out branch**, no runner ref being set: off `main` by hand it passes only for `v0.3.<height>-preview-g<commit>`, and only on a commit `origin/main` reaches. The comparison is the same; the version it is handed differs.
- **Before item 0327 the version carried no label.** `version` was `0.1`, then `0.2` and `0.3` (`0055-F5` § 7), the tag pattern matched digits and dots only, and the tag `v0.1.14` computed `0.1.14`; `v0.1.90` was published that way to GitHub Packages (§ 8). Such a version is what B-014 now refuses.

### Why a dry run cannot push

- **The event.** The only push command is the last step of `publish` and the only Release command is step 3 of `release`, which needs `publish`; each job's `if` is false for every event but `push`. Amended 2026-11-01 (item 0333): was "the last two steps of `release`", with that one job's `if`. Amended 2026-11-01 (decision 0009): the Release command was step 4. A manual run's event is `workflow_dispatch` whatever ref it is started from, a tag included.
- **The token.** No token that can write a package or a Release exists in a dry run: `build`'s is read-only in every run, a tag's included, and a skipped job is given none. Since item 0327 no OIDC token either: `build` takes the workflow's `id-token: none`, so a dry run cannot ask NuGet Trusted Publishing for a key.
- **The file.** A manual run from a branch has `GITHUB_REF_NAME` equal to the branch's name, so the path the push step names, `specht.tool.main.nupkg` from `main`, does not exist (amended 2026-11-01, decision 0009: was the path the two steps name). This holds even if the `if` were lost. It does not hold for a manual run started from an existing `v*` tag; there the event and the token are the barriers.
- **The token's reach.** No target pushes, and neither `SpechtBuild.cs` nor `SpechtBuild.Release.cs` has code that reads the token. The push step and the Release step are the only steps the file hands it to by name. `actions/checkout` takes the job's token by its own default, with no `token` line in the file, and keeps it in the clone's git configuration, so the steps of `build` that run the repository's code can read it. That token is `build`'s, read-only in every run, with `packages: none`; `release` has no checkout.
- **The workflow changes preceded publication.** Item 0083's proof is the generated file, hand runs of `VerifyTag`, and the follow-up dry run on `main` (decision 0002), now recorded in § 8. Item 0084's is the regenerated file and the hand runs, then the dry run on `main` and the first tag, both after the merge and both recorded by a follow-up pull request (OQ-13). The first tag no longer waits for `0001-F5` and `0001-F6` (C-2 as amended).

### What the dry run does not prove

Each of these is first shown by item 0084's tag, unless the line says otherwise.

- **The push itself**: that the token is accepted, that the address is right, that the package lands on `rlittlesii/specht` (B-003; OQ-11, resolved). `dotnet nuget push` has no trial mode. Since item 0327 the same holds for nuget.org: that the trusted-publishing policy for `NUGET_USER` accepts this repository's workflow, that the login step issues a key, and that both packages land there are first shown by the first `v*-preview` tag.
- **The `release` job at all.** A dry run proves the upload and stops there. That the job starts on a tag, and that the artifact arrives as one file at the path the two lines name, wait for the tag. Amended 2026-11-01 (decision 0009): only the push names the path, in `publish`; `release` reads no artifact.
- **The tag check on a runner.** A dry run from a branch skips it. It is exercised by hand on a developer's machine, against the prerelease version and the `origin/main` last fetched. On the tag it first runs live, against the public version.
- **That `origin/main` resolves on a tag's checkout on a runner.** The ancestry check needs it, and only a tag's run makes the check run.
- **The ancestry check's refusal on a runner.** The first tag is cut on `main` and shows the check passing. Its failing side is shown by hand only; nothing short of a `v*` tag pushed on a commit off `main` shows it live, and C-2 rules out pushing one as a trial.
- **The Release step**: that `gh` is on the runner, that the token may create a Release, that the notes are generated (B-012) and that the Release carries no file (B-004). Amended 2026-11-01 (decision 0009): was that the file is attached (B-004, B-007).
- **B-006's range.** Notes "since the previous `v*` tag" need a previous tag: first shown by the second tag.
- **`--skip-duplicate` and a rerun.** Shown only if a run ever fails after its push (OQ-14).
- **B-002 on a runner.** That a failed gate stops the push is the file's shape plus GitHub's rules for `needs` and for an `if` with no status function. Nothing short of a failing gate on a real tag shows it live.
- **The run on `main` before the merge.** GitHub starts a manual run only of a workflow file that is on the default branch, so the dry run of `release.yml` happens after the pull request that delivers item 0084 has merged (OQ-13). That is GitHub's rule as documented, not something observed here.

### Rejected

- **A target that pushes or creates a Release** (§ 5 #7). It would let one `./build.sh` command push from a developer's machine with any token in the environment, which C-1 rules out, and it would need its own guard against a dry run. The cost of rejecting it: two command lines in a workflow that no target runs, which decision 0001's reading of `0055-F1` C-1 allows (decision 0003).
- **`PublishNugetPackagesJobAttribute`** (§ 5 #8).
