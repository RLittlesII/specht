# Specification: The rules command

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-11 -->

A rule can be lowered, raised or switched off from the manifest, but nothing lists the rules a pinned version has: a maintainer learns a rule id from the violation that names it, and its level only by reading the manifest beside the rule's page. This Feature removes that failure state: `specht rules` lists every rule id of the pinned version with its family, its default severity and the level it has under this manifest, as text or as one JSON document.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-26 -->

### Engine catalogue

[`RuleEntriesReader`](../../../../specht/Rules/RuleEntriesReader.cs) is a concrete instance registered by the existing [`AddSpechtEngine`](../../../../specht/Composition/SpechtEngineServiceCollectionExtensions.cs) composition. Its root entry point loads only the manifest through [`SpecSchemasLoader.LoadManifest`](../../../../specht/Model/SpecSchemasLoader.cs), then calls its in-memory overload with that `SpecStructure`. It does not load frontmatter schemas, discover specifications or evaluate rules.

The in-memory overload resolves the exact pin through [`SpecManifestParser.PinnedVersion`](../../../../specht/Manifest/SpecManifestParser.cs), orders that version's `RuleIds` with `StringComparer.Ordinal`, and reads the corresponding `SchemaVersion.RulePages` text. For each page it reuses [`SpecDocument.Parse`](../../../../specht/Model/SpecDocument.cs), taking the `Family` and `Default severity` rows of the `Metadata` section's first pipe table. It does not parse Markdown by splitting pipes. Page metadata is trusted shipped content, whose shape and page-per-vocabulary invariant are already checked by `SchemaVersionRulePagesUnitTests`.

[`RuleEntry`](../../../../specht/Rules/RuleEntry.cs) carries the vocabulary id, family, default severity and effective level. Both level values use the existing `SpecRuleLevel`, including `Off`; the family retains the page's spelling. An explicit value in `SpecStructure.Rules` wins; an omitted entry uses the page's default severity. No entry is filtered for its effective level. The returned entries are produced on demand, with no maintained metadata index or cache. Manifest inspection can consume this same result rather than compute effective levels again.

ADR-0014 retains direct calls and the existing stores, parser and composition. This change introduces no interface, dependency package, mediator, new static parser, vocabulary or rule-page edit.

### Text command

[`RulesCommand`](../RulesCommand.cs) resolves the root as the check does and calls the existing `RuleEntriesReader`. It writes each returned entry directly to the injected console writer as four tab-separated fields, converting both level values with invariant lower casing. It adds no heading, count, filtering or rendered table, and returns `ExitCodes.Success` regardless of the effective levels.

The command catches the same typed root and manifest exceptions as [`CheckCommand`](../../Check/CheckCommand.cs). A missing root echoes the option as typed; missing, unreadable and rejected manifest messages come unchanged from the engine with the same `specht: ` prefix. Failures use the injected error writer or `Console.Error`, leave stdout empty, and return the existing missing-input or invalid-manifest constants. The catalogue is fully read before the first line is emitted. There is no specification discovery, rule evaluation, write or network dependency in this path.

[`RulesRegistration`](../RulesRegistration.cs) registers `rules` as a branch with `RulesCommand` as its default. Its `BranchSettings` hold the shared options and the default command uses the distinct derived `Settings`, so Spectre binds `--json` while branch help exposes both `--root` and `--json`. Using the same settings type for both registrations displayed and accepted the flag without selecting JSON; the dedicated inherited type follows Spectre's branch settings pattern without changing composition. [`Program.cs`](../../../Program.cs) adds that registration to the existing explicit chain; no host-factory migration or mediator is introduced.

### JSON command

`RulesCommand.Settings.Json` selects the JSON form through the same branch-default command. For B-009/B-010 it serializes the complete reader result once with the existing `System.Text.Json` serializer and writes the resulting document directly to the injected console writer. The top-level value is an array in the reader's order. Each object projects exactly the current four values as `id`, `family`, `defaultSeverity` and `effectiveLevel`; both level values use the same invariant lower-case spelling as text. Explicit projection keeps enum numbers and future record properties out of this output without changing the engine model or introducing a renderer abstraction.

These member names are the implementer's current representation, as assigned by the JSON item; they are not a new owner decision, published schema or addition-only compatibility promise. OQ-4 remains open. The existing text loop and typed failure path remain unchanged; the complete catalogue is read before either form writes stdout.

The pure `RuleEntriesReader.Read(SpecStructure)` overload admits synthetic `SchemaVersionFixture` vocabularies and pages. Its root overload calls only `SpecSchemasLoader.LoadManifest` and the parser's pin resolver. The integration tests invoke the shipped composition rather than build a parallel registrar. Direct `RulesCommand.ExecuteAsync` tests use a real reader, `MockFileSystem` and `TestConsole`, without a command parser, registrar or disk.

Final member inspection: `RulesCommand.ExecuteAsync` obtains the complete catalogue before writing, projects four fields with invariant lower casing, returns the success constant and catches only the existing typed input failures; `Fail` writes its supplied message to the error writer and returns its supplied constant. These members are exercised directly by the unit suite. The call path uses only manifest reads and embedded metadata; it contains no specification discovery, rule evaluation, file write, clock or network operation. Mock-file snapshots and process snapshots complement that inspection. The JSON unit tests use the existing `SchemaVersionFixture` to supply an unordered vocabulary, an escaped family and a page default of Off; they observe direct command execution with `Json` selected. They repeat execution and snapshot fake files to retain deterministic, read-only regression proof. A separate empty-vocabulary test pins serialization of the complete collection rather than per-entry writes. `RulesCommand.ExecuteAsync` reads the complete catalogue, selects the JSON branch, projects those four fields with invariant lower-case levels, and calls `JsonSerializer.Serialize` once before one writer call. The process scenarios also pin `RulesRegistration.AddRules` using distinct branch settings inherited by the default command's settings, so `--json` reaches that branch. Both JSON claims have behavioral green at both tiers. No renderer abstraction was added.
