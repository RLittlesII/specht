# Specification: The check command

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The gate runs only as `hooked`'s Nuke target, so a pre-commit hook, a CI step and an agent mid-write each reach it differently or not at all, and a second repository has no step to add. This Feature removes that failure state: `specht` is one command, installed from a package through a local tool manifest, that reads a root, prints one MSBuild-shaped line per violation and the summary, and exits with a code the three call sites all understand (Must-1). It writes nothing under the root but the `--report` file `0001-F3` owns.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 -->

Delivered so far by items 0026, 0027, 0028 and 0133. The slice layout is `dotnet-tool` § Vertical Slice.

- **The command.** `CheckCommand` is an `AsyncCommand` with its `Settings` nested (decision 0002): `--root <DIR>`, defaulting to `.`, and `--strict`. It resolves the root with `Path.GetFullPath`, calls the runner, writes each violation's `ToString()` - the engine's MSBuild-shaped line, in the engine's order, which `SpecViolation` ([`SpecViolation.cs`](../../../../specht/SpecViolation.cs)) ends with ` [<identifier>]` when its `Identifier` is not null and at the message when it is (B-016, decision 0006) - and returns `ExitCodes.Violations` on an error, or on any violation under `--strict`, and `ExitCodes.Success` otherwise (B-001, B-003, B-004).
- **The run summary** (B-002). After the violation lines the command writes each of `SpecReportDocument.From(report).SummaryLines()` through the same raw writer: four lines, `specifications: epics 2, features 1`, `items: 0`, `rules evaluated: 41`, `errors: 1, warnings: 0`, the layouts in the document's order. The lines are formatted in the engine, on the document `0001-F3` B-005 already defines the counts on, beside `SpecViolation`'s line format, so the command stays parse, run, fold (C-4) and the summary and `--json` cannot count differently. A layout is named by its name in the manifest, the string the document's JSON carries (`0001-F6` B-009, item `0005`), so the summary and `--json` cannot name it differently; `epics` and `features` are the default manifest's names (`0001-F6` decision 0008). No summary line has the diagnostic shape, so a log parser reads none as a violation. An input failure returns before the summary, so stdout stays empty for B-005 to B-007.
- **The raw writer.** Lines go to the injected console's `Profile.Out.Writer`, not through `IAnsiConsole.WriteLine`: Spectre renders a line to the console's width, and a redirected console is 80 columns wide, so a rendered diagnostic wraps and GitHub no longer annotates it (C-3).
- **The runner is injected** as a `Func<string, SpechtReport>`, `SpechtRunner.Run` outside a test. It is the seam the warning path needs: the engine emits no warning until `0001-F5`'s rule settings exist, so B-004 is reachable only through a substituted runner.
- **The composition root.** `Program.cs` registers the runner in a `ServiceCollection`, hands it to Spectre through `TypeRegistrar`/`TypeResolver`, and sets `CheckCommand` as the default command (A-1).
- **Paths** are the engine's: every violation's file is root-relative with `/` already (`0001-F1` B-007), and the summary carries counts and layout names only, so nothing absolute reaches stdout (B-013).
- **Input failures are engine exceptions the command folds.** `SpecManifest.Load` is the first read of a root, so it decides, through its `IFileSystem`: a root that is not a directory throws `SpechtRootNotFoundException`, no file at the manifest path throws `SpechtManifestNotFoundException`, and a `JsonException`, `InvalidOperationException` or `FormatException` from parsing or shaping the manifest is rethrown - a JSON `null` where the shape needs a value (the whole manifest, a `sections` element, a table or a grammar) throws `InvalidOperationException` from the private `Present` guard, so it takes the same path and the filter never widens to `NullReferenceException` - as `SpechtManifestUnreadableException`, its message naming `SpecManifest.RelativePath` and never the absolute path (B-005, B-006, B-007). Each is declared in `src/specht/` beside `SpechtManifestException`, which stays distinct and unmapped: a well-formed manifest the engine rejects is `0001-F5`'s (§ 5 row 4).
- **The mapping lives in the command, not in `SetExceptionHandler`.** `CheckCommand.ExecuteAsync` catches exactly those three types around the runner call and returns `ExitCodes.MissingInput` (`2`) or `ExitCodes.InvalidManifest` (`3`); no other exception is caught. A handler set in `Program.cs` would leave the command tester, which composes its own app, exiting `-1`, and C-2 forbids an exception crossing the command boundary.
- **Why the check is not in the command.** A pre-check of the root before the runner would fail every test whose substituted runner is handed a root with no manifest - the working directory, or `some/where`. The decision sits where the real runner reaches it.
- **The root as typed.** The engine holds only the resolved root, so `SpechtRootNotFoundException` carries no path and the command names `settings.Root` (B-005); the manifest messages come from the engine.
- **Stderr** is written with `Console.Error.WriteLine`, `dotnet-tool` § Conventions; it is not injected, because the command tester captures stdout alone and no test substitutes it. The message never reaches stdout (C-3, B-009).
- **Exit codes** hold `0` to `3`; 0040 adds `4`.

## 8. Testing Strategy

<!-- last written by: test-writer, 2026-10-09 (B-001 as amended and B-016: the identifier on the line) -->

- **Unit, B-001 and B-016** (`test/tests/SpecViolation.Unit.Tests.cs`, over violations built with the `SpecViolationFixture` AutoFixture). The mechanism beneath both claims is one decision in `SpecViolation.ToString` (§ 7): whether the line carries a trailing `[<identifier>]`. `CheckCommand.ExecuteAsync` writes each violation through it and adds nothing to the line. Pinned per claim, each a `[Theory]` over an error on a line and a warning on the file as a whole, which renders no position:
  - B-001: a violation with an identifier renders exactly `<path>(<line>): <severity> SPEC###: <message> [<identifier>]`.
  - B-016: a violation with no identifier renders exactly `<path>(<line>): <severity> SPEC###: <message>`.
  - Every other line assertion in the integration tests and the scenarios builds its expected line from `SpecViolation.ToString`, so it holds the command to the engine's line and not the line to its form. The form is held by these two theories, by the integration theory over endings below, and by the bracket steps of the `@B-001` and `@B-016` scenarios. Before `ToString` appended the identifier, the B-001 theory, the identifier row of the endings theory and the `@B-001` scenario were red, each on a line ending at the message; B-016's tests were green, as the claim states a line that did not change.
- **Integration** (`test/tests/CheckCommand.Integration.Tests.cs`), every test through Spectre's command tester on an 80-column console, so none of them is a unit test:
  - over a runner returning a report built with the `SpechtReportFixture` and `SpecViolationFixture` AutoFixtures, one `[Theory]` per shape: stdout is exactly one line per violation in the runner's order, then the report's summary lines (B-002) - the summary alone for no violation, and a line wider than the console unwrapped; the exit code is `1` on an error, `0` on none, `0` on a warning alone and `1` on a warning under `--strict`; and the runner gets the working directory, or `--root` resolved; and one `[Theory]` over endings: the printed line of a violation with an identifier ends with its message and ` [<identifier>]` (B-001), and the line of one with none ends at its message (B-016);
  - over the real runner and a `SpecTree` on disk: the printed lines equal the report's, root-relative with `/`, followed by its summary lines, and a clean tree prints only the summary and exits `0` (C-7);
  - over the real runner and a `SpecTree` arranged into an input failure, one `[Theory]`: a root that does not exist and a root that is a file exit `2` (B-005), a root whose manifest was deleted exits `2` (B-006), and a manifest that is not well-formed JSON, a top-level array, `sections` holding numbers, the JSON literal `null`, or `sections` holding a `null` exits `3` (B-007), each with nothing on stdout. A well-formed manifest the engine rejects is `0001-F5`'s (§ 5 row 4) and has no row here.
- **B-008, help.** The mechanism is Spectre's: `CommandApp` renders usage from `CheckCommand.Settings`' `[CommandOption]` and `[Description]` attributes and returns `0` before `ExecuteAsync` runs; the command holds no help code of its own (`ExecuteAsync`, `Fail` and `Settings` read). No unit tier: there is no decision of this repository's beneath the claim, only the settings' declaration, which only Spectre's pipeline reads. Pinned at the integration tier through the command tester with `--help` - stdout names `--root` and `--strict`, exit `0` - and by the scenario over the launched tool, which goes through `Program.cs`'s `CommandApp`.
- **B-012, no write.** The claim is an absence: nothing on the check's path writes. Read for it: `CheckCommand.ExecuteAsync` calls the runner, writes stdout through `IAnsiConsole` and stderr through `Fail`, and opens no file; `SpechtRunner.Run` loads and evaluates; `SpechtRunner.WriteReport`, the one write in `src/specht` outside `init`, has no caller in the check. No unit tier: there is no decision beneath the claim to pin in memory, and an absence of writes is only observable on a disk. The scenario snapshots every file under a `SpecTree` root, hidden folders included, as its root-relative path to its length and SHA-256, launches the built tool with no report path, and holds a second snapshot equal to the first; a stray file, an appended byte and a deleted manifest each turned it red, naming the path. The integration test C-7 calls for is `0099`'s harness's to host, so the row is `Partial` until it lands (decision 0005); the `--report` exemption is `0001-F3` C-7's.
- **Stderr is the acceptance tier's.** Spectre's command tester captures one console, stdout; it has no stderr channel, and the command writes stderr with `Console.Error` (§ 7). The message each input failure writes - the root as typed (B-005), the manifest path (B-006), the manifest path relative to the root (B-007) - is asserted only by the scenarios, over the launched tool.
- **Unit, B-002** (`test/tests/Report/SpecReportDocument.Unit.Tests.cs`, over a report built with the `SpechtReportFixture` and `SpecViolationFixture` AutoFixtures). The mechanism beneath B-002 is the derivation in `SpecReportDocument.SummaryLines` (§ 7): four lines made from the `0001-F3` B-005 document, so each count is the document's. Pinned: the lines are exactly the specification count per layout, by the document's layout name and in its order, then the item count, the count of rule ids evaluated, and the error and warning counts; and no line of a summary over violations is in the diagnostic shape, so a summary line is never read as a violation. Where the summary goes - after the violation loop, on stdout, and not on an input failure - is the fold in `CheckCommand.ExecuteAsync`, reachable only through Spectre's pipeline; the integration tests above pin it.
- **Unit** (`test/tests/Manifest/SpecManifest.Unit.Tests.cs`, over `MockFileSystem`). The mechanism beneath B-005, B-006 and B-007 is the decision in `SpecManifest.Load` (§ 7): which failure a root and its manifest are. Pinned per claim:
  - B-005: a `[Theory]` over no root at all and a root that is a file - each throws exactly `SpechtRootNotFoundException`.
  - B-006: a root directory with no manifest throws exactly `SpechtManifestNotFoundException`, its message containing `SpecManifest.RelativePath`.
  - B-007: a `[Theory]` over truncated JSON, a top-level `[]`, `sections` holding numbers, the literal `null`, and `sections` holding a `null` - each throws exactly `SpechtManifestUnreadableException`, its message containing `SpecManifest.RelativePath` and not the root, with the parser's or the shape's failure as its inner exception. The boundary stays where § 5 row 4 puts it: the existing unknown-key theory now asserts exactly `SpechtManifestException`, not the unreadable type.
  - The fold from those three exceptions to `2`, `2` and `3`, and B-005's message naming `settings.Root`, live in `CheckCommand.ExecuteAsync` and are reachable only through Spectre's pipeline; the integration theory and the scenarios pin them (C-4). The fold from a report to lines and a code is the same: no unit tier, for the same reason.
- **Acceptance.** `check.feature` is linked into `test/acceptance`; [`Check/CheckSteps.cs`](../../../../../test/acceptance/Check/CheckSteps.cs) builds its trees with `SpecTree`, linked from `test/tests`, and launches the built tool over them, so a scenario reads the process's stdout, stderr and exit code as a shell does. B-005's root is typed relative to the working directory, `no-such-root`, so "as it was typed" is checked against the literal; B-006 deletes the tree's manifest; B-007 overwrites it with truncated JSON. B-013's run from inside the root launches the tool with the root as its working directory and names no root. B-002 writes two specifications in the `epics` layout and one in the `features` layout, and holds stdout's last lines to `SpecReportDocument.From(report).SummaryLines()` for the runner's report, the layout line naming `epics 2` and `features 1`. Every step that reads a diagnostic (B-001, B-009, B-013) reads it over the lines before the summary, and B-009's holds the tail to the summary exactly, so stdout is the violation lines, the summary, and nothing else. B-001's bracket step finds the one violation the runner gives the identifier `B-002`, and holds the printed line carrying its rule id and message to end with that message and ` [B-002]`. B-016 writes a specification in the `epics` layout with no frontmatter, holds the runner's one `SPEC001` violation to carry no identifier, and holds its printed line to end at its message with no bracket after it.
- **Mutations.** Writing through `IAnsiConsole.WriteLine`, dropping `--strict`, and prefixing the root to each line each turned tests red; after the move to the integration tier, `IAnsiConsole.WriteLine` failed the unwrapped row and the real-runner lines, and dropping `--strict` failed the strict row.
- **Waiting on `0001-F5`:** the two warning scenarios (B-004, and B-003's warning-alone case) stay unbound, because no tree yields a warning until rule settings exist; B-004 is proved at the integration tier, over a report built in memory, until then. Every other unbound scenario reports Skipped until its item binds it.
