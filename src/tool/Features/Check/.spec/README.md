# Specification: The check command

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The gate runs only as the consumer's Nuke target, so a pre-commit hook, a CI step and an agent mid-write each reach it differently or not at all, and a second repository has no step to add. This Feature removes that failure state: `specht` is one command, installed from a package through a local tool manifest, that reads a root, prints one MSBuild-shaped line per violation and the summary, and exits with a code the three call sites all understand (Must-1). It writes nothing under the root but the `--report` file `0001-F3` owns.

## 2. User Needs

<!-- last written by: spec-author, 2026-10-17 (working-package self-check, decision 0014, item 0237) -->

| #   | Persona                               | Need                                                                                                    | Pain Point Today                                                               |
| --- | ------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 1   | The maintainer's pre-commit hook      | A command that exits non-zero on a staged specification with an error, fast, with no build              | Only a consumer repository has a hook, and it bootstraps Nuke to read markdown |
| 2   | The CI build, here and in a consumer  | MSBuild-shaped lines GitHub annotates on the diff and an exit code that fails the job                   | Exists through the consumer's Nuke target only                                 |
| 3   | The agent authoring a specification   | A read-only oracle it can run mid-write before it reverts or fixes a damaged draft                      | Re-read the document, or run the repository's whole build                      |
| 4   | A consumer's Nuke `Specht` target     | A tool to call through the local tool manifest, in place of a project reference to the engine           | Carries the engine's code and build wiring                                     |
| 5   | `0001-F3`, `0001-F4`, `0001-F7`       | A host to join as an option or a command                                                                | N/A (internal dependency)                                                      |
| 6   | Someone reading the package on a feed | What the tool is, who publishes it, under what licence, and the repository and commit it was built from | The package names none of them, and its id is not the one every document gives |
| 7   | Someone holding an installed tool     | Which version of the tool it is and the commit it was built from, from the tool itself                  | An installed tool is no longer a package (B-019), and it prints neither        |

### Assumptions

| ID  | Assumption                                                                                                                                                                                                                                                                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | `check` is the default command: `specht` with no command name runs it. `init` and `upgrade` are sibling commands (`dotnet-tool` § Vertical Slice).                                                                                                                                                                                      |
| A-2 | This repository's self-check builds and packs the working checkout, installs that exact package through an isolated local tool manifest under .artifacts/, and invokes it against the requested tree; the hook builds the staged snapshot. The committed consumer package pin remains a separate installation contract (decision 0014). |
| A-3 | The manifest path is `<root>/.specht/manifest.json` (amended 2026-10-11, `0001-F5` decision 0011: was `<root>/.specht/schema/spec-structure.schema.json`, which never shipped and is no retired path). The retired manifest path is `<root>/.spec/schema/spec-structure.schema.json`, where the manifest was read before ADR-0011.      |
| A-4 | While the `Specht` target runs the tool as A-2 quotes, it builds the tool from `src/tool` under the root it checks, so a root checked through the target, or through the pre-commit hook that calls it, carries this repository's source; B-010 holds for such a root (owner, 2026-10-14; decision 0012).                               |

Delivered so far by items 0026, 0027, 0028, 0133, 0171, 0172, 0174, 0182, 0183 and 0217. The slice layout is `dotnet-tool` § Vertical Slice.

- **The command.** `CheckCommand` is an `AsyncCommand` with its `Settings` nested (decision 0002): `--root <DIR>`, defaulting to `.`, and `--strict`. It resolves the root with `Path.GetFullPath`, calls the runner, writes each violation's `ToString()` - the engine's MSBuild-shaped line, in the engine's order, which `SpecViolation` ([`SpecViolation.cs`](../../../../specht/Model/SpecViolation.cs)) ends with ` [<identifier>]` when its `Identifier` is not null and at the message when it is (B-016, decision 0006) - and returns `ExitCodes.Violations` on an error, or on any violation under `--strict`, and `ExitCodes.Success` otherwise (B-001, B-003, B-004).
- **The run summary** (B-002). After the violation lines the command writes each of `SpecReportDocument.From(report).SummaryLines()` through the same raw writer: four lines, `specifications: epics 2, features 1`, `items: 0`, `rules evaluated: 41`, `errors: 1, warnings: 0`, the layouts in the document's order. The lines are formatted in the engine, on the document `0001-F3` B-005 already defines the counts on, beside `SpecViolation`'s line format, so the command stays parse, run, fold (C-4) and the summary and `--json` cannot count differently. A layout is named by its name in the manifest, the string the document's JSON carries (`0001-F6` B-009, item `0005`), so the summary and `--json` cannot name it differently; `epics` and `features` are the default manifest's names (`0001-F6` decision 0008). No summary line has the diagnostic shape, so a log parser reads none as a violation. An input failure returns before the summary, so stdout stays empty for B-005 to B-007.
- **The raw writer.** Lines go to the injected console's `Profile.Out.Writer`, not through `IAnsiConsole.WriteLine`: Spectre renders a line to the console's width, and a redirected console is 80 columns wide, so a rendered diagnostic wraps and GitHub no longer annotates it (C-3).
- **The runner is injected** through the per-run selection delegate declared by [`CheckCommand`](../CheckCommand.cs), the resolved `SpechtRunner`'s `Run` outside a test. It is the seam the warning path needs: the engine emits no warning until `0001-F5`'s rule settings exist, so B-004 is reachable only through a substituted runner.
- **The composition root.** `Program.cs` calls `AddSpechtEngine()` on a `ServiceCollection` (`0001-F1` § 7, item `0107`; ADR-0001 stage D), registers that delegate as the resolved `SpechtRunner`'s `Run`, hands the collection to Spectre through `TypeRegistrar`/`TypeResolver`, and sets `CheckCommand` as the default command (A-1). The registrar and the resolver are unchanged; item `0144` moves the list into the factory (ADR-0007).
- **Frontmatter source selection** (`0001-F7` B-009, B-101 to B-107; decision 0011). Spectre parses and validates the optional `--schema-source` setting. The command maps it to `SchemaSourceSelection` and dispatches it with the root; the engine validates the manifest before applying precedence. The same engine exception fold handles missing or invalid selected schemas and upstream contradictions as stderr, empty stdout and exit `3`. The selection is carried per run and no command reads or writes schema files.
- **Paths** are the engine's: every violation's file is root-relative with `/` already (`0001-F1` B-007), and the summary carries counts and layout names only, so nothing absolute reaches stdout (B-013).
- **Input failures are engine exceptions the command folds.** `SpecManifest.Load` is the first read of a root, so it decides, through its `IFileSystem`: a root that is not a directory throws `SpechtRootNotFoundException`, no file at the manifest path throws `SpechtManifestNotFoundException`, and a `JsonException`, `InvalidOperationException` or `FormatException` from parsing or shaping the manifest is rethrown - a JSON `null` where the shape needs a value (the whole manifest, a `sections` element, a table or a grammar) throws `InvalidOperationException` from the private `Present` guard, so it takes the same path and the filter never widens to `NullReferenceException` - as `SpechtManifestUnreadableException`, its message naming `SpecManifest.RelativePath` and never the absolute path (B-005, B-006, B-007). Each is declared in `src/specht/` beside `SpechtManifestException`, which stays distinct and unmapped: a well-formed manifest the engine rejects is `0001-F5`'s (§ 5 row 4).
- **The retired manifest path** (A-3, B-037 to B-039, item `0183`, [ADR-0011](../../../../../.spec/adr/0011-tool-configuration-lives-in-specht-and-specifications-in-spec.md)). The manifest path is `SpecManifest.RelativePath`, `.specht/manifest.json` since item `0185` (`0001-F5` decision 0011), and `Load` reads no other (`0001-F5` § 7, "The location"). A manifest left at `SpecManifest.RetiredRelativePath` is therefore no manifest: the same `SpechtManifestNotFoundException`, the same fold to `2`, and no new catch in the command (B-037). The exception takes one argument, whether a file is at the retired path, and with it carries `.specht/manifest.json: there is no manifest at the manifest path; the manifest at .spec/schema/spec-structure.schema.json is not read.`; without it the message is B-006's, unchanged (B-038). `Load` asks whether that file exists only after it found none at the manifest path, and never opens it, so with a manifest in place the retired path is not looked at and cannot change a run (B-039). The message is the engine's, beside the other manifest messages, so the command stays parse, run, fold (C-4).

### Working package self-check

Check decision 0014 uses the build-only SelfCheckTool in .build/ to prepare an
isolated package feed, local manifest and caches. Its RunAsync method takes a
root and build configuration; a file-system abstraction and an asynchronous
process delegate are its I/O seams. It returns the first failed preparation
code or the installed checker's code. The NUKE adapter logs the command's output
and supplies annotation input without importing application assemblies.

- **Rule faults, B-015.** Production composition wraps every rule with `FaultIsolatedRule` (ADR-0005 (c); `0001-F1` B-012 to B-016). The runner returns the fault at error severity even under a warning override, so the command's existing report fold returns `ExitCodes.Violations`. Typed input failures pass through to the existing command catches, preserving exits 2 and 3; unexpected rule exceptions become error findings.
