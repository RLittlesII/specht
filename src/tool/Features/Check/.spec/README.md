# Specification: The check command

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The gate runs only as `hooked`'s Nuke target, so a pre-commit hook, a CI step and an agent mid-write each reach it differently or not at all, and a second repository has no step to add. This Feature removes that failure state: `specht` is one command, installed from a package through a local tool manifest, that reads a root, prints one MSBuild-shaped line per violation and the summary, and exits with a code the three call sites all understand (Must-1). It writes nothing under the root but the `--report` file `0001-F3` owns.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-11 (item 0174: what the package leaves out; every other bullet as its item left it) -->

Delivered so far by items 0026, 0027, 0028, 0133, 0171, 0172 and 0174. The slice layout is `dotnet-tool` § Vertical Slice.

- **The command.** `CheckCommand` is an `AsyncCommand` with its `Settings` nested (decision 0002): `--root <DIR>`, defaulting to `.`, and `--strict`. It resolves the root with `Path.GetFullPath`, calls the runner, writes each violation's `ToString()` - the engine's MSBuild-shaped line, in the engine's order, which `SpecViolation` ([`SpecViolation.cs`](../../../../specht/Model/SpecViolation.cs)) ends with ` [<identifier>]` when its `Identifier` is not null and at the message when it is (B-016, decision 0006) - and returns `ExitCodes.Violations` on an error, or on any violation under `--strict`, and `ExitCodes.Success` otherwise (B-001, B-003, B-004).
- **The run summary** (B-002). After the violation lines the command writes each of `SpecReportDocument.From(report).SummaryLines()` through the same raw writer: four lines, `specifications: epics 2, features 1`, `items: 0`, `rules evaluated: 41`, `errors: 1, warnings: 0`, the layouts in the document's order. The lines are formatted in the engine, on the document `0001-F3` B-005 already defines the counts on, beside `SpecViolation`'s line format, so the command stays parse, run, fold (C-4) and the summary and `--json` cannot count differently. A layout is named by its name in the manifest, the string the document's JSON carries (`0001-F6` B-009, item `0005`), so the summary and `--json` cannot name it differently; `epics` and `features` are the default manifest's names (`0001-F6` decision 0008). No summary line has the diagnostic shape, so a log parser reads none as a violation. An input failure returns before the summary, so stdout stays empty for B-005 to B-007.
- **The raw writer.** Lines go to the injected console's `Profile.Out.Writer`, not through `IAnsiConsole.WriteLine`: Spectre renders a line to the console's width, and a redirected console is 80 columns wide, so a rendered diagnostic wraps and GitHub no longer annotates it (C-3).
- **The runner is injected** as a `Func<string, SpechtReport>`, the resolved `SpechtRunner`'s `Run` outside a test. It is the seam the warning path needs: the engine emits no warning until `0001-F5`'s rule settings exist, so B-004 is reachable only through a substituted runner.
- **The composition root.** `Program.cs` calls `AddSpechtEngine()` on a `ServiceCollection` (`0001-F1` § 7, item `0107`; ADR-0001 stage D), registers the `Func<string, SpechtReport>` as the resolved `SpechtRunner`'s `Run`, hands the collection to Spectre through `TypeRegistrar`/`TypeResolver`, and sets `CheckCommand` as the default command (A-1). The command, the registrar and the resolver are unchanged; item `0144` moves the list into the factory (ADR-0007).
- **Paths** are the engine's: every violation's file is root-relative with `/` already (`0001-F1` B-007), and the summary carries counts and layout names only, so nothing absolute reaches stdout (B-013).
- **Input failures are engine exceptions the command folds.** `SpecManifest.Load` is the first read of a root, so it decides, through its `IFileSystem`: a root that is not a directory throws `SpechtRootNotFoundException`, no file at the manifest path throws `SpechtManifestNotFoundException`, and a `JsonException`, `InvalidOperationException` or `FormatException` from parsing or shaping the manifest is rethrown - a JSON `null` where the shape needs a value (the whole manifest, a `sections` element, a table or a grammar) throws `InvalidOperationException` from the private `Present` guard, so it takes the same path and the filter never widens to `NullReferenceException` - as `SpechtManifestUnreadableException`, its message naming `SpecManifest.RelativePath` and never the absolute path (B-005, B-006, B-007). Each is declared in `src/specht/` beside `SpechtManifestException`, which stays distinct and unmapped: a well-formed manifest the engine rejects is `0001-F5`'s (§ 5 row 4).
- **The mapping lives in the command, not in `SetExceptionHandler`.** `CheckCommand.ExecuteAsync` catches exactly those three types around the runner call and returns `ExitCodes.MissingInput` (`2`) or `ExitCodes.InvalidManifest` (`3`); no other exception is caught. A handler set in `Program.cs` would leave the command tester, which composes its own app, exiting `-1`, and C-2 forbids an exception crossing the command boundary.
- **Why the check is not in the command.** A pre-check of the root before the runner would fail every test whose substituted runner is handed a root with no manifest - the working directory, or `some/where`. The decision sits where the real runner reaches it.
- **The root as typed.** The engine holds only the resolved root, so `SpechtRootNotFoundException` carries no path and the command names `settings.Root` (B-005); the manifest messages come from the engine.
- **Stderr** is written with `Console.Error.WriteLine`, `dotnet-tool` § Conventions; it is not injected, because the command tester captures stdout alone and no test substitutes it. The message never reaches stdout (C-3, B-009).
- **Exit codes** hold `0` to `3`; 0040 adds `4`.
- **The package's id** (B-017, C-5) is `PackageId` in [`tool.csproj`](../../../tool.csproj), the one place it is declared. The release's push line in [`SpechtBuild.Publish.cs`](../../../../../.build/SpechtBuild.Publish.cs) spells the file name `specht.tool.<version>.nupkg` again, because the generated workflow carries a literal; `.github/workflows/publish.yml` is regenerated from it and never edited.
- **What the package says** (B-018, B-020 to B-024, B-028, B-029) is one property group in [`tool.csproj`](../../../tool.csproj), each value the claim's: `RepositoryUrl` and `RepositoryType`, `PackageProjectUrl`, `PackageLicenseExpression`, `Authors`, `Copyright`, `Description`, `PackageTags`, `PackageReleaseNotes`. The repository address is written out, not left to the build to read from the clone's `origin`, so a fork packs the same address. The copyright line is `LICENSE.md`'s. `Authors` holds the name with its comma and the manifest carries it unchanged (OQ-5). No version is written (C-5).
