# Specification: init

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

A repository adopting the model copies `hooked`'s `.spec/schema/` and `.spec/templates/` by hand, from whatever day it looked, and nothing records which day. This Feature removes that failure state: `specht init` writes the schema set and the templates from copies embedded in the tool, so every consumer starts from the same bytes as this repository, and the copy is a fact of the tool version rather than of a day. It never overwrites, so a repository that already has a file keeps it.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-11 (item 0183: the writer maps to `.specht/`, the retired location, and the live copy's folder, ADR-0011); 2026-10-10 -->

**The shipping copy (B-004, B-005, C-2).** `src/tool/schema/v<n>/` holds the four schema files (`spec-structure.schema.json` and the three frontmatter schemas) and `src/tool/templates/v<n>/` the four templates (`feature.md`, `decision.md`, `adr.md`, `lesson.md`); `item.yml` is not shipped. `tool.csproj` embeds them under the logical names `schema/v<n>/<file>` and `templates/v<n>/<file>`, `/`-separated on every OS. The newest version is the highest `<n>`. `v1` is a byte copy of the live `.specht/`.

**The writer (B-003, B-006, B-008, B-010, B-028; C-1, C-3, C-4).** `InitWriter` (`Features/Init/InitWriter.cs`) takes the shipping copy as a name-to-bytes map and an `IFileSystem`. `InitWriter.ShippingCopy(Assembly)` builds the map from the resources whose names match `^(schema|templates)/v<n>/<file>$`; other resources are ignored. `Write(root, cancellationToken)`:

- throws `SpechtRootNotFoundException`, the engine's, before touching anything when the root is not a directory, so `init` never creates the root itself (C-3);
- keeps the entries with the highest `<n>`, compared as integers so `v10` outranks `v2`, and maps each to `.specht/<folder>/<file>`, dropping the version (B-008): `<folder>` is the embedded name's, `schema` or `templates`, and `.specht` is the engine's `SpecManifest.ConfigurationFolder`, the one place the location is written (`0001-F5` § 7, "The location");
- for each, in ordinal order of that relative path: an existing file is listed skipped and not opened (C-1); an absent one has its folder created (with `.specht/` if absent, C-3) and is written with `FileMode.CreateNew`, so a file created between the check and the write fails the run rather than being overwritten, then listed written;
- writes the bytes as embedded, with no transformation (B-003).

No path the writer builds is under `<root>/.spec/`, so the retired location (A-5) is neither read nor written, whatever it holds (B-028); nothing was added for that claim.

It returns `(Path, Written)` pairs whose paths are already root-relative with `/`, so nothing absolute reaches stdout (C-4). The map, not the `Assembly`, is the constructor argument, so a unit test hands it two versions before a second one ships.

**The command.** `InitCommand` (`Features/Init/InitCommand.cs`) is an `AsyncCommand` with nested `Settings`: `--root <DIR>`, defaulting to `.` (B-009). It resolves the root with `Path.GetFullPath`, as `CheckCommand` does, calls the writer, and writes one line per file, `written <path>` or `skipped <path>`, through the console's raw `Profile.Out.Writer` so a line is never wrapped. It returns `ExitCodes.Success` after the listing, whatever was skipped (B-011); the writer's loop decides each file on its own, so a partial tree gets each absent file (B-010). A root that is not a directory is folded into `ExitCodes.MissingInput` with `specht: '<root as typed>' is not a directory.` on stderr, echoing `settings.Root` and not the resolved root (B-007, C-4); the writer has thrown before touching anything, so nothing is written (C-3). Stderr is written with `Console.Error`, as the check's is (`0001-F2` § 7), and is not injected: the command tester cannot capture it, so the echo as typed is asserted only by the scenario (§ 8). An injected error writer is the open seam, not built.

**Not built, as of 2026-10-10.** The command has no `--epics` and the writer reads no manifest, so every run's set is the eight files of the newest version, whatever a manifest beside them says. Leaving an existing file alone is built (C-1), and B-002's proof is `0054`'s, with the pin (B-012, B-013). An upstream schema source (B-014 to B-016) is `0095`. A rejected manifest (B-017) is `0096`. The `schemaVersion` the written manifest carries (`0001-F7` B-012) is `0049`. The epic choice - `--epics` into a bare root, the manifest's epic grammar beside an existing manifest (B-018 to B-023; C-5, C-6; OQ-2) - has no item.

**The composition root.** `Program.cs` registers `InitWriter` as a singleton built from `InitWriter.ShippingCopy(typeof(InitWriter).Assembly)` and `new FileSystem()`, and adds `init` with `AddCommand` beside the default `CheckCommand`, so `specht --root <dir>` still reaches the check. `TestableIO.System.IO.Abstractions.Wrappers` reaches the tool through its reference to the engine; no package is added.

The engine's default manifest (`src/specht/specht.csproj`, `specht.default-manifest.json`) stays a link to the live `.specht/schema/spec-structure.schema.json`, not a third copy (C-2). Drift between the shipping copy and the live copy is caught by the B-004 tests, not by a build step that generates one from the other (C-2).

## 8. Testing Strategy

<!-- last written by: test-writer, 2026-10-10, 2026-10-11 (item 0183, ADR-0011: the two folders the tests name, B-028, and what is red until the build), 2026-10-11 (item 0183 as built: the red record made history, B-004, B-008 and B-028 `Covered`, the counts) -->

- **The seams.** The `ShippingCopy` tests and B-004's steps read the shipping copy straight from the `specht.tool` assembly, `typeof(ExitCodes).Assembly`, through `GetManifestResourceNames` and `GetManifestResourceStream`; the newest version is the highest `<n>` among the `schema/v<n>/` names. `InitWriter` (§ 7) takes the shipping copy as a name-to-bytes map and an `IFileSystem`, so its unit tests hand it any set of versions over a `MockFileSystem` with the repository-relative root `repo`; `InitCommand` takes the writer injected, so a command test runs it through `CommandAppTester`. The live copy is this repository's schema set and its four shipped templates, under `.specht/schema/` and `.specht/templates/`, which each test project copies into its output under the same two folders; `item.yml` stays under `.spec/templates/` and is not copied.
- **Unit** (`test/tests/Init/ShippingCopy.Unit.Tests.cs`):
  - A-1 - mechanism: the logical names `tool.csproj` gives the embedded files. `TheNewestEmbeddedVersion_WhenListed_ShouldHoldExactlyTheEightFiles` asserts that the newest version's `schema/v<n>/` and `templates/v<n>/` names are exactly the eight files.
  - B-005 - mechanism: the `$id` each embedded frontmatter schema carries, which `init` will write unchanged (B-003). `TheNewestEmbeddedFrontmatterSchema_WhenRead_ShouldCarryAnIdUnderThisRepositorysSchemaAddressForItsVersion` has one row per frontmatter schema and asserts `https://github.com/rlittlesii/specht/schema/v<n>/<file>`. The @B-005 scenario proves `init` writes it.
