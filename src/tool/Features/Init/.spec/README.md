# Specification: init

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-12 (upstream source adoption, decision 0003) -->

A repository adopting the model copies the consumer's `.spec/schema/` and `.spec/templates/` by hand, from whatever day it looked, and nothing records which day. This Feature removes that failure state: `specht init` writes the manifest, and on request the frontmatter schemas and the templates, from copies embedded in the tool or frontmatter schemas from a supplied upstream source pinned by label and hashes, so the consumer can reproduce the selected source without hand-writing a manifest. It never overwrites, so a repository that already has a file keeps it.

## 2. User Needs

<!-- last written by: spec-author, 2026-10-12 (need 8 and A-3, decision 0003) -->

| #   | Persona                                             | Need                                                                                                            | Pain Point Today                                                                      |

| 1   | The maintainer adopting the tool                    | One command that gives a bare repository the manifest, and the frontmatter schemas and the templates when asked | `cp -R` from a consumer repository, then edit the `$id` URLs by hand                  |
| 2   | The agent authoring a specification                 | The templates, beside the schema, as the generation contract (Should-5)                                         | Copies the template from another repository                                           |
| 3   | A repository with local edits                       | `init` leaves what exists alone and says so                                                                     | A copy overwrites                                                                     |
| 4   | `0001-F7`                                           | The embedded version set `init` writes from, and a written manifest to pin a version in                         | N/A (internal dependency)                                                             |
| 5   | A repository of standalone Features                 | `init` writes no epic tier unless asked for one                                                                 | N/A (epics became opt-in 2026-10-09)                                                  |
| 6   | The maintainer configuring a repository             | A manifest that shows every rule and the level it is at, so a level is changed where it is read                 | The manifest `init` writes names no rule; the ids are in brief § 4 and the rule pages |
| 7   | The maintainer who wants the check and nothing else | An `init` that writes the manifest alone unless asked for more                                                  | `init` writes seven or eight files, and the check reads one of them                   |
| 8   | The maintainer adopting an upstream schema set      | Record the source with init while retaining its manifest defaults                                               | The source can only be recorded in a hand-written manifest                            |

### Assumptions

| ID  | Assumption                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A-1 | What `init` can write is three parts: the manifest, `manifest.json`; the frontmatter schemas, `feature.schema.json`, `task.schema.json` and `epic.schema.json`; and the four templates, `feature.md`, `decision.md`, `adr.md` and `lesson.md`. A run's selection is the manifest, the frontmatter schemas when `--schemas` or `--all` is given, and the templates when `--templates` or `--all` is given. The epic frontmatter schema is in the selection only with the frontmatter schemas, and then only when the root has no manifest and `--epics` is given (B-018), or the root's manifest declares the epic grammar (B-010, B-023; OQ-2, resolved 2026-10-09). Amended 2026-10-11 (decision 0004; `0001-F5` decision 0011): was "the eight files", written by every run. |
| A-2 | The shipping copy is embedded per schema version from `src/tool/schema/` and `templates/`, one folder for each version, named `v<major.minor.patch>` (`0001-F7` B-086; amended 2026-10-09: `0001-F7` decision 0005 retired the integer `v<n>`; amended 2026-10-11, `0001-F7` decision 0009: the name was provisional on `0001-F7` OQ-22); the root `.specht/manifest.json`, `.specht/schema/frontmatter/` and `.specht/templates/` are the live copy (amended 2026-10-11, `0001-F5` decision 0011) this repository checks itself with. They are the same bytes for the frontmatter schemas and templates, and equal manifests on the tool-owned keys (B-004; decision 0001).                                                                                                   |
| A-3 | Into a bare root, `init` writes the newest version the tool ships, and takes no schema-version argument; the upstream version option is an independent label (`0001-F7` C-10); beside a manifest pinning an older shipped version it writes at that version (B-012), and beside an unshipped pin it refuses (B-013). OQ-1, resolved 2026-10-08.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| A-4 | A rule's default level is the level named for its own default severity, `error` or `warning` (`0001-F3` B-032; `0001-F5` decision 0008); no rule of a version the tool ships has `off` as its default.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| A-5 | The retired location is `<root>/.spec/schema/` and `<root>/.spec/templates/`, where the tool wrote and read these files before 2026-10-11 (ADR-0011). `init` reads nothing there: a root that holds a manifest only there has no manifest.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

## 4. Constraints

<!-- last written by: spec-author, 2026-10-11 (C-3 amended, `0001-F5` decision 0011; C-7 added, decision 0004) -->

| ID  | Constraint                                                                                                                                                                                                                                                                                 | Rules Out                                                                                                                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C-1 | `init` never overwrites a file.                                                                                                                                                                                                                                                            | A `--force`; a prompt; a backup-and-replace.                                                                                                                                                                                            |
| C-2 | The shipping copy is embedded per version under `src/tool`; the root `.specht/` is the live copy, and a test asserts the newest version equals it on the tool-owned files and manifest keys (B-004).                                                                                       | A third copy; a build step that generates one from the other and hides a drift.                                                                                                                                                         |
| C-3 | `init` writes no file but `<root>/.specht/manifest.json` and the files under `<root>/.specht/schema/frontmatter/` and `<root>/.specht/templates/`; it may create those folders, `<root>/.specht/schema/` and `<root>/.specht/` to hold them (amended 2026-10-11, `0001-F5` decision 0011). | Writing a tool manifest, a `nuget.config`, a hook or a workflow into the consumer.                                                                                                                                                      |
| C-4 | Every path `init` derives and prints is relative to the root with `/` separators; the `--root` argument alone is echoed as the user gave it.                                                                                                                                               | An absolute derived path on stdout or stderr; rewriting the user's `--root` before echoing it.                                                                                                                                          |
| C-5 | Into a bare root, only `--epics` decides whether `init` writes the epic tier.                                                                                                                                                                                                              | Inferring epics from an `epics/` folder or an epic file under the root; a prompt.                                                                                                                                                       |
| C-6 | Beside an existing manifest, only the manifest's epic grammar decides whether `init` writes the epic frontmatter schema.                                                                                                                                                                   | `--epics` overriding the manifest; inferring epics from an epic frontmatter schema, an `epics/` folder or an epic file under the root.                                                                                                  |
| C-7 | The manifest is in every run's selection; the frontmatter schemas and the templates are written only when the command line asks for them, with `--schemas`, `--templates` or `--all` (decision 0004).                                                                                      | Writing the frontmatter schemas or the templates by default; an option that leaves a part out; an option that selects one file; a prompt; inferring a part from what the root already holds; `--all` deciding the epic tier (C-5, C-6). |

## 7. Technical Design

<!-- last written by: implementer, 2026-10-28 -->

**The shipping copy (B-004, B-005, C-2).** `src/tool/manifest/v<major.minor.patch>/` holds the manifest, `manifest.json`; `src/tool/schema/v<major.minor.patch>/frontmatter/` the three frontmatter schemas (`feature.schema.json`, `task.schema.json`, `epic.schema.json`), each with an `$id` ending in `schema/v<major.minor.patch>/frontmatter/<file>` (B-005); and `src/tool/templates/v<major.minor.patch>/` the four templates (`feature.md`, `decision.md`, `adr.md`, `lesson.md`); `item.yml` is not shipped. `tool.csproj` embeds them under the logical names `manifest/v<major.minor.patch>/manifest.json`, `schema/v<major.minor.patch>/frontmatter/<file>` and `templates/v<major.minor.patch>/<file>`, `/`-separated on every OS (item `0185`, `0001-F5` decision 0011). The newest version is the highest by major, minor and patch, parsed with the engine's `SemanticVersion`. `v0.1.0` is a byte copy of the live `.specht/`.

**The writer (B-002, B-003, B-006, B-008, B-010, B-012, B-013, B-017, B-019, B-028 to B-033; C-1, C-3, C-4, C-7).** `InitWriter` (`Features/Init/InitWriter.cs`) takes the shipping copy as a name-to-bytes map, an `IFileSystem`, and an optional `UpstreamSchemaFetcher`; production supplies the fetcher. `InitWriter.ShippingCopy(Assembly)` builds the map from the resources named `manifest/v<major.minor.patch>/manifest.json` or `(schema|templates)/v<major.minor.patch>/<path>`, where `<path>` may hold folders; other resources are ignored. `Write(root, schemas, templates, cancellationToken)`:

- throws `SpechtRootNotFoundException`, the engine's, before touching anything when the root is not a directory, so `init` never creates the root itself (C-3);
- snapshots whether `.specht/manifest.json` existed before the run, then keeps the manifest, the schemas only when `schemas` is true and the templates only when `templates` is true (C-7); when no manifest existed, the schemas omit `frontmatter/epic.schema.json` (B-019), while the current existing-manifest path includes it for B-010's epic-declaring manifest;
- reads an existing manifest through `SpecManifestStore`, parses it and resolves its pin through `SpecManifestParser.PinnedVersion` before selecting or writing any part; an absent pin means `0.1.0`, and an unshipped pin refuses the entire run, even with no optional parts selected (B-012, B-013);
- keeps the selected entries at that pin, or the highest version when no manifest existed, parsed with `SemanticVersion.TryParse` and compared by major, minor and patch so `v0.10.0` outranks `v0.9.0`, and maps each under `.specht/`, dropping the version (B-008): the manifest to the engine's `SpecManifest.RelativePath`, `.specht/manifest.json`, and every other entry to `.specht/<folder>/<path>`, where `<folder>` is the embedded name's, `schema` or `templates`, `<path>` is what follows the version, such as `frontmatter/task.schema.json`, and `.specht` is the engine's `SpecManifest.ConfigurationFolder`, the one place the location is written (`0001-F5` § 7, "The location");
- for each, in ordinal order of that relative path: an existing file is listed skipped and not opened (C-1); an absent one has its folder created (with `.specht/` if absent, C-3) and is written with `FileMode.CreateNew`, so a file created between the check and the write fails the run rather than being overwritten, then listed written;
- writes the bytes as embedded when no upstream source is recorded, with no transformation (B-003).

No path the writer builds is under `<root>/.spec/`, so the retired location (A-5) is neither read nor written, whatever it holds (B-028); nothing was added for that claim.

It returns `(Path, Written)` pairs whose paths are already root-relative with `/`, so nothing absolute reaches stdout (C-4). The map, not the `Assembly`, is the constructor argument, so a unit test hands it two versions before a second one ships.

**The upstream preparation (B-014 to B-016, B-027, B-034).** For an existing manifest, the writer reuses the structure already parsed and pin-validated during selection. JSON and shape failures retain their manifest-failure wrapper. Pin resolution and rule-vocabulary validation are shared with the check; schemas are fetched only when selected. A new source is validated and recorded in memory regardless of selection; only selected schemas reach the fetch preparation. No source retains the embedded selection. With a source, its `Files` replace the selected embedded schema entries: the authoritative `UpstreamSchemaFile` records supply the file names, addresses and hashes, including the epic kind only when declared. Each output path is confined to `SpecManifest.FrontmatterSchemaFolder` before fetching or writing. Schemas present at preparation are skipped without a fetch and remain skipped if removed before the write loop; the writer never substitutes empty bytes for an unfetched file. Every absent schema is fetched and verified into memory before the write loop begins, so a refused fetch writes neither schemas nor selected templates. A source's version label changes no address. An upstream source without a configured fetcher fails explicitly; it never falls back to the embedded bytes.

[`UpstreamSchemaFetcher`](../../../../specht/Manifest/UpstreamSchemaFetcher.cs) takes an injected `HttpClient`, reads the response as bytes and compares `sha256:` plus its lowercase SHA-256 with the recorded hash. It returns those exact bytes or throws [`SpechtUpstreamSchemaException`](../../../../specht/Manifest/SpechtUpstreamSchemaException.cs) naming the source and the failure. URI user information is stripped before requests and diagnostics; transport exception details are not emitted. It owns no file system and is never called by the check. [ADR-0013](../../../../../.spec/adr/0013-upstream-schema-fetches-use-an-injected-http-client.md) records the adapter and offline `HttpMessageHandler` substitution.

**The command.** `InitCommand` (`Features/Init/InitCommand.cs`) is an `AsyncCommand` with nested `Settings`: `--root <DIR>`, defaulting to `.`, the Boolean flags `--schemas`, `--templates` and `--all`, the strings `--upstream <ADDRESS>` and `--upstream-version <LABEL>`, and repeated `--upstream-hash <KIND=HASH>` strings (B-009, B-029 to B-032). It passes `Schemas || All` and `Templates || All` to the writer, so `--all` selects exactly the same two parts as the two flags together (B-032), writes one line per selected file, `written <path>` or `skipped <path>`, through the console's raw `Profile.Out.Writer` so a line is never wrapped, and lists nothing outside the selection (B-033). It returns `ExitCodes.Success` after the listing, whatever was skipped (B-011); the writer's loop decides each selected file on its own, so a partial tree gets each absent selected file (B-010). A root that is not a directory is folded into `ExitCodes.MissingInput` with `specht: '<root as typed>' is not a directory.` on stderr, echoing `settings.Root` and not the resolved root (B-007, C-4); the writer has thrown before touching anything, so nothing is written (C-3). A fetch/hash failure is folded into `ExitCodes.InvalidManifest` (`3`) and its source-only message on stderr before any listing. Typed manifest parse and validation failures from loading a selected source use the same exit code. An optional injected `TextWriter` captures stderr in command tests; outside a test it defaults to `Console.Error`.

**Rejected manifests (B-017).** The existing `InitWriter.Write` path reuses
`SpecManifestParser.Parse` and `PinnedVersion` before selecting files or fetching
schemas, regardless of the requested parts. JSON and shape failures become
`SpechtManifestUnreadableException`; semantic validation, rule-vocabulary and
explicit embedded/upstream contradictions remain `SpechtManifestException`.
`InitCommand.ExecuteAsync` writes either failure's relative manifest path and
reason to stderr and returns `ExitCodes.InvalidManifest`, before any stdout
listing. This is the existing shared check validator and command fold; no new
validator or architecture is introduced. Malformed version values remain the
separate unresolved OQ-3.

**Not built, as of 2026-10-14.** The command has no `--epics`. The embedded-source writer uses the manifest's presence, not its epic grammar, for the existing-manifest branch; the no-epic existing-manifest cases B-023 and C-6 wait with `--epics` on `0001-F5` OQ-18. The `schemaVersion` the written manifest carries (`0001-F7` B-012) is `0049`.

**The composition root.** `Program.cs` calls the init slice's `AddInit` methods on `IServiceCollection` and `IConfigurator`. The service registration supplies a singleton `HttpClient` with credentials, default credentials, cookies and redirects disabled unless the caller supplies a client; command integration tests supply a synthetic transport. It registers `UpstreamSchemaFetcher` and `InitWriter` as singletons over the engine's registered `IFileSystem`, `SpecManifestParser` and `SpecManifestStore`, and the embedded shipping copy. The configuration registration adds `init` with the same help description beside the default `CheckCommand`, so `specht --root <dir>` still reaches the check. This shares the init slice with command tests; item `0144` still owns the complete host factory. No package is added.

The engine's default manifest (`src/specht/specht.csproj`, `specht.default-manifest.json`) stays a link to the live `.specht/manifest.json`, not a third copy (C-2). Drift between the shipping copy and the live copy is caught by the B-004 tests, not by a build step that generates one from the other (C-2).

### Recording a source during init

`InitWriter` builds a new manifest in memory from the newest shipping copy,
removes the explicit epic grammar for the default bare-root tier and adds
`spechtSchema`. A malformed hash pair or repeated kind is rejected without
printing its value. The existing manifest validator then requires the HTTPS
address, non-empty label and hashes for the declared schema kinds before any
fetch or write. An existing manifest plus any source option is refused first.
The verified bytes replace the embedded schemas only when schemas are selected;
the existing preparation and no-overwrite loop is reused. Without schemas,
the source record is written and no fetch occurs.

[`SpecManifestParser`](../../../../specht/Manifest/SpecManifestParser.cs) turns
text into a manifest without I/O. Its constructor takes the shipped version catalog. `InitWriter` reuses `Parse`
and `PinnedVersion` for an existing manifest before preparing output, so the
manifest's pin determines the embedded files and an unshipped pin is refused.
The check uses the same validator and resolver before loading schemas.
[`SpechtResources`](../../../../specht/Resources/SpechtResources.cs) reads the
embedded text at the resource boundary. `AddSpechtEngine` registers the
resources, catalog, parser and store; the init registration supplies the latter
two to the writer. Both are required dependencies; no static default parser or
legacy `SpecManifest.Load` remains (item `0165`).

Source validation stays in the writer so direct callers receive the same
validation and the command folds the typed failure to the owner's required
exit `3`. A duplicate `Settings.Validate` check would instead trigger Spectre's
validation exit before that fold. No source value is echoed in an option
validation diagnostic. No new network adapter or command is introduced;
ADR-0013's transport policy still applies. `--epics` remains unbuilt.

**Explicit rule defaults (B-004, B-024 to B-026; decision 0006).** The working `0.2.0` embedded manifest carries exactly its vocabulary's rule IDs, each at the rule's own default level. `InitWriter.Selected` selects that manifest and `Write` copies it without deriving levels from the live repository's overrides. New upstream-source recording preserves this map. The original `0.1.0` resources and digest stay unchanged. The `rules` key is consumer configuration and is excluded by name in both shipping-copy comparisons; all other embedded keys remain compared. The live manifest keeps its repository-specific levels. OQ-5 is resolved by that existing separation, not by adding defaults to the live file.

### Fetching the templates a source hashes (item `0292`)

**B-034, B-041 to B-044; decision 0005; `0001-F7` decision 0016, C-15.** After the schema preparation and before the write loop, `InitWriter.Write` prepares the templates when `templates` is selected and the manifest records a source. For each `UpstreamSchemaSource.Templates` entry whose `FileName` the existing manifest's `ConsumerTemplates` does not name, the path is `SpecManifestStore.TemplateFolder` plus that name: a present file is not requested (B-044) and the loop skips it as before (C-1); an absent one is fetched and its bytes replace the embedded entry in the selection (B-041). Schemas are fetched first, then templates, all before any write, so a refusal (B-042, B-043) throws `SpechtUpstreamSchemaException` before anything is written, and `InitCommand` folds it to stderr and exit `3` unchanged. A run without templates selected, or with no absent unnamed hashed template, makes no template request (B-034). The parser's `0001-F7` B-127 check already confines each name to a template the pin ships, so no path check is added here. A manifest built from `--upstream` options records no templates, so that path is unchanged.

`UpstreamSchemaFetcher.Fetch(UpstreamTemplateFile, CancellationToken)` is an overload beside the schema one; both delegate to one private address-and-hash core, so credential stripping, the transport exception filter and the two diagnostics, `upstream schema source '<address>' could not be reached.` and `does not match its recorded SHA-256.`, are shared and unchanged. An HTTP 401 or 404 surfaces through `GetByteArrayAsync` as `HttpRequestException` and so reads as unreachable.

A hashed template the manifest names in `consumerTemplates` keeps today's behaviour, the embedded copy and no request, pending OQ-10, which is open and the owner's; this item does not answer it.
