# Specification: Schema versioning

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-11 (decision 0007) -->

A repository's `.spec/schema/` is a copy of `hooked`'s from one day, and nothing says which day, so either every repository moves with `hooked` at once or the copies diverge silently, and a repository that lags cannot catch up on purpose; and a bare version number cannot tell a breaking schema change from a harmless one, so every change forces every consumer into a deliberate upgrade and the owner cannot try one on this repository alone. This Feature removes that failure state: the manifest pins one `major.minor.patch` `schemaVersion`, numbered by whether a tree's verdict can change; the tool embeds the versions it ships - every published one from `1.0.0` on - and checks with exactly the pinned one; a pin command moves the pin up or down, and `specht upgrade` brings the schema set and the templates to the pin and prints what changed. Lagging becomes deliberate, moving becomes one command each way, the number says whether a move can fail the build, and a document is only ever changed by the agent, from the report.

## 2. User Needs

<!-- last written by: spec-author, 2026-10-11 (need 9 and A-4 added, decision 0009) -->

| #   | Persona                                             | Need                                                                                                 | Pain Point Today                                                                                                                                          |
| --- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | The maintainer of a lagging repository              | Pin a version and stay there until ready; the newest tool still checks it                            | A fork from one day, with no version to name                                                                                                              |
| 2   | The maintainer moving a repository                  | One command that brings the schema set and templates to the pinned version and says what changed     | Hand-copy, then diff by eye                                                                                                                               |
| 3   | The agent migrating documents                       | After an upgrade, the check reports what each document is missing, with what the rule expected       | Nothing says what changed between versions                                                                                                                |
| 4   | A maintainer trying a schema edit locally           | Point the check at the on-disk schema files instead of the embedded ones, deliberately               | The on-disk copy is the only copy, so a hand edit is silently authoritative                                                                               |
| 5   | `0001-F4`                                           | The embedded version set and the newest version number to write                                      | N/A (internal dependency)                                                                                                                                 |
| 6   | `0001-F3`                                           | The version and the source to name in the report                                                     | N/A (internal dependency)                                                                                                                                 |
| 7   | The owner trying a schema change on this repository | A version number that says whether a change can fail a tree, and a pin that moves up or down         | An integer version cannot tell a breaking change from a non-breaking one, so every change forces every consumer into a deliberate upgrade (decision 0005) |
| 8   | A maintainer with a template of its own             | Keep that template across `upgrade`, and still get the pinned version's copy of every other template | `upgrade` rewrites every template with the pinned version's; the frontmatter schemas have an opt-out (B-029) and the templates have none (decision 0006)  |
| 9   | The owner changing a shipped file                   | Know which version is still open to change, and start the next one with one command                  | The folders are `v1` and state no version, nothing marks one published, and a new one is a hand copy (decision 0009)                                      |

## 7. Technical Design

<!-- last written by: implementer, 2026-10-12 -->

**A version number is three integers (item `0120`, decision 0005).** [`SemanticVersion`](../../specht/Versioning/SemanticVersion.cs) is a value of major, minor and patch. It compares by major, then minor, then patch, each as a number, so `0.10.0` follows `0.9.0`; two versions are equal when all three are; it writes itself as `major.minor.patch` in the invariant culture. `TryParse` accepts text that is exactly three parts separated by dots, each part a non-negative decimal integer, and nothing else. The engine declares the type itself. A versioning package would be a dependency outside the five `0001-F1` C-7 names, for one comparison and one parse; `System.Version` reads `0.1` and `0.1.0.0` as versions, which B-039 rejects.

**What `TryParse` does with input no claim names.** These are design choices, not claims (§ 8 lists them as untested), and each is the narrowest reading of "three numbers":

| Input                                                   | Read as       | Why                                                                                                                 |
| ------------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------- |
| A prerelease or build suffix, `0.2.0-beta.1`, `0.2.0+5` | not a version | The last part is not a number. No special handling and no message of its own; OQ-15 decides whether it becomes one. |
| A part with a leading zero, `0.01.0`                    | not a version | A part must be the text its number writes, so one version has one spelling and a pin written back is the pin read.  |
| A sign, `+0.1.0`, `0.-1.0`                              | not a version | A part is digits only.                                                                                              |
| Whitespace around the text or a part                    | not a version | Nothing is trimmed.                                                                                                 |
| A part too large for a 32-bit integer                   | not a version | The part does not parse.                                                                                            |
| An empty part, `0..1`, or digits outside ASCII          | not a version | The part does not parse.                                                                                            |

**A version is data (item `0042`).** [`SchemaVersion`](../../specht/Versioning/SchemaVersion.cs) is one shipped version: its `Number`, a `SemanticVersion` from item `0120`; the text of its three frontmatter schemas; and the rule ids its vocabulary holds. [`SchemaVersions`](../../specht/Versioning/SchemaVersions.cs) is a set of them, ascending by `Number`. `Select(version)` returns the member whose number equals `version` or throws [`SpechtManifestException`](../../specht/Manifest/SpechtManifestException.cs) with the manifest's repository-relative path, the pinned version and every shipped version, each as `major.minor.patch` (B-003) - the same exception a rejected manifest key throws, so `CheckCommand`'s existing catch already writes it to stderr, leaves stdout empty and exits `3`; no command changed. The set takes its versions by constructor, so a test builds `0.1.1` or `1.0.0` in memory from the embedded `0.1.0` rather than shipping a second schema file.

**A pin is exact (B-055).** `Select` compares for equality and nothing else: over `0.1.0`, `0.1.1` and `0.2.0`, a pin of `0.1.0` is `0.1.0`. No range, no "newest patch", no fallback is read anywhere; a pin policy is item `0124`'s, and it will be a second input to the selection, not a change to what equality means.

**The embedded set (B-004).** `SchemaVersions.Embedded` reads the engine's manifest resources named `schema/v<major.minor.patch>/frontmatter/<file>`, one version per distinct version segment, and fills each version's slots from `feature.schema.json`, `task.schema.json` and `epic.schema.json`. The resources come from the tool's shipping copy (`0001-F4` C-2, item `0051`): `src/specht/specht.csproj` includes `..\tool\schema\v*\frontmatter\*.schema.json` as `EmbeddedResource` under the logical name `schema/v<major.minor.patch>/frontmatter/<file>`, the scheme `src/tool/tool.csproj` already uses. Owner decision, 2026-10-09: the engine **links** those files. Moving them into the engine would move `0051`'s shipping copy out from under `init`; copying them would be a second copy to drift; having the tool inject them into the engine would put a seam with one caller in front of the check. The manifest under `src/tool/manifest/v0.1.0/` is not linked: the check reads only the on-disk manifest (C-4).

**The folder gives the version (item `0126`, decision 0009; B-086, B-087, C-6, C-16).** Every shipping tree uses `v<major.minor.patch>`, including the existing `manifest/` home, whose placement remains OQ-52. `SchemaVersions.ReadEmbedded` parses the segment after `schema/v` with `SemanticVersion.TryParse`; no folder-to-version mapping remains. The `$id` of each embedded and live frontmatter schema carries the same segment before `/frontmatter/<file>`. Rule pages carry `0.1.0` in their Schema version row and embed under `rules/v0.1.0/`. `InitWriter` uses the same value type to select the newest shipping folder by major, minor and patch (`0001-F4` § 7); it copies the bytes unchanged. This does not change `init`'s manifest pin (item `0049`) or redesign the vocabulary (§ 5 row 25).

**The rule vocabulary is written per version.** Version `0.1.0`'s twenty-one ids (brief § 4) are a hand-written list inside `SchemaVersions.Shipped`, in the arm matching that `SemanticVersion`; an embedded `schema/v<major.minor.patch>/` with no arm fails on first read rather than checking with an empty vocabulary. The rules that run are the hand-written list of `ISpecRule` registrations in `AddSpechtEngine()` (`0001-F1` § 7, item `0107`), which replaced the static list of item `0106`, itself the replacement for reflection over the assembly. Neither item moved the vocabulary: it stands beside the rules, in `SchemaVersions.Shipped`, not inside them, no rule says which version introduced it, and no item moves it. `0042` does not do `0105`-`0107`'s work.

**The pin (B-002, B-039).** [`SpecManifest`](../../specht/Manifest/SpecManifest.cs) knows the key `schemaVersion`. No key reads as `0.1.0`, the version that predates it (A-1). A JSON string `SemanticVersion.TryParse` accepts loads, even one the tool does not ship: rejecting an unshipped pin is the version set's job, not the loader's. Anything else - the JSON number `1` the retired pin was, the strings `"1"`, `"0.1"` and `"v0.1.0"`, a boolean, `null`, an array - is a `SpechtManifestException` naming the manifest's repository-relative path and the value as the manifest's JSON writes it, a string in its quotes, so `1` and `"1"` read differently in the message. The pin travels on [`SpecStructure`](../../specht/Manifest/SpecStructure.cs)`.SchemaVersion`.

**Loading with the pinned version (B-001, C-4).** [`SpecSchemas.Load(IFileSystem, string, SchemaVersions)`](../../specht/Model/SpecSchemas.cs) reads the manifest from `<root>/.specht/manifest.json` first, selects the pinned version, and builds the three frontmatter schemas from that version's text, each load with its own `SchemaRegistry` as before. A hand edit to a schema under `<root>/.specht/schema/frontmatter/` no longer reaches the check. The two-argument `SpecSchemas.Load(IFileSystem, string)` still reads all four files from disk; nothing in the check calls it, and tests build schemas through it from a mock file system. It is the on-disk source item `0043` selects (B-009), not a second path the check takes. From item `0105` (built 2026-10-09) both loads keep the version they validate with on `SpecSchemas.Version`: the selected version here, and for the on-disk load the pinned embedded version carrying the texts read from disk, so its vocabulary is the pinned embedded version's (B-014, B-028). The member and the reasons are in `0001-F1` § 7. [`SpecModel.Load(string, SchemaVersions)`](../../specht/Model/SpecModel.cs) passes the set through; `SpecModel.Load(string)` uses `SchemaVersions.Embedded`.

**The vocabulary decides the run (B-014).** Item `0042` built the filter in [`SpechtRunner.Run(string, SchemaVersions)`](../../specht/SpechtRunner.cs), which selects the pinned version a second time from the loaded structure. From item `0105` ([ADR-0008](../../../.spec/adr/0008-evaluate-takes-the-rule-set-and-the-model-carries-the-vocabulary.md); built 2026-10-09) the filter's home is `SpechtRunner.Evaluate(SpecModel, IEnumerable<ISpecRule>)`, and `Run` holds none. `Evaluate` reads the vocabulary from `model.Schemas.Version.RuleIds`, evaluates each rule it is given that reports at least one id in it, drops any violation whose rule id is outside it, and counts as evaluated only the vocabulary's ids among the evaluated rules' `ReportedIds`. The rule is the same and so is every verdict; it now holds for any caller of `Evaluate`, not only for `Run`. `Run(string, SchemaVersions)` loads the model and passes the discovered rules; `Run(string)` is `Run(string, SchemaVersions.Embedded)`, so the host's `Func<string, SpechtReport>` registration in `Program.cs` is unchanged. The signatures are in `0001-F1` § 7.

**The report names the version.** [`SpechtReport`](../../specht/SpechtReport.cs) carries `SchemaVersion`, a `SemanticVersion`, as its first positional member, and [`SpecReportDocument.From`](../../specht/Report/SpecReportDocument.cs) writes its `major.minor.patch` text with the source carried by the report (`0001-F3` B-005, § 7 there). Item `0092` adds `SchemaSource`: `embedded` without a recorded source and `upstream` with one. Explicit source selection remains item `0043`'s.

**Version `0.1.0`'s epic schema (B-022, B-023).** Already in the shipping copy (decision 0003, item `0051`): optional `title` and `description` with `minLength: 1`. `0042` only makes the check read it from the embedded set, so an empty value is a `SPEC004` through the existing frontmatter rule.

**The upstream schema source is a record on the structure (item `0176`, decision 0008; built 2026-10-11).** [`SpecManifest`](../../specht/Manifest/SpecManifest.cs) adds `spechtSchema` to the keys it knows and reads it beside the pin, onto [`SpecStructure`](../../specht/Manifest/SpecStructure.cs)`.SpechtSchema`, which is null when the manifest has no such key. Two records join `src/specht/Manifest/`. [`UpstreamSchemaSource`](../../specht/Manifest/UpstreamSchemaSource.cs) holds `Location` and `Version` as the manifest wrote them, and `Files`. [`UpstreamSchemaFile`](../../specht/Manifest/UpstreamSchemaFile.cs) is one fetched kind: its `Kind`, the `frontmatterSchemas` key; its `FileName`, that key's value after the default fill (`0001-F5` B-008, B-019); its `Address`; and its `Hash`. `Files` holds exactly the fetched kinds, in the order `feature`, `task`, `epic`, so "which kinds are fetched" and "each kind's address" are values on the model and nothing computes them a second time. Both records are data: neither loads or parses itself, and the property is named for its key as the structure's other members are. Items `0092`, `0093` and `0095` read them from `SpecStructure`; this item adds no reader, no store, no registration and no network type (OQ-39 is theirs).

**Where the read sits.** In `SpecManifest`'s existing parse, as private members beside `SchemaVersion` and `IdentityFaults`, the way items `0014` and `0120` added their keys. That adds to a static class [ADR-0010](../../../.spec/adr/0010-layered-engine-boundaries-with-io-at-the-edge-and-a-mediator.md) removes in its stage 5; it adds no static class, no non-private static member and no file access, and it moves to `SpecManifestParser` with the rest of the parse. A parser of its own for one key would be a second manifest parse beside the one stage 5 moves.

**Every rejection is code (B-069 to B-073).** The manifest file is data, not a JSON Schema, and nothing validates it against one, so there is no schema for a rejection to sit in. The faults join the list `Check` already collects, so a manifest with several is rejected once, each named, as one `SpechtManifestException` carrying the manifest's repository-relative path; `CheckCommand`'s catch is unchanged (`0001-F5` B-022, B-023).

| Given                                                                                           | Fault, after the manifest's path                                                                                      | Claim        |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------ |
| no `location`, `version` or `hashes` member                                                     | `spechtSchema has no 'location'`, one fault for each absent member                                                    | B-069        |
| a `location` that is not a string, or not an absolute address whose scheme is `https`           | `the 'location' of spechtSchema is not an https address`                                                              | B-070        |
| a `version` that is not a string, or is the empty string                                        | `the 'version' of spechtSchema is not a non-empty string`                                                             | B-071        |
| `hashes` with no entry for a fetched kind                                                       | `the 'hashes' of spechtSchema holds no entry for the kind 'task'`                                                     | B-072, B-076 |
| a fetched kind's entry that is not a string of `sha256:` and 64 digits, each `0`-`9` or `a`-`f` | `the 'hashes' entry of spechtSchema for the kind 'task' is not 'sha256:' followed by 64 lowercase hexadecimal digits` | B-073        |

No fault repeats the value. A `location` that is a folder on the machine is an absolute path, and no output carries one (brief § 9); the member or the kind is what the claims ask to be named. An absent member raises only its own fault, not the ones that would read it. A `spechtSchema` that is not a JSON object, a `hashes` that is not one, and a JSON `null` in the key's place take the path every other key of the wrong JSON type takes: `SpechtManifestUnreadableException`, exit `3` (`0001-F2` B-007). No claim names them.

**The fetched kinds (B-075, B-076).** The Feature and item kinds always; the epic kind when the manifest's own text declares `identifiers.epic`. The read is of the manifest as written, before the fill, because the loader still fills the epic grammar from the default whatever the manifest declares (`0001-F5` B-019 as amended is unbuilt; `0001-F5` § 7), so the filled `SpecStructure.Identifiers` cannot say which manifest declared it. `Identifiers` is not changed: epics opt-in (`0001-F5` B-024 to B-035) has no item, and stopping the fill is that item's. When it lands, the fetched kinds read the same fact from `Identifiers` and this read goes. Every manifest that exists today declares the epic grammar, so each one that records a source owes three hashes.

**The address (B-074).** `Address` is `Location` and `FileName` joined with no character between them, the reading B-074's source column records: a `location` with no trailing `/` gives an address that runs the two together, and nothing here rejects or repairs it. It is text, not a `Uri`, so the join is the claim's and not a resolver's. Until item `0093` fetches, B-074's proof is this value on the model; its scenarios run `upgrade` and stay unbound.

**What is not read (OQ-46).** A `spechtSchema` member other than the three, and a `hashes` entry for a kind that is not fetched, are neither rejected nor carried. OQ-46 is open with rejection as its proposed default, and no claim is written; a rejection built on it would be behaviour no claim states.

**What does not change.** No schema file: `.specht/manifest.json`, which the engine embeds as the default manifest, and `src/tool/manifest/v0.1.0/manifest.json` gain no `spechtSchema`. The key is the consumer's and has no default, and a default would make every manifest that leaves it out record a source. So `0001-F4` B-004 holds as it is, `init` writes what it wrote, and the key is schema `0.1.0`'s (OQ-40) by the engine knowing it. Item `0176` added only the record; item `0092` now reads it as described below. A manifest with no `spechtSchema` keeps the embedded path, and `0001-F1` B-004's golden report is unchanged. `0001-F5` B-012 is unchanged in text and test: the keys it rejects are still unknown. `upgrade` is unbuilt; it adds only the keys the pinned version introduces that the manifest lacks, and every present key keeps its value (decision 0001). The pinned version's manifest holds no `spechtSchema`, so none is added and a recorded one survives. What `upgrade` does with a key the pinned version does not define is OQ-14, and it does not reach this key while `0.1.0`, which has it, is the only version shipped.

**Checking the upstream copy (item `0092`, B-024, B-025, B-028, B-032, B-077 to B-081).** [`SpecSchemasLoader`](../../specht/Model/SpecSchemasLoader.cs) reuses the existing embedded load to read and validate the manifest and select its pinned vocabulary before reading a local schema. With no `SpechtSchema`, it returns that embedded result. With a recording, it reads exactly `UpstreamSchemaSource.Files` through [`FrontmatterSchemaStore`](../../specht/Manifest/FrontmatterSchemaStore.cs), verifies the unchanged bytes through [`UpstreamSchemaCopy`](../../specht/Manifest/UpstreamSchemaCopy.cs), and builds the frontmatter schemas from the verified text. The pinned `SchemaVersion` retains its number and rule ids with only its schema texts replaced. An unfetched epic kind keeps the pinned epic schema; no local epic file is read.

The store reads one file under `.specht/schema/frontmatter/` through the injected `IFileSystem` and returns its bytes or null. It decides no policy. Per the owner's ruling recorded in item `0092`, it is a fifth I/O type until ADR-0010 stage 5 folds it into `SpecManifestStore`; this change does not amend the ADR. The pure verifier compares SHA-256 over the original bytes, before decoding UTF-8 and removing a UTF-8 byte order mark. It collects every absent or mismatched file into one `SpechtManifestException`, naming each path with `/` separators relative to the root. An absent file's fault names `specht init` (OQ-47); whether to name `--schemas` too remains OQ-57. `CheckCommand`'s existing catch prints the fault on stderr with empty stdout and exit `3`. Neither component fetches or writes.

`AddSpechtEngine()` registers both instances alongside the loader. [`SpecSchemaSource`](../../specht/Model/SpecSchemaSource.cs) lives in `Model/`, below the report, so the schemas can carry their source without an upward namespace dependency. `SpechtRunner.Evaluate` copies `SpecSchemas.Source` onto `SpechtReport.SchemaSource`, and `SpecReportDocument.From` copies it into the document. The upstream document says only `upstream`; naming the source address or version is `0001-F3` OQ-6, and B-011 remains item `0043`'s.
