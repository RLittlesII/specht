# SPCT0002: Reserved XML shape, placement or identity is incomplete

| Property         | Value                                                            |
| ---------------- | ---------------------------------------------------------------- |
| Message          | The offending XML role and attributes, or malformed element text |
| Default severity | Warning                                                          |
| Code fix         | Conditional target selection or default materialization          |

## Finding and reporting conditions

In a selected project with available inputs, a reserved `<spec>`, `<verifies>`,
`<implements>`, or `<follows>` element has invalid shape, placement, or incomplete
identity. Reserved elements must be empty, non-nested XML documentation elements
with allowed attributes and no duplicate attributes. `<spec>` belongs on a
named type and needs `feature`; relationship elements need `feature` and `claim`,
or `adr` for `<follows>`. `<verifies>` is valid only on a recognized ordinary test
method; while recognition is provisional (no test-evidence artifact, or one that
does not match this build's project, target framework, configuration and current
sources and policy) it is valid on any ordinary method. A relationship also needs `epic` when the consumer declares an epic grammar.
The analyzer also reports malformed reserved markup it can find in documentation
text. For example, `<implements claim="B-001" />` lacks `feature`.

## Configuration and resolution

The consumer's identity grammar and selected records determine which identity
is complete. Explicit XML is validated even outside mandatory authoring scopes,
including generated code. Suppression does not make an invalid binding evidence.
Fix the element or remove it. When the existing XML can be safely replaced and
eligible targets exist, the code-fix provider offers target selection; a
claim-only relationship may instead materialize an eligible type default. It
does not offer a fix for malformed or unsafe XML.

On a clean checkout no artifact exists, so the first build is provisional: it
accepts `<verifies>` on an ordinary method and does not require `verifies` on test
methods (SPCT0007), and every other check still applies. Run `dotnet test
--list-tests`, then `dotnet test`, to write the artifact under
`obj/specht-test-evidence/`, and supply it as a `SpechtTestEvidence` item to make
the next build authoritative. An artifact from another configuration, such as
Debug beside a Release build, or one made before a source or policy edit, is
never read as current evidence. See the [package guide](../README.md)
for input configuration.
