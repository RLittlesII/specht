# Specification: Reading through MCP

## 1. Business Goal

<!-- last written by: spec-author, 2026-11-06 (a minted id) -->

An agent that asks about a repository through MCP has no `specht` answer to receive: it runs the command and scrapes the output, follows a copied skill that has drifted from the pinned schema version, or answers from memory, and a guessed rule surfaces at the build or in review. This Feature removes that failure state: through `0132-F3`'s host an agent asks for the check's verdict on the whole tree, what a rule requires, what the pinned schema version demands and what the tree holds, or for a new id of a type the manifest opts in (`0001-F19`), and each answer is the command line's own answer on the same tree and pin, so MCP and the command can never disagree and nothing is written.

## 7. Technical Design

<!-- last written by: implementer, 2026-11-04 (item 0330), 2026-11-05 (item 0331), 2026-11-05 (B-022), 2026-11-05 (round 7: strict, the minimum), 2026-11-07 (the minimum cites `0132-F3` OQ-9) -->

**The slice.** One folder, `src/mcp/Features/Reading/`, beside `Host` and `PinnedTool` (`0132-F3` § 7). Each tool is a class of its own with a `Declare` that hands the SDK the tool and one method a call runs: [`CheckTool`](../CheckTool.cs) (`check`, OQ-7, B-019), [`ExplainTool`](../ExplainTool.cs), [`RulesTool`](../RulesTool.cs) and [`ManifestTool`](../ManifestTool.cs). Each asks `SpechtTool` for its command in the session's root through [`ReadingRelay`](../ReadingRelay.cs), the one place that turns what a command wrote into an answer, and keeps nothing between calls (B-014, B-015, C-4).

**The relay.** `ReadingRelay.RunAsync` answers with the command's standard output as the one text block, whether the exit code is `0` or `1` (B-001, B-011), provided it wrote something: exit `0` or `1` with nothing on standard output is not an answer (`dotnet tool run` ends `1` when a pinned tool that passed its version check is no longer restored) and is an error that quotes nothing and names `docs/mcp.md#restore-the-tool` (B-020, B-021). The unpinned report the global tool adds is a second block, apart (`0132-F3` B-024; A-4). Any other exit code, `2`, `3` or `4`, and any refusal of `SpechtTool` is an error result (`isError`) whose text is the tool's standard error or the refusal's message (B-012).

**The commands.** The root is the working directory of every program, so the lookup that finds the pin and the command that reads the tree see the same root (`0132-F3` B-009). `check` runs `--json`, then `--schema-source <schemaSource>` when the optional string is given, then `--strict` when the optional boolean `strict` is true. `explain` runs `--explain <rule>` for its required string. `rules` runs `rules --json` and takes no argument. `manifest` runs `manifest --json`, and `manifest --defaults --json` when its optional boolean `defaults` is true. The argument names `rule`, `defaults`, `schemaSource` and `strict` are the test-writer's reading of B-010 and are passed verbatim; none names a specification or a path (B-002, C-5). `--root`, `--report` and every command that writes are not offered; `--strict` is, as `check`'s `strict`, because it changes only which violations fail the exit code and writes nothing (B-017). An argument is optional where its method parameter has a default (`schemaSource`, `strict`, `defaults`); that is what the SDK reads into the input schema's `required`.

**The minimum.** The host runs a `specht` no older than `SpechtTool.Minimum`, `0.3.1` (`0132-F3` § 7 and `0132-F3` OQ-9, flagged for the owner): `explain` ships in `0.2.4`, and `rules --json` and `manifest --json` in `0.3.1`, so a tool older than that has no command for these tools to run.

**A value that starts with a dash.** The tools pass `rule` and `schemaSource` to the command as a separate argument, so a value such as `--report` would be read by the command as an option, and `--report` writes a file (C-3). `ReadingRelay.RefuseOption` answers such a call with an error and runs no command; B-022 states it. The error names the argument and says no command was run, and never carries the value or a path (OQ-8's default).

`ReadingRegistration.AddReading` registers each tool and the `McpServerTool` it declares; `HostFactory` lists the slice (`0132-F3` § 7, OQ-10). A later tool adds its registration the same way.

No other type is declared here: the answers are the pinned tool's, and the compiler holds the declarations.

## 8. Testing Strategy

<!-- last written by: test-writer, 2026-11-04 (item 0330; the verdict through `check`), 2026-11-04 (unit tier written against the built seams), 2026-11-04 (review follow-ups: a verdict that is empty; B-019 Partial), 2026-11-04 (B-020 and B-021 bound), 2026-11-05 (item 0331; the tools `explain`, `rules` and `manifest`, B-010 arguments, B-012 and B-014 bound), test-writer, 2026-11-05 (B-022 bound), test-writer, 2026-11-05 (review round 7: `check` offers `strict`; the minimum is 0.3.1; the registered tools come from `HostFactory.Compose`; B-014 worded for its three tools; the `strict` example bound) -->

Scope: the claims of item `0330` (B-001, B-002, B-011, B-013, B-015, B-016, B-017, B-019, B-020, B-021) and, from 2026-11-05, of item `0331` (B-003, B-004, B-005, B-010, B-012, B-014, B-022). The other claims are later items'; their scenarios have no binding and their rows stay `Missing`. B-012's three examples and B-014's scenario are bound by `0331`: the step "the answer is marked as an error" no longer pends in any scenario (it pended outside `@B-020`), and "its text is the message the command writes on standard error" runs the same command line in the root and requires the answer to equal its standard error and the exit code the situation states (`2`, `3` or `4`).

The tests drive the built `specht-mcp` as a process over its standard input and output through `AcceptanceTool.McpSession`, as `0132-F3` § 8 describes, and read each answer before the next request or the close. The fake `specht` tools are `0132-F3`'s `AcceptanceTool.FakeTools` (§ 8 there); this item extends them. For `--json` a fake writes `FAKE-SPECHT-OUTPUT <label> json`, then the root's manifest, then every `**/.spec/README.md` under the root in ordinal path order; the root is `--root` when given, else the working directory. It exits `1` when a specification holds the line `FAKE-VIOLATION`, as the check does on a violation. Any other command writes the marker and its label, as before. `AcceptanceTool.FakeTools.JsonOutput` computes the same text in C# from the tree, and `McpHostFakeToolsIntegrationTests` pins that the script and the C# agree, so an answer is compared with what the command wrote, byte for byte: the specifications carry a dash and an accented letter, and the text ends in a newline, so a host that trims, re-encodes or reformats is red. The specifications are fake text, not real Feature specifications: the engine is not run, because the host runs the pinned tool as a process and the claim is that the host relays that tool's stdout; a real-engine case would need a restorable package of the engine in the local tool manifest and proves nothing the relay does not. Every test that calls `check` reads `tools/list` first and fails when the host offers none (`CallTool`), so none is green on the error a missing tool is.

The fake reads the root's files, so B-014 proves the host runs the command at the call and not that the engine honours the pin, which `0001-F7` holds.

What the design makes hard to test: the engine's verdict itself cannot be seen through a fake, so "byte-identical to the check's" is proven as byte-identical to the stand-in that stands where the pinned tool runs; the real check on a real tree is `0001-F3`'s and the host adds nothing to it. A tool-list answer needs no tool, so B-002, B-017 and B-019 run the host with no fake and fail only on the list.

Focused verification selects `net11.0`; the required gates keep their configured matrix. No benchmark is needed: no performance claim is made and no architecture migration is introduced.
