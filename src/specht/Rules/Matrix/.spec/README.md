# Specification: Matrix resolution

## 1. Business Goal

<!-- last written by: spec-author, 2026-11-01 (decision 0003) -->

A § 9 row says which scenario and which tests pin a claim and how far, and today the check reads none of that: a row may say `Covered` beside a test name no file holds, `Missing` beside tests that all exist, or `Waived` with no one named, and every one passes. The matrix is then a claim about the tree that nothing checks, and a reader trusts a status the tree does not bear out. This Feature removes that failure state: under schema `0.3.0` or later the check resolves each row's scenario against the companion scenarios and each named test against the test files the manifest declares, as text, and reports the row whose scenario, test names or status the tree does not bear out; from schema `0.2.0` a manifest may raise the report of a waiver no signed-off reviewer approved and of a retired claim still carried.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-17 (0227) -->

[`SpechtDocument`](../../../Model/SpechtDocument.cs) keeps the existing flattened cells and additionally retains inline-code contents per row/cell in [`SpechtSection`](../../../Model/SpechtSection.cs). Both come from the same Markdig pipe-table parse. Existing rule inputs and baseline verdicts remain unchanged; prose, escaped backticks and code outside the matrix do not become test names.

The existing [`SpechtDiscovery`](../../../Discovery/SpechtDiscovery.cs) store adds `ReadTestFiles`, reusing its glob and exclusion matcher rather than introducing a second file walker or an I/O dependency in a parser. It reads each matched file once, deduplicated across overlapping globs and ordered by root-relative path. No globs means no directory or file read. `SpechtTestFile` carries that relative path and text for reuse across specifications and consumers.

[`MatrixResolver.Resolve`](../MatrixResolver.cs) is pure: the caller supplies the parsed document, selected structure and the already-read files. It selects the matrix role's section, reads the first four columns by position and preserves row order/line. Only the third cell's inline-code contents are split on comma/semicolon, with whitespace trimmed and empty fragments omitted. It reports neither violations nor exemptions. Consumers reuse its returned row resolutions; no check/trace-specific reader is added.

For each test name, the final dotted segment is inserted into each literal declaration form, or matched alone as a whole word when no forms are declared. An open end of a form keeps a whole-word boundary; literal prefixes and suffixes are honored exactly. Every preceding segment must occur as a whole word in the same file. Declaration prefixes/suffixes are escaped literal text; no compiler, assembly or test process is used. The matching name's one-based line and root-relative file are retained; LF, CRLF and CR line endings are counted consistently. When several files match, the first ordinal path supplies the evidence; within that file, the earliest matching name supplies its line. Repeated names reuse the same resolution within a document, keeping their cell order. No `tests` key yields unconfigured names; configured settings with no matching file yield unresolved names.

The resolver is registered in the existing engine composition. Item 0227 now consumes its rows and extends it for already-parsed claim tags; title resolution and other row exemptions remain with their later rule slices. The resolver item introduced no shipped resource or rule id; the two rules below enter working 0.2.0 together without an architecture migration.

### Waivers and retired claims (0227)

<!-- last written by: implementer, 2026-10-17 -->

`WaiverRule` and `RetiredClaimRule` are single-id rules in this slice, registered in the existing engine composition with their own level off. The runner's existing vocabulary selection excludes both under 0.1.0 and excludes/counts neither at 0.2.0 unless raised. No dispatcher or architecture migration is introduced (ADR-0014).

`WaiverRule` consumes `MatrixResolver.Resolve` rows. It checks only the configured waived marker. The visible Test cell must hold an approver and an invariant, real calendar date in YYYY-MM-DD form, separated by a comma. The approver must equal a reviewer in the configured sign-off section whose second column is neither the draft nor blocked marker. Header names may change; status and reviewer remain the second and third positions of `tables.signOff`. Missing or short document rows supply empty cells rather than a parser rejection. No current date or network is read.

`MatrixResolver.ResolveClaims` extends the same pure resolver: each declared claim retains its source line, fourth-column status, matching already-parsed companion tags and matching resolved matrix rows. Tag matching respects the manifest's claim-tag case setting. `RetiredClaimRule` reports one violation per withdrawn/superseded claim when any matching tag remains or an existing matrix row has a different status. Diagnostics use the specification's root-relative path, the matrix row line for a waiver and the declaration line for a retired claim. The expected payloads remain the separate Report work items' scope.

Both ids, rule pages and default off entries enter working 0.2.0 together, followed by its approved relock. Every 0.1.0 resource remains unchanged. The live manifest declares tests and section owners as decision 0002 requires; it does not enable the default-off rules. Other Matrix rules, title matching and Trace remain deferred.

### Unresolved test names (0334)

<!-- last written by: implementer, 2026-11-02 -->

The declared test files reach a rule through the model. [`SpechtModelLoader`](../../../Model/SpechtModelLoader.cs) calls `SpechtDiscovery.ReadTestFiles` once per check, with the selected manifest's `tests.files` and `exclusions`, and [`SpechtModel.TestFiles`](../../../Model/SpechtModel.cs) carries the result; with no `tests` key nothing is enumerated or read. The read is eager, like every other model input. `SPEC033` (item 0337) and the trace (`0001-F13`) take the same list, so a test file is read once whatever reads it (C-3). Rejected: each rule reading its own files, a second read per rule; a lazy read, which moves an I/O failure out of the load into a rule's fault isolation. The frontmatter-only check builds its model with no test files.

[`UnresolvedTestRule`](../UnresolvedTestRule.cs) is `SPEC032`, default level error. With no `tests` key it reports nothing, a cell without inline code included (B-007). Otherwise it takes `MatrixResolver.Resolve` rows over `model.TestFiles` and skips a row whose Status is the manifest's waived, withdrawn or superseded marker, or whose Test cell is its missing marker; a missing-marker Status does not exempt (B-002). Every marker is read from the manifest (C-5). A row with no inline-code name is one finding, "§ 9 Test cell names no test in inline code" (B-006). Otherwise each distinct unresolved name is one finding naming it (B-002 to B-005). Each finding is at the row's line with the claim cell as identifier; the `expected` payload is `0001-F3`'s.

`SchemaVersions.Shipped` gives `0.3.0` the ids of `0.2.1` and `SPEC032`; `0.1.0`, `0.2.0` and `0.2.1` are unchanged (`0001-F7` C-1). The `0.3.0` shipped manifest sets `"SPEC032": "error"` beside the other ids, its page is `docs/rules/v0.3.0/SPEC032.md`, and `0.3.0` is relocked by decision 0014's procedure: its lock entry removed by hand, then `LockSchemaVersion`.

This is a rule, not one of ADR-0010's structural stages, so ADR-0027's no-regression guard does not apply. The whole-check benchmark's tree carries this repository's manifest, which declares `tests`, so from this item the measured check also reads the generated tree's test files and runs `SPEC032`: a change in what is measured, not a structural cost. To keep that tree clean (`0109-F1` B-015), it gains `test/GeneratedTests.cs`, which declares the `GeneratedTests.Input{claim}` names its rows give.
