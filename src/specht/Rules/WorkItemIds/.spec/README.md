# Specification: Work-item id allocation

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-10 (the pair on this repository's trunk is past: one of its items was renumbered) -->

A work-item id is a citation target: a dependency, a parent or a commit subject that says `0118` must name one item. Two branches cut from the same trunk each take the number after the one the sequence file holds and write the same number back, and git merges both without a conflict, because the two item files have different names and the sequence file holds the same text on both sides ([lesson 0005](../../../../../.spec/lessons/0005-an-id-is-not-reserved-until-it-merges.md)). The check says nothing: schema version `0.1.0` reads no work-item file and no sequence file. One such pair, both numbered `0118`, reached this repository's trunk, and only a reader found it; one of the two was renumbered `0134` on 2026-10-10. This Feature removes that failure state: from the major schema version that adds these rules (OQ-3), a repository that declares its work-item files is told, as an error, each id claimed by more than one file with every claimant named, and a sequence file that is missing, is not one id, or is behind the highest id present; a pair the repository has knowingly kept is recorded in its manifest and passes, and a further claimant of that id does not (whether that record stays is OQ-14).

## 2. User Needs

| #   | Persona                                              | Need                                                                   | Pain Point Today                                                                                                |
| --- | ---------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 1   | Whoever follows a bare work-item id                  | The id names exactly one item                                          | Two items can share an id, as two shared `0118` here until 2026-10-10, and a bare id then names both            |
| 2   | The agent merging two branches                       | Be told which id is claimed twice and by which files, from the report  | Two item files sharing an id merge cleanly; the clash is found by reading                                       |
| 3   | The agent taking the next id                         | A sequence file that is not behind the ids already present             | A sequence file left behind hands out an id that is already taken                                               |
| 4   | The owner of a repository that kept a doubled id     | Record that pair once and keep every other duplicate reported          | The only choices are renumbering a cited id or switching the whole rule off                                     |
| 5   | The maintainer of a repository with no such tracker  | A check that says nothing about files it was never told are work items | N/A (the rules do not exist)                                                                                    |
| 6   | The reviewer of a pull request that cuts a work item | Not carry the number space in their head                               | Review is the only thing that enforces it ([`0128`](../../../../../.issue/0128-detect-an-id-claimed-twice.yml)) |
