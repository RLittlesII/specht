# Specification: Work-item id allocation

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-09 -->

A work-item id is a citation target: a dependency, a parent or a commit subject that says `0118` must name one item. Two branches cut from the same trunk each take the number after the one the sequence file holds and write the same number back, and git merges both without a conflict, because the two item files have different names and the sequence file holds the same text on both sides ([lesson 0005](../../../../../.spec/lessons/0005-an-id-is-not-reserved-until-it-merges.md)). The check says nothing: schema version `0.1.0` reads no work-item file and no sequence file. One such pair, both numbered `0118`, is on this repository's trunk, and only a reader found it. This Feature removes that failure state: from the major schema version that adds these rules (OQ-3), a repository that declares its work-item files is told, as an error, each id claimed by more than one file with every claimant named, and a sequence file that is missing, is not one id, or is behind the highest id present; a pair the repository has knowingly kept is recorded in its manifest and passes, and a further claimant of that id does not.

## 2. User Needs

<!-- last written by: spec-author, 2026-10-09 -->

| #   | Persona                                              | Need                                                                   | Pain Point Today                                                                                                |
| --- | ---------------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 1   | Whoever follows a bare work-item id                  | The id names exactly one item                                          | Two items share `0118`, and a bare `0118` names both                                                            |
| 2   | The agent merging two branches                       | Be told which id is claimed twice and by which files, from the report  | Two item files sharing an id merge cleanly; the clash is found by reading                                       |
| 3   | The agent taking the next id                         | A sequence file that is not behind the ids already present             | A sequence file left behind hands out an id that is already taken                                               |
| 4   | The owner of a repository that kept a doubled id     | Record that pair once and keep every other duplicate reported          | The only choices are renumbering a cited id or switching the whole rule off                                     |
| 5   | The maintainer of a repository with no such tracker  | A check that says nothing about files it was never told are work items | N/A (the rules do not exist)                                                                                    |
| 6   | The reviewer of a pull request that cuts a work item | Not carry the number space in their head                               | Review is the only thing that enforces it ([`0128`](../../../../../.issue/0128-detect-an-id-claimed-twice.yml)) |

### Assumptions

| ID  | Assumption                                                                                                                                                                                                                    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | An error is printed, counted and fails the run; a manifest's rule settings lower a rule to a warning or disable it (`0001-F5` B-010, B-011).                                                                                  |
| A-2 | Work-item files are found by discovery from what the manifest declares, as every other file shape is (`0001-F6` C-5); the names and shapes of the keys that declare them are OQ-5, and this specification names no key.       |
| A-3 | An id is read through the manifest's work-item grammar, as `0001-F5` C-2 requires of every rule.                                                                                                                              |
| A-4 | The major schema version that adds these rules (OQ-3) has not been published, so its rule vocabulary can still take them; a version freezes at its first publish (`0001-F7` decision 0002).                                   |
| A-5 | A work-item id is a run of decimal digits, so its number is those digits read as a decimal integer; a grammar under which it is not is OQ-6.                                                                                  |
| A-6 | An epic's id is its epic file's frontmatter id, in a repository whose manifest declares the epic grammar (`0001-F5` C-10); whether epics share the work-item number space in every such repository is OQ-7.                   |
| A-7 | This repository declares its own work-item files and sequence file, and records its `0118` pair, in its own manifest in the change that delivers these rules. That is delivery of item `0128`, and no claim here is about it. |
