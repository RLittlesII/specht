# Specification: Discovery

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The engine walks every directory under the root and discards `bin`, `obj` and `node_modules` afterwards, and the two layouts, the exclusion list and the item, epic and companion file shapes are literals in its code. That is cheap in `hooked` and not in a repository with a front end, and a third layout means a fork. This Feature removes that failure state: discovery reads what to find and what to skip from the manifest, asks git inside a work tree so an ignored tree is never opened, and walks with pruning outside one, and both ways find the same files.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 (item 0005: decision 0008 as built - the layouts named `epics` and `features`, the three file-shape keys lists; what the code does for OQ-12 to OQ-14) -->

Design for item `0005` (B-001, B-002, B-003, B-009, B-012), as built. brief § 5 "Discovery cost" is the drafted direction for `0007` and `0008`, which are not designed here.

**The manifest keys** ([decision 0004](decisions/0004-the-discovery-inputs-are-five-top-level-manifest-keys.md), which resolved OQ-4 on 2026-10-09). The owner ratified the five names, their shapes, their defaults and the `{task}` placeholder as this section proposed them. [Decision 0008](decisions/0008-the-layouts-are-named-epics-and-features-and-the-file-shape-keys-are-lists.md) then renamed the two default layouts and made the three file-shape keys lists. Each default glob is the literal the engine hardcoded (A-2, `0001-F5` A-4, C-4).

```json
"layouts": [
  { "name": "epics", "glob": "epics/**/spec.md" },
  { "name": "features", "glob": "**/.spec/README.md" }
],
"exclusions": [".git", ".artifacts", ".skillfile", ".claude", "graphify-out", "bin", "obj", "node_modules", "/.spec"],
"taskFiles": ["{task}-*.md"],
"epicFiles": ["epics/**/epic.md"],
"companionFiles": ["*.feature"]
```

| Key              | Shape                                                 | Read as                                                                                                                                                    | Claim                         |
| ---------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| `layouts`        | An array of objects, each a `name` and a `glob`       | The specification layouts, in the order the summary and the report list them. `glob` is matched against a file's root-relative path                        | B-001                         |
| `exclusions`     | An array of strings                                   | An entry with no `/` is a directory name excluded at any depth; an entry beginning with `/` is a root-relative path excluded at that place (decision 0003) | B-002                         |
| `taskFiles`      | An array of strings, each a file-name glob; not empty | The file name of an item beside a specification, which matches any one entry. `{task}` stands for the `identifiers.task` grammar                           | B-003, B-012; `0001-F5` B-041 |
| `epicFiles`      | An array of strings, each a glob; not empty           | An epic file, whose root-relative path matches any one entry                                                                                               | B-003, B-012; `0001-F5` B-041 |
| `companionFiles` | An array of strings, each a file-name glob; not empty | A companion file beside a specification, whose name matches any one entry                                                                                  | B-003, B-012; `0001-F5` B-041 |

Why these shapes, as decisions 0004 and 0008 record them:

- **Five top-level keys, not one `discovery` object.** A top-level key gets `0001-F5` B-012's unknown-key rejection and B-019's whole-value fill from the loader as it stands; a nested object would need its own copy of both, or a misspelt member would silently read as the default.
- **`layouts` is an array.** Its order is the order of the summary and the report, and a list is one value, so a manifest that declares `layouts` replaces the default list whole (C-7), as `sections` is replaced. An object keyed by name, filled per name as `identifiers` is, could never drop a default layout. Each entry is an object because `0006` adds the path-identity declaration beside `name` and `glob` (B-004).
- **The default names are `epics` and `features`** (decision 0008), in place of `legacy` and `coLocated`, which the engine printed and decision 0004 kept. A name is public: it is the report's `layout` value and what the summary prints (B-009), so under the default manifest both now read `epics` and `features`. The sibling key `epicFiles` names `epic.md` files, not the `epics` layout.
- **The three file-shape keys are lists** (decision 0008). A file matching any entry counts (B-012), a declared list replaces the default list whole, as `exclusions` and `sections` are replaced, and an empty list is rejected (`0001-F5` B-041).
- **`taskFiles` says `task`**, the kind name `0001-F5` decision 0003 ratified for `frontmatterSchemas.task` and `identifiers.task` already carries; B-003's "item" is the same kind.
- **`{task}`, not a second grammar.** `0001-F5` C-2 gives each identifier one grammar in the manifest. B-003's shape `<epic>-<nn>-*.md` is the task id followed by `-*.md`, so the shape names the grammar and does not restate it: `0001-F5` B-006's three-digit sequence then needs one edit, not two. With the default grammar `^[0-9]{4}-[0-9]{2}$` the shape accepts exactly the names `SpecDiscovery.IsItemFileName` accepts today. A task grammar with no epic part, which `init` writes without `--epics` (`0001-F4` B-022; its form is `0001-F5` OQ-5), needs nothing more of this key: the shape follows whatever the grammar is.

**The glob dialect** (C-6, decision 0004). A glob is `/`-separated and compared ordinally, case-sensitively, against a root-relative path with `/` separators ([`SpecDiscovery.Relative`](../../SpecDiscovery.cs)). A segment that is exactly `**` matches zero or more directories; `*` matches any run of characters inside one segment; every other character is itself. A file-name glob (`taskFiles`, `companionFiles`) has no `/` and is matched against the file name alone. Git's `:(glob)` pathspec reads these tokens the same way, so `0008` can pass a glob to git as written (C-2, C-3). `?`, `[...]` and a leading `!` are not part of the dialect. Decision 0004 did not say what one of them does, so `0005` reads each as the literal character it is and rejects nothing (OQ-7, open). Two more readings are the code's and no claim's: a `**` that is the last segment matches no file, where git's matches every file below, and a `**` beside other characters in a segment is two `*`.

**Where the keys are read.** [`SpecManifest`](../../SpecManifest.cs) stays the one reader of the manifest (`0001-F5` § 7). Item `0005` adds to it, and only this:

- five entries in `KnownKeys`: `layouts`, `exclusions`, `taskFiles`, `epicFiles`, `companionFiles`;
- one private function, `Discovery`, that reads the five keys, each `manifest[key] ?? Defaults[key]`, into one value, and reads nothing else - not `identifiers.epic` (see "Epic files" below) - with `Layout` beside it, which reads one `layouts` entry. `exclusions`, `taskFiles`, `epicFiles` and `companionFiles` are each read by `Strings`, the function that already read `sections`;
- three faults in `Check`, one per file-shape key whose filled list has no entry (`0001-F5` B-041; the rejection is designed in [`0001-F5` § 7](../../Manifest/.spec/README.md));
- one `init` member on [`SpecStructure`](../../SpecStructure.cs), `Discovery`, set beside `FrontmatterSchemas`.

That value is a new record, `SpecDiscoveryInputs`, in its own file: `Layouts`, `Exclusions`, `TaskFiles`, `EpicFiles`, `CompanionFiles`, the last three each an `IReadOnlyList<string>` as `Exclusions` is. It is one record and not five members on `SpecStructure` because it is the one argument discovery takes, today and in both modes `0007` and `0008` add, and because no rule holds it (C-5). [`SpecLayout`](../../SpecLayout.cs) stops being an enum of two and becomes the record a `layouts` entry is read into, `Name` and `Glob`; a third layout is then a third value, with no code change (B-001). `SpecLocation.Layout` keeps its name and its type's name. `SpecStructure.Discovery` is an `init` member whose default holds no layout, no exclusion and no shape: it is what a `SpecStructure` built without the loader carries, and the loader always sets it.

**The same block in both manifest copies.** The five keys go into `.spec/schema/spec-structure.schema.json` and `src/specht.tool/schema/v1/spec-structure.schema.json`, byte for byte, as one block placed between `$comment` and `sections`, each array one element to a line as the rest of the file is written. They ship in the embedded `v1` manifest, so they are tool-owned and `init` writes them (`0001-F4` decision 0001, B-004); version 1 is still open to them (`0001-F7` decision 0002). Item `0015` adds its keys to the same three files in parallel: this item's JSON block sits at the top of the manifest, its `KnownKeys` entries directly after `schemaVersion`, and its `Discovery` initializer line above `FrontmatterSchemas`, so an item that appends after `frontmatterSchemas` touches no line this one does.

**How discovery consumes them.** [`SpecDiscovery`](../../SpecDiscovery.cs) stays a static class until ADR-0001's stage D (item `0107`), and its interface arrives with the second mode (stage E, `0007` and `0008`). Each member this item touches takes the `IFileSystem` and the `SpecDiscoveryInputs`: the first from [`SpecModel.Load`](../../SpecModel.cs), which already holds one, the second from `schemas.Structure.Discovery`.

| Member                                                            | Reads                     | Does                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FindSpecifications(fileSystem, root, inputs)`                    | `Layouts`, `Exclusions`   | For each layout in the manifest's order, every file whose root-relative path matches the layout's glob and is not excluded, ordinally by root-relative path, as a `SpecLocation` carrying that layout                                 |
| `FindChildItems(fileSystem, specifications, inputs, taskGrammar)` | `TaskFiles`               | Beside each specification, the path of every file whose name matches any one of the shapes, once, ordinally. `taskGrammar` is `identifiers.task`, which `SpecModel.Load` passes. Replaces `IsItemFileName`, which had no other caller |
| `FindEpics(fileSystem, root, inputs)`                             | `EpicFiles`, `Exclusions` | The path of every file whose root-relative path matches any one of the globs and is not excluded, once, ordinally by root-relative path. Moves the `epics` and `epic.md` enumeration out of `SpecModel.Load`                          |
| `FindCompanions(fileSystem, specification, inputs)`               | `CompanionFiles`          | Beside one specification, the path of every file whose name matches any one of the globs, once, ordinally. Moves the `*.feature` enumeration out of `SpecModel.Load`                                                                  |

The signatures are the ones `test-writer` declared (§ 8); none changed, with decision 0008 or before it. The members that took no `IFileSystem` - `FindSpecifications(root)`, `FindChildItems(specifications)` and `IsItemFileName` - are gone with their one caller, `SpecModel.Load`. `Relative(root, path)` is unchanged.

Five private functions sit beneath them. `Files` enumerates every file under the root once, with its root-relative path taken through the `IFileSystem`'s own `Path` over full paths, because a `MockFileSystem` returns rooted paths for a relative root. `Matching` takes a list of globs and keeps the files any one of them matches and the exclusions do not skip, ordinally; `FindSpecifications` hands it a layout's one glob, `FindEpics` the `EpicFiles` list. `Beside` takes a list of expressions and lists the files in one specification's folder whose names match any one. Both are one filter over the files, not one pass per entry, so a list's order and length never change the order of what is found, and a file is returned once however many entries match it (B-012). `Pattern` turns a glob into an expression. `IsExcluded` decides one path.

A path is excluded when one of its directory segments equals a bare-name entry, or when it lies under a `/` entry's path; a file's own name is never compared. `Pattern` is the one function that turns a glob into a regular expression: the layouts, `epicFiles`, `taskFiles` and `companionFiles` all pass through it, each `taskFiles` entry with `{task}` replaced by the task grammar less its `^` and `$`, as one group.

Two or three empty lists in one manifest are named in one rejection, in the order `taskFiles`, `epicFiles`, `companionFiles`, after the role, `tables` and marker faults ([`0001-F5` § 7](../../Manifest/.spec/README.md)). **Epic files and the opt-in epic tier.** [`0001-F5` decision 0004](../../Manifest/.spec/decisions/0004-epics-are-opt-in-by-the-manifests-epic-grammar.md) makes epics opt-in: a repository has an epic tier only when its manifest declares `identifiers.epic`, and that grammar alone is the signal (`0001-F5` C-10). § 5 #7 gives discovery no epic-less mode. For `0005` that means:

- **`epicFiles` is read, filled and applied the same way with or without the epic grammar.** The function that reads the five keys does not look at `identifiers`, and `FindEpics` has no branch on it. `epicFiles` is a file glob and not a grammar, so the epic grammar's exemption from the default fill (`0001-F5` B-019) does not reach it: a manifest with no epic grammar that omits `epicFiles` still reads `epics/**/epic.md`.
- **With no epic grammar, a matched epic file still enters `SpecModel.Epics`**, path and frontmatter, as today. What is reported about it is a rule's: `SPEC004` reports nothing (`0001-F5` B-034), in `FrontmatterSchemaRule`, built by the item that delivers `0001-F5` B-033 and B-034. `0005` adds no such check and removes none.
- **This does not contradict decision 0004's default.** Finding the file a glob names is not inferring a tier from it, which is what `0001-F5` C-10 rules out. The `@B-003` scenario runs under the default manifest, which declares the epic grammar, so its "the epic's frontmatter is checked" holds.

Three things follow that no claim states. They are listed for `spec-author` and not settled here:

1. **`init` without `--epics` writes a manifest that names epic files.** The five keys are tool-owned and ship in the embedded manifest (decision 0004), and `0001-F4` B-003 excepts only the epic grammar and the task grammar (`0001-F4` B-021, B-022). So that manifest declares no epic tier and still carries `"epicFiles": ["epics/**/epic.md"]` and the `epics` layout `epics/**/spec.md`. The check is unharmed. Whether `init` leaves either out is `0001-F4`'s to say.
2. **`SPEC001` on an epic file, with no epic grammar.** `FrontmatterSchemaRule` reports `SPEC001` from the same loop that reports `SPEC004`, for an epic file that opens with no frontmatter. `0001-F5` B-034 silences `SPEC004` and says nothing of `SPEC001`. Discovery still lists the file, so the case can occur.
3. **No value of `epicFiles` means "none".** The dialect has no such token and an empty list is rejected (`0001-F5` B-041), so a repository without epics cannot stop the check matching and reading epic files, except with a glob that matches nothing. Skipping the read when no epic grammar is declared would be the epic-less discovery mode § 5 #7 excludes.
