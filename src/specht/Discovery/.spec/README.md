# Specification: Discovery

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The engine walks every directory under the root and discards `bin`, `obj` and `node_modules` afterwards, and the two layouts, the exclusion list and the item, epic and companion file shapes are literals in its code. That is cheap in a consumer repository and not in a repository with a front end, and a third layout means a fork. This Feature removes that failure state: discovery reads what to find and what to skip from the manifest, asks git inside a work tree so an ignored tree is never opened, and walks with pruning outside one, and both ways find the same files.

## 7. Technical Design

### Manifest dependency after ADR-0010 D1

current replacement is `SpechtManifestStore` for file observations and text,

Design for item `0005` (B-001, B-002, B-003, B-009, B-012), item `0006` (B-004) and item `0007` (B-006), as built. brief § 5 "Discovery cost" is the drafted direction for `0007` and `0008`; `0007` is built as "Design for item `0007`" below says, and `0008` is built as "Design for item `0008`" below says.

**The manifest keys** ([decision 0004](decisions/0004-the-discovery-inputs-are-five-top-level-manifest-keys.md), which resolved OQ-4 on 2026-10-09). The owner ratified the five names, their shapes, their defaults and the `{task}` placeholder as this section proposed them. [Decision 0008](decisions/0008-the-layouts-are-named-epics-and-features-and-the-file-shape-keys-are-lists.md) then renamed the two default layouts and made the three file-shape keys lists. Each default glob is the literal the engine hardcoded (A-2, `0001-F5` A-4, C-4).

```json
"layouts": [
  { "name": "epics", "glob": "epics/**/spec.md", "identity": { "epic": 1, "feature": 2 } },
  { "name": "features", "glob": "**/.spec/README.md" }
],
"exclusions": [".git", ".artifacts", ".skillfile", ".claude", "graphify-out", "bin", "obj", "node_modules", "/.spec"],
"taskFiles": ["{task}-*.md"],
"epicFiles": ["epics/**/epic.md"],
"companionFiles": ["*.feature"]
```

| Key              | Shape                                                                   | Read as                                                                                                                                                                                                                         | Claim                         |
| ---------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| `layouts`        | An array of objects, each a `name`, a `glob` and an optional `identity` | The specification layouts, in the order the summary and the report list them. `glob` is matched against a file's root-relative path. `identity` names the path segments `SPEC011` checks (decision 0009; "Path identity" below) | B-001, B-004; `0001-F5` B-043 |
| `exclusions`     | An array of strings                                                     | An entry with no `/` is a directory name excluded at any depth; an entry beginning with `/` is a root-relative path excluded at that place (decision 0003)                                                                      | B-002                         |
| `taskFiles`      | An array of strings, each a file-name glob; not empty                   | The file name of an item beside a specification, which matches any one entry. `{task}` stands for the `identifiers.task` grammar                                                                                                | B-003, B-012; `0001-F5` B-041 |
| `epicFiles`      | An array of strings, each a glob; not empty                             | An epic file, whose root-relative path matches any one entry                                                                                                                                                                    | B-003, B-012; `0001-F5` B-041 |
| `companionFiles` | An array of strings, each a file-name glob; not empty                   | A companion file beside a specification, whose name matches any one entry                                                                                                                                                       | B-003, B-012; `0001-F5` B-041 |

Why these shapes, as decisions 0004 and 0008 record them:

- **Five top-level keys, not one `discovery` object.** A top-level key gets `0001-F5` B-012's unknown-key rejection and B-019's whole-value fill from the loader as it stands; a nested object would need its own copy of both, or a misspelt member would silently read as the default.
- **`layouts` is an array.** Its order is the order of the summary and the report, and a list is one value, so a manifest that declares `layouts` replaces the default list whole (C-7), as `sections` is replaced. An object keyed by name, filled per name as `identifiers` is, could never drop a default layout. Each entry is an object because the path-identity declaration sits beside `name` and `glob` (B-004, item `0006`).
- **The default names are `epics` and `features`** (decision 0008), in place of `legacy` and `coLocated`, which the engine printed and decision 0004 kept. A name is public: it is the report's `layout` value and what the summary prints (B-009), so under the default manifest both now read `epics` and `features`. The sibling key `epicFiles` names `epic.md` files, not the `epics` layout.
- **The three file-shape keys are lists** (decision 0008). A file matching any entry counts (B-012), a declared list replaces the default list whole, as `exclusions` and `sections` are replaced, and an empty list is rejected (`0001-F5` B-041).
- **`taskFiles` says `task`**, the kind name `0001-F5` decision 0003 ratified for `frontmatterSchemas.task` and `identifiers.task` already carries; B-003's "item" is the same kind.
- **`{task}`, not a second grammar.** `0001-F5` C-2 gives each identifier one grammar in the manifest. B-003's shape `<epic>-<nn>-*.md` is the task id followed by `-*.md`, so the shape names the grammar and does not restate it: `0001-F5` B-006's three-digit sequence then needs one edit, not two. With the default grammar `^[0-9]{4}-[0-9]{2}$` the shape accepts exactly the names `SpechtDiscovery.IsItemFileName` accepts today. A task grammar with no epic part, which `init` writes without `--epics` (`0001-F4` B-022; its form is `0001-F5` OQ-5), needs nothing more of this key: the shape follows whatever the grammar is.

**The glob dialect** (C-6, decision 0004). A glob is `/`-separated and compared ordinally, case-sensitively, against a root-relative path with `/` separators, which discovery computes through its file system; the model loader independently maps loaded paths at its boundary. A segment that is exactly `**` matches zero or more directories; `*` matches any run of characters inside one segment; every other character is itself. A file-name glob (`taskFiles`, `companionFiles`) has no `/` and is matched against the file name alone. Git's `:(glob)` pathspec reads `**` and `*` the same way but `?`, `[` and `\` as its own, so `0008` passes a glob to git with those three escaped and keeps `Pattern` as the filter in both modes ("Design for item `0008`"; C-2, C-3). `?`, `[...]` and a leading `!` are not part of the dialect. Decision 0004 did not say what one of them does, so `0005` reads each as the literal character it is and rejects nothing (OQ-7, open). Two more readings are the code's and no claim's: a `**` that is the last segment matches no file, where git's matches every file below, and a `**` beside other characters in a segment is two `*`.

**Where the keys are read.** [`SpecManifest`](https://github.com/RLittlesII/specht/blob/97277d3c85f59a4b0a3b3973ee31b492f9adb1ee/src/specht/Manifest/SpecManifest.cs) stays the one reader of the manifest (`0001-F5` § 7). Item `0005` adds to it, and only this:

- five entries in `KnownKeys`: `layouts`, `exclusions`, `taskFiles`, `epicFiles`, `companionFiles`;
- one private function, `Discovery`, that reads the five keys, each `manifest[key] ?? Defaults[key]`, into one value, and reads nothing else - not `identifiers.epic` (see "Epic files" below) - with `Layout` beside it, which reads one `layouts` entry. `exclusions`, `taskFiles`, `epicFiles` and `companionFiles` are each read by `Strings`, the function that already read `sections`;
- three faults in `Check`, one per file-shape key whose filled list has no entry (`0001-F5` B-041; the rejection is designed in [`0001-F5` § 7](../../Manifest/.spec/README.md));
- one `init` member on [`SpechtStructure`](../../Manifest/SpechtStructure.cs), `Discovery`, set beside `FrontmatterSchemas`.

That value is a new record, `SpechtDiscoveryInputs`, in its own file: `Layouts`, `Exclusions`, `TaskFiles`, `EpicFiles`, `CompanionFiles`, the last three each an `IReadOnlyList<string>` as `Exclusions` is. Five private functions sit beneath them. `Files` walks the tree from the root one directory at a time, entering no directory an exclusion skips (B-006, item `0007`), and returns every file it lists with its root-relative path taken through the `IFileSystem`'s own `Path` over full paths, because a `MockFileSystem` returns rooted paths for a relative root. `Matching` takes a list of globs and keeps the files any one of them matches, ordinally; `FindSpecifications` hands it a layout's one glob, `FindEpics` the `EpicFiles` list. `Beside` takes a root-relative directory and a list of expressions and lists the files in that folder whose names match any one: one specification's folder for `FindChildItems` and `FindCompanions`, and a record folder beside it for `FindRecords` (`0132-F2` item `0368`). Both are one filter over the files, not one pass per entry, so a list's order and length never change the order of what is found, and a file is returned once however many entries match it (B-012). `Pattern` turns a glob into an expression. `Skips` decides one directory.

A directory is skipped when its name equals a bare-name entry, or when its root-relative path is a `/` entry's path, so a file is excluded exactly when one of its ancestors is; a file's own name is never compared. `Pattern` is the one function that turns a glob into a regular expression: the layouts, `epicFiles`, `taskFiles` and `companionFiles` all pass through it, each `taskFiles` entry with `{task}` replaced by the task grammar less its `^` and `$`, as one named group, `task`, in [`SpechtTaskShapes`](../SpechtTaskShapes.cs) (`0001-F5` item `0016`), which also hands the model the text that group captured.

**Path identity (item `0006`, B-004, [decision 0009](decisions/0009-a-layout-declares-its-path-identity-as-segment-indexes.md)). Built.** Decision 0005's interim is ended: no rule names a layout, and `SPEC011` follows what the layout's entry declares.

- **The declaration.** A `layouts` entry may carry `identity`, an object of two optional members, `epic` and `feature`, each the zero-based index of a segment of a specification's root-relative path, split on `/`. The default manifest declares `{ "epic": 1, "feature": 2 }` on `epics` and nothing on `features`, in both manifest copies, byte for byte. Those are the two segments the engine read by literal.

- **How it reaches the rule.** As the name does, on the value discovery hands out: `layouts[].identity -> SpechtLayout.Identity -> SpechtLocation.Layout -> PathIdentityRule`. The rule does not read `SpechtStructure.Discovery` (C-5) and holds no layout name (`0001-F5` C-1).

The messages and the reported lines are the engine's. `SPEC012` is untouched, and the rule still takes no constructor argument. Item `0158` split `IdentityRule`, which reported both ids, into `PathIdentityRule` for `SPEC011` and `DuplicateIdentityRule` for `SPEC012`.
- **The rejection.** A malformed `identity` is `0001-F5` B-043: [`0001-F5` § 7](../../Manifest/.spec/README.md), "The malformed path identity".
- **The proof.** `0001-F1` B-004's golden report and `SpechtManifestBaselineIntegrationTests` are green and unchanged, on the manifest as shipped and with every key omitted.

### Design for item `0007` (B-006)

**Built** (item `0007`), in one production file, [`SpechtDiscovery.cs`](../SpechtDiscovery.cs). The private-function paragraph and the walk's bullet under "What stays for later items" above describe it.

**The walk.** `Files(root, exclusions)` replaces `Files(root)`. It lists one directory at a time through `fileSystem.Directory`: `EnumerateFiles(directory)` for the directory's own files and `EnumerateDirectories(directory)` for its subdirectories, top-level only, through the overloads that take no `EnumerationOptions`. Those use the compatible options, `AttributesToSkip = 0`, so hidden files and dot-directories are listed, as `SearchOption.AllDirectories` lists them today (dotnet/runtime, `EnumerationOptions.cs`). A subdirectory joins a pending stack only when no exclusion skips it. A skipped one is never listed, so no child of it is enumerated and no descendant is checked again (C-1). The root's subdirectories are always listed. Every root-relative path is computed as today, `GetRelativePath` over `GetFullPath` with `/` separators, so a `MockFileSystem`'s rooted paths still work. `Files` returns the same `(Path, Relative)` pairs as before; nothing relies on the order it walks in, because `Matching` still orders ordinally.

**The decision at a directory.** `Skips(p, exclusions)`: a directory whose root-relative path is `p`, with last segment `n`, is skipped when a bare entry equals `n` or a `/` entry equals `/` followed by `p`, compared ordinally. The root is asked as `p` empty and has no name to compare. `FindSpecifications`, `FindEpics` and `FindTestFiles` pass their exclusions to `Files` and not to `Matching`. `IsExcluded` is gone; `Matching` keeps its glob filter and its order. A file is never compared by name, as before.

**Why the verdicts are unchanged.** `IsExcluded`, before `0007`, dropped a file when a directory segment `d_j` of its path equalled a bare entry, or when `/d_1/…/d_n/` started with the entry followed by `/`. A root-relative path has no empty segment, so the prefixes of `/d_1/…/d_n/` that end in `/` are exactly `/d_1/…/d_j/` for `j` from `0` to `n`. For `j` of `1` or more, the entry followed by `/` equals one of them exactly when the entry equals `/d_1/…/d_j`. Both halves therefore ask of each ancestor `d_1/…/d_j` the question the walk asks there, and the walk drops a file exactly when it skips one of the file's ancestors. The edge cases follow:

| Entry                                                                                         | `IsExcluded`, before `0007`                                                          | The walk                                                                                       |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| A trailing `/`, as `/.spec/`; an empty segment, as `/a//b`; `//`                              | Matches nothing                                                                      | Skips nothing: `/` followed by `p` never ends in `/` or holds `//`                             |
| A bare entry equal to the root's own name                                                     | Matches nothing: the root's name is in no relative path                              | Skips nothing: the root is never compared                                                      |
| `/`, which the parser accepts (`0001-F5` B-021 rejects only an inner `/` with no leading one) | Dropped the files directly at the root and nothing below them: `//` starts with `//` | Keeps that: the root's subdirectories are listed and entered, and its own files are not listed |

The last row is `j` of `0`. No claim states it, and B-002's "a root-relative path excluded at that place" would read `/` as the root itself, which excludes everything; it is kept as built, and OQ-19 asks which reading B-002 states. `0001-F1` B-004's golden report and `SpechtManifestBaselineIntegrationTests`, green and unchanged, prove the verdicts unchanged under the default manifest, which declares no `/` entry, so neither runs the last row. That row, the root's skipped flag in `Files`, rests on the argument above alone: no test runs it, and it is left unpinned while OQ-19 is open.

**What differs that no report shows.** A skipped directory is never opened, so an unreadable one inside it no longer fails the run, where the enumeration before `0007`, with `IgnoreInaccessible = false`, threw. The walk throws on an unreadable directory it does enter, as before.

**A linked directory (B-011, item `0009`).** Not changed. On Unix today's enumeration follows a symbolic link to a directory: `FileSystemEntry.Initialize` gives a `DT_LNK` entry the `Directory` attribute when `FileStatus.IsDirectory` finds, through `stat`, that the target is a directory; `FileSystemEnumerator` recurses into any directory entry its options do not skip; and `CompatibleRecursive` skips no attribute (dotnet/runtime `main`, `FileSystemEntry.Unix.cs`, `FileStatus.Unix.cs`, `FileSystemEnumerator.Unix.cs` and `EnumerationOptions.cs`, read 2026-11-06 and not run). `EnumerateDirectories(directory)` lists the same link as a directory under `Compatible`, so the walk enters it as today and skips it by its own name as today. ### Design for item `0008` (B-005, B-006, B-010)

**Built** (item `0008`), as designed below, in [`SpechtDiscovery.cs`](../SpechtDiscovery.cs) and [`ChildProcess.cs`](../ChildProcess.cs); "Choices made while building" closes the section. No claim, constraint or scenario changes. Every behaviour below that no claim states is labelled as the code's, and the git facts were observed with git 2.50.1 in a scratch repository whose excluded and ignored directories were made unreadable: git warns "could not open directory" for each directory it opens.

**The mode.** `Files(root, exclusions)` becomes `Files(root, globs, exclusions)`: `FindSpecifications` passes every layout's glob, `FindEpics` `EpicFiles`, `FindTestFiles` its own globs. The walk ignores them, and `Matching` applies them as before. `Files` asks git, and walks as `0007` built it when any of four things holds:

1. **No `.git` at the root or above it.** The root's full path and each ancestor are probed through the `IFileSystem` for a `.git` directory or file; a linked worktree's `.git` is a file. None is "outside a git work tree" (B-006), and the nearest is the work tree's top. The reading is the implementer's: it is how git itself finds a work tree, and it makes no git call, which C-2 rules out for anything but the file list (`git rev-parse`). The probe tests existence and lists no directory, so `.git`'s exclusion holds (C-1); it reads above the root. A `MockFileSystem` holds no `.git`, so every existing unit test stays in walk mode.
2. **`git` cannot be started.** `IChildProcess.Run` returns `null` for the platform's `Win32Exception`, which is how a program absent from `PATH` surfaces. That is "`git` absent from `PATH`" (B-006). No `PATH` lookup is written; the operating system's is used.
3. **git exits other than `0`.** OQ-2, open; [decision 0010](decisions/0010-item-0008-proceeds-with-the-dialect-questions-open.md) lets `0008` proceed on this answer. As built, and pinned by no claim and no test: the walk runs, silently, and git's standard error is dropped. It is the one answer that adds no exit code and no output; an answer to OQ-2 changes this branch alone. Outside a work tree git exits `128`, which case 1 already routes to the walk.
4. **An exclusion is `/` alone, ends in `/`, or holds `//`**, OQ-19's (a) to (c). The walk reads them as `0007` keeps them; git, given `:(exclude,literal)` and nothing, lists no file, and given `/x/` or `/a//b` excludes `x` and `a/b`. Walking keeps one contract (C-3) without answering OQ-19. The mode is pinned: [`SpechtDiscoveryGitUnitTests`](../../../../test/tests/Discovery/SpechtDiscovery.Git.Unit.Tests.cs)'s `AnExclusionNoClaimStates_WhenSpecificationsAreDiscoveredInAWorkTree_ShouldNeverStartGit` walks each of the three and never starts git. What each excludes is not: OQ-19's verdicts stay unpinned, as its row in "Design for item `0007`" is.

That is once per finder, so a check makes at most three git calls, the number of walks it made: `FindSpecifications`, `FindEpics` (none when the tree is read without an epic tier) and `FindTestFiles` (none with no declared glob). `FindChildItems` and `FindCompanions` do not change. `Beside` lists one discovered specification's directory through the `IFileSystem` in both modes, so an item or companion git ignores is found by both (C-3), and it opens a directory git ignores only where a specification was force-added inside one (below).

**The command line** (decision 0002). Program `git`; working directory the root's full path; standard input closed; these arguments, in this order:

```
ls-files -z --cached --others --exclude-standard
  --exclude=<pattern> ...      one per exclusion
  --
  :(glob)<glob> ...            one per glob
  <exclude pathspec> ...       one per exclusion
```

`--cached` lists the tracked files, and `--others --exclude-standard` the untracked ones that no `.gitignore`, `.git/info/exclude` or `core.excludesFile` ignores (B-005). Every pattern is drawn from the manifest's globs and exclusions (C-2). The root is the working directory, not `-C`, so every argument is root-relative and a test can record them with no absolute path in them (brief § 9).

| Manifest entry            | Pathspec                                                                                                                              | `--exclude` pattern                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| A glob `g`                | `:(glob)` then `g`, each `\`, `?` and `[` preceded by `\`, its first character, unless `*` or `\`, a bracket expression (item `0009`) | None                                             |
| A bare name `n` (B-002)   | `:(exclude,glob)**/` then escaped `n` then `/**`                                                                                      | `/`, the escaped prefix, `**/`, escaped `n`, `/` |
| A root-relative path `/p` | `:(exclude,literal)` then `p`                                                                                                         | `/`, the escaped prefix, escaped `p`, `/`        |

To escape is to precede each `\`, `*`, `?` and `[` with `\`. The prefix is the root's path below the work tree's top with a trailing `/`, empty when the root is the top. Both forms of an exclusion are needed:

- **The exclude pathspec** filters what is listed, the index included, so a tracked file under `bin` is not listed (B-010). Corrected by item `0009`: it does so only when the glob pathspecs share no leading directory, as the probes' `**/...` globs did; beside globs that share one, such as `epics/**/epic.md`'s `epics/`, git 2.50.1 drops every tracked file or keeps a tracked file under an excluded directory, so `Arguments` now writes each glob's first character as a bracket expression ("The epic listing" under "Design for item `0009`"). It does not stop git opening a directory that holds a tracked file: with only the pathspecs, git opened `src/bin/` and `.spec/`, each holding one, and did not open `src/obj/`, which held none.
- **The `--exclude` pattern** is a command-line ignore pattern, which git applies while it scans for untracked files, so it opens no directory the pattern matches, tracked files inside or not (C-1). It does not filter `--cached`. A command-line pattern is anchored at the work tree's top, not the working directory, hence the prefix: with the root at `w`, `/a/b/` let git open `w/a/b/` and `/w/a/b/` did not. A bare name is anchored below the root because `n/` alone also matches an ancestor of the root and then drops every untracked file under it: with the root at `bin/x`, `--exclude=bin/` dropped `a/untracked.md`, which the walk, comparing nothing at or above the root, keeps.
- **A glob's escapes** keep `?`, `[` and `\` literal, as item `0005` built them (OQ-7 (d), open): `:(glob)t/q?/f.md` lists `t/qx/f.md` and `:(glob)t/q\?/f.md` does not. `*` and `**` pass as written, and git agrees with `Pattern` on them, a `**` inside a segment included (OQ-9, open: both read `**.md` as `*.md`), except a final `**` segment, which git reads as every file below (OQ-8, open). The `:(glob)` pathspec is a prefilter and `Pattern` the verdict ([decision 0010](decisions/0010-item-0008-proceeds-with-the-dialect-questions-open.md), which lets `0008` proceed with OQ-7 (d) and OQ-8 open). Its caveat holds here: if OQ-7 (d) makes `?` or `[...]` wildcards, their escapes in this pathspec go too, or git's list loses files `Pattern` keeps.

**The output.** NUL-separated (`-z`), so no path is quoted whatever `core.quotePath` says; read as UTF-8; each path relative to the working directory, with `/`. `Files` keeps an entry that does not begin `../`, is not already kept, and names a file - `IFileSystem.File.Exists` on the root joined to it - as a `(Path, Relative)` pair, `Path` being that join. `Matching` then filters by the same globs and orders ordinally (B-008), as it does the walk's list. `Pattern` thus stays the one reader of the dialect (C-6; decision 0010): a glob git reads more widely, such as a final `**`, gives the walk's set, and an answer to OQ-8 or OQ-9 changes `Pattern` for both modes at once. Each guard is a case the probe showed:

| git lists                                                        | Why it is dropped                               | The walk                                                        |
| ---------------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------- |
| A tracked file deleted from the working tree                     | `--cached` reads the index; no such file exists | Does not list it                                                |
| An unmerged path, once per stage                                 | Kept once                                       | Lists it once                                                   |
| A nested repository as `nested/`, or a submodule's path          | Not a file                                      | Enters `nested/` and lists its files: git mode does not (below) |
| `../x/f.md`, from a glob `../x/*.md` with the root below the top | Outside the root, and `Pattern` would match it  | Lists nothing outside the root                                  |

**What falls out, pinned by no claim and no test.**

- A specification force-added inside an ignored directory is listed by `--cached`, and `Beside` then lists that directory.
- A file git ignores in a directory it does not, such as `x.local.md` under a `*.local.md` rule, is found by the walk and not by git mode. C-3's precondition names git-ignored directories only, so C-3 and B-005 disagree on such a tree. Read, not run, in git's `v2.50.1` source: `ls-files` computes `common_prefix` of the pathspec, prunes the index to it and passes its length to `match_pathspec` (`builtin/ls-files.c`); `common_prefix_len` skips every exclude item (`dir.c`); `do_match_pathspec` advances the name by that length and `match_pathspec_item` advances every item it is given, exclude items included, by the same length (`item->match + prefix`, `item->len - prefix`). What the 0008 design held and missed: its probes of the exclude pathspec ("Design for item `0008`", "Both forms of an exclusion are needed") ran beside globs with no leading directory, the shape of the `features` layout, and the epic and test-file finders' shape was not run.

**The fix, the implementer's choice.** The owner was not asked; `spec-reviewer` held C-2 for the respelt glob, one pathspec per glob in manifest order matching the set the glob matches, as `Escaped` already does. `Arguments` passes each manifest glob through `Bracketed`: its first character becomes a one-character bracket expression and the rest is escaped as before, so `epics/**/epic.md` becomes `:(glob)[e]pics/**/epic.md`. git's prefix stops at the first glob-special character, `[` among them, so no glob pathspec has a literal head and the globs share no leading directory. The bracket spells no `\`, which Git for Windows reads as a directory separator (rejected option 1).

| The glob's first character        | The pathspec's head           | Matches                                                      |
| --------------------------------- | ----------------------------- | ------------------------------------------------------------ |
| None, the glob is empty           | Nothing                       | -                                                            |
| `*`                               | `*`, as `Escaped` leaves it   | The glob's own set; already no literal head                  |
| `\`                               | `\\`, as `Escaped` writes it  | The literal `\`; already no literal head (the finding below) |
| `!` or `^`                        | `[]!]` or `[]^]`              | `]` or that character: a superset                            |
| `]`                               | `[]]`                         | `]`                                                          |
| Any other, `?` and `[` among them | `[c]`, as `[e]`, `[?]`, `[[]` | That character                                               |

- **The superset.** A bracket cannot open with `!` or `^`, which negate it: `:(glob)[!]x/*.md` lists nothing beside a tracked `!x/a.md` (observed). A leading `]` is a literal member, so `[]!]` holds `!` and `]`. The `:(glob)` pathspec is a prefilter and `Pattern` the verdict ([decision 0010](decisions/0010-item-0008-proceeds-with-the-dialect-questions-open.md)), so a path git lists beginning with `]` is dropped by `Pattern`; nothing a glob matches is lost.
- **Which globs.** Every glob, in every finder, whatever the other globs and whether or not an exclusion is declared. A pathspec's spelling then depends on its own glob alone, and adding a glob or an exclusion never respells another; the command line stays a function of the manifest, in manifest order. `FindSpecifications`' `epics/**/spec.md` gains the bracket too, which changes nothing it lists, since `**/.spec/README.md` already gave it no leading directory. **Rejected.**

4. **`--recurse-submodules`**, under which `ls-files` computes no prefix: git refuses it beside `--others` (observed, `fatal: ls-files --recurse-submodules unsupported mode`, exit `128`).
