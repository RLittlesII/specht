# Specification: Discovery

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The engine walks every directory under the root and discards `bin`, `obj` and `node_modules` afterwards, and the two layouts, the exclusion list and the item, epic and companion file shapes are literals in its code. That is cheap in `hooked` and not in a repository with a front end, and a third layout means a fork. This Feature removes that failure state: discovery reads what to find and what to skip from the manifest, asks git inside a work tree so an ignored tree is never opened, and walks with pruning outside one, and both ways find the same files.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 (item 0005: design brought in line with decisions 0004 to 0006 and `0001-F5` decision 0004) -->

Design for item `0005` (B-001, B-002, B-003, B-009), written before its tests and code, and not yet built. brief § 5 "Discovery cost" is the drafted direction for `0007` and `0008`, which are not designed here.

**The manifest keys** ([decision 0004](decisions/0004-the-discovery-inputs-are-five-top-level-manifest-keys.md), which resolved OQ-4 on 2026-10-09). The owner ratified the five names, their shapes, their defaults and the `{task}` placeholder as this section proposed them. Each default is the literal the engine hardcodes today (A-2, `0001-F5` A-4, C-4).

```json
"layouts": [
  { "name": "legacy", "glob": "epics/**/spec.md" },
  { "name": "coLocated", "glob": "**/.spec/README.md" }
],
"exclusions": [".git", ".artifacts", ".skillfile", ".claude", "graphify-out", "bin", "obj", "node_modules", "/.spec"],
"taskFiles": "{task}-*.md",
"epicFiles": "epics/**/epic.md",
"companionFiles": "*.feature"
```

| Key              | Shape                                           | Read as                                                                                                                                                    | Claim |
| ---------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| `layouts`        | An array of objects, each a `name` and a `glob` | The specification layouts, in the order the summary and the report list them. `glob` is matched against a file's root-relative path                        | B-001 |
| `exclusions`     | An array of strings                             | An entry with no `/` is a directory name excluded at any depth; an entry beginning with `/` is a root-relative path excluded at that place (decision 0003) | B-002 |
| `taskFiles`      | A string, a file-name glob                      | The file name of an item beside a specification. `{task}` stands for the `identifiers.task` grammar                                                        | B-003 |
| `epicFiles`      | A string, a glob                                | An epic file, matched against its root-relative path                                                                                                       | B-003 |
| `companionFiles` | A string, a file-name glob                      | A companion file beside a specification                                                                                                                    | B-003 |

Why these shapes, as decision 0004 records them:

- **Five top-level keys, not one `discovery` object.** A top-level key gets `0001-F5` B-012's unknown-key rejection and B-019's whole-value fill from the loader as it stands; a nested object would need its own copy of both, or a misspelt member would silently read as the default.
- **`layouts` is an array.** Its order is the order of the summary and the report, and a list is one value, so a manifest that declares `layouts` replaces the default list whole (C-7), as `sections` is replaced. An object keyed by name, filled per name as `identifiers` is, could never drop the legacy layout. Each entry is an object because `0006` adds the path-identity declaration beside `name` and `glob` (B-004).
- **The default names are `legacy` and `coLocated`.** They are what the summary and the report document print today (`0001-F2` B-002, `0001-F3` B-005), so the default manifest changes no output.
- **`taskFiles` says `task`**, the kind name `0001-F5` decision 0003 ratified for `frontmatterSchemas.task` and `identifiers.task` already carries; B-003's "item" is the same kind.
- **`{task}`, not a second grammar.** `0001-F5` C-2 gives each identifier one grammar in the manifest. B-003's shape `<epic>-<nn>-*.md` is the task id followed by `-*.md`, so the shape names the grammar and does not restate it: `0001-F5` B-006's three-digit sequence then needs one edit, not two. With the default grammar `^[0-9]{4}-[0-9]{2}$` the shape accepts exactly the names `SpecDiscovery.IsItemFileName` accepts today. A task grammar with no epic part, which `init` writes without `--epics` (`0001-F4` B-022; its form is `0001-F5` OQ-5), needs nothing more of this key: the shape follows whatever the grammar is.

**The glob dialect** (C-6, decision 0004). A glob is `/`-separated and compared ordinally, case-sensitively, against a root-relative path with `/` separators ([`SpecDiscovery.Relative`](../../SpecDiscovery.cs)). A segment that is exactly `**` matches zero or more directories; `*` matches any run of characters inside one segment; every other character is itself. A file-name glob (`taskFiles`, `companionFiles`) has no `/` and is matched against the file name alone. Git's `:(glob)` pathspec reads these tokens the same way, so `0008` can pass a glob to git as written (C-2, C-3). `?`, `[...]` and a leading `!` are not part of the dialect. Decision 0004 did not say what one of them does, so `0005` reads each as the literal character it is and rejects nothing (OQ-7, open).

**Where the keys are read.** [`SpecManifest`](../../SpecManifest.cs) stays the one reader of the manifest (`0001-F5` § 7). Item `0005` adds to it, and only this:

- five entries in `KnownKeys`: `layouts`, `exclusions`, `taskFiles`, `epicFiles`, `companionFiles`;
- one private function that reads the five keys, each `manifest[key] ?? Defaults[key]`, into one value, and reads nothing else - not `identifiers.epic` (see "Epic files" below);
- one `init` member on [`SpecStructure`](../../SpecStructure.cs), `Discovery`, set beside `FrontmatterSchemas`.

That value is a new record, `SpecDiscoveryInputs`, in its own file: `Layouts`, `Exclusions`, `TaskFiles`, `EpicFiles`, `CompanionFiles`. It is one record and not five members on `SpecStructure` because it is the one argument discovery takes, today and in both modes `0007` and `0008` add, and because no rule holds it (C-5). [`SpecLayout`](../../SpecLayout.cs) stops being an enum of two and becomes the record a `layouts` entry is read into, `Name` and `Glob`; a third layout is then a third value, with no code change (B-001). `SpecLocation.Layout` keeps its name and its type's name.

**The same block in both manifest copies.** The five keys go into `.spec/schema/spec-structure.schema.json` and `src/specht.tool/schema/v1/spec-structure.schema.json`, byte for byte, as one block placed between `$comment` and `sections`. They ship in the embedded `v1` manifest, so they are tool-owned and `init` writes them (`0001-F4` decision 0001, B-004); version 1 is still open to them (`0001-F7` decision 0002). Item `0015` adds its keys to the same three files in parallel: this item's JSON block sits at the top of the manifest, its `KnownKeys` entries directly after `schemaVersion`, and its `Discovery` initializer line above `FrontmatterSchemas`, so an item that appends after `frontmatterSchemas` touches no line this one does.

**How discovery consumes them.** [`SpecDiscovery`](../../SpecDiscovery.cs) stays a static class until ADR-0001's stage D (item `0107`), and its interface arrives with the second mode (stage E, `0007` and `0008`). Each member this item touches takes the `IFileSystem` and the `SpecDiscoveryInputs`: the first from [`SpecModel.Load`](../../SpecModel.cs), which already holds one, the second from `schemas.Structure.Discovery`.

| Member                 | Reads                     | Does                                                                                                                                                                                    |
| ---------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FindSpecifications`   | `Layouts`, `Exclusions`   | For each layout in the manifest's order, every file whose root-relative path matches the layout's glob and is not excluded, ordinally by path, as a `SpecLocation` carrying that layout |
| `FindChildItems`       | `TaskFiles`               | Beside each specification, every file whose name matches the shape. Replaces `IsItemFileName`, which has no other caller                                                                |
| `FindEpics` (new)      | `EpicFiles`, `Exclusions` | Every file whose root-relative path matches the glob and is not excluded. Moves the `epics` and `epic.md` enumeration out of `SpecModel.Load`                                           |
| `FindCompanions` (new) | `CompanionFiles`          | Beside one specification, every file whose name matches the glob. Moves the `*.feature` enumeration out of `SpecModel.Load`                                                             |

A path is excluded when one of its directory segments equals a bare-name entry, or when it lies under a `/` entry's path. One private function turns a glob into a regular expression; the layouts, `epicFiles`, `taskFiles` and `companionFiles` all pass through it, `taskFiles` with `{task}` replaced by the task grammar less its `^` and `$`, as one group. A file two layouts match is discovered once, in the first of them in the manifest's order (OQ-7).

No package matches the globs. `Microsoft.Extensions.FileSystemGlobbing` would be a sixth engine dependency (`0001-F1` C-7; none joins without an ADR), walks through its own directory abstraction and not `IFileSystem`, and reads more tokens than the dialect has, which C-3 would then have to reconcile with git's.

**Epic files and the opt-in epic tier.** [`0001-F5` decision 0004](../../Manifest/.spec/decisions/0004-epics-are-opt-in-by-the-manifests-epic-grammar.md) makes epics opt-in: a repository has an epic tier only when its manifest declares `identifiers.epic`, and that grammar alone is the signal (`0001-F5` C-10). § 5 #7 gives discovery no epic-less mode. For `0005` that means:

- **`epicFiles` is read, filled and applied the same way with or without the epic grammar.** The function that reads the five keys does not look at `identifiers`, and `FindEpics` has no branch on it. `epicFiles` is a file glob and not a grammar, so the epic grammar's exemption from the default fill (`0001-F5` B-019) does not reach it: a manifest with no epic grammar that omits `epicFiles` still reads `epics/**/epic.md`.
- **With no epic grammar, a matched epic file still enters `SpecModel.Epics`**, path and frontmatter, as today. What is reported about it is a rule's: `SPEC004` reports nothing (`0001-F5` B-034), in `FrontmatterSchemaRule`, built by the item that delivers `0001-F5` B-033 and B-034. `0005` adds no such check and removes none.
- **This does not contradict decision 0004's default.** Finding the file a glob names is not inferring a tier from it, which is what `0001-F5` C-10 rules out. The `@B-003` scenario runs under the default manifest, which declares the epic grammar, so its "the epic's frontmatter is checked" holds.

Three things follow that no claim states. They are listed for `spec-author` and not settled here:

1. **`init` without `--epics` writes a manifest that names epic files.** The five keys are tool-owned and ship in the embedded manifest (decision 0004), and `0001-F4` B-003 excepts only the epic grammar and the task grammar (`0001-F4` B-021, B-022). So that manifest declares no epic tier and still carries `"epicFiles": "epics/**/epic.md"` and the `legacy` layout `epics/**/spec.md`. The check is unharmed. Whether `init` leaves either out is `0001-F4`'s to say.
2. **`SPEC001` on an epic file, with no epic grammar.** `FrontmatterSchemaRule` reports `SPEC001` from the same loop that reports `SPEC004`, for an epic file that opens with no frontmatter. `0001-F5` B-034 silences `SPEC004` and says nothing of `SPEC001`. Discovery still lists the file, so the case can occur.
3. **No value of `epicFiles` means "none".** The dialect has no such token, so a repository without epics cannot stop the check matching and reading epic files, except with a glob that matches nothing. Skipping the read when no epic grammar is declared would be the epic-less discovery mode § 5 #7 excludes.

**Naming a layout (B-009).** The name travels as data from the manifest to the output, and no enum or naming policy spells it:

```
layouts[].name -> SpecLayout.Name -> SpecLocation.Layout -> SpecCheckReport.Layouts -> SpecReportDocument.Layouts -> the summary line and "layout" in the JSON
```

- [`SpecCheckReport`](../../SpecCheckReport.cs) carries `Layouts`, one [`SpecReportLayout`](../../Report/SpecReportLayout.cs) per manifest layout in the manifest's order, a layout with no specification at `0`, in place of `LegacyCount` and `CoLocatedCount`; `SpecModel.LegacyCount` and `CoLocatedCount` go with them. `SpecReportLayout.Layout` becomes the name, a string; the type is reused, not doubled.
- [`SpecReportDocument.From`](../../Report/SpecReportDocument.cs) copies the report's list; `SummaryLines` prints the name as it is, and the `JsonNamingPolicy.CamelCase` over the enum goes (`0001-F2` § 7 names this item as where that changes).
- [`docs/schema/report.schema.json`](../../../../docs/schema/report.schema.json) closes `layout` to the enum `legacy`, `coLocated`, which a renamed or a third layout fails. It becomes a non-empty string. The member name and the document's shape do not change, and under the default manifest the document is the same bytes. The file is `0001-F3`'s published schema; `0001-F3` B-005 already says "each layout's name", and its § 7 is updated in the same change.
- `SpecCheckReport.MigrationSummary` is removed in this item's change ([decision 0006](decisions/0006-the-migration-summary-is-removed.md), which resolved OQ-6). It names both layouts by literal and computes a share that presumes exactly those two; no claim covers it and the tool never prints it. Two tests assert its text, in `SpecCheckRunnerUnitTests` and `SpecCheckRunnerIntegrationTests`; those assertions go with it and are the `test-writer`'s to drop.
- A manifest that declares one layout gives a report with one entry and a summary that names one layout (C-7; the second `@B-001` scenario). Nothing adds a default layout back.

**The collision with item `0105`.** Item `0105` ([`0001-F1` § 7](../../.spec/README.md); ADR-0008) splits the runner: `Run(root, versions)` becomes `Evaluate(SpecModel.Load(root, versions), Discover())`, and `Evaluate(SpecModel, IEnumerable<ISpecRule>)` builds the `SpecCheckReport` from the model. `0105` merges first and `0005` rebases onto it. The two items meet in one statement and one record:

| Where                                                           | What `0005` changes                                                                                                                                                                                                     | What it leaves as `0105` has it                                                                                  |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `SpecCheckRunner`, the `new SpecCheckReport(...)` argument list | The two arguments `model.LegacyCount` and `model.CoLocatedCount` become one, the layout list. They sit in `Run` today and in `Evaluate` after `0105`                                                                    | Both `Run` signatures, `Evaluate`'s signature, the two filters, the rules-evaluated count, `Order`, `Discover()` |
| `SpecCheckReport`, the positional parameters                    | `int LegacyCount, int CoLocatedCount` become one `IReadOnlyList<SpecReportLayout> Layouts`, in the same place, third; their two `<param>` lines become one, and `SpecificationCount`'s line stops saying "both layouts" | `SchemaVersion`, `SpecificationCount`, `ItemCount`, `RulesEvaluated`, `Violations`, and their order              |
| `SpecCheckReport`, the members                                  | `MigrationSummary` is removed                                                                                                                                                                                           | `ErrorCount`, `WarningCount`                                                                                     |
| `SpecModel`                                                     | `LegacyCount` and `CoLocatedCount` are removed; the body of `Load(string, SchemaVersions)` calls discovery with the inputs                                                                                              | The constructor, both `Load` signatures, `Schemas`                                                               |
| `SpecReportDocument.From`                                       | The collection expression that builds two `SpecReportLayout` values becomes `report.Layouts`                                                                                                                            | `0105` does not touch it                                                                                         |

The layout list is computed where the report is built, from the model alone: for each layout of `model.Schemas.Structure.Discovery.Layouts`, in that order, its `Name` and the number of `model.Features` whose `Location.Layout` is that layout. So `Evaluate` still needs no tree: a model built in memory over a manifest that omits `layouts` gives the two default layouts, each at `0`. `0005` touches neither `SpecSchemas`, where `0105` adds `Version`, nor the rule filter or the violation filter. A test `0105` writes that reads `report.LegacyCount` or `report.CoLocatedCount`, or builds a `SpecCheckReport` positionally, is re-pointed to `Layouts` in `0005`'s change.
