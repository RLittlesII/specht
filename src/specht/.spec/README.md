# Specification: The engine, extracted unchanged

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The rule engine exists only inside a consumer repository, as a project reference from its build, under a namespace that names that repository. Every other repository on the model copies it or goes without a gate. This Feature removes that failure state by moving the engine into this repository as the library `specht`, with no behaviour change: the same twenty-one rule ids, the same violations in the same order on the same tree. It is the baseline every later Feature proves itself against (brief § 8 step 2).

## 7. Technical Design

<!-- last written by: implementer, 2026-11-13 (item 0167: the check entry point; the runner deleted) -->

Delivered so far by items 0021, 0104, 0103, 0024, 0105, 0106, 0107, 0156 to 0163, 0164 and 0166. A bullet dated before item `0107` says what its item built; where stage D changed that, the stage D bullet is the current shape, where ADR-0010 stage 3 split a rule, the subsection "ADR-0010 stage 3: one rule per id" is, where ADR-0010 stage 4 replaced the static evaluation, the subsection "ADR-0010 stage 4: the evaluator" is, and where ADR-0010 stage 6 replaced a loader, a static parse or an absolute path, the subsection "ADR-0010 stage 6: the model reader" is.

- **The copy.** The imported `tools/SpecGovernance` (28 `.cs` files and its `.csproj`) is `src/specht`, and `test/SpecGovernance.Tests` (four `.cs` files) is in `test/tests`, imported at commit `e7dba24` (A-2). The draft-spec `.spec/` was already gone at that commit, so nothing was removed.
- **The C-2 edits, and only those.** Each copied `.cs` file differs by its `namespace` line: the original engine namespace becomes `specht`, `.Rules` stays a sub-namespace, and the original test namespace becomes `specht.tests`. The engine's `.csproj` sets `RootNamespace` and `AssemblyName` to `specht` and drops its comment about the consumer's `Directory.Build.props` (B-005).
- **The test project is this repository's**, not the copied one: `test/tests/tests.csproj` was scaffolded before the copy, and keeps its packages and references. It gains one load-bearing item from the import: the live `.specht/**/*.json` - the manifest and the frontmatter schemas - linked into the output at the paths they have under `.specht/`, so the tests run against the schema set the rules enforce (A-3).
- **Implicit usings.** The baseline engine requires `ImplicitUsings` on; this repository turns them off by default. The root `Directory.Build.props` turns them on for the `specht` and `specht.tests` projects only, so the copied files compile unchanged (C-2) and every other project keeps the repository's setting.

- **One id per rule, registered where the old class was.** Each new rule's `ReportedIds` was its own `Id` alone, until item `0164` removed the member, and the old class is deleted. [`AddSpechtEngine()`](../Composition/SpechtEngineServiceCollectionExtensions.cs) registers a split's rules by name where it registered the old class, each at its id's ordinal place, so the registrations stay in ordinal order of `Id` (C-5). `ISpechtRule`, `SpechtRunner.Evaluate` and `SpechtRunner.Order` are untouched; collapsing the interface is item `0164`.
- **No verdict changes** (C-9; ADR-0010 § "Why no structural stage changes a verdict"). Each rule keeps the old class's loops and guards for its id and emits that id in the old class's order; rule id is `Order`'s last key and the sort is stable, so every violation's file, line, identifier, message, expected object and severity, and the report's order, are unchanged. The rules-evaluated count summed enabled `ReportedIds` entries, so it was unchanged too; from item `0164` it counts the rules selected, the same number.
- **Shared work is a class a rule takes, never a base class.** Where rules of one split share work, it is a class registered as a singleton and taken by constructor (`FrontmatterSchemaCheck`, `DeclaredItemCheck`); a split with nothing to share introduces no helper type.
- **What runs changes, not what a clean run reports.** A rule whose id is `off` is not evaluated, so its check no longer executes for a sibling id's sake.
- **A rule fault stays with its id.** [`FaultIsolatedRule`](../Rules/FaultIsolatedRule.cs) decorates each new rule, so a rule that throws discards only its own id's violations and is reported under its own id, where the old class's fault was reported under its `Id`, its first id (`SPEC001`, `SPEC010`, `SPEC011`, `SPEC020`, `SPEC030`, `SPEC040`, `SPEC050`, `SPEC060`), and discarded every id's violations. The rule-failure diagnostic is `FaultIsolatedRule`'s (B-012 to B-016), and no split changes it.
- **Proof.** The golden report `test/tests/Engine/Baseline/engine-e7dba24.json` is unchanged and its comparison green unedited; the composition tests hold the registrations, their ordinal order and the twenty-one ids. Those tests are the test-writer's (§ 8, § 9).
- **Not built**: a folder per rule group (item `0342`).

### ADR-0010 stage 4: the evaluator

<!-- last written by: implementer, 2026-11-01 (item `0164`) -->

Item `0164`, built 2026-11-01, collapses the rule interface to one id and makes the evaluation an instance ([ADR-0010](../../../.spec/adr/0010-layered-engine-boundaries-with-io-at-the-edge-and-a-mediator.md) § "One rule per id", § "The evaluator is pure", stage 4 (C)).

- **The rule.** [`ISpechtRule`](../Rules/ISpechtRule.cs) is `Id`, `DefaultLevel` and `Evaluate(SpechtModel)` returning [`SpechtFinding`](../Rules/SpechtFinding.cs)s; `ReportedIds` is gone. A finding is a file, a line, an identifier, a message and `Expected`, compared by value with `Expected` as JSON, and carries no rule id and no severity. No rule constructs a `SpechtViolation`; the shared checks, [`FrontmatterSchemaCheck`](../Rules/FrontmatterSchemaCheck.cs) and [`DeclaredItemCheck`](../Rules/DeclaredItemCheck.cs), lose the rule-id parameter they were handed.
- **The default level, not a default severity (judgement).** ADR-0010 writes `SpecSeverity DefaultSeverity`. The interface keeps the `SpechtRuleLevel DefaultLevel` item `0223` added, because `SPEC034` and `SPEC035` default to off (`0001-F5` B-061, B-062, decision 0014) and a severity cannot say off. Every rule keeps its level: error, except those two, off. The owner may rule otherwise in review (item `0164`, decision of 2026-11-01).
- **The evaluator.** [`SpechtEvaluator`](../Evaluation/SpechtEvaluator.cs), sealed, takes the rule set and a [`SpechtViolationOrder`](../Evaluation/SpechtViolationOrder.cs) by constructor; `Evaluate(SpechtModel)` selects, runs, stamps and sorts. Select: a rule whose id is in `model.Schemas.Version.RuleIds` and whose level - the manifest's for its id, else its `DefaultLevel` - is not off; a `Where`, no selector type. Run: each selected rule once, in the order given. Stamp: each finding becomes a `SpechtViolation` under the rule's id at the selected level's severity, a rule failure at error whatever the level (B-015). Sort: `SpechtViolationOrder.Order`, the chain item `0103` wrote, unchanged. `RulesEvaluated` is the count selected, which with one id per rule is the count of enabled ids it was.
- **What it replaces.** The static `SpechtRunner.Evaluate`, `SpechtRunner.Order` and their private `Enabled` and `Graded`. The violation filter goes with them: a rule reports one id, so every finding of a selected rule is of a selected id. The one case the filter let a failure through - a rule selected through a second id while its first was off - ended with stage 3: a rule whose one id is off is not selected, so it never runs and never fails.
- **The layout.** [`SpechtReport`](../Evaluation/SpechtReport.cs), [`SpechtViolation`](../Evaluation/SpechtViolation.cs) and, with the layout counts the report holds, [`SpechtReportLayout`](../Evaluation/SpechtReportLayout.cs) move to `Evaluation/`, namespace `Specht.Evaluation` (ADR-0010 § "How each cycle is cut", 2). `Specht.Report` references `Specht.Evaluation`, and nothing in `Specht.Evaluation` references `Specht.Report`. `SpechtSeverity` stays in `Model/`, below both.
- **The composition.** `AddSpechtEngine()` registers `SpechtViolationOrder` and `SpechtEvaluator` as singletons before `SpechtRunner` (before `SpechtCheck` from item `0167`). The evaluator is handed `IEnumerable<ISpechtRule>`, so the decorated registrations reach it, and a rule registered after `AddSpechtEngine()` joins them, as it joined the runner's set before.
- **The runner.** `SpechtRunner` kept `Run(string)`, `Run(string, SchemaSourceSelection?)`, `ParseFrontmatterKind`, `CheckFrontmatter` and `WriteReport` with their signatures until item `0167` deleted it. `Run` was `evaluator.Evaluate(loader.Load(root, selection))`; from item `0166` it was `evaluator.Evaluate(reader.Read(root, selection))`.
- **The single-document check.** `CheckFrontmatter` builds an evaluator over the four frontmatter rules, each taken from the registered set unwrapped from the decorator, and calls its internal `Evaluate(SpechtModel, Func<ISpechtRule, IEnumerable<SpechtFinding>>)`, the overload the public `Evaluate(SpechtModel)` calls with each rule's whole-tree evaluation. The function returns a rule's document overload's findings, empty where the kind is not the rule's. The model is the root's schemas and no Features, items or epics. The evaluator selects, stamps, counts and orders them as it does a tree, so the violations and the count - every enabled one of the four, whether or not the kind is its - are the ones the static gave. The runner takes `SpechtViolationOrder` for this evaluator. Rejected: an adapter binding a rule to the document, which is an `ISpechtRule` the engine declares and does not register, against B-001's one-registration test; a model holding the one document, which counts it as a specification or an item; a selector type or a stage interface (ADR-0004, ADR-0005).
- **No statics added.** `Evaluate`, `Order`, `Enabled` and `Graded` are gone; the evaluator's one private static is `Stamped`, a helper that holds no state (ADR-0010 § "What 'no static' covers").
- **Not built** at item `0164`: the mediator, `Check.Query` and its handler, which ADR-0026 does not adopt; the deletion of `SpechtRunner` and the guard on I/O, which item `0167` built (below); the namespace order (item `0439`); a folder per rule group (item `0342`, moved out of item `0169` by the owner on 2026-11-02: the group folders meet the Feature folders under `Rules/`, `0001-F12`'s `Rules/Matrix/` home among them).

### A rule's id per pinned version

Item `0169`, built 2026-11-02, answers [ADR-0029](../../../.spec/adr/0029-rule-ids-take-four-digits-in-schema-0-3-0-and-published-versions-keep-theirs.md) open point 1 (ADR-0010 open point 7). Schema `0.3.0` names its 24 rules by four-digit ids and `0.1.0`, `0.2.0` and `0.2.1` keep the three-digit ones (`0001-F7` B-151, B-152).

- **The key and the name.** A rule's `Id` is its key: the three-digit id the baseline gives it, and the order `AddSpechtEngine()` registers in (C-5). [`SchemaVersion.RuleNames`](../Versioning/SchemaVersion.cs) maps the key to the version's id, and `RuleId(key)` returns it, or the key where the version maps none. [`SchemaVersions.Shipped`](../Versioning/SchemaVersions.cs) states each version's map as data: the identity below `0.3.0`, ADR-0029's table at `0.3.0`. `RuleIds` is the map's values, so `0.3.0`'s vocabulary is written once and no version holds both forms.
- **Where the name is read.** [`SpechtEvaluator`](../Evaluation/SpechtEvaluator.cs) takes `version.RuleId(rule.Id)` once per rule and uses it to select against `RuleIds`, to read the manifest's level and to stamp each finding. `SpechtViolationOrder`'s fourth key is the stamped id, so the order follows the pin; on the baseline tree the renumbering moves no violation, since no file and line holds two ids whose order the map changes. [`FaultIsolatedRule`](../Rules/FaultIsolatedRule.cs) names a fault by the pinned id (B-013). `specht rules`, `rules set`, `--explain` and the manifest's `rules` validation read `RuleIds` and `RulePages`, already in the pinned form, and are unchanged.
- **Written twice, compared by nothing.** The keys are written in the rule classes and in `Shipped`, and no test compares the two: the composition test holds the rule classes' keys to a list of its own, and `ShippedVocabularies` holds each version's ids. A map key that names no rule class leaves that rule unselected under its version, which the `0.3.0` golden report shows only for a rule the baseline tree breaks. The public `0.3.0` ids are written only in the map. Rejected: `Id` as the `0.3.0` id with a map down to the published ids, which writes the vocabulary twice as well and rewrites every rule class and the tests that state the keys, changing no verdict.
- **Proof.** `engine-e7dba24.json` is unchanged; `test/tests/Engine/Baseline/engine-v0.3.0.json` is the same tree's verdict under `0.3.0`, generated by the engine (B-018). It differs from the first by the map in every rule id and by two `SPEC7001` verdicts `0.3.0` drops on that tree (`0001-F7` decision 0015), and in nothing else.
- **Proof.** No verdict changes (C-9): the golden report `test/tests/Engine/Baseline/engine-e7dba24.json` is unchanged and its comparison green unedited. The evaluator's and the order's unit tests, the composition tests and the frontmatter tests are the test-writer's (§ 8, § 9).
