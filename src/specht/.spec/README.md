# Specification: The engine, extracted unchanged

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

The rule engine exists only inside `hooked`, as a project reference from its build, under a namespace that names that repository. Every other repository on the model copies it or goes without a gate. This Feature removes that failure state by moving the engine into this repository as the library `specht`, with no behaviour change: the same twenty-one rule ids, the same violations in the same order on the same tree. It is the baseline every later Feature proves itself against (brief § 8 step 2).

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 (item 0105: the split as built) -->

Delivered so far by items 0021, 0104, 0103, 0024 and 0105.

- **The copy.** `hooked`'s `tools/SpecGovernance` (28 `.cs` files and its `.csproj`) is `src/specht`, and `test/SpecGovernance.Tests` (four `.cs` files) is in `test/specht.tests`, exported from `6afe8ab` with `git archive` (A-2). The draft-spec `.spec/` was already gone at that commit, so nothing was removed.
- **The C-2 edits, and only those.** Each copied `.cs` file differs by its `namespace` line: `Hooked.SpecGovernance` becomes `specht`, `.Rules` stays a sub-namespace, and the tests' `Hooked.SpecGovernance.Tests` becomes `specht.tests`. The engine's `.csproj` sets `RootNamespace` and `AssemblyName` to `specht` and drops its comment about `hooked`'s `Directory.Build.props` (B-005).
- **The test project is this repository's**, not the copied one: `test/specht.tests/specht.tests.csproj` was scaffolded before the copy, and keeps its packages and references. It gains `hooked`'s one load-bearing item: the live `.spec/schema/*.json` linked into the output, so the tests run against the schema set the rules enforce (A-3).
- **Implicit usings.** `hooked` builds with `ImplicitUsings` on; this repository turns them off. The root `Directory.Build.props` turns them on for the `specht` and `specht.tests` projects only, so the copied files compile unchanged (C-2) and every other project keeps the repository's setting.
- **Dependencies.** The engine references four of C-7's five, each versioned in the `Engine` item group of `Directory.Packages.props`: Markdig, YamlDotNet and JsonSchema.Net at `hooked`'s versions, and `TestableIO.System.IO.Abstractions.Wrappers` (`0001-F5`, item `0011`). The fifth, `Microsoft.Extensions.DependencyInjection.Abstractions`, pinned to the container implementation package's version, arrives with its pin at [ADR-0001](../../../.spec/adr/0001-resolve-the-engine-from-the-container.md)'s stage D, the first stage that needs `AddSpechtEngine()` ([ADR-0003](../../../.spec/adr/0003-microsoft-extensions-dependency-injection-is-the-container.md)).
- **The model is constructible in memory** ([ADR-0001](../../../.spec/adr/0001-resolve-the-engine-from-the-container.md) stage A, item `0104`). `SpecModel` ([`SpecModel.cs`](../SpecModel.cs)), `SpecDocument` ([`SpecDocument.cs`](../SpecDocument.cs)), `FeatureSpec` ([`FeatureSpec.cs`](../FeatureSpec.cs)) and `ChildItem` ([`ChildItem.cs`](../ChildItem.cs)) have public constructors; `EpicFile`, `SpecLocation`, `SpecSection` and `Frontmatter` were already public records. `SpecDocument.Parse` takes the document's text, not its path, and replaces the path-based overload; its frontmatter comes from the same text. `FrontmatterReader` ([`FrontmatterReader.cs`](../FrontmatterReader.cs)) is a sealed instance class taking `IFileSystem` by constructor, with no interface of its own (ADR-0001: the file system is every reader's substitution), pulled forward from stage D on the owner's review of pull request #29; it adds no public static member. `SpecModel.Load` builds one over the `FileSystem` it already loads the schemas with, reads each specification with `File.ReadAllText` and passes the text in; the rest of its disk access stays static until item `0107`. No `InternalsVisibleTo`, no container, no package. `SpecSchemas` keeps its private constructor: a test builds one with `SpecSchemas.Load` over a `MockFileSystem`. Verdicts are unchanged (C-9).
- **The violation order is one public static function** (item `0103`, built 2026-10-09). `SpecCheckRunner` ([`SpecCheckRunner.cs`](../SpecCheckRunner.cs)) declares `public static IReadOnlyList<SpecViolation> Order(IEnumerable<SpecViolation> violations)`, and `Run` calls it; the `OrderByDescending`/`ThenBy` chain that was inline in `Run` moved into it verbatim: severity descending, then file, line and rule id, file and rule id compared with `StringComparer.Ordinal`. The sort stays LINQ's, because LINQ's ordering is stable: violations equal on all four keys keep the order they were collected in (rule by id, then each rule's own order), and that order is part of the verdicts C-9 holds. An `IComparer<SpecViolation>` is rejected: it has no second caller, and it invites `List.Sort`, which is not stable. A new type for one function is rejected for the same reason; the function lives where [ADR-0005](../../../.spec/adr/0005-typed-injected-stages-not-a-chain.md) Decision (a) sketches it, as `Order` beside `Evaluate`. It takes no manifest value and no severity setting: it orders what it is given, and is the same function at every later stage.
  - **A static, under ADR-0001's rule.** [ADR-0001](../../../.spec/adr/0001-resolve-the-engine-from-the-container.md) § Decision, "The statics that stay", keeps a static only for a pure function or a constant with no I/O to substitute. `Order` is a pure function of its argument - no I/O, no clock, no state - so it qualifies, and it stays static when stage D makes `SpecCheckRunner` a sealed instance class: a test calls `SpecCheckRunner.Order` with violations built in memory, no tree and no container.
  - **Who calls it, stage by stage.** Item `0103`: `Run`, after collecting every rule's violations. Stage B, item `0105` ([ADR-0008](../../../.spec/adr/0008-evaluate-takes-the-rule-set-and-the-model-carries-the-vocabulary.md)): `Evaluate(SpecModel, IEnumerable<ISpecRule>)` calls it once over the kept violations, and `Run` loads and calls `Evaluate`; there is no second sort. Item `0014` ([ADR-0004](../../../.spec/adr/0004-per-rule-settings-are-selection-and-a-map.md)): the severity map runs over the violations before `Order`, because `Order` sorts by severity first, so a re-graded warning lands after every error. Stage D, item `0107` (ADR-0005 Decision (a)): the instance `Evaluate` calls it as `Order(graded)`; ADR-0005's fault violation carries a fixed `Error` severity and needs nothing of `Order`.
  - **Proof.** No verdict changes (C-9): the golden-report test and item `0012`'s guard stay green unchanged. The unit test that pins the order through `Order` is the test-writer's (§ 8, § 9), and ADR-0001's stage B reuses it.
- **The runner splits into `Evaluate` and `Run`** ([ADR-0001](../../../.spec/adr/0001-resolve-the-engine-from-the-container.md) stage B as [ADR-0008](../../../.spec/adr/0008-evaluate-takes-the-rule-set-and-the-model-carries-the-vocabulary.md) amends it; item `0105`, built 2026-10-09). [`SpecCheckRunner`](../SpecCheckRunner.cs) stays a static class. The two `Run` signatures do not change, so the host's `Func<string, SpecCheckReport>` registration and every caller of `Run` compile unchanged:
  - `public static SpecCheckReport Evaluate(SpecModel model, IEnumerable<ISpecRule> rules)`
  - `public static SpecCheckReport Run(string root)`, which is `Run(root, SchemaVersions.Embedded)` as today.
  - `public static SpecCheckReport Run(string root, SchemaVersions versions)`, which is `Evaluate(SpecModel.Load(root, versions), Discover())` and nothing else.
  - **What moves from `Run` into `Evaluate`**, each step as it is written today, so no verdict changes (C-9). (1) The rule filter: of `rules`, a rule is evaluated when at least one of its `ReportedIds` is in the vocabulary. (2) The violation filter: a violation is kept when its `RuleId` is in the vocabulary. (3) The rules-evaluated count: over the evaluated rules, the number of `ReportedIds` entries that are in the vocabulary - entries, not distinct ids. (4) The one `Order` call, over the kept violations. (5) The report: `SchemaVersion` from the pinned version's `Number`, and `SpecificationCount`, `LegacyCount`, `CoLocatedCount` and `ItemCount` from the model as today. `Run` keeps the load and `Discover()` and holds no filter, so `0001-F7` B-014 holds for every caller of `Evaluate`. `Run` no longer calls `versions.Select`: the load already selected.
  - **The vocabulary is `model.Schemas.Version.RuleIds`.** `Evaluate` reads no static and takes no version: the rule set is its one input beside the model, and the rule settings of [ADR-0004](../../../.spec/adr/0004-per-rule-settings-are-selection-and-a-map.md) stay on `model.Schemas.Structure`.
  - **Rules run in the order given.** `Evaluate` does not sort `rules`; it evaluates each once, in enumeration order, and collects their violations in that order, which `Order`'s stable sort preserves among violations equal on all four keys. `Run` passes `Discover()`, already ordered by `Id` ordinally, so the report is the one it was. `Evaluate` wraps no rule call: a rule that throws still propagates, until `0001-F2` B-015 (§ 5 row 13).
  - **`Discover()` stays private and reflective** until item `0106` replaces it; from then `Run` passes the hand-written list. Whether the instance `Evaluate` of stage D keeps the rule-set parameter is item `0107`'s to propose (ADR-0008).
- **`SpecSchemas` keeps the version it validates with** (ADR-0008; item `0105`, built 2026-10-09). [`SpecSchemas`](../SpecSchemas.cs) gains one read-only member, `public SchemaVersion Version { get; }`, set through its private constructor, which now takes that version and the structure and builds `Feature`, `Item` and `Epic` from the version's three texts under one `SchemaRegistry` of its own, so the invariant below holds by construction for both loads: the [`SchemaVersion`](../SchemaVersion.cs) whose three schema texts the load built `Feature`, `Item` and `Epic` from, and whose `RuleIds` are the vocabulary a check over these schemas evaluates. Its `Number` always equals `Structure.SchemaVersion`. It is the whole record, not a bare id set, because ADR-0008 decides the schemas keep the version they select, and the report's version number and the vocabulary then come from one value that cannot disagree.
  - **The version-set load**, `SpecSchemas.Load(IFileSystem, string, SchemaVersions)`, keeps the value `versions.Select(structure.SchemaVersion)` already returns and drops today.
  - **The on-disk load**, `SpecSchemas.Load(IFileSystem, string)`, takes no version set. It carries the embedded version the manifest pins, with the three schema texts it read from disk in place of the embedded ones: `SchemaVersions.Embedded.Select(structure.SchemaVersion) with { FeatureSchema, ItemSchema, EpicSchema }` set to the texts read. Two reasons. The vocabulary is fixed per embedded version whatever the source of the frontmatter schemas (brief § 4 and § 9; `0001-F7` B-014 and B-028), so the on-disk source changes the three schemas and nothing about which rules run. And the `with` keeps the one invariant of `Version` - its texts are the ones the schemas were built from - true of both loads, so item `0043` selects a source without the member changing meaning. Rejected: a nullable `Version`, or a sentinel meaning "every rule", which puts a second branch in `Evaluate` and lets a check run outside any vocabulary; an empty vocabulary, under which a check evaluates nothing and reports a clean tree; a `SchemaVersions` parameter on this overload, which is the other overload. This load reads the static `SchemaVersions.Embedded`, as `SpecModel.Load(string)` and `Run(string)` do; `Evaluate` still reads none.
  - **What changes for that overload's callers.** Every caller was checked. No production code calls it; its four callers are tests: `SpecModelFixture`, `SpecCheckRunnerDeterminismUnitTests`, `SpecSchemasUnitTests`, and the manifest acceptance steps' read-from-the-root branch. Each loads a manifest with no `schemaVersion`, which is version 1, and the embedded set holds version 1, so each keeps loading and now carries version 1's twenty-one ids. The one new behaviour: a manifest pinning a version the tool does not ship is a `SpechtManifestException` from this overload too (`SchemaVersions.Select`, with the message of `0001-F7` B-003), thrown before any frontmatter schema is read, where today it loads. No caller pins one.
  - **Building a model for a unit test of `Evaluate`.** `SpecSchemas` keeps its private constructor, so a schema set is still loaded, not built. A fake rule runs only when the model's vocabulary holds one of its `ReportedIds`, so the test loads its schemas through the version-set overload over a set it builds: `SpecSchemas.Load(fileSystem, "repo", new SchemaVersions([version]))`. `fileSystem` is a `MockFileSystem` holding only `repo/.spec/schema/spec-structure.schema.json`, because that overload reads no frontmatter schema from disk. `version` is a `SchemaVersion` whose `Number` is the manifest's pin (1 for the manifest `{}`) and whose `RuleIds` name the fake rules' ids. The result goes into the model through `SpecModel`'s public constructor. A fixture therefore has to be able to set one thing it cannot set today: the rule ids of the version the model's schemas are loaded with. `Evaluate` does not constrain an id's spelling: any string in `RuleIds` is in the vocabulary, so a fake id need not look like `SPEC###`. The on-disk schemas today's `SpecModelFixture` loads by default carry version 1's vocabulary, so under them a fake rule is evaluated only if it reports one of the twenty-one real ids. No public member is added for a test alone.
  - **Proof** (ADR-0001 stage B). The golden-report test and item `0012`'s guard stay green unchanged; item `0103`'s ordering unit test is reused; and a unit test of `Evaluate` over fake rules and a model built in memory, with no tree and no container, pins the rule filter, the violation filter and the count. Those tests are the test-writer's (§ 8, § 9).
- **Schema evaluation runs under the invariant culture** (item `0024`, built 2026-10-09; B-006, C-3; lesson 0001 of this Feature). JsonSchema.Net 9.4.0's `type` keyword (`TypeKeyword`) lowercases the expected type with the culture-sensitive `ToLower()`, so under `tr-TR` a `SPEC002` message read `"ınteger"` where the golden report reads `"integer"`: the locale reached the verdict. `EvaluationOptions.Culture` and the process-wide `ErrorMessages.Culture` choose only the message template and do not reach that call, and 9.4.0 is the latest release, so neither an option nor an upgrade fixes it. `FrontmatterSchemaRule` ([`FrontmatterSchemaRule.cs`](../Rules/FrontmatterSchemaRule.cs)), the engine's one schema evaluation, therefore evaluates through a private `EvaluateInvariant`: it sets `CultureInfo.CurrentCulture` to the invariant culture for the `Evaluate` call alone and restores the caller's culture in a `finally`. The scope is a plain method, not the rule's iterator, so no `yield return` runs under the invariant culture and the caller's thread never observes it. This is the engine's one culture access, and the reference guard names it as its one exemption.
- **The pipeline is described as it is today**: static stages composed with `new`, rules found by reflection. ADR-0001 redraws it as resolved types at stage D, when the engine's classes become instances registered by `AddSpechtEngine()`.
