# Specification: The report contract

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

A violation today says what is wrong and not what would be right, so the agent that reads it opens the rule catalogue, the template or the schema before it can repair the document, and a tree written before the schema existed fails without saying what it is missing. This Feature removes that failure state: the report is one JSON document with a published schema, every violation carries what the rule expected, and `--explain` prints a rule's full text, so an agent repairs a document, and migrates it between schema versions, from the report alone (Must-6).

## 7. Technical Design

<!-- last written by: implementer, 2026-10-10 (item 0120: `schemaVersion` is a `major.minor.patch` string; the pages are gathered by folder) -->

**The document (item `0034`).** [`SpecReportDocument`](../SpecReportDocument.cs) is a record made by `From(SpechtReport)` and nothing else, so its only input is the report (B-006, C-3). `From` maps each `SpecViolation` field by field onto a [`SpecReportViolation`](../SpecReportViolation.cs), keeping the report's order, and copies the report's `Layouts`: one [`SpecReportLayout`](../SpecReportLayout.cs) per manifest layout, in the manifest's order, carrying the layout's name and its count, a layout with no specification included at `0` (`0001-F6` B-009, C-7; item `0005`). `SchemaVersion` is a string: the `major.minor.patch` text of the report's `SemanticVersion`, the version the manifest pinned (`0001-F7` B-002; item `0120`, decision 0005). It was the integer `1` until then. A string and not three members, because a reader compares and prints it whole, and the manifest writes it the same way. [`SpecSchemaSource`](../SpecSchemaSource.cs) is `Embedded` for every run until `0043` makes the source a choice. `Expected` is an empty `JsonObject` until `0037`-`0039` fill it per rule family.

**The JSON.** `ToJson()` serializes the record itself with `System.Text.Json`: camelCase members in declaration order, enums as camelCase strings (`embedded`, `error`, `warning`), a layout's name as the manifest writes it (`epics` and `features` under the default manifest, `0001-F6` decision 0008), indented with `\n` whatever the platform, and an absent `identifier` omitted rather than written as `null` - the conventions the engine's earlier anonymous report already used, so a reader of that output meets the same names. No member is computed at serialization time.

```json
{
  "schemaVersion": "0.1.0",
  "schemaSource": "embedded",
  "layouts": [
    { "layout": "epics", "specificationCount": 2 },
    { "layout": "features", "specificationCount": 1 }
  ],
  "itemCount": 0,
  "rulesEvaluated": 21,
  "errorCount": 1,
  "warningCount": 0,
  "violations": [
    {
      "ruleId": "SPEC031",
      "severity": "error",
      "file": "epics/0001-epic/F1-feature/spec.md",
      "line": 0,
      "identifier": "B-002",
      "message": "...",
      "expected": {}
    }
  ]
}
```

**The run summary (`0001-F2` B-002, item `0028`).** `SummaryLines()` formats the four lines the check prints after its violations - the specification count per layout, the item count, the rules evaluated, and the error and warning counts - from the document's own B-005 members, so the summary and the JSON cannot count differently. A layout is named as the JSON carries it, by its name in the manifest (`epics 2, features 1` under the default manifest), and the layouts keep the document's order.

**The published schema (A-1, C-1).** [`docs/schema/report.schema.json`](../../../../docs/schema/report.schema.json), draft 2020-12, names every member above. `schemaVersion` is a string matching three dot-separated decimal numbers with no leading zero, the texts `SemanticVersion` writes; it was `type: integer` until item `0120`, and whether C-4 binds that change of type before a first package is published is OQ-5. The document, each layout entry and each violation are closed (`additionalProperties: false`), so a field the schema does not name fails validation; `expected` is `type: object` and nothing more, so a rule family adds members to it without a schema change (C-2, C-4). A layout entry's `layout` is a non-empty string, the layout's name in the manifest, where it was the enum `legacy`, `coLocated` until item `0005` (`0001-F6` B-009). A violation's `file` rejects a leading `/`, a drive letter and any `\` (B-021). The schema carries no `$id`: JsonSchema.Net registers a schema by its `$id` in a process-wide registry and refuses a second registration, which every caller loading the file twice in one process would hit. Both test projects copy `docs/schema/*.json` into their output and validate a produced document against that one file (B-008).

**One writer, one shape.** [`SpechtRunner.WriteReport`](../../SpechtRunner.cs) wrote its own anonymous object, `generatedAtUtc` from `DateTimeOffset.UtcNow` among it, which no command calls today. It now writes `SpecReportDocument.From(report).ToJson()`, so the only document the engine can write carries no timestamp and validates (B-006, B-008). Where `--report` writes, and how it replaces a file, is `0036`'s.

**Root-relative paths (B-021).** The engine had three copies of `Path.GetRelativePath(root, path).Replace(Path.DirectorySeparatorChar, '/')`: in `SpecDiscovery`, in `SpecModel` and inline in `FeatureFileRule.Evaluate`. They are now one public member, [`SpecDiscovery.Relative`](../../SpecDiscovery.cs), which the other two call; every path a violation carries passes through it, and the output is unchanged. Being public, it is the seam a unit test of the mapping can call (§ 8).

**`--json` (item `0035`).** [`CheckCommand.ExecuteAsync`](../../../specht.tool/Features/Check/CheckCommand.cs) branches once on `--json`: it makes `SpecReportDocument.From(report)` once, the same document the summary is drawn from, and writes either `ToJson()` or the violation lines and `SummaryLines()`. The document goes whole through `console.Profile.Out.Writer`, the raw writer, so no markup parsing or line wrapping touches it and stdout parses as one JSON document (B-001). The verdict fold after the branch is unchanged, so `--json` never moves the exit code (C-5), and a missing root or an unreadable manifest still returns before anything reaches stdout.

**The rule pages (item `0129`; decision 0003).** A page is a Markdown file at [`docs/rules/v1/`](../../../../docs/rules/v1/), under the repository root's `docs/` and not under the engine's project, named for its rule id, `SPEC031.md`, in the folder of the schema version it ships under (A-4). Schema version `0.1.0`, the version folder `v1` holds, has twenty-one, one per id in its vocabulary (`SchemaVersions.Shipped`, `0001-F7` § 7). Each is typed by hand in the one page shape (B-032), and its Metadata table's Schema version is the folder's number (B-033): the folder and that row keep the integer until `0001-F7` item `0126` renames them (`0001-F7` OQ-22). A page is terse because it is the text `--explain` will print: a one-sentence Cause, then a table of condition and message where the rule reports more than one; what is expected in a sentence or two; the smallest fragment that triggers the rule with the line it prints, and the fixed fragment; one bullet per condition under the fix. A guard stays only where a reader would otherwise be misled, and what a rule does not check is left unsaid.

**Why Markdown files and not strings in code.** A page is prose with tables and fenced examples. As a file it is formatted by the same pinned formatter as every other Markdown file here, it reads on the repository host as it stands, and a change to a rule's text is a diff of that text. As a string literal it would be none of those, and a descriptor type to hold it is the alternative decision 0003 turned down. The cost is that nothing ties a page's words to the rule's code: each Cause was written from the `new SpecViolation(...)` call sites in [`src/specht/Rules/`](../../Rules/), with messages quoted from them and `{name}` standing for each interpolated value, and each example's printed lines were taken from a run of the built tool over a tree holding that example, run again after item `0015` moved the section titles and markers into the manifest and again when the pages were shortened. Every example is an excerpt of such a tree, and the lines under it are every line the tool printed for that rule over that tree, message and line number both. Where the excerpt is the top of a file, the tree's file opens with those same lines, so the number is also the excerpt's own; where it is a table row, a heading or a scenario tag, the number is the tree's. A page names what the manifest sets - the claims, matrix and sign-off sections under `roles`, the contracted headers under `tables`, the claim grammar under `identifiers`, the `Missing`, draft, blocked and approved values under `markers` - by its key and gives the default manifest's value, because the messages themselves keep `§ 3`, `§ 9`, `§ 12`, `'Missing'` and `'approved'` as fixed text. SPEC002's Cause also says that a `null` `scored_by` or `github_issue` adds two lines each beside any real failure: `FrontmatterSchemaRule.Failures` reports the unmet `if` subschemas of the Feature schema's `allOf` as failures, and the page is written to that output, not to a corrected one. Its example is a specification with both keys set, so that it prints the two lines of the real failure and no others. A rule whose message or guard changes needs its page changed in the same pull request; no test says so.

**How the pages are embedded.** [`specht.csproj`](../../specht.csproj) embeds `..\..\docs\rules\v*\*.md`, linked from outside the project as the frontmatter schemas are from the tool's, with the logical name `rules/v<n>/<file>`, built from `%(RecursiveDir)` as the schemas' `schema/v<n>/<file>` names are, so a version's schemas and its pages sit under the same number in the engine's manifest resources. The files are `EmbeddedResource` items only: they are not `Content`, the repository-wide `Content` globs in `Directory.Build.props` match `.spec` and `.issue` folders and not `docs/rules`, the glob names `docs\rules\v*` and so takes nothing else under `docs/`, and `src/specht` does not pack. The package therefore carries the pages inside `specht.dll` and nowhere else.

**How the pages are gathered (B-031).** [`SchemaVersions.ReadEmbedded`](../../SchemaVersions.cs) already finds the embedded folders from the `schema/v<n>/` resource names. For each folder it now also takes every resource whose name starts `rules/v<n>/` and fills [`SchemaVersion.RulePages`](../../SchemaVersion.cs) with it: the key is the file name without its extension, the value the whole text, frontmatter included. The local `Read` takes a resource name where it took a number and a schema file name, so the schemas and the pages share it. From item `0120` the folder's integer `n` is no longer the version's `Number`, which is `major.minor.patch`; the pages are still gathered by folder, and the version they land on is the one `SchemaVersions.Shipped` gives that folder. `--explain` (`0040`) reads the map; nothing else names a resource.

**Why the map is not filtered by the vocabulary.** The gatherer puts in every page embedded under the version's folder, whatever its file is called. B-031 says the pages name exactly the vocabulary, and that is a statement the tests compare: `RulePages.Keys` against `RuleIds`. A gatherer that kept only the ids in `RuleIds` would make the "no page outside the vocabulary" half true by construction, and a stray `SPEC099.md` would ship unseen. Unfiltered, a stray page is a key the comparison rejects. The one page the map cannot show is one under a number with no schemas, `rules/v2/` beside no `schema/v2/`, because no `SchemaVersion` exists to hold it; the embedded-Markdown count in § 8 catches that.

**What a page does not carry.** No part on turning a rule off or re-grading it (§ 5 row 8): the word for a rule's grade appears once on a page, in the Metadata row, and every page gives `Error` there because every `SpecViolation` the engine makes is `SpecSeverity.Error`. No absolute path, and no date, author or machine name of the page's own (C-8): every example path is root-relative, and example frontmatter is cut down to the keys the example is about, which leaves the date and author keys out.
