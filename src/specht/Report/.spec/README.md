# Specification: The report contract

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

A violation today says what is wrong and not what would be right, so the agent that reads it opens the rule catalogue, the template or the schema before it can repair the document, and a tree written before the schema existed fails without saying what it is missing. This Feature removes that failure state: the report is one JSON document with a published schema, every violation carries what the rule expected, and `--explain` prints a rule's full text, so an agent repairs a document, and migrates it between schema versions, from the report alone (Must-6).

## 2. User Needs

<!-- last written by: spec-author, 2026-10-07 -->

| #   | Persona                                  | Need                                                                                             | Pain Point Today                                                                         |
| --- | ---------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 1   | The agent repairing a specification      | Each violation says what the rule wanted - the headers, the grammar, the section order - in data | A message in prose; the expectation lives in the rule's code, the template or the schema |
| 2   | The agent migrating a pre-schema tree    | The same, on Transporter's tree, for every rule at once                                          | Nothing says what a pre-schema document is missing, only that it fails                   |
| 3   | A CI step or a script parsing the result | One JSON document on stdout, or at a path, that validates against a schema it can pin            | `hooked` writes an anonymous object; its shape is whatever the code says this week       |
| 4   | The maintainer reading a rule            | The rule's full text from the tool that enforces it, for the version pinned                      | Prose in a skill file, in another repository                                             |
| 5   | `0001-F7`                                | A report that names the schema version it checked against and where the schemas came from        | N/A (internal dependency)                                                                |

### Assumptions

| ID  | Assumption                                                                                                                                                                                                                    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | The report's JSON Schema is published at `docs/schema/report.schema.json`. It is the tool's contract, versioned with the tool, so it lives outside `.spec/schema/` and `init` never writes it. The folder name is reversible. |
| A-2 | The exit code for `--explain` with a rule id outside the pinned version's vocabulary is `4`, not found (OQ-1, resolved 2026-10-08; `0001-F2` decision 0003). The proposed default `2` was not chosen.                         |
| A-3 | `--explain` is an option on the check command, as brief § 5 writes it (`specht --explain SPEC031`); it prints and exits without running a check.                                                                              |

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 (item 0005: the default layout names, `0001-F6` decision 0008) -->

**The document (item `0034`).** [`SpecReportDocument`](../SpecReportDocument.cs) is a record made by `From(SpecCheckReport)` and nothing else, so its only input is the report (B-006, C-3). `From` maps each `SpecViolation` field by field onto a [`SpecReportViolation`](../SpecReportViolation.cs), keeping the report's order, and copies the report's `Layouts`: one [`SpecReportLayout`](../SpecReportLayout.cs) per manifest layout, in the manifest's order, carrying the layout's name and its count, a layout with no specification included at `0` (`0001-F6` B-009, C-7; item `0005`). `SchemaVersion` is `1` and [`SpecSchemaSource`](../SpecSchemaSource.cs) is `Disk` for every run: the engine reads `<root>/.spec/schema/` and no selection exists yet; `0042` and `0043` replace both with the selected values. `Expected` is an empty `JsonObject` until `0037`-`0039` fill it per rule family.

**The JSON.** `ToJson()` serializes the record itself with `System.Text.Json`: camelCase members in declaration order, enums as camelCase strings (`disk`, `error`, `warning`), a layout's name as the manifest writes it (`epics` and `features` under the default manifest, `0001-F6` decision 0008), indented with `\n` whatever the platform, and an absent `identifier` omitted rather than written as `null` - the conventions the engine's earlier anonymous report already used, so a reader of that output meets the same names. No member is computed at serialization time.

```json
{
  "schemaVersion": 1,
  "schemaSource": "disk",
  "layouts": [
    { "layout": "epics", "specificationCount": 2 },
    { "layout": "features", "specificationCount": 1 }
  ],
  "itemCount": 0,
  "rulesEvaluated": 21,
  "errorCount": 1,
  "warningCount": 0,
  "violations": [
    {
      "ruleId": "SPEC031",
      "severity": "error",
      "file": "epics/0001-epic/F1-feature/spec.md",
      "line": 0,
      "identifier": "B-002",
      "message": "...",
      "expected": {}
    }
  ]
}
```

**The run summary (`0001-F2` B-002, item `0028`).** `SummaryLines()` formats the four lines the check prints after its violations - the specification count per layout, the item count, the rules evaluated, and the error and warning counts - from the document's own B-005 members, so the summary and the JSON cannot count differently. A layout is named as the JSON carries it, by its name in the manifest (`epics 2, features 1` under the default manifest), and the layouts keep the document's order.

**The published schema (A-1, C-1).** [`docs/schema/report.schema.json`](../../../../docs/schema/report.schema.json), draft 2020-12, names every member above. The document, each layout entry and each violation are closed (`additionalProperties: false`), so a field the schema does not name fails validation; `expected` is `type: object` and nothing more, so a rule family adds members to it without a schema change (C-2, C-4). A layout entry's `layout` is a non-empty string, the layout's name in the manifest, where it was the enum `legacy`, `coLocated` until item `0005` (`0001-F6` B-009). A violation's `file` rejects a leading `/`, a drive letter and any `\` (B-021). The schema carries no `$id`: JsonSchema.Net registers a schema by its `$id` in a process-wide registry and refuses a second registration, which every caller loading the file twice in one process would hit. Both test projects copy `docs/schema/*.json` into their output and validate a produced document against that one file (B-008).

**One writer, one shape.** [`SpecCheckRunner.WriteReport`](../../SpecCheckRunner.cs) wrote its own anonymous object, `generatedAtUtc` from `DateTimeOffset.UtcNow` among it, which no command calls today. It now writes `SpecReportDocument.From(report).ToJson()`, so the only document the engine can write carries no timestamp and validates (B-006, B-008). Where `--report` writes, and how it replaces a file, is `0036`'s.

**Root-relative paths (B-021).** The engine had three copies of `Path.GetRelativePath(root, path).Replace(Path.DirectorySeparatorChar, '/')`: in `SpecDiscovery`, in `SpecModel` and inline in `FeatureFileRule.Evaluate`. They are now one public member, [`SpecDiscovery.Relative`](../../SpecDiscovery.cs), which the other two call; every path a violation carries passes through it, and the output is unchanged. Being public, it is the seam a unit test of the mapping can call (§ 8).

**`--json` (item `0035`).** [`CheckCommand.ExecuteAsync`](../../../specht.tool/Features/Check/CheckCommand.cs) branches once on `--json`: it makes `SpecReportDocument.From(report)` once, the same document the summary is drawn from, and writes either `ToJson()` or the violation lines and `SummaryLines()`. The document goes whole through `console.Profile.Out.Writer`, the raw writer, so no markup parsing or line wrapping touches it and stdout parses as one JSON document (B-001). The verdict fold after the branch is unchanged, so `--json` never moves the exit code (C-5), and a missing root or an unreadable manifest still returns before anything reaches stdout.

## 8. Testing Strategy

<!-- last written by: test-writer, 2026-10-09 -->

- **The seam** (item `0034`): `specht.Report.SpecReportDocument.From(SpecCheckReport)` makes the document, a record carrying `SchemaVersion`, `SchemaSource` (`SpecSchemaSource`: `Embedded`, `Disk`, `Upstream`), `Layouts` (`SpecReportLayout(SpecLayout, SpecificationCount)`), `ItemCount`, `RulesEvaluated`, `ErrorCount`, `WarningCount` and `Violations` (`SpecReportViolation(RuleId, Severity, File, Line, Identifier, Message, Expected)`, `Expected` a `JsonObject`); `ToJson()` serializes it. The test-writer named the signatures, with bodies that throw; the bodies, the JSON member names and `docs/schema/report.schema.json` are `implementer`'s (§ 7). The claims are made "given the document", so they are proved at the engine; `--json` is `0035`'s (B-001).
- **Unit** (`test/specht.tests/SpecReportDocument.Unit.Tests.cs`, reports from `SpecCheckReportFixture` and `SpecViolationFixture`):
  - B-005 - mechanism: the derivation of the layout entries, the item and rule counts and the severity counts from the report. `AReport_WhenMadeADocument_ShouldCarryEachLayoutsCountTheItemsTheRulesEvaluatedAndTheSeverityCounts`. The version and the source have no unit test: until `0042` and `0043` they are fixed (version 1, the on-disk files) and no selection exists to pin; the integration test below pins them from a run.
  - B-006 - mechanism: the document's only input is the report. `AReport_WhenItsDocumentIsSerialized_ShouldCarryNoValueFromTheClockOrTheMachine`: no string value parses as a date or a time, and none carries the machine name, the user name, the working directory, the temporary directory or the profile directory. No clock is injected because the engine takes none; a value read from the clock is caught by its content instead.
  - B-007 - mechanism: the mapping of each `SpecViolation` field onto the document's violation, and the presence of an `expected` object. `AViolation_WhenMadeADocument_ShouldCarryItsRuleSeverityFileLineIdentifierMessageAndAnExpectedObject`, over an error with an identifier and a line and a whole-file warning with neither. What `expected` holds per rule family is `0037`-`0039`'s (B-009-B-018, B-026-B-028).
  - B-008 - no unit test: the mechanism is the serialization's agreement with a published file, which a test reads from disk; the integration theory below pins it.
  - B-021 - mechanism: the relativization in `SpecDiscovery.Relative(root, path)`, `Path.GetRelativePath(root, path).Replace(Path.DirectorySeparatorChar, '/')`, the one member `SpecModel` and `FeatureFileRule.Evaluate` now call (§ 7). `SpecDiscoveryUnitTests.APathUnderTheRoot_WhenMadeRelative_ShouldBeRelativeToTheRootWithForwardSlashes` (`test/specht.tests/SpecDiscovery.Unit.Tests.cs`), a theory over a file at the root, a specification at a `features` layout path and one at an `epics` layout path, each built with `Path.Combine` under a relative root, so no absolute path is in the test and the separator replaced is the platform's own. It was written after the consolidation, so it was never red; it fails if the member stops mapping to root-relative `/` paths.
- **Integration** (`test/specht.tests/SpecReportDocument.Integration.Tests.cs`, over a `SpecTree` and the runner):
  - B-005 - `ATreeWhoseManifestPinsNoVersion_WhenItsDocumentIsMade_ShouldNameSchemaVersion1FromTheOnDiskFiles` (`0001-F7` B-002).
  - B-006 - `TheSameTreeUnderTwoRoots_WhenEachDocumentIsSerialized_ShouldBeIdentical`: the root location is the machine-dependent input a test can vary.
  - B-008 - `AReport_WhenItsDocumentIsSerialized_ShouldValidateAgainstThePublishedReportSchema`, over an empty report and one with an error carrying an identifier and a whole-file warning. `docs/schema/*.json` is copied into the output by a wildcard, so an unpublished schema fails this test, not the build.
  - B-021 - `ATreeWithViolationsInBothLayouts_WhenItsDocumentIsSerialized_ShouldCarryOnlyRootRelativeForwardSlashPaths`: a violation in each layout, every file unrooted and free of `\`, and no string in the JSON containing the root.
- **Integration, the command** (item `0035`, `test/specht.tests/CheckCommand.Integration.Tests.cs`, through Spectre's command tester):
  - B-001 - `AReport_WhenCheckedWithJson_ShouldPrintOnlyItsDocument`, a theory over the class's `Reports` (no violation, two violations in the runner's order, one wider than the console): stdout equals `SpecReportDocument.From(report).ToJson()` and parses as one JSON document. `ATreeWithViolations_WhenCheckedWithJson_ShouldPrintTheDocumentAndNoLine`, over the real runner and a `SpecTree` with more than one violation: stdout equals the document and carries none of the violation lines and none of the summary lines. No unit test: the mechanism beneath B-001 is `SpecReportDocument.ToJson()`, unit-tested by `0034` above, and the remaining decision - which writer the host calls for `--json` - lives in `CheckCommand.ExecuteAsync`, which runs only through the parser and the registrar, so it is integration's (`specht-conventions` § Testing).
- **Acceptance.** `report.feature` is linked into `test/specht.acceptance` (discovered entries 51 to 84); [`Report/ReportSteps.cs`](../../../../test/specht.acceptance/Report/ReportSteps.cs) binds B-001, B-005, B-007, B-008 and B-021. - **Red for the right reason** (against the throwing stubs, `0034`): every unit and integration test above and the B-005, B-007 and B-021 scenarios fail with "the report document is not built yet"; the B-008 integration tests fail first on "the report schema is published at docs/schema/report.schema.json (A-1)". - **What the design makes hard to test** (to `implementer`): neither the engine nor the tool host has a clock or environment seam, and a launched process's machine name cannot be set, so B-006's scenarios cannot vary either; B-005's version and source have no selection to unit-test until `0042` and `0043`.
