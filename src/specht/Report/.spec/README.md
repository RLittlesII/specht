# Specification: The report contract

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

A violation today says what is wrong and not what would be right, so the agent that reads it opens the rule catalogue, the template or the schema before it can repair the document, and a tree written before the schema existed fails without saying what it is missing. This Feature removes that failure state: the report is one JSON document with a published schema, every violation carries what the rule expected, and `--explain` prints a rule's full text, so an agent repairs a document, and migrates it between schema versions, from the report alone (Must-6).

## 2. User Needs

<!-- last written by: spec-author, 2026-10-15 (A-5 amended, review round 1) -->

| #   | Persona                                  | Need                                                                                             | Pain Point Today                                                                                |
| --- | ---------------------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 1   | The agent repairing a specification      | Each violation says what the rule wanted - the headers, the grammar, the section order - in data | A message in prose; the expectation lives in the rule's code, the template or the schema        |
| 2   | The agent migrating a pre-schema tree    | The same, on Transporter's tree, for every rule at once                                          | Nothing says what a pre-schema document is missing, only that it fails                          |
| 3   | A CI step or a script parsing the result | One JSON document on stdout, or at a path, that validates against a schema it can pin            | a consumer repository writes an anonymous object; its shape is whatever the code says this week |
| 4   | The maintainer reading a rule            | The rule's full text from the tool that enforces it, for the version pinned                      | Prose in a skill file, in another repository                                                    |
| 5   | `0001-F7`                                | A report that names the schema version it checked against and where the schemas came from        | N/A (internal dependency)                                                                       |
| 6   | A person or agent fixing a violation     | One page per rule in one shape: what it checks, a violating example, the correction, the fix     | brief § 4 gives each rule one line; the rest is in the rule's code                              |

## 4. Constraints

<!-- last written by: spec-author, 2026-10-09 (C-8 added, decision 0003; its Rules Out reworded after review round 7) -->

| ID  | Constraint                                                                                                                                     | Rules Out                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| C-1 | The report's shape is written once, as a JSON Schema in this repository, and a test validates a produced report against it.                    | An anonymous object as the only definition; a field the schema does not name.                                 |
| C-2 | `expected` is structured data an agent can act on without the catalogue: an object with named members per rule family, never a sentence alone. | `expected: "the right headers"`; the message repeated under another name.                                     |
| C-3 | The document is a function of the tree, the manifest and the tool version.                                                                     | A timestamp; a machine name; an absolute path; a locale-dependent string.                                     |
| C-4 | Within a tool major version the document changes only by addition.                                                                             | Renaming or removing a field; changing a field's type.                                                        |
| C-5 | `--json` and `--report` change what is written, never the verdict.                                                                             | A different exit code under `--json`; a violation that appears in one form and not the other.                 |
| C-6 | A rule's full text lives once, in the engine, versioned with the schema; `--explain` prints it and brief § 4 only summarises it.               | A second catalogue in a skill or a wiki that `--explain` does not read.                                       |
| C-7 | The file `--report` names is the only file a check run writes, and it holds exactly one report document.                                       | A temporary or backup file left beside it; appending a second document; any other write under the root.       |
| C-8 | A rule page is a function of the rule and its schema version, as the document is of its inputs (C-3; brief § 9).                               | An absolute path in an example or printed line; when, by whom or on what machine the page itself was written. |

## 7. Technical Design

<!-- last written by: implementer, 2026-10-17 (item 0039); 2026-10-16 (item 0038) -->

**The document (item `0034`).** [`SpecReportDocument`](../SpecReportDocument.cs) is a record made by `From(SpechtReport)` and nothing else, so its only input is the report (B-006, C-3). `From` maps each `SpecViolation` field by field onto a [`SpecReportViolation`](../SpecReportViolation.cs), keeping the report's order, and copies the report's `Layouts`: one [`SpecReportLayout`](../SpecReportLayout.cs) per manifest layout, in the manifest's order, carrying the layout's name and its count, a layout with no specification included at `0` (`0001-F6` B-009, C-7; item `0005`). `SchemaVersion` is a string: the `major.minor.patch` text of the report's `SemanticVersion`, the version the manifest pinned (`0001-F7` B-002; item `0120`, decision 0005). It was the integer `1` until then. A string and not three members, because a reader compares and prints it whole, and the manifest writes it the same way. [`SpecSchemaSource`](../SpecSchemaSource.cs) is `Embedded` for every run until `0043` makes the source a choice. `Expected` is a copy of the violation's own `Expected`, or an empty `JsonObject` where the rule sets none.

**What a violation expected (item `0037`; decision 0004).** The rule that finds a violation is the code that knows what it checked against, so it says so where it makes the violation. [`SpecViolation`](../../Model/SpecViolation.cs) carries `Expected`, a `JsonObject` set with `init` beside its six positional fields and `null` where a rule sets none. It is not on the diagnostic line, which `ToString` writes as before, and not in the golden report, which reads the six fields (`0001-F1` B-004). The record compares it by JSON value with `JsonNode.DeepEquals`, so two runs over one tree still give equal violations, and leaves it out of the hash. The runner's re-grading `with` keeps it. `From` deep-copies it, so a document never shares a node with the report. A map from violation to expectation on `SpechtReport` was not taken: a violation has no key of its own to map from. `From` reads only the report (C-3), so it cannot rebuild an expectation from the manifest or the schemas.

- **`SPEC001`** ([`FrontmatterSchemaRule`](../../Rules/FrontmatterSchemaRule.cs)): `schema` is `.specht/schema/frontmatter/` and the file `Structure.FrontmatterSchemas` names for the kind, under every source (B-026). The same path names the local file in the unresolved-reference error, under the disk and upstream sources only, as before. `required` is the `required` array at the root of the compiled schema the run evaluated, in its order, and empty where it has none.
- **`SPEC002`-`SPEC004`**: `schema` as above, `key` the violation's identifier where it has one, and `constraints`. For each failing evaluation detail the rule walks the detail's evaluation path through the schema's JSON from its root. A segment `if`, `not`, `anyOf` or `oneOf` in keyword position ends the walk with no place, so `constraints` is empty; the segment after `properties`, `patternProperties`, `$defs`, `dependentSchemas`, `allOf` or `prefixItems` is a name or an index, never a keyword. A `$ref` segment in keyword position moves the walk to the place its reference names: a same-document reference, `#` or `#/` and a JSON Pointer, is resolved from the root of the same schema JSON, and any other reference ends the walk with no place (B-009; decision 0004). Each `$ref` resolves one pointer and the walk takes one step per segment, so it ends with the evaluation path and a reference cycle cannot loop it. At the place, each keyword the detail's errors name that is a Validation-vocabulary assertion or `format` is copied with its value there, in the schema's order. An applicator, a boolean `false` place and a place the walk cannot reach give an empty `constraints`.
- **Why the evaluation path and not the schema location.** Only the evaluation path says whether the place was reached through a condition: the schema location is where the place is written, which a `$ref` from inside an `if` or a `not` leaves outside it. The schema location is also not a pointer the walk can always follow: under an `allOf` member, JsonSchema.Net `9.4.0` writes an index after `if`, `then` and `not` (`#/allOf/0/then/0`, `#/allOf/1/not/1`), which names nothing in the schema; a top-level `if` or `then` gets none (`#/then`).
- **`SPEC010` and `SPEC013`** ([`SectionStructureRule`](../../Rules/SectionStructureRule.cs)): each of the three `SPEC010` branches carries `sections`, the `Structure.Sections` list the rule checked (B-010). Both `SPEC013` branches carry `section`, the title `Structure.Roles` gives the role and the violation's identifier, and `headers`, the list `Structure.Tables` gives the role (B-011). Each violation gets its own object, because a JSON node has one parent.

**Identity and traceability expectations (item `0038`; decision 0005).** These existing rules set their own fresh `JsonObject` at each violation site; their guards, messages, positions, ordering and verdicts stay unchanged.

- **`SPEC011`**: `form` is the manifest's `identifiers.epic` or `identifiers.feature` grammar; `value` is the containing directory's identity prefix. To support a grammar whose identity contains a hyphen, examine prefixes ending before each hyphen in order and take the first matching the whole grammar; if none matches, take the literal prefix before the first hyphen (or the whole directory without one). This derives an expectation without adding validation.
- **`SPEC012`**: `form` is `{epic}-{feature}`; `value` is the reused qualified identity; `firstDeclaration` is the first Feature's root-relative path in the group's existing model order, even when the message's sorted path list starts elsewhere.
- **`SPEC043`**: an item id mismatch uses the task identifier grammar as `form` and the already parsed filename id as `value`; a parent mismatch uses `{epic}-{feature}` and the containing Feature's qualified identity.
- **`SPEC020`** requires `companionCount: 1`. **`SPEC021`** lists `claims`, the existing `SpecClaims.Ids` keys: distinct valid declarations in declaration order, with no invalid or repeated ids.
- **`SPEC030`** carries the evaluated `grammar`; only a duplicate adds `firstDeclarationLine`, already derived by `SpecClaims`.
- **`SPEC031`** carries `requiredRows: 1` and `rowsByClaim`. Every distinct valid declared claim appears once in declaration order with its matrix row count, including zero. The same complete map accompanies missing, duplicate and undeclared-row violations; undeclared matrix ids are excluded. Build each map from the rule's existing row index so no second parser or report-level derivation is needed.

**Item, dependency and approval expectations (item `0039`; decision 0006).** Each existing violation site owns a fresh object. No guard, message, diagnostic location, identifier, count, ordering or verdict changes. `SpecReportDocument.From` remains the existing copier; the golden report and diagnostic lines do not include these members.

- **`SPEC040`, `SPEC041`**: `fileName` is `<declared>-*.md` for missing and ambiguous declarations; a spike declaration also carries `type: spike`, including the wrong-type branch. The file shape is not a new validation rule.
- **`SPEC044`**: a reused id carries `fileName: <id>-*.md` and `firstDeclaration`, the same root-relative path the existing first-holder dictionary uses. A sequence violation carries `fileName: <epic>-<nextNumber padded to two digits>-*.md` and integer `nextNumber`, the existing loop's expected number. Even the baseline's duplicate-induced sequence diagnostic is preserved.
- **`SPEC050`**: `features` is the graph's distinct qualified identity set, sorted with `StringComparer.Ordinal`; include the source Feature, since the graph already reports self-reference separately.
- **`SPEC051`**: `edge` names the target as `feature`, the opposite frontmatter edge name as `key`, and the source's qualified identity as `value`. Both directions reuse the graph's already resolved identities.
- **`SPEC052`**: `cycle` copies the diagnostic's existing ordered path, including any lead-in and repeated closing node. A direct self-reference uses the qualified identity twice; both existing self-reference diagnostics remain.
- **`SPEC060`**: `section` is the selected matrix title; integer `row` is the one-based body-row index; `columns` holds every one-based cell position whose trimmed value equals the effective missing marker. One diagnostic still covers a row with several missing cells.
- **`SPEC061`**: `section` is the selected sign-off title and integer `row` is its one-based body-row index. The existing scan for the effective draft or blocked marker remains; this change decides no header interpretation or new approval policy.

**The JSON.** `ToJson()` serializes the record itself with `System.Text.Json`: camelCase members in declaration order, enums as camelCase strings (`embedded`, `error`, `warning`), a layout's name as the manifest writes it (`epics` and `features` under the default manifest, `0001-F6` decision 0008), indented with `\n` whatever the platform, and an absent `identifier` omitted rather than written as `null` - the conventions the engine's earlier anonymous report already used, so a reader of that output meets the same names. No member is computed at serialization time.

```json
{
  "schemaVersion": "0.1.0",
  "schemaSource": "embedded",
  "layouts": [
    { "layout": "epics", "specificationCount": 2 },
    { "layout": "features", "specificationCount": 1 }
  ],
  "itemCount": 0,
  "rulesEvaluated": 21,
  "errorCount": 1,
  "warningCount": 0,
  "violations": [
    {
      "ruleId": "SPEC031",
      "severity": "error",
      "file": "epics/0001-epic/F1-feature/spec.md",
      "line": 0,
      "identifier": "B-002",
      "message": "...",
      "expected": {}
    }
  ]
}
```

**The run summary (`0001-F2` B-002, item `0028`).** `SummaryLines()` formats the four lines the check prints after its violations - the specification count per layout, the item count, the rules evaluated, and the error and warning counts - from the document's own B-005 members, so the summary and the JSON cannot count differently. A layout is named as the JSON carries it, by its name in the manifest (`epics 2, features 1` under the default manifest), and the layouts keep the document's order.

**The published schema (A-1, C-1).** [`docs/schema/report.schema.json`](../../../../docs/schema/report.schema.json), draft 2020-12, names every member above. `schemaVersion` is a string matching three dot-separated decimal numbers with no leading zero, the texts `SemanticVersion` writes; it was `type: integer` until item `0120`, and whether C-4 binds that change of type before a first package is published is OQ-5. The document, each layout entry and each violation are closed (`additionalProperties: false`), so a field the schema does not name fails validation; `expected` is `type: object` and nothing more, so a rule family adds members to it without a schema change (C-2, C-4). A layout entry's `layout` is a non-empty string, the layout's name in the manifest, where it was the enum `legacy`, `coLocated` until item `0005` (`0001-F6` B-009). A violation's `file` rejects a leading `/`, a drive letter and any `\` (B-021). The schema carries no `$id`: JsonSchema.Net registers a schema by its `$id` in a process-wide registry and refuses a second registration, which every caller loading the file twice in one process would hit. Both test projects copy `docs/schema/*.json` into their output and validate a produced document against that one file (B-008).

**One writer, one shape.** [`SpechtRunner.WriteReport`](../../SpechtRunner.cs), an instance member that writes through the runner's injected `IFileSystem` since item `0107`, wrote its own anonymous object, `generatedAtUtc` from `DateTimeOffset.UtcNow` among it, which no command calls today. It now writes `SpecReportDocument.From(report).ToJson()`, so the only document the engine can write carries no timestamp and validates (B-006, B-008). Where `--report` writes, and how it replaces a file, is `0036`'s.

**Root-relative paths (B-021).** [`SpecModelLoader`](../../Model/SpecModelLoader.cs) owns the private root-relative mapping until ADR-0010 stage 6. Companion snapshots carry relative paths before evaluation; the feature-file rule maps nothing. `SpecPath` is deleted. The report retains paths from the findings unchanged, pinned by loader and report tests (§ 8).

**`--json` (item `0035`).** [`CheckCommand.ExecuteAsync`](../../../tool/Features/Check/CheckCommand.cs) branches once on `--json`: it makes `SpecReportDocument.From(report)` once, the same document the summary is drawn from, and writes either `ToJson()` or the violation lines and `SummaryLines()`. The document goes whole through `console.Profile.Out.Writer`, the raw writer, so no markup parsing or line wrapping touches it and stdout parses as one JSON document (B-001). The verdict fold after the branch is unchanged, so `--json` never moves the exit code (C-5), and a missing root or an unreadable manifest still returns before anything reaches stdout.

**The rule pages (item `0129`; decision 0003).** A page is a Markdown file at [`docs/rules/v0.1.0/`](../../../../docs/rules/v0.1.0/), under the repository root's `docs/` and not under the engine's project, named for its rule id, `SPEC031.md`, in the folder of the schema version it ships under (A-4). Schema version `0.1.0`, the version folder `v0.1.0` holds, has twenty-one, one per id in its vocabulary (`SchemaVersions.Shipped`, `0001-F7` § 7). Each is typed by hand in the one page shape (B-032), and its Metadata table's Schema version is the folder's number (B-033): the folder and that row keep the integer until `0001-F7` item `0126` renames them (`0001-F7` OQ-22). A page is terse because it is the text `--explain` will print: a one-sentence Cause, then a table of condition and message where the rule reports more than one; what is expected in a sentence or two; the smallest fragment that triggers the rule with the line it prints, and the fixed fragment; one bullet per condition under the fix. A guard stays only where a reader would otherwise be misled, and what a rule does not check is left unsaid.

**Why Markdown files and not strings in code.** A page is prose with tables and fenced examples. As a file it is formatted by the same pinned formatter as every other Markdown file here, it reads on the repository host as it stands, and a change to a rule's text is a diff of that text. As a string literal it would be none of those, and a descriptor type to hold it is the alternative decision 0003 turned down. The cost is that nothing ties a page's words to the rule's code: each Cause was written from the `new SpecViolation(...)` call sites in [`src/specht/Rules/`](../../Rules/), with messages quoted from them and `{name}` standing for each interpolated value, and each example's printed lines were taken from a run of the built tool over a tree holding that example, run again after item `0015` moved the section titles and markers into the manifest and again when the pages were shortened. Every example is an excerpt of such a tree, and the lines under it are every line the tool printed for that rule over that tree, message and line number both. Where the excerpt is the top of a file, the tree's file opens with those same lines, so the number is also the excerpt's own; where it is a table row, a heading or a scenario tag, the number is the tree's. A page names what the manifest sets - the claims, matrix and sign-off sections under `roles`, the contracted headers under `tables`, the claim grammar under `identifiers`, the `Missing`, draft, blocked and approved values under `markers` - by its key and gives the default manifest's value, because the messages themselves keep `§ 3`, `§ 9`, `§ 12`, `'Missing'` and `'approved'` as fixed text. SPEC002's Cause also says that a `null` `scored_by` or `github_issue` adds two lines each beside any real failure: `FrontmatterSchemaRule.Failures` reports the unmet `if` subschemas of the Feature schema's `allOf` as failures, and the page is written to that output, not to a corrected one. Its example is a specification with both keys set, so that it prints the two lines of the real failure and no others. A rule whose message or guard changes needs its page changed in the same pull request; no test says so.

**How the pages are embedded.** [`specht.csproj`](../../specht.csproj) embeds `..\..\docs\rules\v*\*.md`, linked from outside the project as the frontmatter schemas are from the tool's, with the logical name `rules/v<major.minor.patch>/<file>`, built from `%(RecursiveDir)` as the schemas' `schema/v<major.minor.patch>/<file>` names are, so a version's schemas and its pages sit under the same number in the engine's manifest resources. The files are `EmbeddedResource` items only: they are not `Content`, the repository-wide `Content` globs in `Directory.Build.props` match `.spec` and `.issue` folders and not `docs/rules`, the glob names `docs\rules\v*` and so takes nothing else under `docs/`, and `src/specht` does not pack. The package therefore carries the pages inside `specht.dll` and nowhere else.

**How the pages are gathered (B-031).** [`SchemaVersions.ReadEmbedded`](../../Versioning/SchemaVersions.cs) already finds the embedded folders from the `schema/v<major.minor.patch>/` resource names. For each folder it now also takes every resource whose name starts `rules/v<major.minor.patch>/` and fills [`SchemaVersion.RulePages`](../../Versioning/SchemaVersion.cs) with it: the key is the file name without its extension, the value the whole text, frontmatter included. The local `Read` takes a resource name where it took a number and a schema file name, so the schemas and the pages share it. From item `0126` the folder's `major.minor.patch` segment is parsed directly with `SemanticVersion.TryParse`, so the folder and the version's `Number` are the same version; no mapping supplies it. Each page's Schema version row gives that number as `major.minor.patch` (`0.1.0` for the current set). `--explain` (`0040`) reads the map; nothing else names a resource.

**Why the map is not filtered by the vocabulary.** The gatherer puts in every page embedded under the version's folder, whatever its file is called. B-031 says the pages name exactly the vocabulary, and that is a statement the tests compare: `RulePages.Keys` against `RuleIds`. A gatherer that kept only the ids in `RuleIds` would make the "no page outside the vocabulary" half true by construction, and a stray `SPEC099.md` would ship unseen. Unfiltered, a stray page is a key the comparison rejects. The one page the map cannot show is one under a number with no schemas, `rules/v0.2.0/` beside no `schema/v0.2.0/`, because no `SchemaVersion` exists to hold it; the embedded-Markdown count in § 8 catches that.

**What a page does not carry.** No part on turning a rule off or re-grading it (§ 5 row 8): the word for a rule's grade appears once on a page, in the Metadata row, and every page gives `Error` there because every `SpecViolation` the engine makes is `SpecSeverity.Error`. No absolute path, and no date, author or machine name of the page's own (C-8): every example path is root-relative, and example frontmatter is cut down to the keys the example is about, which leaves the date and author keys out.
