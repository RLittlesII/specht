# Specification: The manifest carries the roles

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

Half of the model's contract is not in the schema files: which section holds the claims and which the matrix, what `Missing`, 🟡 and 🔴 mean, which frontmatter key is the parent and which the edge, how an item's number is read. Those are string literals in the engine, invisible to whoever is held to them and unchangeable without forking it. This Feature removes that failure state: every such literal is read from the manifest the engine already loads, a rule reads a role, and the default manifest reproduces `hooked`'s baseline verdicts, so a repository brings its own schema and `hooked` notices nothing.

## 2. User Needs

<!-- last written by: spec-author, 2026-10-09 (need 6 added, decision 0004), 2026-10-10 (A-4 amended: the `rules` key is no default, B-044) -->

| #   | Persona                                      | Need                                                                                                     | Pain Point Today                                                                         |
| --- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1   | The maintainer of a sibling repository       | Rename a section, a marker or a key in the manifest and have the same rules follow                       | Each is a `const string` in a rule; renaming means a fork                                |
| 2   | Transporter, a tree the schema did not write | Lower or disable the rules its pre-schema tree cannot yet pass, and promote them as the tree is repaired | All-or-nothing: every rule is an error                                                   |
| 3   | The agent reading a violation                | A message that spells the key and the section as the manifest it is editing does                         | The message names `hooked`'s literal                                                     |
| 4   | `0001-F6`                                    | The manifest as the one place a layout, an exclusion or a file shape is declared                         | N/A (internal dependency)                                                                |
| 5   | `0001-F7`                                    | A manifest with a shape a version can be pinned on                                                       | N/A (internal dependency)                                                                |
| 6   | A repository of standalone Features          | Check Features that belong to no epic, each identified by its `id` alone                                 | `epic` is required, and a Feature without one is skipped by the identity and edge checks |

### Assumptions

| ID  | Assumption                                                                                                                                                                                                                                                                                                      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | The manifest keeps its file name and place, `.spec/schema/spec-structure.schema.json`; it gains keys, in the same change that teaches the engine to read them, and this repository's live copy is amended in that change.                                                                                       |
| A-2 | Each literal moves one rule at a time, each move with a test that the default manifest reproduces the baseline verdicts (brief § 8 step 5). That is a delivery rule and lives in the skills; here it is B-016.                                                                                                  |
| A-3 | The exact key names in the manifest for roles, markers, keys and rule settings are the `implementer`'s to propose in § 7 and the spec-author's to ratify as a decision record. See OQ-1.                                                                                                                        |
| A-4 | The default manifest is `hooked`'s manifest at the baseline commit with every key this Feature reads declared at the value `hooked`'s engine hardcodes; this repository's own manifest is it, less its `rules` key, which holds this repository's own rule settings and is no default (B-044; `0001-F4` B-004). |
| A-5 | Until `0001-F7` lands the engine reads the frontmatter schemas from `<root>/.spec/schema/`, as `hooked`'s does; after it, that is the on-disk source `0001-F7` B-009 selects. "The on-disk source" here means both.                                                                                             |

## 4. Constraints

| C-1  | A rule reads a section, a marker, a key name or a path through a manifest role; no such literal lives in a rule.                                                                                | A `private const string` section title or marker; `"epics"`, `".spec"` or `"epic.md"` in a rule; a message that spells a key the manifest could rename.                                                                                                                                     |

## 7. Technical Design

<!-- last written by: implementer, 2026-10-10 (item 0014: rule settings as built, restated after B-043, B-044, the amended B-017, B-019 and A-4, and the merge of item 0106; the default's source, the `IFileSystem` seam and the unreadable manifest as the code stands) -->

The literal each claim moves is cited by file and line in `hooked`'s draft `0008-F3` § 3 (`hooked@a6d056f:tools/SpecGovernance/.spec/README.md`, `0001-F1` A-2).

**The loader (item `0011`).** [`SpecManifest`](../SpecManifest.cs) is the one reader of the manifest. `Load(IFileSystem, root)` reads `<root>/.spec/schema/spec-structure.schema.json` as a `JsonObject`, collects every top-level key that neither begins with `$` nor is one the engine knows (`schemaVersion`, the five discovery keys `layouts`, `exclusions`, `taskFiles`, `epicFiles` and `companionFiles` that item `0005` added (`0001-F6` decision 0004), `sections`, `tables`, `identifiers`, `frontmatterSchemas`, from item `0015` `roles` and `markers` and, from item `0014`, `rules`), and throws [`SpechtManifestException`](../SpechtManifestException.cs) naming all of them, with the manifest's repository-relative path, before it builds anything. It then returns the [`SpecStructure`](../SpecStructure.cs) the rules already read, so no rule changed.

**Filling an omitted value (B-019).** A top-level key the manifest leaves out reads as the default manifest's value. Inside `identifiers` the fill is per grammar: a grammar is read by name, so a manifest declaring some grammars gets the default for the rest. `sections` and each `tables` entry are replaced whole, because a section list or a header row is one value, not a set of defaults to merge into; each of the five discovery keys is one value too, so a declared `layouts` or `exclusions` replaces the default list (`0001-F6` C-7). `rules` is the one known key that is never filled: B-019 does not list a rule setting, and an omitted one is B-044's ("The default-manifest leak" below). Later families choose their own granularity as they add their keys.

**The frontmatter schema file names (item `0017`, B-008, [decision 0003](decisions/0003-the-frontmatter-schema-file-names-are-one-key-by-kind.md)).** `frontmatterSchemas` is a top-level object keyed `feature`, `task` and `epic`, each value a file name under `<root>/.spec/schema/`. `SpecManifest.Load` fills it per kind from the default manifest, by the same per-name fill `identifiers` uses, and sets it on [`SpecStructure.FrontmatterSchemas`](../SpecStructure.cs). The on-disk `SpecSchemas.Load(IFileSystem, root)` reads each kind's schema by that name, `task` into `Item`. The key ships in this repository's live manifest and the embedded `v1` manifest, so it is tool-owned (`0001-F4` decision 0001). The names are read only on that on-disk path (C-9): `SpecSchemas.Load(IFileSystem, root, SchemaVersions)`, the path the runner takes, reads the pinned version set's schemas and ignores them.

**The default manifest has one copy (A-4).** `src/specht/specht.csproj` embeds this repository's own `.spec/schema/spec-structure.schema.json` as the resource `specht.default-manifest.json` - a link to that file, not a copy of it, so the default cannot drift from the manifest this repository checks itself with. It is read once per process and only ever supplies omitted values; a root without a manifest still fails on the read (C-6), exactly as it did. The default is that file less its `rules` key (A-4): the resource carries the key, as the live file does, and the loader never reads it from there. Item `0051` embedded the `v1` shipping copy and did not move this source, so the default is still the live file. A rule setting this repository chooses there (item `0062`) therefore reaches no consumer ("The default-manifest leak" below). Any other key this repository set to its own preference would, since every other known key is filled from the resource, and a default must hold `hooked`'s values (C-4); the item that first wants such a key moves the source first.

**Validation before any rule (B-018, C-5).** [`SpecSchemas.Load`](../../Model/SpecSchemas.cs) calls `SpecManifest.Load` before it reads a frontmatter schema, and [`SpecModel.Load`](../../Model/SpecModel.cs) loads `SpecSchemas` before it discovers or parses the tree. A rejected manifest therefore leaves `SpechtRunner.Run` before any discovery, parse or rule, and no report exists. Against an accepted manifest the model, the rules and the report are unchanged; only the order of the reads moved.

**The `IFileSystem` seam (owner direction 2026-10-08; [ADR-0001](../../../../.spec/adr/0001-resolve-the-engine-from-the-container.md)).** File access goes through `System.IO.Abstractions` (`TestableIO.System.IO.Abstractions.Wrappers`). `SpecManifest.Load` and `SpecSchemas.Load` take the `IFileSystem`; `SpecModel.Load` passes `new FileSystem()`. Item `0011` deferred the rest, each to the item that first needs a test double there:

- Since then [`SpecDiscovery`](../../Discovery/SpecDiscovery.cs) and [`FrontmatterReader`](../../Model/FrontmatterReader.cs) take the `IFileSystem` too, handed the one `SpecModel.Load` creates. Still on `File` and `Directory`: `SpecModel.Load`'s read of each specification for `SpecDocument.Parse`, `FeatureFileReader`, and `SpechtRunner.WriteReport`. Item `0011` held that threading the abstraction through them was a change across the copied engine with no claim asking for it, and that an overload of `Run` taking an `IFileSystem` only the manifest honoured would be a seam that lies. ADR-0001 supersedes that deferral: it is the ask, and its stage D threads `IFileSystem` through the readers, the parser's caller, the walk and the loader, proven against the baseline (`0001-F1` C-9).
- The host registers no `IFileSystem` service: `Program.cs` hands `InitWriter` a `new FileSystem()` inside that one registration, and no command takes one. That stays true until stage D, whose `AddSpechtEngine()` registers the readers and the loader that take an `IFileSystem` by constructor. `CheckCommand` is where the host meets the loader: it folds `SpechtManifestException` and `SpechtManifestUnreadableException` to exit `3` and stderr (item `0013`).

**What 0011 does not reject.** A manifest that does not parse, or a known key of the wrong shape, is not one of this Feature's rejections and names no key: `SpecManifest.Load` wraps the library's exception in [`SpechtManifestUnreadableException`](../SpechtManifestUnreadableException.cs), the unreadable manifest, which the command also folds to exit `3`. Each family owns its rejections. Three are built and described below: roles, `tables` keys and markers (item `0015`), the exclusion entry (item `0019`, B-021 under "The rejections at load") and rule ids and levels (item `0014`, "Where rule settings apply"). Grammars (B-014, item `0016`) are not built.

**Where rule settings apply (item `0014`; B-010, B-011, B-013, B-017, B-042, B-043, B-044). Built.** The key and its values are ratified by the owner ([decision 0007](decisions/0007-rule-settings-are-one-rules-key-mapping-a-rule-id-to-a-level.md), OQ-1's part for rule settings); the shape is [ADR-0002](../../../../.spec/adr/0002-no-chain-of-responsibility-for-the-check.md)'s, [ADR-0004](../../../../.spec/adr/0004-per-rule-settings-are-selection-and-a-map.md)'s and [ADR-0008](../../../../.spec/adr/0008-evaluate-takes-the-rule-set-and-the-model-carries-the-vocabulary.md)'s. A consumer writes:

```json
{ "rules": { "SPEC010": "warning", "SPEC031": "off" } }
```

**The member and the read.** [`SpecStructure`](../SpecStructure.cs) gains one `init` member, `Rules`, a dictionary from rule id to level with an empty ordinal default, in the idiom of `Roles` and `Markers`. The level stays the text the manifest writes. `off` is not a severity, so `SpecSeverity` cannot hold the three, and a type for them would have the check and two functions as its only readers. [`SpecManifest`](../SpecManifest.cs) adds `rules` to `KnownKeys` and reads it with one private function, `Levels`: an absent key is an empty dictionary, a text value is itself, and a value that is not text is kept as the JSON the manifest writes for it, so that `Check` can name it. A `rules` value that is not an object fails as any known key of the wrong shape does, as an unreadable manifest.

**The rejections.**

| Claim | Fault                                                                                  | Where                                                                                                                                 | The message, after the manifest's path and a colon                                                                          |
| ----- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| B-042 | a level that is not exactly `error`, `warning` or `off`, compared ordinally            | `SpecManifest.Check`, after the exclusion entries: one fault per entry, in the manifest's order, in the one `SpechtManifestException` | `the rule 'SPEC010' in rules is set to 'loud', which is not 'error', 'warning' or 'off'`                                    |
| B-017 | a value that is not text: an object naming a type and a library, a number, a JSON null | the same fault; the JSON kept for the value is never one of the three levels                                                          | the same, the value being that JSON, such as `'{"type":"Consumer.Rules.MarkingRule","library":"rules/consumer-rules.dll"}'` |
| B-013 | a rule id outside the pinned version's vocabulary                                      | `SpecSchemas.Pinned`                                                                                                                  | `rules names the rule id 'SPEC999', which schemaVersion 0.1.0 does not hold`, every such id in one message                  |

A declared rule is rejected as a level because reading it as text is what must not happen: the readers the other keys use call `GetValue<string>`, which throws for an object, and `Load` wraps that as an unreadable manifest that names no id. `Levels` never asks a value that is not text for its text.

**What loads a rule (B-017, C-3).** Nothing under `rules` is loaded or run, and nothing a manifest names can be. `SpechtRunner.Run` hands `Evaluate` [`SpecRules.All`](../../Rules/SpecRules.cs), a hand-written list of eight `new` expressions that takes no argument (item `0106`, ADR-0001 stage C, which removed `SpechtRunner.Discover` and the engine's one `Activator.CreateInstance`). `Evaluate` runs the rules it is handed and reads the manifest's `rules` only as the dictionary of texts `Enabled` and `Graded` look a rule id up in. The engine creates no type by name and loads no assembly; it names `Assembly` only to read its own embedded resources, the default manifest and the version set. So a rule that is not on that list does not run, whatever a manifest holds.

**Why the vocabulary check is in `SpecSchemas`.** `SpecManifest.Load` reads `schemaVersion` as a version number and does not know which rule ids that version holds: the version set that answers is an argument of [`SpecSchemas.Load`](../../Model/SpecSchemas.cs). `Pinned` is one private function that both `Load` overloads call where each called `Select` on the version set: it selects the pinned version, which rejects a pin the set does not hold, and then rejects every id under `rules` that the version's `RuleIds` lacks. It is a function both overloads call, and not a statement in the private constructor they share, because the on-disk overload reads the three frontmatter schema files before it constructs, and a rejection of the manifest belongs ahead of them, beside the unshipped pin's. Each overload has its own unit test of the rejection (§ 8), because one private function with two call sites is pinned per call site. Both rejections are thrown by the load, so no rule has run (C-5).

Two functions reject, so a manifest with a faulty level and an id outside the vocabulary is told of the level, and of the id on the next run. B-012 and the `schemaVersion` check already stand ahead of `Check` in the same way.

**Resting on OQ-13 (open, owner not asked).** Both proposed defaults are built. (a) `Warning` is rejected: the comparison is ordinal, and a test row pins it. (b) A value that is not text is named as the manifest writes it, its JSON; no test pins that. If either is answered otherwise, (a) is the one comparison in `Check` and (b) the one expression in `Levels`.

**Selection and the map.** Both are in [`SpechtRunner.Evaluate(SpecModel model, IEnumerable<ISpecRule> rules)`](../../SpechtRunner.cs), the signature ADR-0008 gave it in place of the `Evaluate(SpecModel)` ADR-0004 names. Both read `model.Schemas.Structure.Rules`; `Evaluate` gains no parameter and reads no static.

- **Selection** is the private function `Enabled`: the pinned vocabulary less the ids set `off`. That one set replaces the vocabulary in the three places ADR-0008 put `0001-F7` B-014's filter: the rules run, the violations kept, and the count of rule ids evaluated.
- **The order of the two filters, which ADR-0008 left to this item:** the vocabulary first, selection over it. They are one set, built once, so an id outside the vocabulary is never enabled whatever the settings hold, and B-013 has already rejected a setting that names one.
- **Per id, not per class.** A rule whose every reported id is `off` is never asked for its violations. A rule that reports two ids with one of them `off`, as [`SectionStructureRule`](../../Rules/SectionStructureRule.cs) reports `SPEC010` and `SPEC013`, still runs: that id's violations are dropped and it leaves the count (B-011). `ISpecRule` has one `Evaluate`, so for such an id "not evaluated" is what the report shows, not what the class executed.
- **The map** is the private function `Graded`, applied to each kept violation as it is collected, before `SpechtRunner.Order`, because that function sorts by severity first (B-010). An id set `warning` carries that severity (B-010) and so does an id set `error`, which raises a finding the rule gave at warning (B-043); an id `rules` gives no level keeps the severity the rule gave it (B-044). Each of the three arms has a unit test (§ 8). No shipped rule gives a warning, so B-043 is seen only where a rule can be handed in, `Evaluate`'s second argument, until epic `0101`'s first rule exists.

The sort still runs once, so the report stays independent of evaluation order (`0001-F1` C-9). Per-rule settings are selection and a map however many accumulate: no chain of handlers, decorator, stage list, rule-set filter or context object (ADR-0004). A rule's default severity and first schema version become `ISpecRule` members with epic `0101`'s first item, not before; the member is a fact about the rule, not a switch (`0101-F1` decision 0001), and the manifest's rule settings override it, which `0101-F1` C-6's wording is owed (ADR-0004). `CheckCommand` is unchanged: it already prints a warning, counts it, fails on it only under `--strict`, and folds `SpechtManifestException` to exit `3` and stderr.

**The default-manifest leak (to item `0062`).** `rules` is read as the manifest writes it and is never read from the embedded default: `Levels` takes the manifest's own node and nothing else, so an absent key is no settings (B-044). B-019 does not cover a rule setting, and A-4 leaves the key out of the default. It is not filled because the embedded default is a link to this repository's own manifest ("The default manifest has one copy" above). Item `0062` lowers `SPEC060` to a warning there, and a fill per entry would hand that setting to every consumer whose manifest leaves it out, against C-4 and decision 0007 call 2. As built, item `0062`'s edit changes this repository's verdicts and no consumer's, and it owes no engine code. What it meets is on the item: the file it edits is also the embedded default and the manifest the acceptance scenarios of this Feature and `0001-F6` start from, so the baseline proof (B-016) reads it less its `rules` key, and B-044's second half gains its first case that can fail. Until then that half is a guard no committed test can break: the resource carries `"rules": {}`, and `SpecManifest.ReadDefaults` reads it into a private static with no seam, so no test can hand the loader a default that sets a level (§ 8). No seam is added for it: its one caller would be that test. A later item that fills `rules` from a default must first move the default's source off the live file.

**The shipping copies.** This repository's live manifest gains `"rules": {}` as its last key (A-1). Because B-015 and B-040 walk the names the default manifest declares, each reaches a name in the move that adds it to the default: B-015 covers `signOff` from move 5, and B-040 covers `draft` and `blocked` from move 5, which is where the `@B-040` scenario, written on the draft marker, can first go green. `SPEC013` moves last because it is the one move that changes a key the manifest already ships, and B-039's fault lands in that same change and no earlier or later: before it the default manifest's own `tables` key is a section title and would be rejected, and after it without the fault a manifest keyed by title would be read as declaring no headers. In move 6 `SectionStructureRule.CheckTables` walks `Tables` as role and headers and takes the title from `Roles`; B-039 has already guaranteed that every key is a role, and B-015 that its title is one `sections` lists. After move 6, renaming a section touches `sections` and `roles` and nothing else, which is what B-001's scenario and B-002's second scenario write.

**What does not move.** The messages keep `§ 3`, `§ 9`, `§ 12`, `'Missing'` and `'approved'` as text, and `SPEC013` keeps the section title as its identifier and in its message: the golden report compares both (`0001-F1` C-9), and naming the manifest's value in a message is B-009 and item `0018`. `FeatureSpec.SpecStatus` keeps reading `spec_status` (B-004, item `0016`). `SPEC010` already reads `sections`. What each rule asserts is unchanged (C-7): `SPEC060` still matches a whole trimmed cell against the missing marker, `SPEC061` still looks for either sign-off marker inside a cell, and both still compare ordinally.

**The rejections at load (B-015, B-039, B-040; B-041 from item `0005`; B-021 from item `0019`).** One private function in `SpecManifest`, `Check`, checks the built `SpecStructure`, after the fill and before `Read` returns it, so the check is part of the whole-manifest validation no rule runs ahead of (B-018, C-5), and it sees the values a rule would see. It collects faults in a fixed order and, when there is one or more, throws one [`SpechtManifestException`](../SpechtManifestException.cs):

| Claim | Fault                                                          | Walks, in this order                                                                                                        | The fault names                              |
| ----- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| B-015 | a role's title is not in `sections`                            | the default manifest's role names, over the filled `roles`                                                                  | the role, the title it names, and `sections` |
| B-039 | a `tables` key is not one of the default manifest's role names | the `tables` keys, in the manifest's order                                                                                  | the key, and `tables`                        |
| B-040 | a marker's text is empty                                       | the default manifest's marker names, over the filled markers                                                                | the marker, and `markers`                    |
| B-041 | a file-shape list holds no entry                               | `taskFiles`, `epicFiles`, `companionFiles`, over the filled [`SpecDiscoveryInputs`](../../Discovery/SpecDiscoveryInputs.cs) | the key                                      |
| B-021 | an exclusion entry has a `/` inside it and no leading `/`      | the filled `SpecDiscoveryInputs.Exclusions`, in the manifest's order                                                        | the entry                                    |

The message has the shape B-012's has: the manifest's repository-relative path once, a colon, then every fault, each quoting the name it rejects in single quotes, in the order above; the faults are joined by `; `. The `tables` keys are walked as `SpecStructure.Tables` enumerates them, which is the manifest's order because the loader builds that dictionary by insertion and never removes from it. It is one exception and not one per claim because a manifest written before decision 0006 can carry all of the first three faults, and a consumer who is told of one per run edits it three times; B-012 already names every unknown key in one message for the same reason. It is the existing exception type and not a new one because `CheckCommand.ExecuteAsync` already folds `SpechtManifestException` to exit `3` and stderr (B-022, B-023), so the host does not change and no catch is added. Two rejections stay ahead of this one and separate from it, as they are today: the unknown top-level key (B-012) and the `schemaVersion` check both throw before a structure exists to walk.

Three consequences a consumer meets. A manifest that renames a section in `sections` and leaves `roles` out is rejected, because the omitted role reads as the default title (B-019), which `sections` no longer lists. A manifest whose `tables` is keyed by a section title, as every manifest written before decision 0006 is, `hooked`'s included, is rejected from move 6 with that title named (decision 0006 call 3). And a manifest that declares `"tables": {}` is accepted and switches `SPEC013`'s header check off, as it does today: B-039 rejects a key, and there is none.

**The empty file-shape list (B-041, item `0005`, [`0001-F6` decision 0008](../../Discovery/.spec/decisions/0008-the-layouts-are-named-epics-and-features-and-the-file-shape-keys-are-lists.md)).** `Check` reads the three lists from the filled `structure.Discovery`, so an omitted key is the default's list of one and never at fault. The fault reads `the list 'taskFiles' is empty`, with the key in single quotes as the other faults quote a name. The three keys are written as a literal array in `Check`, in the order above, because they are three members of a record and not entries of the default manifest to walk. Nothing else is held to this check: an empty `layouts` or `exclusions` list loads (`0001-F6` OQ-12), and a file-shape key that is a bare string, or a list holding an entry that is not a string, still fails ahead of `Check` as a value of the wrong shape, an unreadable manifest with no key named (`0001-F6` OQ-14; "What 0011 does not reject" above). A list holding only an empty string is not empty and loads. What the tool does in each case is recorded in [`0001-F6` § 7](../../Discovery/.spec/README.md).

**The malformed exclusion entry (B-021, item `0019`, [`0001-F6` decision 0003](../../Discovery/.spec/decisions/0003-a-root-relative-exclusion-begins-with-a-slash.md)).** `Check` walks the filled `structure.Discovery.Exclusions` after the three file-shape lists, so an omitted `exclusions` is the default's list and never at fault. An entry is at fault when it holds a `/` and does not begin with one: the complement of decision 0003's two forms, a name with no `/` and a path beginning with `/`. The fault reads `the exclusion 'build/output' has a '/' inside it and no leading '/'`, one per entry at fault, in the manifest's order, in the same message as every other fault of `Check`. `build/`, a name with only a trailing `/`, is rejected, because it is neither form. An entry beginning with `/` is not held to this check whatever follows, so `/foo/` and `/` load, and as `SpecDiscovery.IsExcluded` reads them today each excludes nothing; no claim covers either. An empty `exclusions` list loads (`0001-F6` OQ-12), and so does an entry that is the empty string, which holds no `/`. [`SpecDiscovery.IsExcluded`](../../Discovery/SpecDiscovery.cs) is unchanged: it never sees an entry this check rejects. No type, exception or catch is added.

**Resting on OQ-10 (open, owner not asked).** The design follows OQ-10's proposed default: a name inside `roles` or `markers` that the default manifest does not declare, such as `roles.constraints`, is kept in the dictionary and never read. Never read includes the check: B-015 and B-040 walk the default's names, so such a name is not held to `sections` and may be empty. It is not thereby a role: `tables.constraints` is rejected under B-039 even beside a declared `roles.constraints`, because B-039 names B-001's roles and those are the engine's. If OQ-10 is answered the other way, the same function gains a fourth fault, a `roles` or `markers` name the default does not declare, and nothing else changes.

**Resting on OQ-11 (open, owner not asked).** B-040 claims the empty text, and the empty text is what is built: `Check` rejects a marker whose filled text has no characters. A text of white space alone is left as written and loads, because no claim rejects it and no test pins either answer; a blank `draft` or `blocked` is then inside almost every sign-off cell, which is the harm OQ-11 asks about. If OQ-11 is answered with its proposed default, that one comparison widens to "empty or white space" and nothing else changes.

**What item `0015` does not reject.** A `roles`, `tables` or `markers` value of the wrong shape, a number or a JSON null where a text is read, fails as any known key of the wrong shape does, as an unreadable manifest and not as one of the three faults. A header list is not checked against anything. A marker that is a substring of another is the consumer's to avoid.

**Epics opt-in ([decision 0004](decisions/0004-epics-are-opt-in-by-the-manifests-epic-grammar.md), B-024 to B-035) and this item.** That change is specified and not built; it merged as text. It reads `SPEC011` and `SPEC012` (`IdentityRule`), `SPEC043` and `SPEC044` (`ChildItemRule`), `SPEC050`-`SPEC052` (`DependencyRule`) and `SPEC004` (`FrontmatterSchemaRule`), and item `0015`'s four classes are `ClaimRule`, `FeatureFileRule`, `ApprovalRule` and `SectionStructureRule`: no rule class is shared, and none of the six rules reads the epic grammar, `epic` or an identity. The move order is unchanged. The one shared file is `SpecManifest.cs`: the amended B-019 stops filling the epic grammar, which changes how `identifiers` is filled, the `Filled(manifest, "identifiers")` argument or `Filled` itself. Item `0015` edits neither and calls `Filled` with a manifest and a key; if that item changes `Filled`'s parameters, the two new calls follow it, a compile error and not a silent change. `roles` and `markers` are filled per name with no exception, since no absent role or marker is a signal. The guard each move runs under, B-016's omission row, is owed an edit by that change, to keep the epic grammar; whichever lands first, the moves need only that it is green.

**As built, where it differs from the design above.** Three small things, none a new type or helper. `FeatureFileRule.ClaimIds` takes the model as its first parameter, as `SectionStructureRule.CheckTables` does, to reach `Roles`. `ApprovalRule` lost its private `NotApproved` function with its two literals: the two marker comparisons sit in the one lambda that called it. And OQ-11's widening was not built, as its paragraph says.

**To `test-writer`.** From move 6 a manifest fixture that keys `tables` by a section title is rejected. `SpecManifestUnitTests`' synthetic `DefaultManifest()` and `AManifestDeclaringATableEntry_WhenLoaded_ShouldReadItInPlaceOfTheDefaultsEntry` both write `9. Traceability Matrix` as that key today; `SpecTree` copies the live manifest and follows by itself.

**Rejected: a list of role and marker names in C#.** A static set beside `KnownKeys` reads plainly. It is rejected because the default manifest already declares every name the engine reads (A-4), so the set would be a second copy that a move could update in one place and not the other. **Rejected: one exception type or one throw per rejection.** Nothing catches them apart, and the first throw would hide the other faults. **Rejected: checking the declared values and not the filled ones.** A role left out while its section is renamed would pass the load and fail inside a rule (C-5). The alternatives to the key names and to re-keying `tables` are decision 0006's, and are not restated here.
