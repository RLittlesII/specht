# Specification: Schema versioning

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-09 -->

A repository's `.spec/schema/` is a copy of `hooked`'s from one day, and nothing says which day, so either every repository moves with `hooked` at once or the copies diverge silently, and a repository that lags cannot catch up on purpose; and a bare version number cannot tell a breaking schema change from a harmless one, so every change forces every consumer into a deliberate upgrade and the owner cannot try one on this repository alone. This Feature removes that failure state: the manifest pins one `major.minor.patch` `schemaVersion`, numbered by whether a tree's verdict can change; the tool embeds every version it has ever shipped and checks with exactly the pinned one; a pin command moves the pin up or down, and `specht upgrade` brings the schema set and the templates to the pin and prints what changed. Lagging becomes deliberate, moving becomes one command each way, the number says whether a move can fail the build, and a document is only ever changed by the agent, from the report.

## 2. User Needs

<!-- last written by: spec-author, 2026-10-09 (A-2 amended, `0001-F5` decision 0004; A-1 to A-3 amended, decision 0005; need 8 added, decision 0006) -->

| #   | Persona                                             | Need                                                                                                 | Pain Point Today                                                                                                                                          |
| --- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | The maintainer of a lagging repository              | Pin a version and stay there until ready; the newest tool still checks it                            | A fork from one day, with no version to name                                                                                                              |
| 2   | The maintainer moving a repository                  | One command that brings the schema set and templates to the pinned version and says what changed     | Hand-copy, then diff by eye                                                                                                                               |
| 3   | The agent migrating documents                       | After an upgrade, the check reports what each document is missing, with what the rule expected       | Nothing says what changed between versions                                                                                                                |
| 4   | A maintainer trying a schema edit locally           | Point the check at the on-disk schema files instead of the embedded ones, deliberately               | The on-disk copy is the only copy, so a hand edit is silently authoritative                                                                               |
| 5   | `0001-F4`                                           | The embedded version set and the newest version number to write                                      | N/A (internal dependency)                                                                                                                                 |
| 6   | `0001-F3`                                           | The version and the source to name in the report                                                     | N/A (internal dependency)                                                                                                                                 |
| 7   | The owner trying a schema change on this repository | A version number that says whether a change can fail a tree, and a pin that moves up or down         | An integer version cannot tell a breaking change from a non-breaking one, so every change forces every consumer into a deliberate upgrade (decision 0005) |
| 8   | A maintainer with a template of its own             | Keep that template across `upgrade`, and still get the pinned version's copy of every other template | `upgrade` rewrites every template with the pinned version's; the frontmatter schemas have an opt-out (B-029) and the templates have none (decision 0006)  |

## 7. Technical Design

<!-- last written by: implementer, 2026-10-10 (item 0120: the version is `major.minor.patch`; the folder-to-version mapping) -->

**A version number is three integers (item `0120`, decision 0005).** [`SemanticVersion`](../../specht/SemanticVersion.cs) is a value of major, minor and patch. It compares by major, then minor, then patch, each as a number, so `0.10.0` follows `0.9.0`; two versions are equal when all three are; it writes itself as `major.minor.patch` in the invariant culture. `TryParse` accepts text that is exactly three parts separated by dots, each part a non-negative decimal integer, and nothing else. The engine declares the type itself. A versioning package would be a dependency outside the five `0001-F1` C-7 names, for one comparison and one parse; `System.Version` reads `0.1` and `0.1.0.0` as versions, which B-039 rejects.

**What `TryParse` does with input no claim names.** These are design choices, not claims (§ 8 lists them as untested), and each is the narrowest reading of "three numbers":

| Input                                                   | Read as       | Why                                                                                                                 |
| ------------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------- |
| A prerelease or build suffix, `0.2.0-beta.1`, `0.2.0+5` | not a version | The last part is not a number. No special handling and no message of its own; OQ-15 decides whether it becomes one. |
| A part with a leading zero, `0.01.0`                    | not a version | A part must be the text its number writes, so one version has one spelling and a pin written back is the pin read.  |
| A sign, `+0.1.0`, `0.-1.0`                              | not a version | A part is digits only.                                                                                              |
| Whitespace around the text or a part                    | not a version | Nothing is trimmed.                                                                                                 |
| A part too large for a 32-bit integer                   | not a version | The part does not parse.                                                                                            |
| An empty part, `0..1`, or digits outside ASCII          | not a version | The part does not parse.                                                                                            |

**A version is data (item `0042`).** [`SchemaVersion`](../../specht/SchemaVersion.cs) is one shipped version: its `Number`, a `SemanticVersion` from item `0120`; the text of its three frontmatter schemas; and the rule ids its vocabulary holds. [`SchemaVersions`](../../specht/SchemaVersions.cs) is a set of them, ascending by `Number`. `Select(version)` returns the member whose number equals `version` or throws [`SpechtManifestException`](../../specht/SpechtManifestException.cs) with the manifest's repository-relative path, the pinned version and every shipped version, each as `major.minor.patch` (B-003) - the same exception a rejected manifest key throws, so `CheckCommand`'s existing catch already writes it to stderr, leaves stdout empty and exits `3`; no command changed. The set takes its versions by constructor, so a test builds `0.1.1` or `1.0.0` in memory from the embedded `0.1.0` rather than shipping a second schema file.

**A pin is exact (B-055).** `Select` compares for equality and nothing else: over `0.1.0`, `0.1.1` and `0.2.0`, a pin of `0.1.0` is `0.1.0`. No range, no "newest patch", no fallback is read anywhere; a pin policy is item `0124`'s, and it will be a second input to the selection, not a change to what equality means.

**The embedded set (B-004).** `SchemaVersions.Embedded` reads the engine's manifest resources named `schema/v<n>/<file>`, one version per distinct `n`, and fills each version's slots from `feature-spec`, `task` and `epic.frontmatter.schema.json`. The resources come from the tool's shipping copy (`0001-F4` C-2, item `0051`): `src/specht/specht.csproj` includes `..\specht.tool\schema\v*\*.frontmatter.schema.json` as `EmbeddedResource` under the logical name `schema/v<n>/<file>`, the scheme `src/specht.tool/specht.tool.csproj` already uses. Owner decision, 2026-10-09: the engine **links** those files. Moving them into the engine would move `0051`'s shipping copy out from under `init`; copying them would be a second copy to drift; having the tool inject them into the engine would put a seam with one caller in front of the check. The manifest under `schema/v1/` is not linked: the check reads only the on-disk manifest (C-4).

**The folder is not the version (item `0120`; temporary).** Decision 0005 made the version `major.minor.patch`, and the embedded folder, the `$id` segment and a rule page's `Schema version` row still carry the integer `v1`: what they are renamed to is OQ-22, and the rename is item `0126`. Until then one private switch in `SchemaVersions`, `Shipped(folder)`, says which version a folder holds: folder `1` is `0.1.0`. It is the switch that already carried the rule vocabulary, so a folder is given its version and its vocabulary in one arm, and a folder with no arm still fails on first read. `SchemaVersion` carries no member for the folder integer: nothing in the engine or the host reads it after the set is built, and it would be a member item `0126` deletes. A test that needs the folder finds it by schema text (§ 8). `init` still picks the newest shipping copy by folder integer (`0001-F4` § 7); that is a choice among folders, not a read of a schema version, and item `0120` does not touch it. When `0126` lands, the mapping goes with the integer.

**The rule vocabulary is written per version.** Version `0.1.0`'s twenty-one ids (brief § 4) are a hand-written list inside `SchemaVersions.Shipped`, in the arm of the folder that holds that version; an embedded `schema/v<n>/` with no arm fails on first read rather than checking with an empty vocabulary. Rule discovery is still reflection over the assembly. Item `0106` replaces it with an explicit rule list, and that is where each rule can say which version introduced it; until then the vocabulary stands beside the rules, not inside them, and `0042` does not do `0105`-`0107`'s work.

**The pin (B-002, B-039).** [`SpecManifest`](../../specht/SpecManifest.cs) knows the key `schemaVersion`. No key reads as `0.1.0`, the version that predates it (A-1). A JSON string `SemanticVersion.TryParse` accepts loads, even one the tool does not ship: rejecting an unshipped pin is the version set's job, not the loader's. Anything else - the JSON number `1` the retired pin was, the strings `"1"`, `"0.1"` and `"v0.1.0"`, a boolean, `null`, an array - is a `SpechtManifestException` naming the manifest's repository-relative path and the value as the manifest's JSON writes it, a string in its quotes, so `1` and `"1"` read differently in the message. The pin travels on [`SpecStructure`](../../specht/SpecStructure.cs)`.SchemaVersion`.

**Loading with the pinned version (B-001, C-4).** [`SpecSchemas.Load(IFileSystem, string, SchemaVersions)`](../../specht/SpecSchemas.cs) reads the manifest from `<root>/.spec/schema/` first, selects the pinned version, and builds the three frontmatter schemas from that version's text, each load with its own `SchemaRegistry` as before. A hand edit to `<root>/.spec/schema/*.frontmatter.schema.json` no longer reaches the check. The two-argument `SpecSchemas.Load(IFileSystem, string)` still reads all four files from disk; nothing in the check calls it, and tests build schemas through it from a mock file system. It is the on-disk source item `0043` selects (B-009), not a second path the check takes. From item `0105` (built 2026-10-09) both loads keep the version they validate with on `SpecSchemas.Version`: the selected version here, and for the on-disk load the pinned embedded version carrying the texts read from disk, so its vocabulary is the pinned embedded version's (B-014, B-028). The member and the reasons are in `0001-F1` § 7. [`SpecModel.Load(string, SchemaVersions)`](../../specht/SpecModel.cs) passes the set through; `SpecModel.Load(string)` uses `SchemaVersions.Embedded`.

**The vocabulary decides the run (B-014).** Item `0042` built the filter in [`SpecCheckRunner.Run(string, SchemaVersions)`](../../specht/SpecCheckRunner.cs), which selects the pinned version a second time from the loaded structure. From item `0105` ([ADR-0008](../../../.spec/adr/0008-evaluate-takes-the-rule-set-and-the-model-carries-the-vocabulary.md); built 2026-10-09) the filter's home is `SpecCheckRunner.Evaluate(SpecModel, IEnumerable<ISpecRule>)`, and `Run` holds none. `Evaluate` reads the vocabulary from `model.Schemas.Version.RuleIds`, evaluates each rule it is given that reports at least one id in it, drops any violation whose rule id is outside it, and counts as evaluated only the vocabulary's ids among the evaluated rules' `ReportedIds`. The rule is the same and so is every verdict; it now holds for any caller of `Evaluate`, not only for `Run`. `Run(string, SchemaVersions)` loads the model and passes the discovered rules; `Run(string)` is `Run(string, SchemaVersions.Embedded)`, so the host's `Func<string, SpecCheckReport>` registration in `Program.cs` is unchanged. The signatures are in `0001-F1` § 7.

**The report names the version.** [`SpecCheckReport`](../../specht/SpecCheckReport.cs) carries `SchemaVersion`, a `SemanticVersion`, as its first positional member, and [`SpecReportDocument.From`](../../specht/Report/SpecReportDocument.cs) writes its `major.minor.patch` text with the source `embedded` (`0001-F3` B-005, § 7 there). The source becomes a choice with item `0043`.

**Version `0.1.0`'s epic schema (B-022, B-023).** Already in the shipping copy (decision 0003, item `0051`): optional `title` and `description` with `minLength: 1`. `0042` only makes the check read it from the embedded set, so an empty value is a `SPEC004` through the existing frontmatter rule.
