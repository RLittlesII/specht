# Specification: init

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07 -->

A repository adopting the model copies `hooked`'s `.spec/schema/` and `.spec/templates/` by hand, from whatever day it looked, and nothing records which day. This Feature removes that failure state: `specht init` writes the schema set and the templates from copies embedded in the tool, so every consumer starts from the same bytes as this repository, and the copy is a fact of the tool version rather than of a day. It never overwrites, so a repository that already has a file keeps it.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-09 -->

**The shipping copy (B-004, B-005, C-2).** `src/specht.tool/schema/v<n>/` holds the four schema files (`spec-structure.schema.json` and the three frontmatter schemas) and `src/specht.tool/templates/v<n>/` the four templates (`feature.md`, `decision.md`, `adr.md`, `lesson.md`); `item.yml` is not shipped. `specht.tool.csproj` embeds them under the logical names `schema/v<n>/<file>` and `templates/v<n>/<file>`, `/`-separated on every OS. The newest version is the highest `<n>`. `v1` is a byte copy of the live `.spec/`.

**The writer (B-001, B-003, B-006, B-008; C-1, C-3, C-4).** `InitWriter` (`Features/Init/InitWriter.cs`) takes the shipping copy as a name-to-bytes map and an `IFileSystem`. `InitWriter.ShippingCopy(Assembly)` builds the map from the resources whose names match `^(schema|templates)/v<n>/<file>$`; other resources are ignored. `Write(root, cancellationToken)`:

- throws `SpechtRootNotFoundException`, the engine's, before touching anything when the root is not a directory, so `init` never creates the root itself (C-3);
- keeps the entries with the highest `<n>`, compared as integers so `v10` outranks `v2`, and maps each to `.spec/<folder>/<file>`, dropping the version (B-001);
- for each, in ordinal order of that relative path: an existing file is listed skipped and not opened (C-1); an absent one has its folder created (with `.spec/` if absent, C-3) and is written with `FileMode.CreateNew`, so a file created between the check and the write fails the run rather than being overwritten, then listed written;
- writes the bytes as embedded, with no transformation (B-003).

It returns `(Path, Written)` pairs whose paths are already root-relative with `/`, so nothing absolute reaches stdout (C-4). The map, not the `Assembly`, is the constructor argument, so a unit test hands it two versions before a second one ships.

**The command.** `InitCommand` (`Features/Init/InitCommand.cs`) is an `AsyncCommand` with nested `Settings`: `--root <DIR>`, defaulting to `.` (B-009). It resolves the root with `Path.GetFullPath`, as `CheckCommand` does, calls the writer, and writes one line per file, `written <path>` or `skipped <path>`, through the console's raw `Profile.Out.Writer` so a line is never wrapped. It returns `ExitCodes.Success`. A root that is not a directory is folded into `ExitCodes.MissingInput` with `specht: '<root as typed>' is not a directory.` on stderr; this is the minimum that keeps C-3 and C-4 when the root is missing, and B-007's proof is `0053`'s. A manifest beside the files is not read: pin handling (B-012, B-013) and rejected manifests (B-017) are `0053`, `0054`, `0049` and `0096`.

**The composition root.** `Program.cs` registers `InitWriter` as a singleton built from `InitWriter.ShippingCopy(typeof(InitWriter).Assembly)` and `new FileSystem()`, and adds `init` with `AddCommand` beside the default `CheckCommand`, so `specht --root <dir>` still reaches the check. `TestableIO.System.IO.Abstractions.Wrappers` reaches the tool through its reference to the engine; no package is added.

The engine's default manifest (`src/specht/specht.csproj`, `specht.default-manifest.json`) stays a link to the live `.spec/schema/spec-structure.schema.json`, not a third copy (C-2). Drift between the shipping copy and the live copy is caught by the B-004 tests, not by a build step that generates one from the other (C-2).

## 8. Testing Strategy

<!-- last written by: test-writer, 2026-10-09 -->

- **The seams.** The `ShippingCopy` tests and B-004's steps read the shipping copy straight from the `specht.tool` assembly, `typeof(ExitCodes).Assembly`, through `GetManifestResourceNames` and `GetManifestResourceStream`; the newest version is the highest `<n>` among the `schema/v<n>/` names. `InitWriter` (§ 7) takes the shipping copy as a name-to-bytes map and an `IFileSystem`, so its unit tests hand it any set of versions over a `MockFileSystem` with the repository-relative root `repo`; `InitCommand` takes the writer injected, so a command test runs it through `CommandAppTester`. The live copy is this repository's `.spec/schema/*.json` and `.spec/templates/{feature,decision,adr,lesson}.md`, which each test project copies into its output; `item.yml` is not copied.
- **Unit** (`test/specht.tests/ShippingCopy.Unit.Tests.cs`):
  - A-1 - mechanism: the logical names `specht.tool.csproj` gives the embedded files. `TheNewestEmbeddedVersion_WhenListed_ShouldHoldExactlyTheEightFiles` asserts that the newest version's `schema/v<n>/` and `templates/v<n>/` names are exactly the eight files.
  - B-005 - mechanism: the `$id` each embedded frontmatter schema carries, which `init` will write unchanged (B-003). `TheNewestEmbeddedFrontmatterSchema_WhenRead_ShouldCarryAnIdUnderThisRepositorysSchemaAddressForItsVersion` has one row per frontmatter schema and asserts `https://github.com/rlittlesii/specht/schema/v<n>/<file>`. The @B-005 scenario proves `init` writes it.
- **Unit** (`test/specht.tests/InitWriter.Unit.Tests.cs`, written by `implementer` with 0052's code), the writer over a `MockFileSystem`:
  - `AShippingCopyOfSeveralVersions_WhenWritten_ShouldWriteOnlyTheHighestNumberedVersion` - the newest-version choice, compared as integers (`v10` over `v2`) (B-001).
  - `AnEmbeddedName_WhenWritten_ShouldLandUnderItsFolderInDotSpecWithItsBytesUnchanged` - the map from `schema|templates/v<n>/<file>` to `.spec/schema|templates/<file>`, root-relative with `/`, and the bytes written unchanged, a BOM and CRLF included (B-001, B-003, B-008, C-4).
  - `AFileThatExists_WhenWritten_ShouldBeListedSkippedAndLeftAsItWas` - the written-or-skipped choice (B-006, C-1).
  - `TheEmbeddedShippingCopy_WhenWrittenIntoABareRoot_ShouldWriteTheEightFilesAndNothingOutsideTheTwoFolders` - the real embedded copy yields exactly the eight files, all under the two folders (B-001, B-008, C-3).
  - `ARootThatIsNotADirectory_WhenWritten_ShouldThrowRootNotFoundAndCreateNothing` - the writer never creates the root (C-3). It is the mechanism beneath B-007, whose scenario and § 9 row stay `0053`'s.
- **Integration** (`test/specht.tests/ShippingCopy.Integration.Tests.cs`), B-004 - mechanism: a byte copy for the tool-owned files, and the subset equality of the manifest, whose tool-owned keys are the top-level keys the embedded manifest carries. `TheNewestEmbeddedFile_WhenComparedWithTheLiveCopy_ShouldBeByteIdentical` has one row per frontmatter schema and template. `TheNewestEmbeddedManifest_WhenComparedWithTheLiveManifest_ShouldEqualItOnEveryKeyTheEmbeddedManifestCarries` asserts that each embedded key is present in the live manifest and equal under `JsonNode.DeepEquals`; a key only the live manifest carries is outside the comparison. These tests are Integration because they read the live files from disk. Assertion messages carry repository-relative paths only.
- **Acceptance.** `init.feature` is linked into `test/specht.acceptance`; [`Init/InitSteps.cs`](../../../../../test/specht.acceptance/Init/InitSteps.cs) binds B-001, B-003, B-004, B-005, B-006, B-008 and B-009. B-004 reads the live manifest, adds a synthetic `rules` setting lowering `SPEC031` to warning in memory, and asserts that the comparison still holds. The others launch the built tool through `Tool.Launch` over a synthetic root, `repo/` inside a fresh temporary sandbox seeded with a `README.md`, a `.spec/README.md` and a file beside the root. `init --root repo` runs from the sandbox, so a write beside the root is caught (B-008), and a bare `init` runs from the root (B-009). The B-008 step also requires that `init` created something, so a run that does nothing cannot pass it. B-005 is bound because at a bare root it follows directly from B-003 and the `$id` the unit test pins: the version written is the newest. B-002, B-007 and B-010 to B-017 report Skipped until their items (`0053`, `0054`, `0095`, `0096`) bind them.
- **Integration** (`test/specht.tests/InitCommand.Integration.Tests.cs`):
  - B-006 and C-4 - the listing through the composition root and the real shipping copy. `OneOfTheEightFilesPresent_WhenInitRuns_ShouldListItSkippedAndEveryOtherWrittenRelativeToTheRoot` has one row per file: that file, copied from the live copy, is present; stdout names each of the eight once, relative to the root, the present one with `skipped` and every other with `written`, and carries neither the sandbox path nor a backslash. The scenario holds only the feature template; the theory holds every file. It launches the built tool through `test/specht.acceptance/Tool.cs`, linked into the project, so `Program.cs`'s registration of `init` is under test too.
  - B-009 - the root resolution. `NoRootOption_WhenInitRuns_ShouldWriteUnderTheWorkingDirectory` runs `init` with no `--root` through `CommandAppTester`, over an `InitWriter` on a `MockFileSystem` holding only the process's working directory, and asserts the file lands under it. A command that handed the writer `.` unresolved would write under the fake's own current directory instead. Integration, because the command tester composes the parser, the registrar and the command.
- **Verdicts per claim.**
  - B-001 - mechanism: the newest-version choice and the name-to-path map in `InitWriter`, pinned by its unit tests above; the eight names by `ShippingCopyUnitTests`. `Covered`.
  - B-003 - mechanism: the bytes written as embedded, with no transformation; `AnEmbeddedName_WhenWritten_ShouldLandUnderItsFolderInDotSpecWithItsBytesUnchanged`. `Covered`.
  - B-005 - mechanism: the `$id` the embedded schema carries (`ShippingCopyUnitTests`) and the byte copy (B-003). `Covered`.
  - B-006 - mechanism: the written-or-skipped choice (`AFileThatExists_WhenWritten_ShouldBeListedSkippedAndLeftAsItWas`) and the line per file, pinned for every file by the integration theory. `Covered`.
  - B-008 - mechanism: the only targets are the eight, under the two folders, and the root is never created (C-3); `TheEmbeddedShippingCopy_WhenWrittenIntoABareRoot_ShouldWriteTheEightFilesAndNothingOutsideTheTwoFolders` and `ARootThatIsNotADirectory_WhenWritten_ShouldThrowRootNotFoundAndCreateNothing`. The scenario snapshots the whole sandbox. `Covered`.
  - B-009 - mechanism: the `--root` default of `.` resolved by `Path.GetFullPath` in the command; `NoRootOption_WhenInitRuns_ShouldWriteUnderTheWorkingDirectory`. `Covered`.
- **What the design still makes hard to test.** Nothing for these claims.
- **Red for the right reason.** Before the shipping copy was embedded, every `ShippingCopy` test failed on "Expected versions not to be empty because the tool embeds at least one schema/v<n>/ resource": no compile error and no missing live file. Before `init` exists, the B-001, B-003, B-005, B-006, B-008 and B-009 scenarios and every row of the integration theory fail at runtime: the tool answers `Error: Unknown command 'init'.` with exit `255` and writes nothing, so each assertion fails on a missing file, an empty listing or an empty set of created files. Nothing fails to compile. `NoRootOption_WhenInitRuns_ShouldWriteUnderTheWorkingDirectory` was written after `InitCommand` took its writer injected and has not been seen red; it fails if the command hands the writer the root unresolved, which the `MockFileSystem` places at its own current directory.
