# Specification: Release baseline comparison

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-13 -->

Published benchmark files do not tell the maintainer whether a release became materially more expensive than its predecessor. This Feature gives every release an automatic comparison report with identifiable evidence and explicit review flags, so performance regressions receive attention without making a measurement a build or publication gate.

### Measurement equivalence

Measurement conditions comprise operating system, runtime version, architecture, toolchain, garbage-collection mode, benchmark job and timing confidence level. Workload identity covers the fixture definition and measured operation, independently of its display name. A changed product implementation is the object of comparison, not a workload change. Unknown workload or configuration equivalence is not comparable. Metric validity is checked first: absent or invalid timing uncertainty, including an unknown confidence level, receives `Insufficient evidence` rather than an equivalence judgment. Compatible time or byte scales are normalised; incompatible dimensions or observer boundaries cannot be paired.

### Comparison policy

Decision 0002 records the owner's 2026-10-13 answers. Eligible releases are successfully published stable releases and prereleases; drafts and bare tags are excluded. The baseline is the most recent eligible publication before the current release's first publication, and that pair stays fixed on reruns. Equal publication timestamps are ordered by immutable release identifier, with the larger identifier later in the sequence.

A timing flag requires a mean increase strictly greater than 10% and a current confidence interval whose lower bound is strictly greater than the previous interval's upper bound, using the same confidence level. Overlapping or touching intervals do not flag. An allocation flag requires an increase strictly greater than 10% in managed bytes per operation. Increases exactly at 10% do not flag. These are review screens, not claims of statistical significance or build thresholds.

Percentage change is `100 × (current − previous) / previous` for a positive previous value, computed without display rounding. With zero allocation in both releases, the allocation is unchanged and its percentage is undefined. A zero-to-positive allocation has no defined percentage and receives `Insufficient evidence`, making the overall comparison incomplete unless another metric already requests review. A non-positive timing baseline is invalid evidence. A known review flag takes precedence over coverage gaps in the comparison judgment. If a later reporting stage fails, available run-summary output retains any already-computed flags alongside the incomplete reporting state; it does not invent a successful attachment or a regression-free result.

### Composition and existing reuse

The non-packable [comparison assembly](../comparison.csproj), namespace `Specht.Comparison`, joins `specht.slnx` without referencing the benchmark assembly or product host. It is an executable: [`Program`](../Program.cs) is an internal repository-tooling entry point the release workflow runs as `request`, `attach` or `compare` with a repository-relative directory, and every one of them exits 0. `System.Text.Json`, `HttpClient`,
`TimeProvider` and the existing `System.IO.Abstractions` substitution provide its
boundaries. It adds no public `specht` command or consumer configuration.

`Program` composes concrete readers, selection, evaluation, rendering and
collection. Pure functions receive immutable values. Provider access, filesystem
access and child processes are asynchronous and cancellable; `HttpMessageHandler`,
`IFileSystem` and a process delegate supply the existing test seams. No interface
is introduced for an in-memory calculation. The publisher consumes data files,
never executes a downloaded report, and validates the bundle before uploading.

Reuse `.performance/benchmarks/BenchmarkConfiguration.cs` and the measuring
Features' native harness at each revision: Release, out-of-process BenchmarkDotNet,
`MemoryDiagnoser`, full JSON and GitHub Markdown. The collector builds and runs
each revision's own `.performance/benchmarks/benchmarks.csproj` directly and
replicates the `Benchmark` target's selection (`--list flat`, names starting
`Specht.Benchmarks.`) and conditional packing (`src/tool/tool.csproj` only when a
`Specht.Benchmarks.Startup.` case is selected). It does not call the target: the
target's `Restore` dependency restores local tools, which needs the package-source
credential C-10 keeps away from a measured revision. The target and its
broken-benchmark failure semantics are unchanged (C-9).
`ColdStartSession` already installs packed tools locally and keeps fixture setup
outside measurement; its allocation is the harness process's, not the child
product's. Its current inherited process environment needs the collection
boundary's sanitisation. Do not transplant a current harness into an older product
or add missing stage/startup benchmarks under this Feature.

Workflow composition stays in `.build/SpechtBuild.Release.cs`'s existing
`ReleaseMiddleware`; its `configuration.Jobs`, per-job `Permissions`, explicit
step insertion and `ContinueOnError` are the extension points. The gates and
package artifact retain `0055-F6`'s existing order and authority. The comparator
executable and dependencies are a separate artifact built from the gated current
commit; the release job can use that coordinator without checking out or executing
either measured revision. No publishing operation becomes a NUKE target; the
comparator's build is the `PublishComparator` target, a `dotnet publish` of the
comparison project for `net10.0` into `.artifacts/comparator`, which `Release`
depends on. The comparator steps run that output directly with `dotnet`, not
through `./build.cmd`: the entry script restores local tools from the
authenticated package source, a credential the comparison job never holds (C-10).

### Selection and persistence

The provider reader follows every release-catalog page before selection. A failed
page is an incomplete catalog, not evidence that no predecessor exists. Select
published non-drafts, including prereleases, by `(publishedAt, immutableReleaseId)`;
choose the immediately preceding eligible record in that order, never semantic
version or tag creation order. The current first-publication ordering key is
captured once. Resolve annotated tags to exact commits; preserve an unresolved
selected predecessor's identity with its failure. Do not choose the next usable
older release. Concurrent equal timestamps use the agreed immutable-id tie-breaker.

After successful package and Release publication, the existing release job creates
`comparison-pair-v1.json` as a durable asset on the current Release, before issuing
a collection receipt. The value includes the selection snapshot and resolved
commits. Creation is insert-only: an existing asset is read and validated, never
clobbered. On a concurrent creation conflict, read the winning value and use it;
an invalid or unreadable existing asset is `Incomplete`. Reruns, including a new
workflow run for the same Release, load this value instead of selecting again.
An explicit null predecessor is durable too. If saving the pair fails, collection
does not start. No result claims a fixed pair that was only stored transiently.

The pair is established before the first collection attempt; a failure before its
creation has made no selection durable. The selection predicate still uses the
current Release's original publication key when retrying that stage. Release
creation/push recovery is owned by `0055-F6`; its release job carries the
comparison steps after publication, so a rerun reaches them only past both
publication steps. "Push release packages" skips a package version already
pushed. "Create GitHub Release" keeps a Release that is published, not a draft,
under this tag, whose tag resolves to this run's commit and which carries both
package files; any other state, no Release included, runs `gh release create` as
before, so a failed first publication still fails the job and a failed package
publication is never bypassed.

### Implemented selection and evidence boundaries

[`ReleaseSelection`](../Selection/ReleaseSelection.cs) consumes a complete catalog and the current first-publication record. [`ReleaseCatalogReader`](../Selection/ReleaseCatalogReader.cs) reads all provider pages and peels annotated tags; a failed page leaves an incomplete catalog, and an unresolved tag retains its release identity. [`ReleasePairStore`](../Selection/ReleasePairStore.cs) uses a completed temporary file and an insert-only move for local persistence. [`ReleasePairAssetStore`](../Selection/ReleasePairAssetStore.cs) reads or inserts the durable release asset, reloads a concurrent winner and verifies a successful upload. Its `HttpClient` and authority are supplied by the caller; nothing invokes it automatically or creates credentials.

[`ComparisonJson`](../Model/ComparisonJson.cs) owns version-1 pair/session encoding, canonical object-key order, digests, duplicate-property rejection and read validation. [`WorkloadIdentity`](../Evidence/WorkloadIdentity.cs) keys operations with typed canonical parameters. [`BenchmarkEvidenceReader`](../Evidence/BenchmarkEvidenceReader.cs) decodes the pinned native full JSON against caller-supplied audited mappings, preserving source locators and per-metric invalidity. [`CasePairing`](../Evidence/CasePairing.cs) retains the union, expected missing results and duplicate metric locators. Matching observed and expected keys retain the union of required metrics; contradictory operation, fixture or boundary contracts remain not comparable. Unidentified records cannot establish Added/Removed coverage, including when labels change. Saved pairs reject an equal current/predecessor immutable release id regardless of timestamp. Common parameter keys pair independently. A one-sided parameter case is Added or Removed; when both sides instead have unmatched input keys for the same operation, those cases remain not comparable with an input-parameter reason. [`MetricUnits`](../Evidence/MetricUnits.cs) recognises dimensional scales and is the one unit table; evaluation scales with it.

The supported producer is BenchmarkDotNet 0.15.8. Its [pinned exporter](https://github.com/dotnet/BenchmarkDotNet/blob/v0.15.8/src/BenchmarkDotNet/Exporters/Json/JsonExporterBase.cs) supplies nanosecond statistics and bytes per operation. The cached pinned assembly's serializer was probed with invented statistics: its legacy confidence enum encodes `L999` as numeric `Level: 12`; the importer uses the version-bound enum mapping rather than treating that number as a percentage. Unsupported producers, ambiguous JSON and missing full-export metadata remain unavailable. Raw exports are caller-owned inputs; retention sanitisation and bundle construction are under [Implemented rendering and publication](#implemented-rendering-and-publication). No benchmark was run for this probe.

### Implemented evaluation

[`ComparisonEvaluation`](../Evaluation/ComparisonEvaluation.cs) is a pure function from the session and `CasePairing`'s cases to a [`ComparisonDocument`](../Model/ComparisonDocument.cs), keeping pairing's case order and evidence. It does not re-derive validity: a metric pair that pairing judged insufficient or not comparable keeps that judgment and its reason. A comparable pair is scaled through `MetricUnits.Scale` to ns or B per operation, timing intervals with their mean, and its absolute and percentage changes are computed on unrounded `decimal` values. A `decimal` overflow in scaling or arithmetic is invalid evidence, `Insufficient evidence` with a reason, never an exception. The [`ComparisonPolicy`](../Model/ComparisonPolicy.cs) applied is version 1, decision 0002's strict 10% screens, recorded in the document. Each [`MetricComparison`](../Model/MetricComparison.cs) carries a [`MetricJudgment`](../Model/MetricJudgment.cs); a flag's reason states the screen it met, and the numbers stay in the value fields, rounded only when rendered. Tool peak memory is `Informational` whatever its evidence, never flagged and never a gap (§ 5 item 9, C-6). Each [`CaseComparison`](../Model/CaseComparison.cs) keeps pairing's status and reason. A [`CoverageGap`](../Model/CoverageGap.cs) is recorded per case with no time or managed-allocation row, whatever its status, carrying pairing's reason, else the case evidence's failure, else evaluation's own reason for Added, Removed or a case with nothing to judge; and per insufficient or not comparable time or managed allocation. A case whose only non-comparable metric is tool peak memory adds no gap. The [`ComparisonJudgment`](../Model/ComparisonJudgment.cs) reduction is any flag, then an empty case list or any gap, then no regression flagged. No predecessor is `ComparisonEvaluation.NoBaseline`: the session, policy version 1, no cases, no gaps and the judgment `No baseline` (B-003), never a regression verdict.

### Implemented rendering and publication

[`ComparisonReport`](../Reporting/ComparisonReport.cs) projects one `ComparisonDocument` into `report.json` and `report.md` and recomputes no judgment, delta, gap or reason. `report.json` is the canonical `ComparisonJson` encoding of `{ formatVersion: 1, pair, comparison }`; `comparison` is the document with each observation's `sourceFile` rewritten from its workspace path to its bundle path `raw/<side>/<file name>`, otherwise unchanged and in its own order. `report.md` gives, in the document's order, the overall judgment, both releases and the pair digest, the session, each side's conditions, harness, exporter and invocation, the policy screens, cases, workloads, metrics, coverage gaps and every observation's bundle path and locator, in the wording of § 3 (`Review required`, `Not defined`). Numbers are rounded for display only: half away from zero to at most two decimal places, trailing zeros dropped, invariant culture; a positive change carries `+`, a percentage `%`, and a null number reads `Not defined`. Table cells escape backslash, pipe and backtick with a backslash and `<`/`>` as entities, and turn control characters into spaces, so display text cannot break a table or inject HTML.

[`ReportBundler`](../Reporting/ReportBundler.cs) writes `<workspace>/comparison-<releaseId>-<runId>-<attempt>.zip` from caller-supplied repository-relative [`RawExport`](../Model/RawExport.cs)s. It checks closure before writing: a valid pair whose digest is the session's; every observation citing a supplied export of its own side; each export a repository-relative `-report-full.json`, with no symbolic link or reparse point at it or at any directory between it and the repository root, without duplicate properties whose producer version `BenchmarkEvidenceReader.IsSupportedProducer` accepts, the one definition the reader also uses; no two exports sharing a bundle path, compared case-insensitively. An export no observation cites is retained with empty cases. A failure throws `InvalidDataException` with a path-free message and writes nothing. A string value that is a rooted path (`/`, `~`, `\` or a drive letter) becomes `[path removed]` and every other token keeps its raw text; such a file records `absolute-paths-removed`, any other keeps its original bytes with `none`, and `SourceSha256` is always the original's digest. The [`EvidenceManifest`](../Model/EvidenceManifest.cs) lists every other entry as an [`EvidenceFile`](../Model/EvidenceFile.cs) in ordinal path order, and `ComparisonJson.ReadManifest` owns its version-1 wire checks; identity mappings are ordered by full name, then product commit. The archive is deterministic: ordinal entry order, a fixed 2000-01-01 entry time, regular-file attributes, no directory entries. `Create` validates its own archive before writing, so a generated entry holding a rooted value - a session invocation, a workload parameter or boundary, a case or gap reason, a mapping source - is rejected, never rewritten, and nothing is written. The archive is written to a temporary file and moved without overwrite, so an existing bundle raises `IOException` and stays intact. `Validate` rejects unsafe, symbolic-link or duplicated entries, names that differ only by case included; an entry outside the manifest; a missing or altered listed file; an unsupported manifest version; a session whose pair digest is not `pair.json`'s; a report whose `pair` is not `pair.json`, whose `comparison.session` is not `session.json` in canonical form, or whose evidence references are not the bundle's raw exports; and any JSON entry, a raw export marked `none` included, holding a rooted string value or one that embeds an absolute path. The whole-value predicate is the one path removal uses. The embedded predicate is C-11's, as [decision 0004](decisions/0004-reject-an-absolute-path-embedded-in-any-bundle-value.md) defines it: at the start of a string value, or after whitespace or one of `=` `,` `;` `:` `(` `)` `[` `]` `"` `'`, a `/`-delimited segment closed by a second `/`, `~/` or `~\`, an ASCII drive letter with `:\` or `:/`, `\\`, or `file:` in any ASCII case followed by `/`. Property names are not examined, and an embedded path is never rewritten: it rejects the bundle, in `Create` before anything is written, and in `Validate`, including one left in a raw export after whole-value removal. A report observation's `locator` is exempt from both predicates only when it is a JSON pointer of at least two reference tokens whose parent pointer, every token but the last after `~1` and `~0` unescaping, resolves inside the raw export the observation's `sourceFile` cites, as the reader's `/Benchmarks/<index>/Statistics` and `/Memory` do. An array token is a decimal index without a leading zero inside the array. A locator that does not resolve, or an observation with a locator and no listed raw export, is rejected; every `locator` property anywhere in `report.json` is held to that, not only those under `comparison`. `report.md` must be exactly `ComparisonReport.Markdown` of the report's `pair` and `comparison`, so it holds nothing those values' absolute-path checks did not pass (C-8, C-11). Entry order is not required.

[`ReportBundleAssetStore`](../Reporting/ReportBundleAssetStore.cs) publishes through the caller's `HttpClient` and authority. Before any request it validates the bundle and requires the asset name its `pair.json` release and `session.json` run and attempt give. It reads every asset page: an existing asset of that name is downloaded and confirmed only when its digest matches, and is never replaced or deleted. Otherwise it uploads once as `application/zip`, treats a conflict like the pair asset does, re-lists for exactly one `uploaded` asset, downloads it and checks its digest and validity. Only then does it return a [`PublishedBundle`](../Model/PublishedBundle.cs); a transport, parse or verification failure is `InvalidDataException`, never a reported success.

### Acyclic execution and credential boundary

The generated release workflow has `build`, `release` and `comparison` jobs.
Both latter jobs need only `build`; neither needs the other's completion. Both
retain the tag-push predicate, excluding workflow dispatch. `comparison` has only
contents-read and actions-read; packages and all write scopes are absent. `release`
keeps the sole write grants, contents-write and, since `0055-F6` item 0327,
id-token-write in place of package-write, and gains actions-read solely for
the same-run return artifact. No new secret, dispatch credential or write job is
introduced. Ordinary PR/main workflows stay outside this path.

```mermaid
flowchart TD
    G[build: correctness gates and artifacts] --> P[release: package and Release publication]
    G --> W[comparison: wait for same-run receipt]
    P --> S[release: persist pair and upload receipt]
    S --> C[comparison: collect both revisions on its runner]
    W --> C
    C --> E[comparison: evaluate, render and upload bundle]
    E --> A[release: bounded wait, validate and attach bundle]
    S --> A
```

The temporal chain is publication → saved pair → receipt → collection → bundle →
attachment. There is no completion edge back to publication. The release job
uploads `comparison-request-<runId>-<attempt>` after saving the pair, then waits
for `comparison-result-<runId>-<attempt>`. The comparison job polls the same run's
artifact list for that exact receipt, validates repository, run, attempt, current
commit and pair digest, then starts work. The receipt proves successful publication
in this run; observing a tag or an old Release alone cannot trigger measurement.
The release job similarly accepts only the result for that receipt, never an old
attempt. A rerun of only failed jobs cannot consume an old receipt/result: missing
participants produce `Incomplete`; rerunning all jobs resumes with the saved pair.

Artifact upload must finish before its reader proceeds, but job completion is not
required. This relies on the immediate availability of immutable v4 artifacts,
[documented by upload-artifact](https://raw.githubusercontent.com/actions/upload-artifact/v4/README.md),
and the [run-artifact read API](https://docs.github.com/en/rest/actions/artifacts).
Do not use `needs.release.outputs` as an early signal. Insertion of a read-only
third job uses the existing generator; it does not use its built-in publisher or
a second workflow. The disposable probe and its observed limits are recorded in
the ADR; generated declarations are evidence about generation, not a live run.

The comparison runner owns both sequential revision checkouts/builds and benchmark
process trees for one session. Use separate workspace/cache/output folders under
`.artifacts/benchmarks/comparison/<sessionId>/` or its temporary workspace. Checkout
credentials are not persisted. No publisher artifact, publishing token or mutable
publisher workspace is shared with it. Child environments are built from an
allowlist of SDK/runtime and session paths; omit GitHub tokens, Actions runtime
credentials, user tool manifests and credential-bearing NuGet configuration.
Restore dependencies before measurement with read-only access where needed.
Record the OS, runtime, architecture, SDK toolchain and job each side's exports
declare; a historical SDK mismatch is visible rather than fixed by silently
retargeting. The garbage-collection condition is what the job declares, or
`Job default` when it declares nothing: the export does not record the GC mode
the process actually ran with, so two default jobs on runners with different
default GC settings are not told apart.

The receipt wait is bounded to 30 minutes; paired preparation/collection to 60
minutes total, with each revision capped at 25 minutes and failures leaving time
to render. The release-side result wait is bounded to 100 minutes from receipt,
including runner queue delay. Use injected `TimeProvider`, cancellable waits and
process-tree termination. Normal deadlines are handled in code before the platform's job safety
timeout; they do not depend on an unprobed generator timeout property. A queued, failed or cancelled collector causes a
bounded incomplete outcome, never indefinite waiting.

Every comparison-owned step after successful publication, including receipt save,
transport, rendering and attachment, has advisory failure handling. The comparison
job's setup/upload steps also continue on error and a final summary runs on failure.
Earlier gates and publication retain their failure semantics. Pre-write an
`Incomplete: comparison pending` summary before waits; replace it on completion.
On graceful cancellation kill both process trees and retain available evidence.
An explicit user cancellation or platform hard kill can prevent any final step;
it leaves the workflow cancelled, the published release intact and the prewritten
summary/pair as available evidence, never a fabricated success. No design can turn
a platform cancellation into a successful run. Recovery is a rerun with the saved
pair, not a retry loop that changes the baseline.

### Implemented collection

[`CollectionPlan`](../Collection/CollectionPlan.cs)`.For` returns no plan when the pair has no predecessor, when either side lacks a resolved 40- or 64-hex commit, when the comparator commit is not 40 or 64 hex, or when the session id is not one path segment of `[A-Za-z0-9._-]` (or is `.` or `..`). The unresolved pair outcomes are the no-baseline and unresolved-revision paths of [Implemented release reporting](#implemented-release-reporting). Its `PairDigest` is `ComparisonJson.Digest` of the saved pair. The plan carries no identity mappings: each side's come from that revision's own declarations ([Implemented workload identity declarations](#implemented-workload-identity-declarations)).

[`PairedCollector`](../Collection/PairedCollector.cs) collects the previous revision, then the current, never overlapping, under `.artifacts/benchmarks/comparison/<sessionId>/<side>/`:

| Folder    | Holds                                                                                                  | After the side |
| --------- | ------------------------------------------------------------------------------------------------------ | -------------- |
| `source`  | a shared no-checkout clone, detached at the pinned commit and verified with `git rev-parse HEAD`       | removed        |
| `home`    | the child's `HOME`, `USERPROFILE` and `DOTNET_CLI_HOME`                                                | removed        |
| `temp`    | the child's `TMPDIR`, `TMP` and `TEMP`                                                                 | removed        |
| `results` | the harness's `--artifacts ../results`; full-JSON exports land in `results/results/*-report-full.json` | kept           |

The session's `nuget` package cache and `session-manifest.json`, written with `ComparisonJson.Write`, sit beside the two sides. The manifest is written only when absent, with create-new semantics, so an earlier attempt's manifest is never overwritten, even by a concurrent run; the result is still returned. A session id names one attempt: when a side's folder already exists, that side is unavailable ("Revision workspace already exists."), no process runs for it and nothing in it is deleted. A revision without its own harness is unavailable; no harness is copied from another revision. The build and pack steps pass `--disable-build-servers`, so no build server outlives its revision.

[`RevisionEvidence`](../Collection/RevisionEvidence.cs) holds the pure derivations the collector uses: the selection (`--list flat` lines starting `Specht.Benchmarks.`, in listing order), whether the tool must be packed (a selected `Specht.Benchmarks.Startup.` name), the expected inventory, the export reading ([`ExportReading`](../Model/ExportReading.cs)) and the child environment.

Every step is a [`ProcessRequest`](../Model/ProcessRequest.cs) to the injected process delegate, answered by a [`ProcessOutcome`](../Model/ProcessOutcome.cs). Arguments and working directories are repository-relative. [`ProcessRunner`](../Collection/ProcessRunner.cs) is the real child process: it resolves the working directory against the repository root, clears the inherited environment and sets the request's, and captures standard output lines. On cancellation it kills the entire process tree, waits at most 30 seconds, timed by its injected `TimeProvider`, for the exit and the end of output, since an orphan outside the tree can hold the output open, and then rethrows the cancellation. The child environment copies only `PATH`, `DOTNET_ROOT*`, `LANG`, `LC_ALL`, `SystemRoot`, `windir`, `ComSpec` and `PATHEXT` from the parent, then sets the workspace folders above, `NUGET_PACKAGES`, `DOTNET_CLI_TELEMETRY_OPTOUT` and `DOTNET_NOLOGO`. Workspace values are absolute in the environment only and are never recorded. Tokens, Actions runtime variables and package-source credentials never reach a child.

Collection supports Linux and macOS runners. On Windows, NuGet reads the user configuration under `%APPDATA%`, which a redirected `HOME` and `USERPROFILE` do not isolate, so a credential-bearing user configuration could reach a measured revision; Windows is unsupported for collection.

Deadlines are timers from the injected `TimeProvider`, linked with the caller's token: 60 minutes for the pair and 25 for each revision; no clock is read after a step. Expiry or cancellation cancels the in-flight process and the side issues no further invocation; a side that would start after the pair budget is spent or after cancellation issues none. The reason prefers caller cancellation, then the pair bound, then the revision bound. Any other exception on a side makes that side unavailable ("Revision collection failed unexpectedly."), without the exception's text. Cleanup of `source`, `home` and `temp` ignores a folder it cannot remove, so a cleanup failure never replaces or throws over the side's result. The current side still runs, the manifest is written and a result is returned, never thrown.

A collected [`RevisionCollection`](../Model/RevisionCollection.cs) records:

- `HarnessVersion` `native-v1`: the revision's own harness run with this command line. A changed command line is a new label.
- `ExporterVersion` from `HostEnvironmentInfo` `BenchmarkDotNetVersion`, and the six measurement conditions from each benchmark record of the side's exports:
  - operating system, runtime, architecture and toolchain from `HostEnvironmentInfo` `OsVersion`, `RuntimeVersion`, `Architecture` and `DotNetCliVersion`;
  - job: the benchmark's `DisplayInfo` after its first `: `, without a trailing ` [parameters]` block, such as `ShortRun(Toolchain=.NET 10.0, IterationCount=3, LaunchCount=1, WarmupCount=3)`;
  - garbage collection: the characteristics that job declares among `Server`, `Concurrent`, `Force`, `HeapCount`, `CpuGroups`, `AllowVeryLargeObjects`, `RetainVm`, `HeapAffinitizeMask` and `NoAffinitize`, joined with `, ` in displayed order, or `Job default` when it declares none.

  Every benchmark of every export of the side must agree on the exporter version and all six conditions, or the side is unavailable with disagreeing exports. An export without benchmarks, without any one of the five host values, or with a benchmark whose `DisplayInfo` has no job segment is malformed; a missing operating system, runtime or architecture is treated the same way as a missing toolchain, so no condition is ever recorded as unknown on a collected side.

- `Invocation`: the application arguments after `--`, the same on both sides.
- `Mappings`: the side's declared identity mappings, and `InventoryReason`: "Revision benchmarks declare no workload identity." when there are none, "Revision benchmarks do not declare one workload identity for every selected benchmark." when they do not cover the selection, otherwise null. A collected side with a reason has an unknown inventory.
- The expected inventory. `--list flat` names methods, while exports name parameterised cases, so a mapping belongs to a selected name when its `FullName` equals the name or starts with the name followed by `(`. A mapping counts only when `BenchmarkEvidenceReader` would also accept it: this side's commit, a repository-relative source file and a 64-hex source digest. The inventory is known when every selected name has at least one such mapping and all their workload identities are distinct; its cases are then ordered by workload key. Otherwise it is unknown and no cases are expected.

An unavailable side keeps its pinned commit and invocation, records `unavailable` as harness and exporter version so `ComparisonJson.ReadSession` still accepts the manifest, all-null conditions, an unknown empty inventory and no result files. Its reason is fixed text, never process output: the contract reasons for a mismatched checkout, a missing harness, an empty selection, an existing workspace, an unexpected failure and the bounds; `<step> failed with exit code <n>.` for the clone, checkout, identity check, build, listing, pack and run steps; and fixed reasons for no export ("Benchmark run produced no full JSON export."), a malformed export ("Benchmark export is malformed or names no exporter version.") and disagreeing exports ("Benchmark exports disagree on their measurement conditions."). Session manifest version 1 has no reason field, so the reason lives in `RevisionCollection` and reaches the run summary through the reporting outcome; the manifest format is unchanged. A failed or unavailable previous side never stops the current side or substitutes another commit.

### Implemented workload identity declarations

A benchmark method declares its workload with [`WorkloadIdentityAttribute`](../../benchmarks/WorkloadIdentityAttribute.cs): operation id and revision, fixture id and revision, measurement boundary, and the declaring file, which the compiler supplies through `[CallerFilePath]`. Nothing reads it at run time and it changes nothing a benchmark measures (C-3). [`DeclaredIdentity`](../Collection/DeclaredIdentity.cs) reads it from the side's built `specht.benchmarks.dll` metadata with `System.Reflection.Metadata`; the measured assembly is never loaded or executed in the comparator's process. Each declared method gives one [`IdentityMapping`](../Model/IdentityMapping.cs) per `[Params]` combination:

- `FullName` is `<namespace>.<type>.<method>`, followed for a parameterised class by `(<Name>: <value>, ...)` in member declaration order, fields before properties. That is BenchmarkDotNet 0.15.8's full name, confirmed with an in-process dry run of `BindingLookupBenchmarks` (`ResolveBindings(Records: 1, Bindings: 40)`); no measurement was taken.
- Parameters are typed `number`; only integral `[Params]` values are read. A method with `[Arguments]` or `[ArgumentsSource]`, a class with `[ParamsSource]`, `[ParamsAllValues]` or a non-integral `[Params]`, a nested or generic class, or an attribute without six non-empty strings declares nothing.
- Every declared case requires time and managed allocation; tool peak memory stays informational (C-6).
- `ProductCommit` is the side's pinned commit. `SourceFile` is the compiled path made relative to that side's `source` checkout, with `\` read as `/`, and must satisfy `EvidencePaths.IsRelative`; `SourceDigest` is the SHA-256 of that file's bytes at the checkout. A path outside the checkout or an unreadable file drops the declaration, so it can only leave the inventory unknown, never put an absolute path in output (C-8, C-11).

The measured build runs in the child environment, which does not carry `GITHUB_ACTIONS`, so `Directory.Build.props` does not set `ContinuousIntegrationBuild` and no deterministic `/_/` source path map applies: the compiler records the checkout's physical path, and the collector passes the same checkout root it built in. No `PathMap` is added: it would erase the prefix relativisation needs. If deterministic paths ever reached a measured build, no declaration would relativise and every comparison would be `Incomplete` with the undeclared reason, visible rather than silently mapped.

A revision whose benchmarks declare nothing has no mappings and an unknown inventory, and its comparison is `Incomplete` with that reason; nothing is borrowed from another revision and no hand-written mapping exists (decision 0005, B-025). Every release published before this attribute therefore compares `Incomplete` as a predecessor. The operation id is unique within the harness because a workload key is the operation id with its parameters. Revisions start at `1`: an operation revision rises when what the method measures changes, a fixture revision when its input changes. The current declarations:

| Benchmark method                                     | Operation                    | Fixture                        | Boundary       |
| ---------------------------------------------------- | ---------------------------- | ------------------------------ | -------------- |
| `Check.CheckBenchmarks.Check`                        | `check`                      | `generated-specification-tree` | `in-process`   |
| `Analysis.BindingLookupBenchmarks.ResolveBindings`   | `resolve-bindings`           | `synthetic-binding-catalog`    | `in-process`   |
| `Analysis.InputReconstructionBenchmarks.Reconstruct` | `reconstruct-analysis-input` | `synthetic-analysis-inputs`    | `in-process`   |
| `Startup.ColdStartBenchmarks.EmptyTool`              | `start-empty-tool`           | `empty-tool-package`           | `tool-process` |
| `Startup.ColdStartBenchmarks.Help`                   | `start-help`                 | `installed-tool`               | `tool-process` |
| `Startup.ColdStartBenchmarks.Check`                  | `start-check`                | `one-specification-tree`       | `tool-process` |

`in-process` is a method BenchmarkDotNet measures inside the harness process; `tool-process` starts an installed tool, whose allocation is the harness's (§ 7, Composition and existing reuse).

### Implemented release reporting

The generated [release workflow](../../../.github/workflows/release.yml) comes from `ReleaseMiddleware` in [`SpechtBuild.Release.cs`](../../../.build/SpechtBuild.Release.cs):

| Job          | Needs   | Grants                                    | Runner                        | Comparison steps, each `continue-on-error: true`                                                                                                                                                                                                                                                                                  |
| ------------ | ------- | ----------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `build`      | -       | workflow default: contents, packages read | `[self-hosted, macOS, ARM64]` | `PublishComparator` after `Build`, then upload `comparator` (`.artifacts/comparator`, one day), apart from `nupkg`; the final `Release` step skips `PublishComparator`.                                                                                                                                                           |
| `release`    | `build` | actions read, contents and id-token write | `[self-hosted, macOS, ARM64]` | Checkout (`fetch-depth: 0`, `clean`, `persist-credentials: false`); after "Log in to NuGet", "Push release packages" and "Create GitHub Release": download the comparator, `request`, upload `comparison-request-${{ github.run_id }}-${{ github.run_attempt }}`, `attach`, and a fallback summary when `attach` did not succeed. |
| `comparison` | `build` | actions read, contents read               | `[self-hosted, macOS, ARM64]` | Checkout (`fetch-depth: 0`, `clean`, `persist-credentials: false`), the SDKs, download the comparator, `compare`, upload `comparison-result-${{ github.run_id }}-${{ github.run_attempt }}`, and an `always()` fallback summary when `compare` did not succeed.                                                                   |

Both later jobs carry the tag-push predicate. The publication steps keep no `if` and no `continue-on-error`, so a failed publication still fails the job and stops it before any comparison step; a comparison step can never fail the run (C-1, B-017). There is no third write job, no new secret and no `needs.release.outputs`. The fallback summary is the one comparison step that does not run the comparator, so a comparator that could not be downloaded or started still leaves `Incomplete` in the summary.

C-10 holds structurally. The comparison job's token is its own `github.token`, granted contents and actions read; the job's definition contains no `secrets.` reference. Its checkout persists no credential, so neither the checkout nor the `--shared` revision clones hold a token. The token is in the `compare` step's environment only, and every measured process gets `RevisionEvidence.ChildEnvironment`'s allowlist, which omits it. The release job's write token stays in the release job; no artifact carries a token. The comparator is the build job's output from the tagged commit; neither later job builds it.

The release job's checkout persists no credential either, so during `attach`'s wait of up to 100 minutes no write token lies in its workspace or its git configuration. The workflow token is set in the environment of three steps only: "Create GitHub Release", as `GH_TOKEN`, and the two advisory comparison steps, "Request the release comparison" (`request`) and "Attach the comparison report" (`attach`), as `GITHUB_TOKEN`. Since `0055-F6` item 0327, "Push release packages" carries no workflow token: its `NUGET_API_KEY` is a short-lived nuget.org key that the "Log in to NuGet" step before it mints from the job's OIDC token through NuGet Trusted Publishing (`0055-F6` § 7, "Item 0327 amendment"). A step split cannot narrow either credential. Actions issues one `GITHUB_TOKEN` per job, `attach`'s artifact wait needs that token's actions read, and the runner process holds the token for the whole job whichever steps name it. With `id-token: write`, the runner sets the OIDC request credential, `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, in the environment of every step of the job, not only the login step: the advisory comparison steps and `attach`'s wait of up to 100 minutes included. A separate job for the wait would be either a third job with contents write, which C-10 rules out, or one without the grant `attach` needs to publish. Nothing in the workflow keeps either credential from a measured revision of the comparison job on the same host: under a shared operating-system account, a measured process can read the release job's step environment during the wait, and that environment now holds the means to request an OIDC token and exchange it for a nuget.org push key, not only the workflow token. The owner accepts that exposure for the workflow token and relies on one release run at a time, not on isolation between the pool's runners (A-5, decision 0005 addendum). The OIDC request credential is the same A-5 exposure applied to the `id-token: write` grant item 0327 added; neither A-5 nor the addendum names that grant.

[`ReleaseTrigger`](../Workflow/ReleaseTrigger.cs) admits only a `push` of a `refs/tags/v…` ref; every other event, including workflow dispatch, makes each command a no-op with no summary (B-023): `RequestAsync`, `AttachAsync` and `ComparisonRun.RunAsync` return no outcome, so `AdvisoryStep` writes nothing. [`RunContext`](../Model/RunContext.cs) reads event, ref, repository, run id, attempt and commit from the Actions environment.

[`ReleaseReporting`](../Workflow/ReleaseReporting.cs)`.RequestAsync` reads the catalog, requires the release of this tag to be at this run's commit, gets or creates the durable pair asset, then writes `pair.json` and a [`ComparisonReceipt`](../Model/ComparisonReceipt.cs) (`receipt.json`: format version 1, repository, run id, attempt, commit, release id and pair digest), each create-new. A failure before the pair is saved is `PairPersistence`; nothing is uploaded and the comparison job's receipt wait ends `Incomplete`.

[`ComparisonRun`](../Workflow/ComparisonRun.cs) waits up to 30 minutes for this run and attempt's request, validates it with `ReleaseTrigger.Validate` against this run, attempt and commit and the pair's digest, and then:

- No predecessor: no process runs. The session's previous side has the commit of forty zeros, `unavailable` harness and exporter, no invocation, null conditions and an unknown empty inventory; the current side has this commit and otherwise the same. `ComparisonEvaluation.NoBaseline` gives the document and the bundle has no raw exports or mappings (B-003). `session.json` and `report.json` keep the forty zeros `ComparisonJson.ReadSession` requires; `report.md` shows `None` as the previous product commit when the pair has no predecessor.
- An unresolved predecessor is `Collection` incomplete through `ReportingOutcome.UnresolvedPredecessor`, naming the tag and its failure and saying that the saved pair fixes this predecessor for every rerun, so a rerun reports the same; no older release is substituted (B-024).
- Otherwise it collects with session id `<runId>-<attempt>`, comparator commit this run's commit, comparator version the assembly's informational version, runner identity `RUNNER_NAME`, filter `*` and job `short`. The short job is chosen to keep the full selection within the 25-minute revision bound, a judgement from the default job's iteration counts, not a measurement. An unavailable side is `Collection` incomplete with each side's reason. Each export is read again from the workspace without per-file expected cases, so `CasePairing` alone adds the missing ones.
- `Parsing` has two causes. An export the collector read that can no longer be read (an `IOException` or `UnauthorizedAccessException`) is `Parsing` incomplete with no detail. An export collection accepted but `BenchmarkEvidenceReader` rejects is `Parsing` incomplete naming each such side and the reader's fixed diagnostic, such as `Current revision: Exporter version or Release/debugger evidence is unsupported.` Collection checks only the host conditions and the job, so a non-Release configuration, an attached debugger, a producer other than 0.15.8, a record without `FullName` or `Measurements`, or a duplicate property reaches the reader. No bundle is rendered.
- Otherwise pairing, evaluation and a completed outcome whose reason is each side's inventory reason, then the bundle. Evaluation has no failure stage in the run: what `CasePairing.Pair` and `ComparisonEvaluation.Evaluate` receive is already valid, because every workload key was computed by the reader or by `RevisionEvidence.Inventory` under their own `InvalidDataException` handling, a comparable metric has exactly one valid observation per side in a recognised unit, and arithmetic overflow is `Insufficient evidence` inside evaluation. Invalid evidence is a judgment, never an exception, so `ComparisonRun` catches nothing there and returns no `Failed(Evaluation)` of its own. `ReportingStage.Evaluation` names a completed outcome's stage, and an unexpected exception thrown while evaluation is the stage in progress is summarised as `Failed(Evaluation)` by `AdvisoryStep`.

It writes `outcome.json` and the bundle into the result directory. `AttachAsync` re-validates the request, waits up to 100 minutes for the result, rejects an outcome that already claims a report, and returns an incomplete one as delivered. A completed one must have the bundle `comparison-<releaseId>-<runId>-<attempt>.zip` that `ReportBundler.Validate` accepts, whose `pair.json` is the saved pair, whose session is this run and attempt, and whose `report.json` comparison gives, through `ReportingOutcome.Completed`, the outcome's judgment and the outcome's flags in order; otherwise it is `ResultTransport`. The outcome summarised is that one, derived from the validated `report.json` with the delivered inventory reason, so no flag reaches the summary that the bundle does not carry. `ReportBundleAssetStore` then publishes it, and only its confirmed result becomes the outcome's [`ReportReference`](../Model/ReportReference.cs); a failure keeps the judgment and flags with `Attachment` incomplete.

[`RunArtifacts`](../Workflow/RunArtifacts.cs) lists the run's artifacts by exact name across every page, polling every 30 seconds, within the bound from the injected `TimeProvider`. Exactly one unexpired match is accepted and more than one is a transport failure. Every entry is checked as relative, a regular file and unique ignoring case before any is written, each create-new under `.artifacts/benchmarks/comparison/<runId>-<attempt>/request` or `/result`. A transient failure of a listing or download - no response, a request timeout, HTTP 429 or a 5xx - is retried at the next poll within the same bound; any other HTTP failure, an unsafe archive or a second match ends the wait as a transport failure.

`ReleaseReporting` and `ComparisonRun` take that action as an optional last constructor argument and call it on entering each stage; `Program` passes the one `AdvisoryStep` gives it. The stages entered, in order, with `Program`'s starting stage first:

| Command   | Starting stage    | Stages entered                                                                                                                                                                                                       |
| --------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `request` | `PairPersistence` | `PairPersistence` (catalog read and pair asset), then `Receipt` (writing `pair.json` and `receipt.json`)                                                                                                             |
| `attach`  | `Receipt`         | `Receipt` (reading and validating the request), `ResultWait`, `ResultTransport` (reading and checking the result), `Attachment` (publishing the bundle)                                                              |
| `compare` | `ReceiptWait`     | `ReceiptWait`, `Receipt` (reading and validating the request), then `Collection`, `Parsing`, `Evaluation`, or `Evaluation` alone without a predecessor; `Rendering`, then `ResultTransport` (writing `outcome.json`) |

Marking only names the stage of an unexpected exception; every explicit `Failed` above keeps its own stage. Cancellation is handled as before: a caller cancellation that escapes a step is an exception like any other and is summarised at the stage in progress.

A [`ReportingOutcome`](../Model/ReportingOutcome.cs) names its [`ReportingStage`](../Model/ReportingStage.cs) and [`ReportingState`](../Model/ReportingState.cs). Each stage has one fixed cause and a remedy that a rerun can honour, because a rerun reaches the comparison steps past a Release already published at its commit: "Re-run all jobs to retry." for `PairPersistence`; "Re-run all jobs to retry; a pair already saved on the release is reused." for `Receipt` and `ReceiptWait`, where the comparison job cannot tell whether `request` saved the pair; "Re-run all jobs to retry with the saved pair." for every later stage. An unresolved predecessor offers no retry, since the saved pair fixes it. Detail text is sanitised: control characters become spaces and a rooted or embedded path token becomes `[path removed]`; `ComparisonJson.ReadOutcome` rejects an outcome that still holds one. A completed outcome carries every `Review required` metric as a [`ReviewFlag`](../Model/ReviewFlag.cs) in case and metric order.

[`AdvisoryStep`](../Workflow/AdvisoryStep.cs) runs each command: it writes `Incomplete: comparison pending` to the step summary first, hands the step an `Action<ReportingStage>` that records the stage it enters, maps any unexpected exception, `OutOfMemoryException` aside, to `Failed(<last stage entered>, null)`, else to the command's starting stage, replaces the summary with [`RunSummary`](../Workflow/RunSummary.cs)'s rendering, and exits 0. The summary gives the incomplete reason, the overall judgment when known, a completed outcome's inventory reason, the confirmed report link `https://github.com/<repository>/releases/download/<tag>/<bundle>` only after attachment, and the flagged cases with their reasons (B-014, B-018). Outside Actions it writes `.artifacts/benchmarks/summary.md`.

With one free runner in the pool, OQ-4's default holds. If the comparison job takes it first, it waits its 30 minutes, uploads a `ReceiptWait` outcome and ends; publication then runs up to that much later, never prevented, and the release job's attach finds that result and reports it. If the release job takes it first, its attach ends `ResultWait` after 100 minutes and the later comparison result is not attached. Both are `Incomplete` and advisory (A-4, C-1).

### Evidence reading, identity and evaluation

Discover the union of expected native harness cases on both revisions, including
failed cases. Missing historical harness/export/identity metadata is an explicit
gap. The importer supports explicitly recognised BenchmarkDotNet full-JSON shapes
and a session sidecar; unknown shapes cannot be treated as empty valid inventories.
A supported exporter adapter must declare the value/unit fields and how it decodes
confidence levels. BenchmarkDotNet's [JSON sample](https://benchmarkdotnet.org/articles/samples/IntroExportJson.html)
serialises an enum-like confidence `Level`; never read it as a percentage or use
standard deviation as a confidence interval. Support is bound to the producer
version and tested with invented payloads of that shape; no current default is
silently assigned to historical uncertainty. An audited mapping can establish a
historical workload contract from its source revision, fixture definition and
measured operation; matching names alone cannot.
Store that mapping and its source digest with the evidence. Unavailable discovery
is distinct from a known empty inventory and cannot imply `Added` or `Removed`.

Case pairing uses operation identity plus canonical parameters; differing fixture
contract, input, boundary or conditions produces `Not comparable`. A known
one-sided case is `Added`/`Removed`; each size stays separate. Every case carries
the required metrics its measuring contract supplies. Mean time and managed bytes
per operation are separate; child peak memory is informational with its own
observer, never substituted for managed allocation. Harness allocation remains
labelled as harness allocation for startup cases.

Validation order is decode and duplicate detection → per-metric validity →
equivalence → unit conversion → arithmetic → review screen → overall reduction.
Two records for the same side/case/metric are invalid duplicate evidence, not
last-write-wins or an average; keep both locators. Other valid metrics may still
flag. Non-finite, negative or missing values cannot prove a clean result. Timing
means must be positive, intervals finite and ordered around the mean, and the
confidence level known and valid. Absent/invalid uncertainty is `Insufficient
evidence`; differing valid confidence levels are `Not comparable`.

Normalise recognised ns/µs/us/ms/s scales to ns per operation and B/KB/MB or
B/KiB/MiB to bytes per operation with explicit decimal/binary factors. Unknown
units or incompatible dimensions/observers are `Not comparable`; conversion
failure or overflow is invalid evidence. Never infer a scale from display width.
Calculate on unrounded values and round only rendered numbers. Apply decision
0002's strict thresholds and zero-allocation policy per metric, then reduce:
any flag → `Review required`; otherwise any required gap or empty union →
`Incomplete`; otherwise → `No regression flagged`. No predecessor → `No baseline`
with no regression judgment. Reporting failure is tracked separately so an
already-computed review flag survives an incomplete attachment.

### Rendering and durable publication

Render Markdown and JSON from one immutable `ComparisonDocument`. A bundle
contains `report.md`, `report.json`, `pair.json`, `session.json`,
`evidence-manifest.json`, raw exporter documents and supported identity mappings.
Preserve raw numerical evidence; sanitise only path-bearing metadata at ingestion,
recording that transformation, and reject a value that only embeds an absolute
path ([decision 0004](decisions/0004-reject-an-absolute-path-embedded-in-any-bundle-value.md)). Reject unknown payloads that cannot be safely
retained; do not attach arbitrary logs, generated projects or absolute paths.
Keep original local exports in the workspace only. Every referenced evidence file
must exist with its recorded digest; reject rooted paths, traversal and symlinks.

Use one self-contained ZIP per attempt, named
`comparison-<releaseId>-<runId>-<attempt>.zip`, with bundle-relative links valid
after extraction. The pair asset remains separate for rerun recovery. The
release job validates the returned bundle and attaches it through the existing
workflow token. Verify the uploaded asset before linking it as retained evidence;
failed or partial uploads are `Incomplete`. Insert-only attempt names prevent
reruns from making earlier report references stale. The summary lists flagged
cases/reasons and the confirmed Release asset link; before successful attachment
it states the incomplete reporting stage and retains known flags without a
successful report link. Expiring workflow artifacts removes transport only;
reports and their entire evidence closure remain in the Release bundle.

The fixtures are independently invented, never captured exports. `ExportData` carries the pinned producer's wire shape. Contract tests distinguish decimal/binary units and typed parameter identity; `ComparisonEvaluationUnitTests` pins the conversion and delta arithmetic. A non-finite mean has no `decimal` representation, so the unit tier cannot hand one to evaluation; the reader turns it into invalid evidence, which the B-013 outline proves end to end. Tool peak memory has no reader yet, so its informational row is proven with generated observations only. Timing uncertainty may cross zero as long as the mean is positive and finite bounds contain it. No test starts a benchmark, uses a live release, credential or network, or asserts elapsed time or measured allocation. The provider adapters run against `HttpMessageHandler`; persistence tests use owned temporary directories. All test classes carry their one tier trait, and the new project discovers the shared governance test. The full-build result is recorded in the delivery report rather than duplicated here.
