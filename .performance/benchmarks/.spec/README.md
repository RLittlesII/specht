# Specification: Benchmark harness

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-09 -->

No cost the tool incurs is measured, so every specification constraint about time, scaling or allocation is unverifiable, and a design chosen for its cost is never checked against it. This Feature removes that failure state: the repository has one benchmark project that any developer runs with one build target and CI runs on every build, with memory measured on every benchmark and the results kept as files a person and a machine can read - and nothing it measures ever fails a build.

## 7. Technical Design

<!-- last written by: implementer, 2026-10-11 (item 0147: the tree and its store, replacing the static generator; item 0146: the project, its package version, the entry point, the shared configuration, the project-file lookup and the hand-run record) -->

Design for item `0146` (B-001, B-002, B-007; C-2 to C-6) and item `0147` (B-015, B-016; C-7 to C-9, under `### The tree generator`), as built. The `Benchmark` target (`0148`) and the CI step (`0149`) are not designed here.

- **The project** is [`benchmarks.csproj`](../benchmarks.csproj) in `.performance/benchmarks/`: a console project with assembly `specht.benchmarks` and root namespace `Specht.Benchmarks`, set as `tool.csproj` and `tests.csproj` set theirs. The owner fixed that naming on 2026-10-11 - the folder and file named for the role, the assembly prefixed - and it replaces the folder `.performance/specht.benchmarks` the Feature was specified under; the specifications, records and items moved with it (`git mv`; epic `0109` § Placement). § 4 C-2 now names `.performance/benchmarks` (owner, 2026-10-11), and [decision 0001](decisions/0001-benchmarks-report-and-never-gate.md) records the change in a dated Reversal entry. It references `src/specht` and `BenchmarkDotNet`, inherits `IsPackable=false`, and declares no `IsTestProject` (C-2). Implicit usings stay off, as the root properties leave them for every project but the two copied ones.
- **It is compiled with the solution** because [`specht.slnx`](../../../specht.slnx) lists it, under `/.performance/` (B-001). Nothing the default build runs starts it (B-002): the mechanism is § 8's.
- **The package version** is `BenchmarkDotNet` 0.15.8 in [`Directory.Packages.props`](../../../Directory.Packages.props), in a `Benchmarking` group (C-3). It was the newest stable release on 2026-10-11; 0.16.0 existed only as a preview. Transitive pinning moved nothing: the solution restored and built with no downgrade or conflict warning.
- **The entry point** is [`Program.cs`](../Program.cs): one `BenchmarkSwitcher` over the benchmark assembly, given the command line and one `BenchmarkConfiguration` (C-5, decision 0002). No other code starts a run.
- **The exit code** is the entry point's: `1` when any summary the switcher returns has a critical validation error or a report that did not succeed - a benchmark that failed to generate, to build, or whose process threw - and `0` otherwise, whatever was measured. BenchmarkDotNet itself exits `0` in both cases. This is the mechanism B-011 and B-012 need from the process; the target that reads it is `0148`'s. A filter that matches nothing, and an argument the library rejects, return no summary and so exit `0`; nothing here changes that, so item `0148`'s target must account for both (B-004; B-008's `--artifacts`).
- **The shared configuration** is [`BenchmarkConfiguration`](../BenchmarkConfiguration.cs), a `ManualConfig` whose constructor starts no run. It starts empty, not from the library's default configuration, because that one carries the CSV and HTML exporters and offers no way to remove them (decision 0002). It adds the console logger, the default column providers, the default configuration's analysers and validators, the memory diagnoser (C-4, B-007), and exactly two exporters: GitHub-flavoured Markdown and full JSON. No benchmark class carries `[MemoryDiagnoser]`.
- **The results folder** is not in the configuration. Decision 0002 gives it to the caller's `--artifacts`; a run by hand that names none writes the library's default `BenchmarkDotNet.Artifacts/` under the working directory, which is gitignored.
- **The toolchain** is the library's out-of-process one - a generated project, built with the `dotnet` CLI and run in its own process (C-6, decision 0003) - with one part replaced. BenchmarkDotNet finds the benchmark project by searching every folder under the solution root for a project file named after the benchmark assembly. With the owner's naming that search fails: `Unable to find specht.benchmarks in <root> and its subfolders`. [`BenchmarkProjectGenerator`](../BenchmarkProjectGenerator.cs) derives from the library's `CsProjGenerator` and overrides that one lookup: it walks up from the benchmark assembly's own location to the first folder holding `benchmarks.csproj`, and falls back to the library's search when there is none. The configuration builds a `Toolchain` from that generator and the library's `DotNetCliBuilder` and `DotNetCliExecutor`, from the library's `net10.0` settings, and adds it as a mutator job, so it applies to the default job and to any job `--job` names. 0.15.8 offers no property, attribute or setting that names the project file. So the toolchain is a `Toolchain` built from this project's generator and the library's own .NET CLI builder and executor: out of process and a Release build, as C-6 requires, but not the library's `CsProjCoreToolchain` instance.
- **What that replacement costs.** The target framework is named in the configuration, so a framework change edits it. The toolchain is not the library's `CsProjCoreToolchain`, whose constructor is internal, so its extra validation of the installed SDK does not run; a missing SDK surfaces as a failed build. A summary's header prints `Toolchain=.NET 10.0`. And `--inProcess` on the command line is overridden - the run stays out of process - so a by-hand in-process run is not available; [decision 0003](decisions/0003-a-finding-comes-from-the-default-toolchain.md)'s Reversal entry (2026-10-11, a `spec-author` default the owner may reverse) withdraws the allowance it first gave.
- **What it also removes.** The library's search throws `Found more than one matching project file` when two project files under the root share the name, which a checkout holding worktrees of itself under `.claude/worktrees/` would produce. The lookup from the assembly's location never searches the root. This was shown inside one worktree by placing copies of the project file under the gitignored `.artifacts/`; it was not run from a checkout that holds worktrees.
- **Nothing inherited was neutralised.** The generated project sits under the benchmark project's `bin/` and imports the root `Directory.Build.props`: warnings as errors, code style in build, the analyzer package, Nerdbank.GitVersioning, central package versions with transitive pinning, and the `Content` globs. It restored and built unchanged.
- **The run log is not a result.** BenchmarkDotNet's console output and the `.log` file it writes beside `results/` carry absolute paths; the exporters' files under `results/` are what C-13 publishes.

### The tree generator

Item `0147` (B-015, B-016; C-7 to C-9; [decision 0004](decisions/0004-a-generated-clean-tree-sized-in-specifications.md)), as built.

- **Three types, one per file.** [`SpechtTree`](../SpechtTree.cs) is the state: the tree's files, built for a size by `SpechtTree.Of` and held in `Files`. [`SpechtTreeFile`](../SpechtTreeFile.cs) is one of them: a root-relative path and its bytes. [`SpechtTreeStore`](../SpechtTreeStore.cs) is the persistence: constructed over an `IFileSystem`, its `Save` writes a tree under a root. They replace the static `SpecTreeGenerator`, which built the content and wrote the files in one method (owner, pull request #114; § 10, 2026-10-11). There is no template file, no options and no builder.
- **Why state and persistence are split.** The tree knows what it holds and nothing about where it goes; the store knows how to write and nothing about what a tree holds. So B-016's claim - the same size gives the same files, at relative paths - is read off the object with no file system, and the store is shown over an in-memory file system, where the old tests could only write to disk and read back. `SpechtTree` names no `IFileSystem` and no root. The store takes `IFileSystem`, the abstraction the engine already reads through; no interface was added over either type, because nothing substitutes for them.
- **`SpechtTree` has no public constructor.** `Of` is the only way to one, so a tree that exists is one built for a size (C-8). Each call builds a new tree and nothing is cached: a benchmark that holds a tree decides how long.
- **A file's path** is written with `/` and is relative to the tree's root by construction: it is assembled from literals, the manifest's own relative path and the four-digit index, and never from a root (C-9). The store is where the separator becomes the file system's: `Save` replaces `/` with the file system's directory separator, joins the result to the root, creates the file's directory, and writes the file's bytes through a stream with no copy. It writes the tree's files and nothing else.
- **They are compiled into two assemblies.** `specht.benchmarks` compiles the three files as its own, and `test/tests/tests.csproj` links the same three, as `acceptance.csproj` links `SpecTree.cs`. A project reference was not taken: the benchmark project is an executable with its own entry point, and referencing it would bring BenchmarkDotNet into the test assembly. So each file names every namespace it uses, because implicit usings are off in one assembly and on in the other, and they use the engine, `System.IO.Abstractions` - which both assemblies already receive through the engine - and the base class library only: nothing from BenchmarkDotNet and no other type of the benchmark project.
- **The caller owns the directory.** `root` is a directory the caller creates and deletes (C-10); its name is the one thing that may vary between runs, and it may be relative or absolute. The store checks neither that it is empty nor that it exists, and `Of` does not check the size: no claim states any of those cases.
- **The manifest** is the engine's embedded default, the resource `specht.default-manifest.json` of the assembly that declares `SpecManifest`, copied stream to byte array with no decoding. That resource is this repository's `.spec/schema/spec-structure.schema.json`, embedded by [`specht.csproj`](../../../src/specht/specht.csproj). The engine has no public accessor for it, and none was added: a member in `src/` whose only caller is a benchmark is the seam `0109-F2` C-11 rules out, and `init` is not a second caller - it reads the tool assembly's `schema/v<n>/` copy through `InitWriter.ShippingCopy`, not this resource. The cost is one resource name repeated here; if the engine renames it `Of` throws and every tree test fails.
- **The frontmatter schemas** are the three texts of the schema version the manifest pins, selected from `SchemaVersions.Embedded` and placed beside the manifest under the file names the manifest's `frontmatterSchemas` gives. Neither a schema file name nor a schema folder is written in the tree: the folder is the directory of `SpecManifest.RelativePath`.
- **How `Of` stays off the disk.** The static read the manifest back through `SpecManifest.Load`, which takes a file system and a root; the engine's parse of manifest text, `SpecManifest.Read`, is private. `Of` instead parses the manifest's bytes with `System.Text.Json` and reads two keys, `frontmatterSchemas` and `schemaVersion`. Two engine rules are repeated to do it, and both are reversible by a public in-memory read of the manifest, which spike `0153` weighs: the three role names `feature`, `task` and `epic`; and the rule that a manifest with no `schemaVersion` pins `0.1.0`, as `SpecManifest` reads it, written as a literal because the embedded manifest carries no such key. The engine's own validation of the manifest does not run in `Of`; it runs when the check loads the saved tree, which the integration test does at every size. `SemanticVersion.TryParse` and `SchemaVersions.Select` are the engine's.
- **What the check reads.** `SpechtRunner.Run(root)` needs only the manifest on disk; it takes the frontmatter schemas from the embedded version set. The three schema files are in the tree because decision 0004 makes the tree the shipped copy, and because `SpecSchemas.Load(fileSystem, root)`, a stage `0109-F2` may measure, reads them from disk.
- **Why not the assembly or its directory.** `typeof(SpechtTree).Assembly` is a different assembly in a test and in a benchmark, and `AppContext.BaseDirectory` is a third place in BenchmarkDotNet's generated executable. The engine assembly is the same in all three. The tree never reads this repository's `.spec/` tree by path (C-7).
- **The tree** is `4 + 2n` files for `n` specifications:

  ```
  .spec/schema/spec-structure.schema.json
  .spec/schema/feature-spec.frontmatter.schema.json
  .spec/schema/task.frontmatter.schema.json
  .spec/schema/epic.frontmatter.schema.json
  features/feature-0001/.spec/README.md
  features/feature-0001/.spec/feature-0001.feature
  ```

  and so on to `feature-<n>`. The default manifest discovers each `README.md` through its `features` layout, `**/.spec/README.md`, and excludes the root `.spec/`. No epic file and no item file is written; no rule asks for one.

- **The shape's numbers** (decision 0004 leaves them to `implementer`; the owner may reverse them):

  | What                                    | Value                                                                                                    |
  | --------------------------------------- | -------------------------------------------------------------------------------------------------------- |
  | Claims per specification                | 3: `B-001` to `B-003`, each with one § 9 row and one tagged scenario                                     |
  | Sections per specification              | 14: the twelve, then `Tasks` and `Scoring`, in the manifest's order                                      |
  | Tables per specification                | 8: § 2 to § 6, § 9, § 12 and `Scoring`; § 3 and § 9 hold three rows, `Scoring` two, the others one       |
  | Frontmatter keys                        | 24: the template's, in the template's order                                                              |
  | Identity                                | epic `0001`; id `F<index>`, `F1` to `F1000`                                                              |
  | Folder                                  | `features/feature-<index>`, the index written as four digits, so ordinal order is index order up to 9999 |
  | Dependencies between specifications     | None: `depends_on`, `blocks`, `children` and `spikes` are empty                                          |
  | Maturity                                | `spec_status: approved`, `status: done`; every § 9 row `Covered`, the one § 12 row approved              |
  | Dates                                   | `created` and `updated` are the literal `2026-01-01`; `scored_on` and `synced_at` are null               |
  | Size of one specification, as generated | About 2.4 KB                                                                                             |

- **Approved, not draft.** The approval rule returns at once for a specification that is not approved, and reads every § 9 and § 12 row of one that is. An approved tree is the path a passing consumer's repository takes, so every rule does its work on every specification.
- **What varies between specifications** is the index alone: the folder and companion file name, the frontmatter `id`, and the four-digit number in the title, the description, § 1 and the `Feature:` line. Every other byte is the same in every specification.
- **Determinism (C-8, C-9).** The text is assembled from an array of lines joined with a literal `\n`; no multi-line string literal is used, because one takes the line endings its source file was checked out with. Each number is formatted with the invariant culture. Each date is a literal. Every generated text is encoded with one UTF-8 encoding that emits no byte-order mark, and the manifest's bytes are the resource's. Files are added in index order, and nothing is enumerated. The tree reads no clock, GUID, random value, environment variable, user or machine name, and holds no path but the relative ones. The rendering was carried over from the static unedited, so a file's bytes are the bytes the static wrote.
- **Rendering is not a separate surface.** The specification text, the scenario text and the three-digit claim number are private functions of the index with no branch and no boundary inside the four sizes; `Of` is the only way in, and every test goes through it. A fifth digit in the index would break the folder order, which no claim reaches.
