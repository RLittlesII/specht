# Specification: Benchmark harness

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-09 -->

No cost the tool incurs is measured, so every specification constraint about time, scaling or allocation is unverifiable, and a design chosen for its cost is never checked against it. This Feature removes that failure state: the repository has one benchmark project that any developer runs with one build target and CI runs on pushes to main, with memory measured on every benchmark and the results kept as files a person and a machine can read - and nothing it measures ever fails a build.

## 7. Technical Design

### Resource inputs after ADR-0010 D1

**Implemented 2026-10-13; superseded by item `0153`**, which moved the types
into the engine and gave `SpechtTreeGenerator` the reads below (§ 7
`### The tree generator`). The earlier generator account
below describes the implementation at its cited commits. D1 replaces its direct
assembly read, static version access and repeated pin parsing as follows.

`SpechtTree.Of` receives the size, the resource reader's original default-manifest
bytes, its already parsed `SpechtStructure`, and the selected `SchemaVersion`.
It still returns a new in-memory tree for the same size; it opens no resource or
file and holds no container. It uses the parsed frontmatter-schema names, the
selected schema texts and the store's relative-path constants. No manifest is
serialized again, so the tree keeps the original manifest bytes. No engine API
is added solely for the benchmark: the resource reader and parser are already
check dependencies.

`CheckBenchmarks` builds its existing provider first in `GlobalSetup`, resolves
the resource snapshot, parser and runner from that provider, parses/resolves the
default once and passes those values to `Of` before saving the tree. The measured
`Check` call stays the runner's whole run. Resource loading, service resolution
and generation stay outside measurement. Other tree callers and tests supply
the same explicit inputs at setup. Types remain in the benchmark assembly until
the later tree move; the existing project reference stays.

This replaces `SchemaVersions.Embedded`, `SpecManifest.Load`, the formerly
private `SpecManifest.Read`, and the direct embedded-resource copy mentioned
below. D1 neither moves the types nor changes the benchmark workload or scope.

Design for item `0146` (B-001, B-002, B-007; C-2 to C-6) and items `0147` and `0153` (B-015, B-016; C-7 to C-9, under `### The tree generator`), as built. The `Benchmark` target is described below (`0148`); the CI integration is described below (`0149`).

- **The project** is [`benchmarks.csproj`](../benchmarks.csproj) in `.performance/benchmarks/`: a console project with assembly `specht.benchmarks` and root namespace `Specht.Benchmarks`, set as `tool.csproj` and `tests.csproj` set theirs. The owner fixed that naming on 2026-10-11 - the folder and file named for the role, the assembly prefixed - and it replaces the folder `.performance/specht.benchmarks` the Feature was specified under; the specifications, records and items moved with it (`git mv`; epic `0109` § Placement). § 4 C-2 now names `.performance/benchmarks` (owner, 2026-10-11), and [decision 0001](decisions/0001-benchmarks-report-and-never-gate.md) records the change in a dated Reversal entry. It references `src/specht` and `BenchmarkDotNet`, inherits `IsPackable=false`, and declares no `IsTestProject` (C-2). Implicit usings stay off, as the root properties leave them for every project but the two copied ones.
- **It is compiled with the solution** because [`specht.slnx`](../../../specht.slnx) lists it, under `/.performance/` (B-001). Nothing the default build runs starts it (B-002): the mechanism is § 8's.
- **The package version** is `BenchmarkDotNet` 0.15.8 in [`Directory.Packages.props`](../../../Directory.Packages.props), in a `Benchmarking` group (C-3). It was the newest stable release on 2026-10-11; 0.16.0 existed only as a preview. Transitive pinning moved nothing: the solution restored and built with no downgrade or conflict warning.
- **The entry point** is [`Program.cs`](../Program.cs): one `BenchmarkSwitcher` over the benchmark assembly, given the command line and one `BenchmarkConfiguration` (C-5, decision 0002). No other code starts a run.
- **The exit code** is the entry point's: `1` when any summary the switcher returns has a critical validation error or a report that did not succeed - a benchmark that failed to generate, to build, or whose process threw - and `0` otherwise, whatever was measured. BenchmarkDotNet itself exits `0` in both cases. This is the mechanism B-011 and B-012 need from the process; the target that reads it is `0148`'s. A filter that matches nothing, and an argument the library rejects, return no summary and so exit `0`; nothing here changes that, so item `0148`'s target must account for both (B-004; B-008's `--artifacts`).
- **The shared configuration** is [`BenchmarkConfiguration`](../BenchmarkConfiguration.cs), a `ManualConfig` whose constructor starts no run. It starts empty, not from the library's default configuration, because that one carries the CSV and HTML exporters and offers no way to remove them (decision 0002). It adds the console logger, the default column providers, the default configuration's analysers and validators, the memory diagnoser (C-4, B-007), and exactly two exporters: GitHub-flavoured Markdown and full JSON. No benchmark class carries `[MemoryDiagnoser]`.
- **The results folder** is not in the configuration. Decision 0002 gives it to the caller's `--artifacts`; a run by hand that names none writes the library's default `BenchmarkDotNet.Artifacts/` under the working directory, which is gitignored.
- **The toolchain** is the library's out-of-process one - a generated project, built with the `dotnet` CLI and run in its own process (C-6, decision 0003) - with its project lookup and build-output location replaced. BenchmarkDotNet finds the benchmark project by searching every folder under the solution root for a project file named after the benchmark assembly. With the owner's naming that search fails: `Unable to find specht.benchmarks in <root> and its subfolders`. [`BenchmarkProjectGenerator`](../BenchmarkProjectGenerator.cs) derives from the library's `CsProjGenerator` and overrides that one lookup: it walks up from the benchmark assembly's own location to the first folder holding `benchmarks.csproj`, and falls back to the library's search when there is none. The configuration builds a `Toolchain` from that generator and the library's `DotNetCliBuilder` and `DotNetCliExecutor`, from the library's `net10.0` settings, and adds it as a mutator job, so it applies to the default job and to any job `--job` names. 0.15.8 offers no property, attribute or setting that names the project file. So the toolchain is a `Toolchain` built from this project's generator and the library's own .NET CLI builder and executor: out of process and a Release build, as C-6 requires, but not the library's `CsProjCoreToolchain` instance.
- **What that replacement costs.** The target framework is named in the configuration, so a framework change edits it. The toolchain is not the library's `CsProjCoreToolchain`, whose constructor is internal, so its extra validation of the installed SDK does not run; a missing SDK surfaces as a failed build. A summary's header prints `Toolchain=.NET 10.0`. And `--inProcess` on the command line is overridden - the run stays out of process - so a by-hand in-process run is not available; [decision 0003](decisions/0003-a-finding-comes-from-the-default-toolchain.md)'s Reversal entry (2026-10-11, a `spec-author` default the owner may reverse) withdraws the allowance it first gave.
- **What it also removes.** The library's search throws `Found more than one matching project file` when two project files under the root share the name, which a checkout holding worktrees of itself under `.claude/worktrees/` would produce. The lookup from the assembly's location never searches the root. This was shown inside one worktree by placing copies of the project file under the gitignored `.artifacts/`; it was not run from a checkout that holds worktrees.
- **Nothing inherited was neutralised.** Since `0148` the generated project sits under the configured artifacts folder's `build/` subdirectory and imports the root `Directory.Build.props`: warnings as errors, code style in build, the analyzer package, Nerdbank.GitVersioning, central package versions with transitive pinning, and the `Content` globs. It restored and built unchanged.
- **The run log is not a result.** BenchmarkDotNet's console output and the `.log` file it writes beside `results/` carry absolute paths; the exporters' files under `results/` are what C-13 publishes.

### The Benchmark target

### The tree generator

<!-- last written by: implementer, 2026-11-02 (item 0166: the store's load and the tree file's decoding; item 0153: the four types are engine code, decision 0005; item 0334: the generator also writes `test/GeneratedTests.cs`, so the tree is `5 + 2n` files) -->

- **Four types, one per file, in `Specht.Tree`** (ADR-0010 § "The layout"), under [`src/specht/Tree/`](../../../src/specht/Tree/). [`SpechtTree`](../../../src/specht/Tree/SpechtTree.cs) is the state: a tree's files, held in `Files` in the order its public constructor was given them. [`SpechtTreeFile`](../../../src/specht/Tree/SpechtTreeFile.cs) is one of them: a root-relative path and its bytes; from item `0166` its `Text()` decodes them as `File.ReadAllText` does, the one place the check decodes a tree file. [`SpechtTreeStore`](../../../src/specht/Tree/SpechtTreeStore.cs) is the persistence: constructed over an `IFileSystem`, its `Save` writes a tree under a root; it is the `SpechtTreeStore` of ADR-0010 § "I/O is confined", with `Save` and no load until item `0166`, whose `Load(root, relativePaths)` reads exactly the named files, in the order named, into a tree for the check's `SpechtModelReader` (`0001-F1` § 7, "ADR-0010 stage 6: the model reader"). The benchmarks write their tree with `Save`; the check they measure reads it back with `Load`. [`SpechtTreeGenerator`](../../../src/specht/Tree/SpechtTreeGenerator.cs) holds the rendering: constructed over `SpechtResources` and `SpechtManifestParser`, its `Generate(int)` builds the tree for a size. `AddSpechtEngine()` registers the store and the generator as singletons beside the other engine parts, the store over the registered `IFileSystem`. `.performance/benchmarks/` declares none of the four.
- **The analyzer reads this specification.** Each of the four types, and each of their constructors and methods, carries an `<implements epic="0109" feature="F1" .../>` tag, as `codeAnalysis.enforcement` requires of everything under `src/specht/`. The analyzer resolves a tag only against the Feature inputs [`Directory.Build.props`](../../../Directory.Build.props) lists in `SpechtFeatureInputs`, which named only specifications under `src/`; this one is added to that list, so B-015 and B-016 resolve where decision 0005 keeps them. Its `.feature` file is not added to `SpechtScenarioInputs`: no tag names a scenario.
- **Why a generator instance.** ADR-0010 § "What 'no static' covers" rules out a public static that computes, so `SpechtTree.Of` could not move as written; the owner chose an instance registered in the engine (decision 0005), and the synthetic specification rendering ships inside `specht.tool`. The generator holds no state but its two dependencies, and each call builds a new tree; nothing is cached.
- **Why state and persistence are split.** The tree knows what it holds and nothing about where it goes; the store knows how to write and nothing about what a tree holds. So B-016's claim - the same size gives the same files, at relative paths - is read off the object with no file system, and the store is shown over an in-memory file system. `SpechtTree` names no `IFileSystem` and no root. No interface was added over any of the four, because nothing substitutes for them.
- **`SpechtTree` has a public constructor.** A tree is any list of files, so the test-side fixture builder can write through the store (§ 7 below, "The test tree is fed"). C-8 is the generator's: a tree it generates is one built for a size.
- **A file's path** is written with `/` and is relative to the tree's root by construction: the generator assembles it from literals, the manifest's own relative path and the four-digit index, and never from a root (C-9). The store is where the separator becomes the file system's: `Save` replaces `/` with the file system's directory separator, joins the result to the root, creates the file's directory, and writes the file's bytes through a stream with no copy. It writes the tree's files and nothing else, and overwrites a file that exists.
- **The tests reach them as production code.** [`tests.csproj`](../../../test/tests/tests.csproj) references the engine and the tool and no longer `benchmarks.csproj`; the tests live under `test/tests/Tree/` and resolve the generator and the store from `AddSpechtEngine()` through `EngineServices`. The 21 packages the benchmark reference brought into the test project (BenchmarkDotNet and its graph, listed in this section at item `0147`) left with it.
- **The test tree is fed.** `test/tests/Shared/SpechtTree.cs`, linked into `test/acceptance`, keeps its API and its callers; each of its file writes saves a one-file `SpechtTree` through a `SpechtTreeStore` over the real file system, resolved once from `AddSpechtEngine()`, so writing a file under a root has one implementation (item `0153` criterion 5(b)). Its deletes and its reads of the build output stay on `File` and `Directory`. `InitWriter` is left alone (criterion 5(a)).
- **The caller owns the directory.** `root` is a directory the caller creates and deletes (C-10); its name is the one thing that may vary between runs, and it may be relative or absolute. The store checks neither that it is empty nor that it exists, and `Generate` does not check the size: no claim states any of those cases.
- **The manifest** is the engine's embedded default, `SpechtResources.DefaultManifestBytes`, copied with no decoding. That resource is this repository's `.specht/manifest.json`, embedded by [`specht.csproj`](../../../src/specht/specht.csproj).
- **The frontmatter schemas** are the three texts of the version `SpechtManifestParser.PinnedVersion` resolves for the parsed default manifest, from the registered `SchemaVersions`, placed in `SpechtManifestStore.FrontmatterSchemaFolder` under the file names the manifest's `frontmatterSchemas` gives. Neither a schema file name nor a schema folder is written in the generator.
- **One read of the manifest (item `0153` criterion 6).** The generator parses the default manifest and resolves its pin itself; its callers pass only a size. The three role names `feature`, `task` and `epic` are written once each, in `Generate`, as the keys of `frontmatterSchemas`. The engine's own validation of the manifest runs in that parse.

- **Approved, not draft.** The approval rule returns at once for a specification that is not approved, and reads every § 9 and § 12 row of one that is. An approved tree is the path a passing consumer's repository takes, so every rule does its work on every specification.

Each number is formatted with the invariant culture. Each date is a literal.
