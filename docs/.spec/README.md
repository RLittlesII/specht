# Specification: Docs as first-class citizen

## 1. Business Goal

<!-- last written by: spec-author, 2026-10-07, 2026-10-11 (the command-line reference, decision 0001) -->

No Feature of epic `0001` names documentation as something it owns. Nothing requires a public type or member to carry a doc comment, nothing generates a reference from them, and nothing says where a command's usage documentation lives or that it changes when the command does. So `specht`'s API surface and its usage docs will either not exist, or exist as hand-written prose with no structural guarantee that they still describe the code: `README.md` and the readme the package carries already list commands and options the tool does not accept. This Feature removes that failure state at the mechanism level: the API reference is generated inside the build from the code that defines it, the command-line reference is one page held to the tool's own help by a test, and both are checked by the same build that compiles and tests the code. It stands up no hosted site; that is `0002-F2`, deferred.

## 2. User Needs

### Assumptions

| ID  | Assumption                                                                                                                                                                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-1 | NUKE drives the build (`.build/SpechtBuild.cs`); documentation generation is a NUKE target, not a script outside it.                                                                                                                                                                                          |
| A-2 | .NET's XML documentation comment (`///`) is the doc-comment convention; no third-party syntax is introduced.                                                                                                                                                                                                  |
| A-3 | The generated reference is a build artifact under `.artifacts/`, consumed later by `0002-F2`; this Feature publishes it nowhere.                                                                                                                                                                              |
| A-4 | A "usage doc" is narrative documentation of a command - what it does and how a consumer runs it - distinct from the command's `.spec/README.md`, which is the agreement and stays the agreement. A command's usage doc is its section of `docs/cli.md` (amended 2026-10-11, decision 0001).                   |
| A-5 | The public surface is the public types and members of `src/specht` and `src/tool`. `src/specht` is not packable, but its public surface is the engine's contract with the tool and with every contributor who reads it.                                                                                       |
| A-6 | The command-line surface is what the built tool's own help lists: the default command `specht`, every command reached recursively through the help's command branches, and for each of them every option its help lists, `--help` included. A command or option that is specified and not built is not in it. |
| A-7 | A page names a command or an option when it shows it in code formatting, as part of a `specht` command line or as an option on its own. Prose, paths and the value an option takes are not names.                                                                                                             |

## 7. Technical Design

<!-- last written by: spec-author, 2026-10-07; implementer, 2026-10-11 (B-003 and B-006 to B-011, item 0181; the `--version` entry, item 0182) -->

The design for B-001, B-002, B-004 and B-005 is pending: they are not cut into an item.

**No code (C-7).** Item 0181 adds no type, no build target and no package. The deliverable is the text of `docs/cli.md` and of the two readmes; the surface they are held to is already declared in `src/tool/Program.cs`, `src/tool/Features/Check/CheckCommand.cs` and `src/tool/Features/Init/InitCommand.cs`.

**The page's shape (B-003, B-006, B-007, C-6).** `docs/cli.md` has one `##` section per command, its heading a single code span holding the command as typed, and every section has the same six parts in the same order: the synopsis in a fenced block, one sentence on what the command does, an options table (`Option`, `Value`, `Default`, `Does`), what it prints on stdout, the exit codes it can return, and one example with its output. The shape is the one § 8 reads: a table row whose first cell is a code span starting with `-` is an option's entry.

**`--help` under each command (A-6, B-007).** Spectre.Console.Cli lists `-h, --help` in the help of every command, so A-6 puts it in each command's options and B-007 asks for an entry in each section. It is a row of both tables, not a note above them, so a command added later gets its row the same way.

**Facts stated once (C-6, § 5 row 4).** The page says which exit codes a command can return and links `docs/exit-codes.md` for what each means; it claims a code for a command only where that command's `ExecuteAsync` returns it: `0` to `3` for `specht`, `0` and `2` for `specht init`. The manifest is `docs/configuration.md`'s, the rules `docs/what-it-checks.md`'s and `docs/rules/v1/`'s, the `--json` document `docs/schema/report.schema.json`'s, and the first run `docs/setup.md`'s. Defaults are the ones the `Settings` classes declare.

**The readmes (B-009 to B-011, C-8; `0001-F2` C-9, C-10, B-026).** `README.md` § Usage keeps a two-line synopsis and links `docs/cli.md`, which is also in its Documentation list; its command table is gone. `src/tool/README.md` keeps the same two lines and links the page at its absolute `https` address, as every link in the packed readme is.

**`--version` (C-5; item 0182, `0001-F2` B-040 to B-044).** `Program.cs` sets the application version, so the help of `specht` lists `-v, --version` and the help of `specht init` does not. The `specht` section gains a second synopsis line, a `--version` row, and one sentence each under stdout and exit codes; each readme's synopsis gains the line `specht --version`, its third. The row names the long form, the one § 8 looks for, and not `-v`, which `0001-F2` OQ-7 leaves open. The page describes the option as the only argument and says nothing of it beside another (`0001-F2` OQ-8).

**Not on the page (C-8).** `specht upgrade`, `--explain`, `--report`, `specht manifest` and `specht rules` have no section, entry or synopsis line. `AGENTS.md` § CLI keeps the specified command line and says which of it is not built.

## 8. Testing Strategy

<!-- last written by: spec-author, 2026-10-07; test-writer, 2026-10-11 (B-003 and B-006 to B-011, item 0181) -->

B-001, B-002, B-004 and B-005 are not cut into an item; their strategy is pending, and their scenarios have no step definitions, so `test/acceptance/reqnroll.json` (`missingOrPendingStepsOutcome: Ignore`) reports them skipped.

- **The seam.** `test/acceptance/Docs/CommandLineReferenceSteps.cs` launches the built tool through `AcceptanceTool.Launch`, so it reads the commands `Program.cs` registers. A test under `test/tests` registers its commands itself and would not see a new one. `acceptance.csproj` copies `docs/*.md`, `README.md` and `src/tool/README.md` beside the tests at their repository-relative paths, and the steps read them there.
- **The command-line surface (A-6), as read.** `--help` gives the default command, `specht`, and its options; each name a help page's `COMMANDS:` block lists is appended to its parent command and launched with `--help`, recursively, including branches and their leaf commands. An option is a line of an `OPTIONS:` block that starts with `-`; its names are every `-x` and `--name` before the description, and the last of them, the long one, is the option B-007 looks for.
- **A command section (B-006, B-008).** A heading of any level whose whole text is one code span holding the command line as typed: `` ## `specht` ``, `` ## `specht init` ``. It runs to the next such heading. Each command the help lists has exactly one; a section whose code span is anything else that starts with `specht` is a command the help does not list.
- **An option entry (B-007, B-008).** A table row or a list item inside a command section whose first cell or first text is a code span starting with `-`: ``| `--root <DIR>` |``, `` - `-h, --help` ``. It documents every `-x` and `--name` in that code span; the value an option takes is not a name. Each long option of the command's help has an entry in that command's section, and every name in an entry is one that command's help lists.
- **A name in a readme (A-7, B-009, B-010).** Code is a code span, or a line of a fenced block. Code that begins `specht`, `dotnet specht` or `dotnet tool run specht` is a command line: the longest command prefix found in the recursively read help is the command, or the default one when no command name follows; every `-x` and `--name` on the line is an option of that command. Any other code that begins with `-` is an option on its own, checked against the options of every command. Prose, HTML, a path, and code that begins with anything else name nothing.
- **The link (B-011).** A Markdown link in `README.md` whose target is `docs/cli.md`, with or without a fragment.
- **Not a specification (B-003).** The page is found at `docs/cli.md`, and no line of it is `type: feature`, the frontmatter type every specification carries. This reading is `test-writer`'s.
- **A command specified and not built (B-008's boundary).** `specht upgrade`, `specht manifest` and `specht rules`, from § 5 row 6, less any the help lists. The pull request that delivers the last of them rewords the scenario or this list.

One line per claim, its mechanism, and its unit test or why it has none:

- **B-003, B-006, B-007, B-008, B-011** - mechanism: the text of `docs/cli.md` and of `README.md`, which a person writes (C-7). No code of this repository decides it, so there is no unit tier; the scenario is the proof.
- **B-009, B-010** - mechanism: the text of the two readmes. As above.
- **The surface the pages are held to** - Spectre.Console.Cli renders it from `Program.cs` (`SetDefaultCommand<CheckCommand>()`, `AddCommand<InitCommand>("init")`) and from the `[CommandOption]` attributes on `CheckCommand.Settings` and `InitCommand.Settings` (all read). None of them holds a decision of this repository's about help; `0001-F2` § 8 gives the same verdict for B-008 there.

What the design makes hard to test, for `implementer`:

- The steps recognise sections, entries and names with regular expressions that live in the step class. They are test code with no test of their own. If the page needs a shape these rules do not read, the rules change here first; if they grow past a few expressions, they are a parser, and a parser is production code with a unit tier.
- The help is read as Spectre prints it at its default width: `OPTIONS:` and `COMMANDS:` blocks, ended by a blank line, with a command name at four spaces. A Spectre upgrade that moves these fails the scenarios, loudly.
- A copied page is refreshed by the build. A page deleted from the repository stays in a stale output folder until it is cleaned; CI builds clean.
- C-5's second half, that a page changes when what a command does changes, is `spec-reviewer`'s. No test sees prose.
